# Objective 2.4 — Describe Azure identity, access, and security

Identity is the front door of the cloud, and AZ-900 treats this objective as the security heart of Domain 2. The exam tests whether you can name the right identity or security service for a scenario — "employees sign in once and reach all their apps" (SSO), "require a second verification step only when sign-in looks risky" (Conditional Access + MFA), "give a new admin permission to manage only one resource group" (RBAC) — and whether you know the big security philosophies (Zero Trust, defense-in-depth) at slogan depth. Questions are definitional or short-scenario; almost never deep technical. Learn each service's one-line job, the keyword that maps a scenario to it, and the contrasts the exam blurs (Entra ID vs. Entra Domain Services, B2B vs. B2C, RBAC vs. Conditional Access — authorization vs. authentication). Note the naming refresh: the exam now says **Microsoft Entra ID (formerly Azure Active Directory)** everywhere — expect Entra names.

## Directory services: Microsoft Entra ID and Microsoft Entra Domain Services

### Microsoft Entra ID

- **What it is:** Microsoft's **cloud-based identity and access management (IAM) service** — formerly Azure Active Directory (Azure AD). It stores user identities and controls sign-in and access to Azure, Microsoft 365, and thousands of third-party SaaS apps.
- **What it provides:** authentication (sign-in, self-service password reset), **single sign-on**, **MFA**, application management, and device registration/management.
- **Who uses it:** IT admins (control access), developers (add sign-in to apps via standards-based auth), and every cloud service user.
- **Hybrid story:** it works with **both cloud and on-premises** resources — **Microsoft Entra Connect** synchronizes on-prem Active Directory identities to Entra ID so users have one identity (and one password) in both worlds.
- **What it is NOT:** it is *not* on-prem Active Directory in the cloud. Entra ID is a flat, web-protocol-based directory — **no Kerberos/NTLM, no Group Policy, no organizational units, no domain join** in the classic sense.

### Microsoft Entra Domain Services

- **What it is:** A **managed domain service** that supplies classic AD capabilities — **domain join, Group Policy, LDAP, Kerberos/NTLM authentication** — **without you deploying, managing, or patching domain controllers**.
- **How it works:** Azure runs two managed Windows Server domain controllers (a replica set) in your chosen region; a **one-way sync** from Entra ID populates the managed domain. You never get local-admin/Domain-Admin access to those DCs — Azure operates them.
- **Why it matters:** legacy **lift-and-shift** applications often depend on LDAP or Kerberos and can't use modern web auth. Entra Domain Services lets them run in Azure unmodified.

| | On-prem Active Directory | Microsoft Entra ID | Microsoft Entra Domain Services |
|---|---|---|---|
| Where it runs | Your domain controllers | Microsoft's cloud (global service) | Managed DCs run by Azure |
| Protocols | Kerberos, NTLM, LDAP | Modern web auth (SAML, OAuth/OIDC) | Kerberos, NTLM, LDAP |
| Group Policy / domain join | Yes | **No** | **Yes** |
| You patch domain controllers | Yes | No DCs at all | **No — Azure does** |
| Best for | Traditional on-prem network | Cloud/SaaS identity, SSO, MFA | Legacy apps lifted to Azure |

> 💡 **Exam Tip:** Scenario says "legacy application moved to Azure needs **domain join / Group Policy / LDAP / Kerberos** but the company doesn't want to manage domain controllers" = **Microsoft Entra Domain Services**. Scenario says "cloud identity, sign-in, SSO, MFA for users and apps" = **Microsoft Entra ID**.

> ⚠️ **Common Pitfall:** Entra ID is not a cloud copy of Active Directory — it lacks Kerberos and Group Policy. And Entra Domain Services is not "your DCs hosted in Azure VMs" — it's a *managed* service; Azure patches the DCs and you never log into them. Also remember Entra Connect syncs **on-prem AD → Entra ID**, while Entra Domain Services gets a **one-way sync from Entra ID**.

## Authentication methods: SSO, MFA, and passwordless

Authentication = proving who you are. Azure supports a spectrum from passwords (low security, low convenience) to passwordless (high security **and** high convenience).

### Single sign-on (SSO)

- **What it is:** Sign in **once with one credential** and access **multiple applications** without re-authenticating to each.
- **Why it matters:** fewer passwords = **smaller attack surface**, less password fatigue and reuse, simpler provisioning/deprovisioning (disable one identity, all access ends), fewer helpdesk resets.
- **The catch:** SSO is **only as secure as the initial authenticator** — one stolen credential opens every connected app. That's why SSO is paired with MFA.

### Multifactor authentication (MFA)

- **What it is:** Requiring **two or more** different *categories* of evidence at sign-in:
  - **Something you know** — password or PIN
  - **Something you have** — phone, Microsoft Authenticator app, hardware key
  - **Something you are** — biometric (fingerprint, face)
- **Why it matters:** a stolen password alone is no longer enough — MFA blocks the vast majority of credential-based attacks. Microsoft Entra MFA delivers this (phone call, app notification, code).

### Passwordless

- **What it is:** The password is **removed entirely and replaced with something you have plus something you know or are** (e.g., your registered device + a biometric or PIN). **High security + high convenience** — the security/usability trade-off finally broken.
- **The three Microsoft options (memorize):**
  1. **Windows Hello for Business** — biometric/PIN sign-in tied to a specific PC.
  2. **Microsoft Authenticator app** — phone app; match the number, confirm with fingerprint/face/PIN.
  3. **FIDO2 security keys** — unphishable hardware keys (USB/NFC/Bluetooth), great for shared or restricted environments.

> 💡 **Exam Tip:** Two of three factors from the **same** category (password + PIN) is **not** MFA — both are "something you know." MFA requires *different* categories.

> ⚠️ **Common Pitfall:** Passwordless is not "no authentication" and not weaker than passwords — it's *stronger*, because it binds sign-in to a physical device plus a biometric/PIN that never leaves that device.

## External identities: B2B and B2C

Both let people **outside your organization** access resources using **their own credentials** — you don't create or manage passwords for them. The difference is *who* they are:

| | B2B collaboration | B2C (Azure AD B2C / External ID for customers) |
|---|---|---|
| Who | **Business partners, suppliers, guests** | **Customers/consumers** of your public-facing apps |
| How they sign in | **Invited as guest users**; use their own work, school, or social identity | Social accounts (Google, Facebook) or local accounts |
| Where the identity lives | Stays with their home organization; a guest object in *your* tenant | A **separate customer-focused directory**, apart from your workforce tenant |
| Typical scenario | Share a project site with a partner firm | Retail website sign-in for shoppers |

- **Why it matters:** the partner's own admin (or the customer) manages the credential; you only govern what they can reach — and you can layer **Conditional Access and MFA on external identities** too.

> 💡 **Exam Tip:** "Invite a **partner/vendor/guest** to collaborate using their own credentials" = **B2B**. "Let **customers** sign in to your app with social or local accounts" = **B2C**. Partner = B2B, shopper = B2C.

## Microsoft Entra Conditional Access

- **What it is:** The Entra ID engine for **if-then access policies based on signals**: *if* the sign-in matches conditions, *then* apply a decision.
- **Signals it evaluates:** **who** the user is (role/group), **where** they are (location/IP), **what device** (compliant? managed?), **which application**, and **real-time risk** detection.
- **Decisions:** **allow**, **require MFA** (or other controls), or **block** access.
- **Why it matters:** it makes MFA **only-when-needed** — skip the prompt from the office network, demand it from an unknown location — and it can **block legacy/older clients** that can't do modern auth.
- **Examples:** require MFA for admins from any location; require managed devices for a sensitive app; block sign-ins from countries you never operate in.

> 💡 **Exam Tip:** The trigger phrase is conditional logic about *sign-in circumstances*: "require MFA **only when** users are outside the corporate network" or "**block access from** unmanaged devices" = **Conditional Access**. It decides *how/whether you authenticate*; RBAC decides *what you can do afterward*.

## Azure role-based access control (RBAC)

- **What it is:** Azure's **authorization** system — grant access by assigning a **role** (a bundle of permissions) to a **security principal** (user, group, service principal, managed identity) at a **scope**.
- **Built-in roles to know:** **Owner** (full control including granting access), **Contributor** (create/manage resources but **cannot grant access**), **Reader** (view only) — plus hundreds of service-specific roles (e.g., Virtual Machine Contributor).
- **Scopes (broad → narrow):** **management group → subscription → resource group → individual resource.** Assignments are **inherited by child scopes** — Reader on a subscription means Reader on every resource group and resource in it.
- **Allow model:** RBAC **grants** permissions; it doesn't have deny-first semantics. Multiple role assignments **add together** (Read at subscription + Write at resource group = both apply there).
- **Why it matters:** it enforces **least privilege** — give each principal only what its job requires, at the narrowest sensible scope. Assign roles to **groups**, not individuals, for manageability.

> ⚠️ **Common Pitfall:** RBAC vs. Conditional Access confusion. Conditional Access = **authentication** (can you get in, under what conditions). RBAC = **authorization** (what you may do once in). "User signed in fine but can't create a VM" is an **RBAC** question; "prompt for MFA off-network" is Conditional Access. Also: **Contributor cannot assign roles to others** — only Owner (or User Access Administrator) can.

## Zero Trust

- **What it is:** A security model that **assumes nothing is safe** — no user, device, or network — and **verifies every request as if it originated from an open, untrusted network**. "Never trust, always verify."
- **The three guiding principles (memorize):**
  1. **Verify explicitly** — always authenticate and authorize on all available signals (identity, location, device health, workload, data classification, anomalies).
  2. **Use least-privilege access** — just-in-time and just-enough access, risk-based policies, data protection.
  3. **Assume breach** — minimize blast radius, segment access, encrypt end-to-end, use analytics to detect threats.
- **The shift:** old model = trusted corporate network behind a firewall (everything inside is trusted); Zero Trust = **identity is the new perimeter** — protect identities and verify every access, wherever it comes from. Devices and users prove themselves; being "on the LAN" earns nothing.

> 💡 **Exam Tip:** Match the phrase to the principle: "authenticate every request using all signals" = verify explicitly; "just-enough, just-in-time access" = least privilege; "segment and encrypt because attackers may already be inside" = assume breach.

## Defense-in-depth

- **What it is:** A layered strategy: **multiple independent layers of protection**, so an attacker who penetrates one layer meets the next. The purpose is to **protect information and prevent it from being stolen** by **slowing the attack** and giving defenders telemetry and time to respond — no single point of failure.
- **The seven layers, outermost to innermost (memorize the order and one example each):**

| Layer | Example protections |
|---|---|
| 1. **Physical security** | Locked datacenter buildings, badges, cameras (Microsoft handles this in Azure) |
| 2. **Identity & access** | Entra ID, SSO, MFA, audit sign-in events |
| 3. **Perimeter** | **DDoS protection**, perimeter firewalls |
| 4. **Network** | **NSGs**, segmentation, limit connectivity, deny-by-default, no unnecessary Internet exposure |
| 5. **Compute** | Patch VMs promptly, endpoint protection, close unneeded ports |
| 6. **Application** | Secure code, fix vulnerabilities, **no secrets stored in code** (use a vault) |
| 7. **Data** | Encryption at rest/in transit, access controls — the attacker's ultimate target |

- **Data is the center:** almost every attack is ultimately after data; each outer ring exists to protect it.

> ⚠️ **Common Pitfall:** Don't blur defense-in-depth (a **layered architecture**) with Zero Trust (a **trust philosophy** — verify everything). They're complementary: Zero Trust principles are applied *within* each defense-in-depth layer. And for ordering questions, remember **physical is outermost, data is the innermost core**.

## Microsoft Defender for Cloud

- **What it is:** Azure's **cloud security posture management (CSPM) + workload protection** tool — it continuously **assesses** your environment, **recommends** hardening, and **detects and alerts** on active threats.
- **Posture side (CSPM):** a **secure score** quantifying your current posture, prioritized **hardening recommendations** against security benchmarks, and a **regulatory compliance** view.
- **Protection side:** threat detection and **security alerts** for servers, storage, databases, containers, and more, with guidance to respond.
- **Coverage:** natively integrated with Azure (agentless for many PaaS services) and extends to **on-premises and other clouds (AWS/GCP)** — hybrid/multicloud machines connect via **Azure Arc**.
- **Cost model:** **free foundational CSPM** (secure score + recommendations) for Azure subscriptions; enhanced **Defender plans** (per workload type) are paid.

> 💡 **Exam Tip:** Keywords "**secure score**," "security **recommendations**/posture," "**regulatory compliance** dashboard," or "threat protection **across Azure, on-prem, and multicloud**" = **Microsoft Defender for Cloud**. If the multicloud/on-prem angle appears, the connector is **Azure Arc**.

## How It Fits Together (mental model)

Picture one employee's day: her identity lives in **Microsoft Entra ID**, synced from the on-prem directory by Entra Connect, while a legacy finance app the company lifted into Azure authenticates against **Microsoft Entra Domain Services** because it still needs Kerberos and Group Policy. She signs in once (**SSO**) using **passwordless** Windows Hello; when she later connects from a hotel, a **Conditional Access** policy notices the unfamiliar location and demands **MFA** via the Authenticator app before allowing access. A consultant from a partner firm collaborates on her project as an invited **B2B** guest with his own credentials, while the company's shopping site lets customers register through **B2C** with their Google accounts. Once inside Azure, **RBAC** limits her to Contributor on a single resource group — least privilege at a narrow scope. All of this embodies **Zero Trust** (verify explicitly, least privilege, assume breach — identity is the perimeter) and forms the identity-and-access ring of the **defense-in-depth** model, whose other layers (perimeter DDoS protection, network NSGs, patched compute, secure code, encrypted data) stand behind it. Watching over the whole estate — Azure, on-prem, and the AWS accounts connected through Arc — **Microsoft Defender for Cloud** scores the posture, recommends hardening, and raises alerts when something slips through.

## Quick Contrast Drills

Four pairings the exam loves to blur — rehearse the one-line distinction:

1. **Entra ID vs. Entra Domain Services:** both are Microsoft-managed identity services, but Entra ID is modern cloud IAM (SSO, MFA, web protocols) while Entra Domain Services provides *legacy* AD features (domain join, Group Policy, Kerberos/LDAP) for lift-and-shift apps — with Azure patching the domain controllers.
2. **B2B vs. B2C:** both are external identities using their own credentials, but B2B = invited business **partners/guests** into your tenant; B2C = **customers** of your public app in a separate customer directory.
3. **Conditional Access vs. RBAC:** Conditional Access governs **authentication** (whether/how you sign in, based on signals); RBAC governs **authorization** (what you can do at what scope once signed in).
4. **Zero Trust vs. defense-in-depth:** Zero Trust is the *philosophy* — trust no request, verify everything, identity is the perimeter; defense-in-depth is the *architecture* — seven concentric layers (physical → identity → perimeter → network → compute → application → data) that each slow an attack.

## Key Takeaways

- [ ] **Microsoft Entra ID (formerly Azure Active Directory)** = cloud identity and access management: sign-in, SSO, MFA, app and device management; syncs with on-prem AD via Entra Connect; no Kerberos or Group Policy of its own.
- [ ] **Microsoft Entra Domain Services** = managed domain join, Group Policy, LDAP, and Kerberos/NTLM without deploying or patching domain controllers — the answer for lift-and-shift apps needing legacy auth.
- [ ] **SSO** = one credential for many apps (smaller attack surface, but only as secure as the initial authenticator); **MFA** = two or more *different* factor categories (know/have/are); **passwordless** = Windows Hello for Business, Microsoft Authenticator app, FIDO2 keys.
- [ ] **B2B** invites partner guests who keep their own credentials; **B2C** gives customers social/local sign-in to your public apps.
- [ ] **Conditional Access** = if-then policies on signals (user, location, device, app, risk) that allow, require MFA, or block — MFA only when needed, and a way to block legacy clients.
- [ ] **RBAC** assigns roles (Owner / Contributor / Reader + service-specific) to security principals at a scope (management group → subscription → resource group → resource); permissions **inherit downward**; it's an **allow** (grant) model enforcing least privilege.
- [ ] **Zero Trust** = verify explicitly, use least-privilege access, assume breach — protect identities, not network locations.
- [ ] **Defense-in-depth** = seven layers, outside in: physical, identity & access, perimeter (DDoS), network (NSGs), compute (patching), application (secure code, no secrets), data (encryption) — each layer slows the attack.
- [ ] **Microsoft Defender for Cloud** = CSPM + workload protection: secure score, recommendations, regulatory compliance, threat alerts — across Azure, on-prem, and multicloud (via Arc); foundational CSPM is free.

## Self-Check Questions

1. A company migrates a 15-year-old application to Azure VMs. The app requires Kerberos authentication and Group Policy, but the team refuses to build and patch domain controllers in Azure. Which service solves this?
2. Security wants users to skip MFA when signing in from the corporate office but be forced to complete MFA from anywhere else. Which capability implements this, and what three decisions can it output?
3. A new engineer signed in successfully but gets "authorization failed" when creating a VM in the Production resource group. Is this a Conditional Access or an RBAC issue, and which built-in role (least privilege) would let her create and manage VMs without granting access to others?
4. Name the three Zero Trust guiding principles, and state which one "just-in-time, just-enough access" belongs to.
5. In the defense-in-depth model, which layer is outermost, which sits at the center, and at which layer do NSGs and "limit connectivity" belong?
