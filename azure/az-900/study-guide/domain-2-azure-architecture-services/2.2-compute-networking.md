# Objective 2.2 — Describe Azure compute and networking services

This is the largest single objective on AZ-900, and the exam mines it heavily for scenario questions. You are rarely asked to recite a definition; instead you get a requirement ("a team needs to run code only when a file is uploaded, paying nothing while idle") and must pick the matching service (Azure Functions). Success comes from knowing each service's one-line identity, the axis on which it differs from its neighbors (VMs vs. containers vs. functions = decreasing management responsibility; VPN Gateway vs. ExpressRoute = public Internet vs. private circuit; scale sets vs. availability sets = scaling out vs. surviving hardware failure), and the keyword phrases Microsoft uses to signal each one. Work through every comparison table below until you can answer from the scenario keywords alone.

## Comparing compute types: virtual machines, containers, and functions

Azure's compute spectrum runs from "you manage almost everything" to "you manage almost nothing." The exam constantly tests where a workload belongs on that spectrum.

### Virtual machines (VMs)

- **What it is:** Software emulation of a complete computer — virtual CPU, memory, disk, and NIC — running a **full operating system** of your choice on Azure's hypervisors. This is classic **IaaS**.
- **What you control:** everything from the OS up — you choose the image and size, install software, configure it, and **you are responsible for patching and maintaining the OS**.
- **Why it matters:** total control and the easiest lift-and-shift path for legacy or custom workloads — at the cost of the most management overhead, the slowest startup, and the largest footprint (every VM carries its own guest OS).

### Containers

- **What it is:** A **lightweight, virtualized application environment** that packages an app with its dependencies. Containers **virtualize the operating system rather than the hardware** — many containers share one host OS kernel, so there is **no guest OS for you to manage**.
- **Traits:** start in seconds (no OS boot), far smaller and denser than VMs, portable across environments, designed to be created/scaled/stopped dynamically.
- **Azure's container services — know all three by their one-liners:**
  - **Azure Container Instances (ACI):** the **simplest and fastest** way to run a single container in Azure — no VMs to manage, no orchestration; PaaS-style, pay while it runs.
  - **Azure Kubernetes Service (AKS):** managed Kubernetes for **orchestrating containers at scale** — automated deployment, scaling, and management of fleets of containers.
  - **Azure Container Apps:** **serverless containers** — like ACI but adds built-in features such as automatic scaling (including scale-out under load) and load balancing, without you managing any orchestration infrastructure.

### Azure Functions

- **What it is:** **Serverless, event-driven** compute — you deploy small pieces of code that run **in response to an event** (HTTP request, timer, queue message, blob upload) without provisioning or managing any servers or VMs.
- **Traits:** runs for milliseconds-to-minutes per invocation, **scales automatically — including down to zero** when idle, and with consumption-plan billing you **pay only for time and resources actually consumed** (nothing while idle).
- **"Serverless" caveat:** servers still exist — Azure manages them entirely; they are simply invisible to you.

| | Virtual machines | Containers | Functions |
|---|---|---|---|
| Virtualizes | Hardware (full guest OS per VM) | Operating system (shared kernel, no guest OS) | Nothing you see — just your code runs |
| You manage | OS + everything above (patching!) | App + container image only | Code only |
| Startup | Minutes (OS boot) | Seconds | Milliseconds |
| Billing | While allocated/running | While running | Per execution (consumption); scales to zero |
| Best for | Full OS control, lift-and-shift, legacy apps | Portable microservices, dense/fast-scaling workloads | Short, event-driven tasks; spiky/intermittent demand |

> 💡 **Exam Tip:** Keyword mapping — "full control of the OS / lift-and-shift" = **VM**; "lightweight, no guest OS to manage, starts fast" = **container**; "event-driven, runs only when triggered, pay per execution, scales to zero" = **Functions**. Within containers: "simplest single container" = **ACI**, "orchestrate many containers" = **AKS**, "serverless containers with built-in scaling" = **Container Apps**.

> ⚠️ **Common Pitfall:** Containers do **not** contain a full operating system. A VM virtualizes hardware and boots its own guest OS; a container virtualizes the OS and shares the host's kernel. If a question stresses "no operating system to patch or maintain," the answer is a container (or something even higher up the stack), never a VM.

## Virtual machine options

Azure offers several ways to run VMs beyond a single instance — the exam tests which packaging fits which requirement.

- **Azure Virtual Machines (single instances):** one VM per workload; you handle everything above the hypervisor. Fine for one-off servers, but a single VM in a single datacenter is a single point of failure.
- **Azure Virtual Machine Scale Sets:** a group of **identical, load-balanced VMs** created from the same image. The scale set can **automatically increase or decrease the number of instances** in response to demand or a defined schedule, and it deploys the load balancer for you. Use it for large-scale stateless workloads — web front ends, big compute/data jobs.
- **Availability sets:** a way to spread VMs so they **don't all fail or reboot at the same time**, by placing them in different:
  - **Update domains** — groups that undergo **planned maintenance** (and its reboots) at different times; Azure updates one update domain at a time.
  - **Fault domains** — groups that share a **power source and network switch**; spreading VMs across fault domains protects against a **hardware/rack failure** taking everything down.
  - Availability sets protect against unplanned hardware failure and planned maintenance **within a datacenter**, and there is **no additional cost** for configuring one — you pay only for the VMs.
- **Azure Virtual Desktop (AVD):** a desktop-and-application virtualization service that runs in the cloud — users get a **full Windows desktop and apps from almost any device, anywhere** (browser or client app). It supports **multi-session Windows**, allowing multiple concurrent users on a single VM, and centralizes data/security (data stays in Azure, not on the endpoint).

| | VM Scale Sets | Availability sets |
|---|---|---|
| Purpose | **Scale** — add/remove identical instances with demand | **Resilience** — survive hardware failure & maintenance reboots |
| VMs are | Identical, from one image, load-balanced | Can differ; distributed across fault/update domains |
| Automatic scaling | Yes (autoscale on demand/schedule) | No — it changes placement, not count |
| Protects against | Traffic spikes, instance failure (redundancy in numbers) | Rack power/switch failure, planned maintenance |
| Extra cost | Pay per VM instance | **None** beyond the VMs themselves |

> 💡 **Exam Tip:** "Identical, load-balanced VMs that automatically scale with demand" = **VM Scale Sets**. "Spread VMs across fault domains and update domains so maintenance or a rack failure can't take them all down" = **availability set**. "Cloud-hosted Windows desktop, multiple users on one VM, work from any device" = **Azure Virtual Desktop**.

> ⚠️ **Common Pitfall:** Don't invert the two domains: **fault domain = unplanned** (shared power/network — hardware failure); **update domain = planned** (maintenance reboot groups). And remember an availability set is free — you're never charged for the set itself.

## Resources required for virtual machines

A VM never travels alone. When you create one, Azure creates (or you attach) a set of companion resources — the exam asks what a VM needs:

- **Size and image choices:** you pick a **VM size** (CPU/memory/disk profile) and an **OS image** (Windows/Linux, from Azure Marketplace or your own) at creation.
- **Virtual disks / managed disks:** every VM has an OS disk, and optionally data disks, stored as **Azure managed disks** — Azure handles the storage accounts behind them.
- **Virtual network + subnet:** the VM must land in a **subnet of a virtual network** to communicate.
- **Network interface (NIC):** the VM's connection into that subnet — a VM needs **at least one NIC**.
- **Commonly also:** a **public IP address** (only if it must be reachable from the Internet) and a **network security group (NSG)** to filter its traffic.

> 💡 **Exam Tip:** If asked which resources a new VM requires, think: **disk(s), a VNet/subnet, and a NIC** — with a public IP and NSG as common optional companions. Deleting a VM does not automatically delete all of these companions, which is why orphaned disks and NICs keep billing.

## Application hosting options

You have an app to run in Azure. The three broad homes for it:

- **Azure Virtual Machines:** maximum control over the hosting environment (full OS access) — but you configure, patch, and maintain everything (IaaS).
- **Containers (ACI / AKS / Container Apps):** package the app with its runtime; portable, fast-starting, ideal for microservices and multi-instance scaling.
- **Azure App Service:** **PaaS** built specifically for hosting **web apps, REST APIs, and mobile back ends** in the language of your choice (.NET, Java, Node.js, Python, PHP...) on Windows or Linux — **without managing any infrastructure**. It provides **built-in scaling and load balancing** on a pay-for-what-you-use plan, **deployment slots** (e.g., staging → swap to production), and CI/CD integration with GitHub/Azure DevOps.

| | Virtual machines | Containers | App Service |
|---|---|---|---|
| Model | IaaS | CaaS/PaaS-style | PaaS |
| You manage | OS + runtime + app | Image + app | App code only |
| Signature strengths | Total control, any software | Portability, density, orchestration (AKS) | Built-in scaling/LB, deployment slots, multi-language, zero server care |
| Pick when... | App needs OS-level customization | Microservices, consistent deploys everywhere | Standard web app/API — fastest path to production |

> 💡 **Exam Tip:** "Host a website/REST API without managing the underlying servers or OS" = **Azure App Service**. If the scenario adds "swap a staging version into production with no downtime," that's App Service **deployment slots**.

> ⚠️ **Common Pitfall:** App Service is PaaS, not serverless — an App Service plan bills while it runs even with zero traffic, whereas Functions on the consumption plan scales to zero and bills per execution. And you never patch the OS in App Service; if a scenario demands OS-level access, you've left App Service territory for a VM.

## Virtual networking

Azure networking mirrors on-premises networking in software. Know the purpose of each piece:

### Azure virtual networks (VNets) and subnets

- **What it is:** a VNet is your **logically isolated private network in Azure** — you define its **private IP address space**, and resources inside it (VMs, etc.) can communicate securely with each other, the Internet, and on-premises networks.
- **Subnets** divide the VNet's address space into segments so you can group resources (web tier vs. data tier) and apply security and routing per segment — **network security groups (NSGs)** filter traffic to/from subnets and NICs with allow/deny rules.
- VNets enable **isolation and segmentation**, name resolution, and traffic filtering/routing — the container everything else in this section plugs into.

### VNet peering

- **What it is:** connects **two virtual networks** so their resources communicate as one network — traffic between peered VNets travels over the **Microsoft private backbone network, never the public Internet**.
- Peering works across regions (**global virtual network peering**), letting you connect VNets worldwide privately.

### Azure DNS

- **What it is:** a **hosting service for DNS domains** that resolves names using Azure's global anycast infrastructure — you manage DNS records with the same Azure credentials, tools, and billing as everything else.

> ⚠️ **Common Pitfall:** Azure DNS **hosts** zones and answers queries — it does **not** register or sell domain names. You buy the domain from a registrar, then delegate it to Azure DNS name servers to manage its records in Azure.

### Azure VPN Gateway

- **What it is:** a gateway that creates an **encrypted (IPsec) tunnel over the public Internet** between your Azure VNet and other networks.
- **Site-to-site (S2S):** connects an entire **on-premises office/datacenter** to the VNet via its VPN device.
- **Point-to-site (P2S):** connects an **individual device** (a remote worker's laptop) to the VNet.
- Cheap and quick, encrypted end to end — but bandwidth and latency depend on the public Internet.

### Azure ExpressRoute

- **What it is:** a **private, dedicated connection** between your on-premises network and Microsoft's cloud, arranged through a connectivity provider — traffic **never touches the public Internet**.
- **Traits:** higher bandwidth, consistent/predictable performance and latency; because the path is private it is **not encrypted by default** (add encryption on top if required). Costlier and slower to provision than a VPN.

| | VPN Gateway | ExpressRoute |
|---|---|---|
| Path | Encrypted tunnel **over the public Internet** | **Private dedicated circuit** — never the public Internet |
| Encryption | Built in (IPsec) | Not inherent (private path) |
| Performance | Variable — Internet-dependent | High bandwidth, consistent low latency |
| Cost / setup | Low, fast | Higher, provisioned via a provider |
| Best for | Quick/low-cost hybrid links, remote users (P2S), failover | Production hybrid workloads, large data, compliance ("must avoid the Internet") |

> 💡 **Exam Tip:** "Encrypted tunnel over the Internet" = **VPN Gateway** (whole site = site-to-site; single laptop = point-to-site). "Private connection that does not traverse the public Internet, predictable performance" = **ExpressRoute**. "Connect two VNets over the Microsoft backbone" = **peering** (cross-region = global peering). "Host and resolve your domain's records in Azure" = **Azure DNS**.

> ⚠️ **Common Pitfall:** ExpressRoute is private but **not automatically encrypted** — privacy of the path is not encryption. Conversely, a VPN is encrypted but rides the **public** Internet. Also don't confuse **peering** (VNet ↔ VNet inside Azure) with **VPN/ExpressRoute** (on-premises ↔ Azure).

## Public and private endpoints

How do clients reach a service?

- **Public endpoint:** the service is exposed on a **public IP address reachable from the Internet**. Anyone (subject to your security rules) can attempt to connect from anywhere.
- **Private endpoint:** the service gets a **private IP address from your VNet's own address space** via **Azure Private Link**, so resources in the VNet reach a PaaS service (a storage account, Azure SQL database...) **over the private network — traffic never leaves the Microsoft/private network for the public Internet**, and the public exposure can be disabled.

> 💡 **Exam Tip:** "Access a storage account or database from your VNet using a private IP so traffic stays off the public Internet" = **private endpoint** (Private Link). If a service must be reachable by customers on the Internet, that's a **public endpoint**.

## How It Fits Together (mental model)

Picture one company's deployment touching every bullet: its legacy ERP runs on **Azure Virtual Machines** (each built from an image and size with **managed disks, a NIC, an NSG**, and a spot in a **subnet** of a **VNet**), placed in an **availability set** so a rack failure (**fault domain**) or maintenance reboot (**update domain**) can't take both nodes down. The public website runs on a **VM Scale Set** of identical load-balanced instances that autoscale on traffic, while the newer microservices run as **containers** — a one-off job in **ACI**, the main fleet orchestrated by **AKS**, one team trying serverless scaling in **Container Apps** — and a nightly cleanup task is an event-driven **Azure Function** that scales to zero. The marketing site needed no infrastructure at all, so it lives in **App Service** with a staging **deployment slot**. Remote staff get full Windows desktops through **Azure Virtual Desktop**. Networking ties it together: two regional **VNets** connected by **global peering** over the Microsoft backbone, the corporate domain hosted in **Azure DNS**, the branch office linked by a **site-to-site VPN Gateway** tunnel, headquarters on **ExpressRoute** for private, predictable bandwidth, and the storage account reached through a **private endpoint** so data never crosses the public Internet.

## Quick Contrast Drills

Four pairings the exam loves to blur — rehearse the one-line distinction:

1. **VM Scale Sets vs. availability sets:** both involve multiple VMs, but scale sets are about **capacity** (identical instances autoscaling with demand behind a load balancer) while availability sets are about **survival** (spreading VMs across fault and update domains so hardware failure or maintenance can't hit them all).
2. **Containers vs. VMs:** both isolate workloads, but a VM virtualizes **hardware** and carries a full guest OS you must patch, while a container virtualizes the **OS**, shares the host kernel, and gives you no OS to manage — hence its speed and density.
3. **VPN Gateway vs. ExpressRoute:** both connect on-premises to Azure, but VPN = **encrypted over the public Internet** (cheap, fast to set up, variable performance) and ExpressRoute = **unencrypted-by-default over a private dedicated circuit** (predictable, high bandwidth, never the public Internet).
4. **Public vs. private endpoint:** both are ways to reach a service, but a public endpoint is a **public IP open to the Internet**, while a private endpoint is a **private IP inside your VNet** (Private Link) that keeps traffic off the public Internet.

And one more that spans the whole objective: **App Service vs. Azure Functions** — both mean "run my code without touching servers," but App Service hosts an always-available web app or API (billed while the plan runs), while Functions runs short event-triggered pieces of code billed per execution that **scale to zero** between events.

## Key Takeaways

- [ ] Compute spectrum by what you manage: **VMs** (full OS control, IaaS, you patch) → **containers** (virtualize the OS, no guest OS, seconds to start) → **Functions** (serverless, event-driven, scales to zero, consumption billing).
- [ ] Container services: **ACI** = simplest single container; **AKS** = orchestration at scale; **Container Apps** = serverless containers with built-in scaling and load balancing.
- [ ] **VM Scale Sets** = identical, load-balanced, autoscaling VMs; **availability sets** = VMs spread across **fault domains** (power/switch — unplanned failure) and **update domains** (planned maintenance) at **no extra cost**; **Azure Virtual Desktop** = cloud-hosted multi-session Windows desktops from any device.
- [ ] A VM's required companions: managed disk(s), a VNet + subnet, and a NIC — commonly plus a public IP and an NSG; you choose size and image at creation.
- [ ] App hosting ladder: **App Service** (PaaS web apps/APIs, built-in scaling and load balancing, deployment slots) vs. **containers** (portability/microservices) vs. **VMs** (maximum control).
- [ ] **VNet** = isolated private network with your own address space; **subnets** segment it; **NSGs** filter traffic; **peering** joins VNets over the Microsoft backbone (global peering = cross-region); **Azure DNS** hosts your domains.
- [ ] **VPN Gateway** = encrypted IPsec tunnel over the public Internet (site-to-site for offices, point-to-site for devices); **ExpressRoute** = private dedicated circuit, never the public Internet, higher bandwidth and consistency, not encrypted by default.
- [ ] **Public endpoint** = public IP reachable from the Internet; **private endpoint** = private IP from your VNet via Private Link, keeping PaaS traffic off the public Internet.

## Self-Check Questions

1. A development team runs a small piece of code that processes each image uploaded to storage. It runs for a few seconds at unpredictable times, and the team wants to pay nothing while it's idle. Which Azure compute service fits best?
2. An application must run on ten identical VMs behind a load balancer, automatically adding instances during business hours and removing them at night. Should you use a VM Scale Set or an availability set, and why?
3. What is the difference between a fault domain and an update domain in an availability set?
4. A regulated firm must connect its datacenter to Azure with consistent bandwidth and a guarantee that traffic never traverses the public Internet. Which connectivity service should it choose, and what should it remember about encryption?
5. A VNet-hosted app must reach an Azure SQL database without any traffic crossing the public Internet. What should be configured for the database?

<summary>Answers</summary>

1. **Azure Functions** — serverless, event-driven compute that runs on a trigger (like a blob upload), scales automatically **to zero**, and bills per execution on the consumption plan, so idle time costs nothing.
2. A **VM Scale Set** — it deploys **identical, load-balanced** VMs from one image and **autoscales** the instance count with demand or a schedule. An availability set only distributes VMs across fault/update domains for resilience; it does not scale.
3. A **fault domain** is a group of VMs sharing a **power source and network switch** — spreading across fault domains protects against unplanned **hardware failure**. An **update domain** is a group that undergoes **planned maintenance** (and reboots) together — Azure updates one at a time so some VMs always stay up.
4. **ExpressRoute** — a private, dedicated connection to Microsoft's cloud that never touches the public Internet, with higher bandwidth and consistent performance. Remember it is **not encrypted by default**; add encryption on top if required. (A VPN Gateway is encrypted but rides the public Internet.)
5. A **private endpoint** (Azure Private Link) — it gives the database a **private IP address from the VNet's own address space**, so the app reaches it over the private network and the public endpoint can be disabled.
