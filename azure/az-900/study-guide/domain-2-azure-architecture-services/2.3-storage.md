# Objective 2.3 — Describe Azure storage services

Storage questions are among the most predictable on AZ-900, and this objective is dense with them. The exam tests whether you can pick the right storage *service* for a data shape (object vs. file share vs. message vs. NoSQL vs. VM disk), the right *access tier* for an access pattern (Hot → Cool → Cold → Archive), the right *redundancy* option for a resilience requirement (LRS → ZRS → GRS/GZRS → RA-variants), and the right *tool* for getting data into Azure (AzCopy, Storage Explorer, File Sync, Azure Migrate, Data Box). Questions are usually scenario-based ("Backups accessed once a year at the lowest cost — which tier?" or "80 TB and a slow Internet link — how do you migrate?"). Learn each option's one defining attribute and the thresholds (30/90/180 days, 3 vs. 6 copies) that separate it from its neighbors.

## Compare Azure Storage services

An Azure **storage account** exposes several distinct data services, each shaped for a different kind of data:

| Service | Data shape | Access | Classic use case |
|---|---|---|---|
| **Blob Storage** | Unstructured objects (text, binary, images, video, backups) | HTTP/HTTPS via REST, SDKs, tools | Media serving, backups/archives, data lakes, streaming |
| **Azure Files** | Fully managed **file shares** (SMB or NFS) | Mounted like a network drive, from cloud **and** on-premises simultaneously | Lift-and-shift apps expecting a file share, shared config, user profiles |
| **Queue Storage** | **Messages** up to **64 KB** each | REST/SDK, consumed asynchronously | Decoupling app components; order intake buffered for a backend processor |
| **Table Storage** | **NoSQL** structured, non-relational key/attribute data | REST/SDK | Flexible-schema datasets: user metadata, device data, address books |
| **Managed Disks** | **Block-level** storage volumes | Attached to Azure VMs | OS and data disks for virtual machines |

### Blob Storage

- **What it is:** **Object storage** for massive amounts of **unstructured data** — data with no rigid model, such as text, binary, images, video, and backups — stored as objects ("blobs") in containers and addressed over **HTTP/HTTPS through REST APIs**, SDKs, PowerShell/CLI, or tools like AzCopy.
- **Why it matters:** It is Azure's default answer for serving media to browsers, storing backup/restore and archive data, feeding data-lake analytics, and streaming audio/video — and it is the service that access tiers (below) apply to.

### Azure Files

- **What it is:** Fully managed **file shares** in the cloud, mountable over the industry-standard **SMB** or **NFS** protocols — a network drive with no file server to patch or manage.
- **Why it matters:** The same share can be mounted **simultaneously from cloud and on-premises** Windows, Linux, and macOS machines — ideal for lift-and-shift apps that expect a mapped drive, shared configuration/tools, and centralized user files.

### Queue Storage

- **What it is:** A service for storing **large numbers of messages, each up to 64 KB**, retrieved and processed asynchronously.
- **Why it matters:** Queues **decouple** application components — a front end can enqueue work faster than the backend processes it, so each side scales and fails independently.

### Table Storage

- **What it is:** A **NoSQL** store for **structured, non-relational** key/attribute data with a **schemaless** design.
- **Why it matters:** Cheap, fast storage for flexible datasets — user metadata, device information, address books — without the overhead of a relational database. If the stem says "non-relational" or "NoSQL," think Tables.

### Managed Disks

- **What it is:** **Block-level storage volumes** managed by Azure and attached to **virtual machines** as OS and data disks — you choose size and performance; Azure handles the underlying storage.
- **Why it matters:** Every Azure VM runs on managed disks; "block-level" and "VM disk" in a stem point here, not at Blob or Files.

> 💡 **Exam Tip:** Map the noun in the stem: "images/videos/backups/unstructured" = **Blob**; "mount a share / SMB / drive letter" = **Files**; "messages between components" = **Queues**; "NoSQL / non-relational structured data" = **Tables**; "disk for a VM" = **Managed Disks**.

> ⚠️ **Common Pitfall:** Blob vs. Files. Both can hold "files," but Blob is object storage reached over **REST/HTTP(S)**, while Azure Files is a **mountable SMB/NFS share**. If the scenario says an app expects a traditional file share or drive mapping, Blob is the wrong answer.

## Describe storage tiers

- **What they are:** Four Blob Storage **access tiers** that trade **storage cost against access cost and availability**, so data can be kept in the most cost-effective state for how often it is read.
- **Why they matter:** Most real datasets go cold over time; tiering (often automated with lifecycle policies) is how organizations avoid paying Hot-tier prices for data nobody reads.

| Tier | Access pattern | Minimum storage duration | Online? | Cost profile |
|---|---|---|---|---|
| **Hot** | Frequent access | none | Online | Highest storage cost, lowest access cost |
| **Cool** | Infrequent access | **≥ 30 days** | Online | Lower storage, higher access cost |
| **Cold** | Rarely accessed | **≥ 90 days** | Online | Lower still, higher access cost |
| **Archive** | Rarely/never accessed; latency of **hours** acceptable | **≥ 180 days** | **Offline** | Cheapest storage, highest retrieval cost |

- Tiers can be set at the **account level** (Hot/Cool default) and **per individual blob**, and blobs can be moved between tiers over their lifecycle (often automatically via lifecycle management policies).
- **Archive is the only offline tier**: an archived blob cannot be read until it is **rehydrated** back to an online tier, which can take **hours**.
- Deleting or moving data before the minimum duration triggers an early-deletion charge — that's why the 30/90/180-day floors matter.

> 💡 **Exam Tip:** The pattern is a see-saw — as storage cost goes **down** (Hot → Archive), access cost and retrieval latency go **up**. "Lowest storage cost" + "retrieval can wait hours" = **Archive**. "Infrequently accessed but must be available immediately" = **Cool** (or Cold if kept ≥ 90 days).

> ⚠️ **Common Pitfall:** Archive is *not* just "very cool." Hot, Cool, and Cold are all **online** — data is readable instantly. Archive is **offline** — reads fail until rehydration completes. If the scenario needs immediate availability, Archive is disqualified no matter how cheap it is.

## Describe redundancy options

- **What they are:** Replication settings on the storage account that determine **how many copies** of your data exist and **where they live** — one datacenter, multiple availability zones, or a second region.
- **Why they matter:** Redundancy is the resilience-versus-cost dial: every step outward (datacenter → zones → second region) survives a bigger failure and costs more. Every write to Azure Storage is copied multiple times; the option chooses *where*:

| Option | Copies | Protects against | Notes |
|---|---|---|---|
| **LRS** (locally redundant) | 3 synchronous copies in **one datacenter** | Drive/rack failure | Cheapest; **no** protection if the datacenter or zone is lost |
| **ZRS** (zone-redundant) | 3 copies across **three availability zones** in one region | Entire datacenter/zone failure | Still one region — no regional disaster protection |
| **GRS** (geo-redundant) | LRS in primary **+** async copy to a **secondary region** (6 copies) | Regional disaster | Secondary readable **only after failover** |
| **GZRS** (geo-zone-redundant) | ZRS in primary **+** copy in secondary region | Zone **and** regional failure | Highest resilience |
| **RA-GRS / RA-GZRS** | Same as GRS/GZRS | Same | Adds **always-on read access** to the secondary region |

- Geo-replication to the secondary region is **asynchronous**, so a regional failover can lose the most recent writes (a small RPO).
- With plain GRS/GZRS the secondary is invisible until Microsoft or the customer initiates failover; the **RA-** prefix is what makes the secondary *readable at all times*.

> 💡 **Exam Tip:** Count and place the copies: **3 in one building = LRS**, **3 across zones = ZRS**, **6 across two regions = GRS**, **zones + second region = GZRS**. If the stem says "read from the secondary region *without* failover," the answer must start with **RA-**.

> ⚠️ **Common Pitfall:** GRS does **not** let you read from the secondary during normal operation — that's RA-GRS. And ZRS does **not** protect against a regional outage; three zones are still inside one region.

## Describe storage account options and storage types

- **What it is:** A **storage account** is the top-level container that holds blobs, files, queues, and tables and provides a **unique namespace** for them. The account *type* determines performance (Standard HDD vs. Premium SSD), which services it supports, and which redundancy options are available.
- **Why it matters:** Nearly every AZ-900 storage question implicitly starts at the account: you pick the account type first, and everything inside inherits its performance and replication behavior.
- **Naming:** the account name must be **globally unique across all of Azure** (it forms part of the public endpoint URL, e.g. `mydata.blob.core.windows.net`) — lowercase letters and numbers only.
- **Standard general-purpose v2:** the default recommendation. Supports **blobs, files, queues, and tables**; HDD-backed pricing; all redundancy options (LRS/ZRS/GRS/GZRS and RA-variants). Right for **most scenarios**.
- **Premium accounts:** **SSD-backed** for consistently **low latency and high throughput**, at higher cost and with more limited redundancy (typically LRS/ZRS only). Three flavors, each a separate account type:
  - **Premium block blobs** — high-transaction-rate or latency-sensitive blob workloads.
  - **Premium file shares** — performance-critical SMB/NFS shares (NFS requires premium).
  - **Premium page blobs** — page-blob workloads (page blobs underlie disk-style random read/write).

> 💡 **Exam Tip:** Unless the scenario shouts "high performance / low latency / SSD," the answer is **Standard general-purpose v2**. If it does shout, pick the Premium type that matches the data: block blobs, file shares, or page blobs.

> ⚠️ **Common Pitfall:** Storage account names are unique across **all of Azure**, not just your subscription — a favorite true/false trap. Also note you cannot mix: a Premium account is dedicated to one storage type, while Standard GPv2 covers all four services.

## Identify options for moving files

Day-to-day file movement (as opposed to full migrations) has three named tools:

| Tool | What it is | Best when... |
|---|---|---|
| **AzCopy** | **Command-line** utility to copy or sync blobs and files to/from storage accounts (even between cloud providers) | Scripting, automation, bulk transfers. **Sync is one-direction** — you pick source → destination |
| **Azure Storage Explorer** | **Cross-platform GUI** (Windows/macOS/Linux) for browsing and managing storage accounts; uses AzCopy underneath | Visual, ad-hoc upload/download/management of blobs and files |
| **Azure File Sync** | Agent that **caches Azure Files shares on an on-prem Windows Server**; **bi-directional** sync | Keeping local SMB performance while centralizing file shares in Azure; every office sees the same files |

- **Azure File Sync** turns a Windows Server into a fast local cache of an Azure file share — users keep LAN-speed access via SMB/NFS while the authoritative copy lives in the cloud; changes sync **both ways** automatically. Cloud tiering can keep only recently used files cached locally, with the rest recalled from Azure on demand.
- Storage Explorer and AzCopy are related: the GUI **uses AzCopy under the hood** for its transfers — the choice between them is interactive convenience versus scriptable automation.

> 💡 **Exam Tip:** "Command line / script" = **AzCopy**. "Graphical tool" = **Storage Explorer**. "Windows Server caches the cloud file share locally" = **Azure File Sync**. And remember the asymmetry: AzCopy sync is **one-way**, File Sync is **two-way**.

> ⚠️ **Common Pitfall:** These three move *files day to day*; they are not migration services. If the scenario is about assessing servers or shipping tens of terabytes, jump to the next section — Azure Migrate and Data Box.

## Describe migration options

For whole-infrastructure or very large data movement, the exam names two services:

| Service | What it is | Best when... |
|---|---|---|
| **Azure Migrate** | A unified **hub** that discovers, **assesses**, and migrates on-prem **servers (VMware/Hyper-V/physical), databases, web apps, and VDI** to Azure over the network | You want guided, tool-supported migration of workloads with readiness/sizing/cost assessment first |
| **Azure Data Box** | A rugged **physical appliance (~80 TB usable)** Microsoft ships to you; you load data and ship it back for **offline** import (or export) | Datasets too large — or bandwidth too limited/costly — for network transfer: 40+ TB moves, one-time migrations, disaster recovery seeding, remote sites |

- Azure Migrate is about *workloads*: it inventories what you run, tells you whether and how it fits in Azure, estimates cost, and orchestrates the move — all **over the network**. Its integrated tools cover server migration, database assessment, web apps, and VDI.
- Data Box is about *bulk bytes offline*: when uploading would take weeks or saturate the link, sneakernet wins. The workflow: order in the portal → Microsoft ships the appliance → copy data locally → ship it back → Microsoft uploads it into your storage account and securely wipes the device. Data Box also handles **export** out of Azure the same way.

> 💡 **Exam Tip:** Do the math the exam implies: tens of terabytes plus a slow or expensive link = **Data Box**. "Assess on-premises servers for readiness and cost before moving them" = **Azure Migrate** — *assessment* is the giveaway word.

> ⚠️ **Common Pitfall:** Azure Migrate and Data Box are complements, not competitors: Migrate moves *workloads over the wire*; Data Box moves *raw data offline*. Also don't confuse Data Box (one-time physical transfer) with Azure File Sync (ongoing two-way synchronization).

## How It Fits Together (mental model)

Picture one company's move to Azure. It creates a **Standard general-purpose v2 storage account** with a **globally unique name** — one container for **blobs**, a mounted **Azure Files** SMB share, a **queue** decoupling its order intake from processing, and a **table** of NoSQL customer metadata, while its VMs run on **managed disks** (the latency-critical database VM uses a **Premium** SSD-backed account). Active website images sit in the **Hot** tier, monthly reports drop to **Cool**, compliance data kept untouched for a year sits in **Cold**, and seven-year legal records go **offline in Archive**, rehydrated in hours on the rare subpoena. The account uses **RA-GRS**, so three copies live in the primary datacenter, six exist across two regions, and reports can be *read* from the secondary region anytime — where **ZRS/GZRS** would have added zone-level protection. Admins script nightly uploads with **AzCopy**, browse ad hoc with **Storage Explorer**, and each branch office's Windows Server caches the central file share **bi-directionally** via **Azure File Sync**. The migration itself was planned in **Azure Migrate**, which assessed every on-prem server — and the initial 200 TB archive arrived not over the wire but inside an **Azure Data Box**.

## Quick Contrast Drills

Four pairings the exam loves to blur — rehearse the one-line distinction:

1. **Blob vs. Files:** both store files, but Blob is **object storage over REST/HTTP(S)** while Azure Files is a **mountable SMB/NFS share** — "drive letter" or "lift-and-shift file share" means Files.
2. **Cool/Cold vs. Archive:** all are cheap tiers for infrequent access, but Cool and Cold are **online (instant reads)** while Archive is **offline (hours to rehydrate)**.
3. **GRS vs. RA-GRS:** both keep six copies across two regions, but only **RA-** lets you **read the secondary before a failover**.
4. **AzCopy sync vs. Azure File Sync:** AzCopy's sync is a **one-direction command-line copy**; File Sync is an **ongoing bi-directional service** caching an Azure Files share on a Windows Server.

And one spanning bullets: **Azure Migrate vs. Azure Data Box** is really *workloads over the network with assessment* vs. *bulk data shipped offline* — pick by whether the scenario stresses discovering/assessing servers (Migrate) or moving huge data past a weak link (Data Box).

## Key Takeaways

- [ ] Five storage services by data shape: **Blob** (unstructured objects via HTTP/REST), **Files** (managed SMB/NFS shares mountable from cloud and on-prem), **Queues** (async messages ≤ 64 KB), **Tables** (NoSQL non-relational), **Disks** (block storage for VMs).
- [ ] Blob access tiers trade storage cost for access cost/latency: **Hot** (frequent), **Cool** (≥ 30 days), **Cold** (≥ 90 days), **Archive** (≥ 180 days, **offline**, hours to rehydrate); tier can be set per blob.
- [ ] Redundancy by copy placement: **LRS** = 3 copies/one datacenter; **ZRS** = 3 copies/three zones; **GRS** = LRS + async secondary region (6 copies); **GZRS** = ZRS + secondary region; **RA-** prefix = always-readable secondary.
- [ ] Geo-replication is **asynchronous** — a failover can lose the latest writes; plain GRS/GZRS secondaries are readable **only after failover**.
- [ ] Storage account names are **globally unique**; **Standard general-purpose v2** fits most scenarios, **Premium** (block blob / file share / page blob) is SSD-backed for low latency.
- [ ] Moving files: **AzCopy** = CLI copy/sync (one-direction sync); **Storage Explorer** = cross-platform GUI; **Azure File Sync** = bi-directional Windows Server cache of Azure Files.
- [ ] Migration: **Azure Migrate** = discover/assess/migrate servers, databases, web apps, VDI over the network; **Azure Data Box** = ~80 TB physical appliance for offline bulk transfer when data is too big or bandwidth too thin.

## Self-Check Questions

1. A media company stores raw video footage that editors touch daily for two weeks, after which clips are kept for seven years for legal reasons and essentially never opened — but must be retrievable within a day if subpoenaed. Which two blob access tiers fit these two phases?
2. A regulated firm must ensure its storage survives the loss of an entire Azure region, and its reporting app must be able to **read** data from the secondary region during normal operations. Which redundancy option is the minimum fit?
3. An on-prem application being lifted to Azure expects to write to a mapped network drive over SMB. Which Azure storage service should replace the file server, and which tool would keep a local Windows Server cache of it for branch-office performance?
4. A company must move 150 TB of historical data to Azure from a site with a 20 Mbps uplink, and separately wants to assess 300 VMware VMs for migration readiness and Azure cost. Which service handles each need?
5. What distinguishes a Standard general-purpose v2 storage account from a Premium block blob account, and when would you choose each?

<summary>Answers</summary>

1. **Hot** for the two-week editing window (frequent access), then **Archive** for the seven-year retention — it's the cheapest storage, and its hours-long rehydration still satisfies "within a day." Cool/Cold would cost more and their instant availability isn't required.
2. **RA-GRS** (or RA-GZRS) — GRS alone replicates to a secondary region but that secondary is readable **only after failover**; the **RA-** (read-access) variant provides always-on read access. ZRS never leaves the region.
3. **Azure Files** — fully managed SMB (or NFS) shares mountable from cloud and on-premises simultaneously. **Azure File Sync** installs on a Windows Server to cache the share locally with bi-directional synchronization, keeping LAN performance.
4. The 150 TB over a 20 Mbps link would take many months — use **Azure Data Box**, the shipped physical appliance (~80 TB usable each) for offline transfer. The VM discovery, readiness assessment, and cost estimation is **Azure Migrate**'s job.
5. Standard GPv2 is the HDD-backed default supporting **all four services** (blobs, files, queues, tables) and every redundancy option — right for most workloads. Premium block blob accounts are **SSD-backed** for high transaction rates and consistently low latency, cost more, and support fewer redundancy choices — choose Premium only when the scenario demands performance.
