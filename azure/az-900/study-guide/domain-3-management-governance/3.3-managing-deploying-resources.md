# Objective 3.3 — Describe features and tools for managing and deploying Azure resources

This objective covers *how you actually work with Azure day to day*: the tools you click, type, and script. AZ-900 questions here are almost always tool-selection scenarios — "an administrator needs to run CLI commands from a locked-down kiosk with nothing installed," "a team wants deployments that produce the same environment every time," "a company wants to apply Azure Policy to servers running in AWS." Your job is to map each requirement to exactly one tool: portal, Cloud Shell, Azure CLI, Azure PowerShell, Azure Arc, ARM, ARM templates, or Bicep. Learn what each one is, the one attribute that makes it the *only* correct answer in its scenario, and the pairings the exam deliberately blurs (ARM the *service* vs. ARM *templates* the files; Bicep vs. ARM template JSON; Arc vs. ARM).

## Azure portal

- **What it is:** The **web-based graphical user interface** for building, managing, and monitoring **everything in Azure** — from simple web apps to complex cloud deployments — at `portal.azure.com`.
- **Key traits:**
  - Point-and-click resource creation with **guided wizards** — no command-line or scripting knowledge required.
  - **Customizable dashboards** for an organized, at-a-glance view of exactly the resources and metrics you care about.
  - Visual monitoring, cost/billing views, alerting, and access to every Azure service in one place.
- **Resilience:** the portal is designed for continuous availability and maintains a presence in every Azure datacenter, so it stays responsive and close to users worldwide.
- **Why it matters:** it is the lowest-friction way to explore, do one-off tasks, and visualize resources — but manual clicks are hard to repeat identically, which is exactly the gap IaC (below) fills.
- **Azure mobile app:** for **on-the-go management** when you're away from a computer — from a phone or tablet you can:
  - Check the **health and status** of resources and view **alerts and metrics**.
  - Take corrective actions — e.g., **restart a VM** or a web app.
  - Even **run Azure CLI or PowerShell commands** through Cloud Shell from the app.

> 💡 **Exam Tip:** Keyword mapping — "web-based, graphical, no scripting required, dashboards" = **Azure portal**. "Monitor and manage resources from a phone while away from the office" = **Azure mobile app**.

## Azure Cloud Shell (Azure CLI and Azure PowerShell)

- **What it is:** A **browser-based shell hosted inside the Azure portal** (also reachable at `shell.azure.com` and from the mobile app). It gives you a command line **without installing anything locally**.
- **Key traits:**
  - **Nothing to install or maintain** — the tools are hosted and kept up to date for you; works from any browser on any OS.
  - **Automatically authenticated** as the signed-in Azure user — no separate login or credential management.
  - Perfect for locked-down, borrowed, or unmanaged machines where you can't (or shouldn't) install tooling.
- **Two environments, your choice of both:** Cloud Shell offers **Bash with the Azure CLI** and **PowerShell with the Az module** — you can switch between them at will.
- **Why it matters:** it removes every setup barrier between you and a scriptable Azure session; the same `az` commands and cmdlets you'd run locally work identically here.

| | Azure CLI | Azure PowerShell |
|---|---|---|
| Command style | Bash-style commands starting with **`az`** (e.g., `az vm create`) | PowerShell **cmdlets** from the **Az module** (e.g., `New-AzVM`) |
| Syntax heritage | Familiar to Linux/bash administrators | Verb-Noun, familiar to Windows/PowerShell administrators |
| Runs on | Windows, Linux, macOS — cross-platform | Windows, Linux, macOS — cross-platform (PowerShell Core) |
| Where available | Local install **or** Cloud Shell | Local install **or** Cloud Shell |
| Capabilities | Same Azure operations — create, manage, automate, script | Same Azure operations — create, manage, automate, script |

- **How to choose:** both tools can do the same work; the deciding factor is **which scripting language your team already knows** — bash shops pick the CLI, PowerShell shops pick Azure PowerShell.

> ⚠️ **Common Pitfall:** Don't let "PowerShell = Windows only" trick you — **both** the Azure CLI and Azure PowerShell run on Windows, Linux, and macOS. Also, Cloud Shell is not a third language: it's a *hosted environment* that contains **both** the CLI and PowerShell.

> 💡 **Exam Tip:** "Run commands from a borrowed/locked-down machine with nothing installed, already authenticated" = **Cloud Shell**. "`az` commands" = Azure CLI; "cmdlets / Az module / `New-AzVM`" = Azure PowerShell.

## Azure Arc

- **What it is:** A service that **extends the Azure management plane to resources running OUTSIDE Azure** — on-premises servers, Kubernetes clusters, SQL Server instances, and virtual machines hosted in **other public clouds** (AWS, GCP).
- **How it works:** Arc-enabled resources are projected into **Azure Resource Manager** as first-class Azure resources, so you can govern them with the same tools you use for native Azure resources: **Azure Policy, role-based access control (RBAC), tags, and Azure Monitor**, all from the Azure portal.
- **Why it matters:** it delivers a **single pane of glass** — one consistent management, governance, and security experience across **hybrid and multicloud** estates instead of one toolset per environment.
- **What it is NOT:** Arc does not migrate or host the workloads — the servers stay where they are; only their *management* moves into Azure.

| | Without Azure Arc | With Azure Arc |
|---|---|---|
| On-prem / other-cloud servers | Managed with separate, per-environment tools | Appear in the Azure portal as Azure resources |
| Governance | Azure Policy/RBAC/tags stop at Azure's border | Policy, RBAC, tags, Monitor apply everywhere |
| Operational view | One console per environment | Single pane of glass for the whole estate |
| Workload location | Unchanged | Still unchanged — only management is centralized |

> 💡 **Exam Tip:** The instant you see "manage/govern servers **on-premises or in another cloud** with Azure tools" or "single pane of glass for hybrid/multicloud," the answer is **Azure Arc**. If everything in the scenario already lives in Azure, Arc is a distractor.

## Infrastructure as code (IaC)

- **What it is:** Managing and provisioning infrastructure by **describing it in code files** (templates/definitions) rather than clicking through a GUI or running ad-hoc manual steps.
- **Why it matters:**
  - Deployments become **repeatable and consistent** — the same file produces the same environment every time (dev = test = prod).
  - Definitions are **version-controlled, code-reviewed, and audited** like application source — you know exactly who changed what, when.
  - Entire environments spin up (or tear down) in **minutes**, on demand, for testing or disaster recovery.
  - Rebuilding from the definition **avoids configuration drift** — environments silently diverging from the intended state through manual, untracked changes.
- **Two approaches:**

| | Imperative | Declarative |
|---|---|---|
| You specify | The **step-by-step commands** to run, in order ("how") | The **desired end state** ("what"); the platform figures out how |
| Examples | A bash script of `az` commands; a PowerShell script of cmdlets | **ARM templates, Bicep**, Terraform |
| Drift/repeat handling | You handle errors, ordering, and existing resources yourself | Platform reconciles to the end state; re-running is safe (**idempotent**) |

> ⚠️ **Common Pitfall:** A script full of CLI commands *is* automation, but it is **imperative** — it lists steps. ARM templates and Bicep are **declarative** — they state the outcome. AZ-900 favors the declarative approach when the scenario stresses "consistent, repeatable" deployments.

## Azure Resource Manager (ARM), ARM templates, and Bicep

### Azure Resource Manager — the service

- **What it is:** The **deployment and management layer for Azure**. **Every** request to create, update, or delete a resource — whether it comes from the **portal, Azure CLI, Azure PowerShell, REST APIs, or SDKs** — goes through ARM.
- **How it works:** ARM receives the request, **authenticates and authorizes** it, then sends it on to the appropriate Azure service (resource provider) to carry out the action.
- **Why it matters:** one consistent entry point means **consistent results and capabilities across all tools** — the same feature works the same way whichever tool submits it — plus platform-wide capabilities:
  - **Role-based access control (RBAC)** applied natively to every service.
  - **Organizing tags** to label and logically sort resources (and clarify billing).
  - **Resource locks** to protect critical resources from accidental change or deletion.
  - **Group-based management** — deploy, manage, monitor, and delete related resources as a single unit.

### ARM templates — the files

- **What it is:** **JSON files that declaratively define** the resources to deploy — infrastructure as code for Azure.
- **Key traits:**
  - **Declarative** — you state the intended resources and properties, not the commands to create them.
  - **Validated before deployment** — ARM checks the template first and won't start a half-broken rollout.
  - **Idempotent** — deploy the same template repeatedly and get the same resulting environment, with no duplicates.
  - **Orchestrates dependencies** — ARM determines resource ordering and creates independent resources **in parallel**, so you don't script the sequence yourself.
- **Why it matters:** repeatable, reviewable, versionable deployments that can be wired into CI/CD pipelines.

### Bicep — the friendlier language

- **What it is:** A **domain-specific language (DSL)** that uses **simpler, cleaner declarative syntax** to define Azure resources — the same capabilities as ARM templates **without the JSON boilerplate** (no nested quotes/braces sprawl, easier parameters and variables).
- **How it works:** a Bicep file **transpiles to standard ARM template JSON** at deployment time, so ARM ultimately processes the same thing.
- **Key traits:** **supports all resource types and API versions immediately** upon release — no waiting for tooling updates; easier to author and read; same idempotent, validated, orchestrated deployment model because it *is* an ARM template underneath.

| | ARM (the service) | ARM template | Bicep |
|---|---|---|---|
| What it is | Azure's deployment & management **layer** | Declarative **JSON file** | Declarative **DSL file** (simpler syntax) |
| Role | Authenticates, authorizes, routes every request | Defines *what* to deploy | Defines *what* to deploy, transpiles to ARM JSON |
| You interact via | Portal, CLI, PowerShell, REST, SDKs | Author/deploy the file | Author/deploy the file |

> 💡 **Exam Tip:** "Every request from every tool passes through it" = **Azure Resource Manager** (the service). "Declarative **JSON** deployment file" = **ARM template**. "Simpler syntax, less boilerplate, transpiles/converts to an ARM template" = **Bicep**.

> ⚠️ **Common Pitfall:** "ARM" in a question can mean the *service* or the *template*. Read for context: routing/authenticating/authorizing requests → the service; defining resources in a file → the template. And Bicep is not a separate deployment engine — it compiles down to ARM template JSON.

## How It Fits Together (mental model)

Picture one deployment travelling through every bullet: an engineer opens the **Azure portal** to prototype a VM with a wizard (and later checks its health from the **Azure mobile app** on the train). To make the build repeatable, she opens **Azure Cloud Shell** right in the browser — nothing installed, already authenticated — and, since her team knows bash, uses the **Azure CLI** (`az deployment group create`) while a teammate prefers **Azure PowerShell** cmdlets; both work because the tools are equivalent. Instead of scripting imperative steps, she writes the environment as **infrastructure as code**: a **Bicep** file with clean declarative syntax, which transpiles to an **ARM template** (JSON) at deploy time. Whichever tool submits it, the request lands at **Azure Resource Manager**, which authenticates, authorizes, validates the template, orders the dependencies, and routes the work to each service — idempotently, so re-running changes nothing that's already correct. Finally, the company's remaining on-prem servers and a few AWS VMs are connected through **Azure Arc**, so the same RBAC, Policy, tags, and Monitor govern the entire hybrid estate from one pane of glass.

## Quick Contrast Drills

Four pairings the exam loves to blur — rehearse the one-line distinction:

1. **Azure portal vs. Azure Cloud Shell:** both live in the browser, but the portal is the **graphical point-and-click** experience while Cloud Shell is the **command-line** environment hosted *inside* it (CLI + PowerShell, zero install, auto-authenticated).
2. **Azure CLI vs. Azure PowerShell:** both are cross-platform and functionally equivalent — the CLI uses **bash-style `az` commands**, PowerShell uses **Az-module cmdlets**; choose by the scripting language your team already knows.
3. **ARM (the service) vs. ARM templates (the files):** Azure Resource Manager is the **management layer every request passes through**; an ARM template is a **declarative JSON file** that describes what ARM should deploy.
4. **ARM templates vs. Bicep:** same declarative engine, different authoring experience — templates are **verbose JSON**, Bicep is a **cleaner DSL that transpiles to that JSON** and supports every resource type immediately.

And one that spans management planes: **Azure Arc vs. ARM** — ARM manages everything *inside* Azure; Arc **projects outside resources into ARM** so on-prem and other-cloud machines can be governed as if they were Azure resources.

## Key Takeaways

- [ ] The Azure portal is the web-based GUI for building, managing, and monitoring everything in Azure — customizable dashboards, no CLI skills needed; the Azure mobile app extends monitoring and quick actions to your phone.
- [ ] Azure Cloud Shell is a browser-based shell in the portal: nothing to install, automatically authenticated, and it offers **both** the Azure CLI and Azure PowerShell.
- [ ] Azure CLI = bash-style `az` commands; Azure PowerShell = Az-module cmdlets; **both are cross-platform** (Windows/Linux/macOS) and equally capable — pick by team skill set.
- [ ] Azure Arc extends Azure governance (Policy, RBAC, tags, Monitor) to resources **outside** Azure — on-prem servers, Kubernetes, SQL Server, VMs in other clouds — a single pane of glass for hybrid/multicloud.
- [ ] Infrastructure as code defines environments **declaratively in files** for repeatable, consistent, version-controlled deployments and protection against configuration drift; declarative = desired end state, imperative = step-by-step commands.
- [ ] Azure Resource Manager is the deployment and management layer: **every** request from portal, CLI, PowerShell, REST, or SDKs is authenticated, authorized, and routed by ARM — enabling consistent tooling plus RBAC, tags, and locks everywhere.
- [ ] ARM templates are **declarative JSON** files: validated before deployment, idempotent, and ARM orchestrates resource dependencies (parallel where possible).
- [ ] Bicep is a simpler DSL on top of ARM templates — cleaner syntax, no JSON boilerplate, transpiles to ARM JSON, and supports all resource types and API versions immediately.
