# Objective 3.4 — Describe monitoring tools in Azure

AZ-900 tests this objective almost entirely through "which tool tells you about X?" questions. Three tools own three different jobs: **Azure Advisor** proactively recommends how to improve what you have already deployed; **Azure Service Health** tells you about the health of *Azure itself* as it affects you (outages, planned maintenance); and **Azure Monitor** collects and analyzes telemetry from *your* resources — with **Log Analytics** (query the logs), **Azure Monitor alerts** (get notified on thresholds), and **Application Insights** (application performance) as its named features. Expect scenario stems like "a VM went down — how do you find out whether Azure caused it?" or "you want an email when CPU exceeds 80%." Learn each tool's one-line job description and the keywords that point to it, and this objective becomes free points.

## Azure Advisor

- **What it is:** A **free** service that evaluates your deployed Azure resources against best practices and makes **personalized, actionable recommendations** — a built-in cloud consultant.
- **How it works:** Advisor continuously analyzes your resource configurations and usage telemetry, then surfaces recommendations in the Azure portal (and via API). Because it looks at *your* actual usage, two subscriptions get two different recommendation lists.
- **Acting on recommendations:** Each recommendation includes suggested actions you can take **directly in the portal**, or you can **postpone** or **dismiss** it. Advisor never changes anything on its own — you stay in control.
- **Delivery:** Recommendations can also be set up as **alerts or periodic digests**, so new findings are pushed to the right team automatically instead of waiting to be discovered.
- **The five categories (memorize these — the exam asks):**

| Category | Example recommendation |
|---|---|
| **Reliability** | Enable VM backup; add redundancy to ensure continuity of business-critical applications |
| **Security** | Remediate configuration gaps that could lead to security breaches |
| **Performance** | Right-size or upgrade SKUs to improve the speed of applications |
| **Operational Excellence** | Improve process/workflow efficiency, resource manageability, and deployment best practices |
| **Cost** | Shut down or resize underutilized VMs; buy reserved instances to optimize spend |

- **Why it matters:** Advisor is *proactive* — it doesn't wait for something to break or for a threshold to be crossed. It closes the gap between "deployed" and "well-architected" without hiring a consultant.

> 💡 **Exam Tip:** Any scenario about "recommendations," "best practices," or "reducing spend on underutilized resources" = **Azure Advisor**. And burn in the five categories: **Reliability, Security, Performance, Operational Excellence, Cost** — a favorite question style is spotting the fake category (e.g., "Scalability" or "Compliance") slipped into the list.

> ⚠️ **Common Pitfall:** Advisor's Cost category vs. Cost Management: **Cost Management reports what you are spending**; **Advisor recommends how to spend less** (e.g., "this VM has been under 5% CPU for 30 days — resize it"). If the stem says "recommend," it's Advisor.

## Azure Service Health

- **What it is:** The service that reports on the **health of the Azure platform itself** as it affects **you** — service outages, planned maintenance, and other health advisories. When something goes wrong on Microsoft's side, this is where you find out.
- **Why it matters:** It cleanly separates "Azure has a problem" from "my stuff has a problem," and it warns you *before* planned maintenance touches your workloads.

Service Health is really **three views at three zoom levels** — the exam expects you to pick the right one:

### Azure Status

- **What it is:** A **public web page** (status.azure.com) showing **service-wide outages across all of Azure** — every service, every region, visible to anyone with a browser.
- **Use case:** "Is Azure as a whole having a bad day?" No subscription or sign-in required — useful even to journalists and customers who run nothing in Azure.

### Service Health (the personalized view)

- **What it is:** A portal experience scoped to **the services and regions YOU actually use**, showing **service issues** (active incidents), **planned maintenance** (upcoming work that could affect availability), and **health advisories** (changes requiring your attention, like feature retirements).
- **Extras the exam mentions:** you can configure **Service Health alerts** to be notified when an event affects your services/regions, and after an incident Service Health stores Microsoft's **root cause analyses (RCAs)** for you to review and share internally.

### Resource Health

- **What it is:** The health of **one individual resource** — e.g., a specific virtual machine — right now and historically.
- **Use case:** the classic exam scenario — "my VM was down for 40 minutes last night; **was it an Azure platform issue or something I did?**" Resource Health answers exactly that.

| View | Scope | What it shows |
|---|---|---|
| **Azure Status** | **Global** — all of Azure, everyone | Public page of service-wide outages across all regions and services |
| **Service Health** | **Your** services and regions | Personalized incidents, planned maintenance, health advisories; alerts and RCAs |
| **Resource Health** | **One individual resource** | Whether a specific resource is healthy now and its health history |

> 💡 **Exam Tip:** Scope words are the tell: "**global/public** status of Azure" = Azure Status; "**my services/my region**, planned maintenance" = Service Health; "**this one VM**, platform-caused?" = Resource Health.

> ⚠️ **Common Pitfall:** Don't confuse Service Health with Azure Monitor. **Service Health = the health of Azure** (Microsoft's platform: outages, maintenance). **Azure Monitor = the health and performance of YOUR resources** (CPU, logs, app response times). "Regional outage" or "planned maintenance notification" is never a Monitor question.

## Azure Monitor

- **What it is:** The **umbrella platform** for collecting, storing, analyzing, visualizing, and acting on **metrics and logs** from your entire environment.
- **What it collects from — every layer of the stack:**
  - the **application** itself,
  - the **operating system** the application runs on,
  - the **Azure resources** it depends on,
  - the **subscription** (activity/administrative events),
  - the **tenant** (organization-level services such as Microsoft Entra ID — formerly Azure Active Directory),
  - plus resources in **other clouds and on-premises**.
- **How the data flows:** all telemetry lands in two stores — **metrics** (numeric time-series values, e.g., CPU percentage) and **logs** (records and events). From those stores the data feeds **insights** (like Application Insights), **visualizations** (dashboards, workbooks, Power BI), **analysis** (Log Analytics), and **actions** (alerts, autoscale, automation).

| Stage | What happens | Examples |
|---|---|---|
| **Collect** | Telemetry gathered from every layer and location | App, guest OS, resources, subscription, tenant, on-prem, multicloud |
| **Store** | Data lands in one of two stores | **Metrics** (time-series numbers), **Logs** (records/events) |
| **Consume** | Stored data is put to work | Insights (App Insights), visualize (dashboards/workbooks), analyze (Log Analytics), act (alerts/autoscale) |

- **Why it matters:** One platform, full-stack visibility. The three named features below are all *parts of Azure Monitor* — the exam expects you to know both the umbrella and the pieces.

### Log Analytics

- **What it is:** The **tool in the portal where you write and run log queries** against the data Azure Monitor's log store has gathered, kept in a **Log Analytics workspace**.
- **How it works:** Queries are written in **Kusto Query Language (KQL)** — from simple sorting and filtering of records up to advanced multi-table queries whose results can be visualized or pinned to dashboards.
- **Scenario keyword:** "query," "analyze weeks of log data," "correlate events across VMs" = Log Analytics.

> ⚠️ **Common Pitfall:** Log Analytics (the **tool** you query with) vs. the Log Analytics **workspace** (the **store** the data lives in). If the question asks *where log data is kept*, it's the workspace; if it asks *what you use to run the query*, it's Log Analytics.

### Azure Monitor alerts

- **What they are:** **Automated notifications** that fire when a threshold is crossed — **metric alerts** watch numeric values (e.g., CPU > 80%), **log alerts** watch the results of log queries.
- **Action groups:** an alert rule triggers an **action group**, which defines *who* gets notified (email, SMS, push, voice) and *what* runs automatically (webhook, Azure Function, Automation runbook for auto-remediation like restarting a service).
- **Scenario keyword:** "notify the team when...", "trigger automatic remediation when a threshold is exceeded" = Azure Monitor alerts.

> 💡 **Exam Tip:** Two alert flavors, one rule of thumb: watching a **number** (CPU %, disk space, request count) = **metric alert**; watching **records/events returned by a query** (error entries, failed sign-ins) = **log alert**. Either way, the **action group** is what actually sends the email/SMS or runs the runbook.

### Application Insights

- **What it is:** Azure Monitor's **application performance management (APM)** feature — it instruments your application via an **agent or SDK** and monitors it from the inside.
- **What it tracks:** request rates, **response times**, **failure rates**, dependency performance (are external calls slowing you down?), page views and load performance, user sessions.
- **Availability probing:** it can send **synthetic requests** to your application even during quiet periods with no real traffic — so you learn the app is down at 3 a.m. before your users do at 9 a.m.
- **Where the app runs doesn't matter:** Application Insights can monitor apps in Azure, on-premises, or in other clouds — instrumentation, not hosting, is what connects it.
- **Scenario keyword:** "response times," "failure rates," "page views," "dependency performance," "APM" = Application Insights.

| | Azure Monitor (platform) | Log Analytics | Monitor alerts | Application Insights |
|---|---|---|---|---|
| Job | Collect metrics + logs everywhere | Write/run KQL queries on log data | Notify/act when thresholds are crossed | Monitor app performance and availability |
| Question keyword | "single platform for telemetry" | "query the logs" | "CPU > 80% → email" | "response times, failure rates, page views" |

> 💡 **Exam Tip:** All three features belong to Azure Monitor, but the exam asks about them individually. Map the verb: **query** → Log Analytics, **notify** → alerts (via action groups), **application performance** → Application Insights.

> ⚠️ **Common Pitfall:** Advisor vs. Monitor alerts both "tell you things." **Advisor recommends improvements** (best practices — no threshold involved); **Monitor alerts react to conditions you defined** (a metric or log threshold crossed right now). "Recommendation" = Advisor; "notification when X exceeds Y" = alert.

## How It Fits Together (mental model)

Picture running a production web app in Azure. **Azure Monitor** is the always-on telemetry platform, pulling metrics and logs from the application, the VM guest OS, the Azure resources, the subscription, and the tenant — even from your on-prem and AWS boxes. **Application Insights** (a Monitor feature, wired in via SDK) watches the app itself: response times, failure rates, dependency calls, and synthetic availability probes overnight. When engineers need to dig into events, they open **Log Analytics** and run **KQL** queries against the workspace. A **metric alert** on CPU > 80% triggers an **action group** that emails on-call and fires a runbook. Meanwhile **Azure Advisor** quietly reviews the deployment and recommends — across **Reliability, Security, Performance, Operational Excellence, and Cost** — that you back up the VM and resize an underutilized one. And when the app goes down through no fault of yours, **Azure Service Health** shows the regional incident affecting your services, **Resource Health** confirms your VM's downtime was platform-caused, and the **RCA** appears there once Microsoft completes it.

## Quick Contrast Drills

Four pairings the exam loves to blur — rehearse the one-line distinction:

1. **Service Health vs. Azure Monitor:** Service Health reports on **Azure's** problems (outages, maintenance affecting you); Monitor reports on **your resources'** telemetry (metrics, logs, app performance).
2. **Advisor vs. Monitor alerts:** Advisor gives **proactive best-practice recommendations** (no thresholds); alerts are **reactive notifications** when a metric/log condition you defined is met.
3. **Azure Status vs. Service Health vs. Resource Health:** the same tool at three zoom levels — **all of Azure (public page) → your services/regions → one specific resource**.
4. **Log Analytics vs. Application Insights:** both live under Monitor, but Log Analytics is the **query tool** for any collected log data, while Application Insights is **instrumentation inside an application** for APM.

And one more that trips people up: **metric alert vs. log alert** is really **number-crossed-a-threshold vs. query-returned-matching-records** — pick based on whether the scenario watches a live numeric value (CPU, disk, requests/sec) or patterns inside collected log entries. Both end the same way: the action group notifies and remediates.

## Key Takeaways

- [ ] Azure Advisor = free, personalized, actionable best-practice recommendations in **five categories: Reliability, Security, Performance, Operational Excellence, Cost**; act on them in the portal or receive them as alerts/digests.
- [ ] Azure Service Health = the health of **Azure itself** as it affects you: **Azure Status** (global public page) → **Service Health** (your services/regions, incl. planned maintenance) → **Resource Health** (one resource); supports alerts and stores incident RCAs.
- [ ] Azure Monitor = the umbrella platform collecting **metrics and logs** from app, OS, resource, subscription, and tenant layers — plus on-premises and other clouds — feeding insights, visualizations, analysis, and actions.
- [ ] Log Analytics = the tool/workspace where you write and run **KQL** queries against Monitor's log data, from simple filters to advanced queries.
- [ ] Azure Monitor alerts = threshold-based notifications (**metric** and **log** alerts); **action groups** define notification recipients and automated responses (email/SMS/webhook/runbook).
- [ ] Application Insights = Monitor's **APM** feature; via agent/SDK it tracks requests, response times, failure rates, dependencies, and page views — and can probe availability during quiet periods; works for apps anywhere, not just Azure.
- [ ] Tool-picker reflex: cost recs = Advisor; outage/maintenance = Service Health; query logs = Log Analytics; app performance = Application Insights; threshold notification = Monitor alerts.

## Self-Check Questions

1. Your finance team wants to cut the Azure bill. Which free tool identifies underutilized VMs and recommends resizing or shutting them down — and what are its five recommendation categories?
2. Users report your app was unreachable for an hour last night. You suspect Azure itself. Which view answers "was my specific VM's downtime a platform issue?" — and which view would show a datacenter-wide incident in your region?
3. An administrator must be emailed, and a runbook must run automatically, whenever a database server's CPU stays above 80%. Which Azure Monitor feature fires the notification, and what defines the recipients/actions?
4. A DevOps engineer needs to search weeks of collected VM event logs for a recurring error pattern, using a query language. Which tool and which language?
5. A web team wants per-request response times, failure rates, and dependency timings for their application — plus confirmation the site is up at 3 a.m. when no customers are browsing. Which feature of Azure Monitor provides all of this, and how does it get its data?
