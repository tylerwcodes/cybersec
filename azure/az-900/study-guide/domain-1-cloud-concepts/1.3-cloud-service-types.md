# Objective 1.3 — Describe cloud service types

AZ-900 devotes an entire objective to the three cloud service types — IaaS, PaaS, and SaaS — because nearly every Azure question ultimately reduces to "who manages what?" The exam (passing score 700 on a 1–1000 scale) rarely asks for bare definitions; instead it hands you a scenario and expects you to hear the keyword: "migrate servers without changing them" (IaaS), "deploy code without managing the underlying operating system" (PaaS), "subscription email in a browser" (SaaS). Every one of those phrasings is really a question about the **shared responsibility model** — the split of management duties between you and Microsoft. Learn the responsibility ladder cold, attach two or three Azure product examples to each rung, and map each classic use case to the responsibility split that justifies it. That is exactly how the questions are written.

## The shared responsibility ladder (who manages what)

Everything in this objective hangs off one table. As you move left to right, Microsoft absorbs more of the stack and you keep less:

| You manage → | On-premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Applications | You | **You** | **You** | Provider |
| Data | You | **You** | **You** | **You** — always yours |
| Runtime/middleware | You | **You** | Provider | Provider |
| Operating system | You | **You** | Provider | Provider |
| Virtualization | You | Provider | Provider | Provider |
| Servers/storage | You | Provider | Provider | Provider |
| Networking/data center | You | Provider | Provider | Provider |

Three anchor facts:

- **The physical layer is never yours in the cloud.** Datacenters, physical networking, physical hosts, and the virtualization/hypervisor layer are Microsoft's responsibility in *all three* service types — even IaaS.
- **Data, devices, and accounts/identities are always yours** — even in SaaS. You govern who signs in (via **Microsoft Entra ID**, formerly Azure Active Directory), what devices connect, and how your information is classified and used.
- **The OS row is the exam's favorite dividing line.** In IaaS *you* patch the operating system; in PaaS and SaaS *Microsoft* does. Tools like **Microsoft Defender for Cloud** exist precisely to help you monitor *your* side of this split.

> 💡 **Exam Tip:** If a question describes a responsibility and asks "whose job is it?", find the row and column in this table. "Customer patched the guest OS" = IaaS. "Provider patches OS and runtime, customer deploys code" = PaaS. "Customer manages only user accounts and data" = SaaS.

## Describe infrastructure as a service (IaaS)

- **What it is:** The provider rents you **raw, virtualized building blocks** — compute, networking, and storage — and manages everything physical: the datacenter, the physical hosts, and the hypervisor.
- **What you manage:** everything from the **operating system up** — OS installation and **patching**, security agents, middleware, runtime, applications, and data. It is the closest cloud analog to running your own servers, minus the hardware.
- **Azure examples:**
  - **Azure Virtual Machines** — rentable Windows/Linux VMs (compute)
  - **Azure virtual networks (VNets)** — your isolated network, subnets, and private IP ranges (networking)
  - **Azure Storage** — disks, blobs, and file shares (storage)
- **Why it matters:** IaaS offers the **maximum control and flexibility** of any cloud service type — and therefore the **maximum customer responsibility**. You choose the OS build, installed software, and configuration; you also carry the patch cycle.
- **Shared responsibility example:** if a VM is breached through a missing guest-OS patch, that failure is the **customer's**, not Microsoft's — Microsoft's duty ended at the hypervisor.
- **Cost model:** no capital purchase of hardware; you pay for what you provision (consumption/pay-as-you-go) and can track that spend with **Microsoft Cost Management**.

> ⚠️ **Common Pitfall:** "Microsoft manages the infrastructure" does NOT mean Microsoft patches your VMs. In IaaS, guest OS updates, antimalware on the VM, and everything installed on it are the *customer's* job. Only the physical hosts and hypervisor beneath the VM are Microsoft's.

## Describe platform as a service (PaaS)

- **What it is:** A **managed environment for developing, testing, and running applications**. The provider manages everything IaaS covers *plus* the **operating system, middleware, runtime, and development tools**.
- **What you manage:** only your **application code and data** — the two rungs PaaS never takes from you.
- **Azure examples:**
  - **Azure App Service** — managed hosting for web apps and APIs; Microsoft runs the OS, web server, and runtime
  - **Azure SQL Database** — managed relational database; **no database licenses to buy, no OS or engine patching**
  - **Azure Functions** — event-driven **serverless** compute: you upload code, it runs only when triggered, and you never provision a server
- **Why it matters:** development teams ship faster because the platform supplies the framework — OS images, language runtimes, database engines, and often built-in **analytics and business intelligence** tooling — with no OS patch cycles or software licenses to administer.
- **Serverless is PaaS taken to its logical end:** servers still exist, but the provider allocates them invisibly, scales them automatically (including to zero), and bills only while your code executes.
- **Shared responsibility example:** Microsoft patches the runtime and OS under your App Service app; **you** are still accountable for insecure application code and for the data it handles.

> 💡 **Exam Tip:** The single highest-yield phrase on this objective: **"without managing the underlying operating system" (or servers/runtimes) = PaaS.** Also map "avoid database licensing and patching" → Azure SQL Database (PaaS), and "run code only when an event fires, pay per execution" → Azure Functions (serverless PaaS).

> ⚠️ **Common Pitfall:** PaaS is not "no responsibility." You still own your application's code quality and security and the data it handles. And "serverless" does not mean "no servers exist" — it means *you* never see or manage them.

## Describe software as a service (SaaS)

- **What it is:** A **complete, finished software product**, licensed by subscription and delivered over the Internet — typically through a browser or lightweight client.
- **What the provider manages:** the *entire* stack — infrastructure, OS, middleware, runtime, and the application itself, including feature updates, patching, and availability.
- **Azure/Microsoft examples:**
  - **Microsoft 365** — email, calendaring, and Office productivity apps
  - **Dynamics 365** — CRM/ERP business applications
  - Communication/collaboration apps in the **Teams/Skype** mold
- **Why it matters:** SaaS carries the **least customer management responsibility** of the three types — and correspondingly the **least flexibility**. You configure the product; you do not build, host, or patch it.
- **What's still yours:** your **data**, the **devices** that connect, and your **accounts and identities** — provisioning users, enforcing MFA, and controlling access, typically through **Microsoft Entra ID**.
- **Shared responsibility example:** if a former employee's account is never disabled and their mailbox is abused, that is a **customer** identity-management failure — even though Microsoft runs every layer of the mail service itself.

> 💡 **Exam Tip:** "Complete product," "ready to use," "subscription," "accessed from a web browser," "no infrastructure to manage" — any of these signals **SaaS**. If the scenario is company email or a productivity suite, the answer is SaaS (Microsoft 365) before you finish reading the question.

## The three types at a glance

| | IaaS | PaaS | SaaS |
|---|---|---|---|
| You get | Virtualized compute/network/storage | A managed app platform | A finished application |
| You manage | OS and everything above it | Application code + data | Data, devices, accounts/identities |
| Control/flexibility | **Maximum** | Moderate (code-level) | Minimum (settings only) |
| Management effort | **Maximum** | Low | **Minimum** |
| Who patches the OS | **You** | Microsoft | Microsoft |
| Azure examples | Virtual Machines, VNets, Storage | App Service, SQL Database, Functions | Microsoft 365, Dynamics 365 |
| Signature keyword | "Full control of the OS" | "Without managing the underlying OS" | "Complete product by subscription" |

## Identify appropriate use cases for each cloud service type

The exam tests use cases *through* the responsibility split — the correct service type is the one whose responsibility ladder matches what the scenario says the customer wants to control (or stop controlling).

### IaaS use cases

- **Lift-and-shift migration (rehosting):** move existing workloads/VMs to the cloud with minimal or no changes. The workload expects a full OS the customer controls; only the hardware layer changes hands.
- **Testing and development:** dev/test teams that need environments stood up and torn down quickly *and* need **full control of the operating system** — specific OS builds, low-level agents, custom configurations.
- **Legacy or custom applications** requiring particular OS versions or kernel-level access: anything you must touch *below* the application tier forces IaaS.

### PaaS use cases

- **Development framework:** build web/mobile apps on a provider-supplied platform (OS, runtime, tools) without buying or managing the stack beneath your code.
- **Analytics and business intelligence:** mine and analyze data using tools built into the platform, with no analysis infrastructure of your own to maintain.
- **Shedding licenses and patch cycles:** keep running *your own* application while eliminating OS/database **license purchasing and patch management** — the rungs PaaS transfers to the provider are exactly the ones you want to shed.

### SaaS use cases

- **Email and calendaring** for the whole organization — a finished product; the customer manages only mailboxes (data) and users (identities).
- **Productivity applications** (documents, spreadsheets, CRM) available on any device by subscription — zero build effort, fastest adoption, least responsibility.

| Scenario need | Best fit | Responsibility logic |
|---|---|---|
| Migrate existing VMs unchanged | **IaaS** | Workload keeps its own OS; only the physical layer moves to Microsoft |
| Test/dev with full OS control | **IaaS** | Only IaaS leaves the OS rung with the customer |
| Build/deploy apps without touching servers | **PaaS** | Provider supplies OS, runtime, and tools; you keep code + data |
| Analytics/BI without infrastructure | **PaaS** | Platform-supplied tools; you bring the data and questions |
| Stop buying licenses and patching, keep your own app | **PaaS** | OS/middleware/runtime (and their upkeep) shift to Microsoft |
| Organization-wide email/calendaring | **SaaS** | Finished product; customer keeps data + identities only |
| Subscription productivity/CRM apps | **SaaS** | Nothing to build or host; least responsibility |

> ⚠️ **Common Pitfall:** Don't pick the model with the *most* capability — pick the one matching the *stated* responsibility. A team that "wants full control of the operating system" must accept IaaS even though PaaS is easier; a team that "does not want to manage VMs or runtimes" must give up that control and take PaaS. The scenario's control/effort trade-off *is* the answer.

## How It Fits Together (mental model)

Picture one company modernizing in three moves, each a rung up the ladder. First it performs a **lift-and-shift** of its aging servers into **Azure Virtual Machines** on a **virtual network** with **Azure Storage** — that's **IaaS**: nothing about the workload changed, Microsoft took over the datacenter, hardware, and hypervisor, and the IT team still patches every guest OS (a duty **Microsoft Defender for Cloud** now helps them monitor). Next, developers rebuild the customer-facing web app on **Azure App Service** backed by **Azure SQL Database**, and bolt on an event-driven image processor in **Azure Functions** — that's **PaaS** (and **serverless**): the OS, runtime, middleware, and database licensing/patching moved to Microsoft's side of the **shared responsibility model**, leaving the team only code and data, plus platform analytics for BI. Finally, the company retires its email servers for **Microsoft 365** and its homegrown CRM for **Dynamics 365** — **SaaS**, the complete finished product — keeping responsibility only for its **data, devices, and identities**, which it governs through **Microsoft Entra ID** while watching the whole journey's spend in **Microsoft Cost Management**. Same company, three service types, one sliding scale of who-manages-what.

## Quick Contrast Drills

Four pairings the exam loves to blur — rehearse the one-line distinction:

1. **IaaS vs. PaaS:** both host your application, but in IaaS **you manage and patch the OS**; in PaaS the provider does, leaving you **only code and data**. The OS row is the tiebreaker.
2. **PaaS vs. SaaS:** PaaS is a platform for apps **you build**; SaaS is a **finished app you consume**. If the customer writes code, it isn't SaaS.
3. **PaaS vs. serverless:** serverless (Azure Functions) is a **consumption-billed pattern *within* PaaS** — provider-managed platform either way; serverless just adds "runs per event, scales to zero, pay per execution."
4. **SaaS vs. "no responsibility":** even in SaaS the customer still owns **data, connected devices, and identities** (managed via Microsoft Entra ID). No service type reduces customer responsibility to zero.

## Key Takeaways

- [ ] The three service types are points on the shared responsibility ladder: **IaaS = OS and up is yours; PaaS = only code and data; SaaS = only data, devices, and identities.**
- [ ] Microsoft always manages the physical datacenter, physical network, physical hosts, and virtualization — in every cloud service type.
- [ ] The customer always retains data, devices, and accounts/identities — in every cloud service type (governed through Microsoft Entra ID, formerly Azure Active Directory).
- [ ] IaaS = maximum control and flexibility; Azure examples: Virtual Machines, virtual networks, Azure Storage; the customer patches the guest OS.
- [ ] IaaS use cases: lift-and-shift migration, and test/dev environments where full control of the OS is required.
- [ ] PaaS = provider manages OS, middleware, runtime, and development tools; Azure examples: App Service, Azure SQL Database, Azure Functions.
- [ ] PaaS use cases: a ready development framework, analytics/BI, and avoiding license purchases and patch management; keyword: "without managing the underlying operating system."
- [ ] Azure Functions is serverless computing — an event-driven, pay-per-execution model inside the PaaS category; servers exist but are invisible to you.
- [ ] SaaS = a complete finished product by subscription (Microsoft 365, Dynamics 365, Teams-style apps); use cases: email/calendaring and productivity apps; least customer responsibility, least flexibility.
- [ ] To pick a use case's model, match the scenario's stated control/effort trade-off to the ladder — never assume "more managed" is automatically the right answer.

## Self-Check Questions

1. A company plans to close its datacenter and move 40 existing Windows and Linux servers to Azure as-is, with no application changes. Which service type fits, and who patches those servers' operating systems afterward?
2. A development team wants to deploy a web application and its relational database "without managing the underlying operating system, runtimes, or database patching." Which service type and which two Azure services fit?
3. In which cloud service type(s) is Microsoft responsible for the virtualization layer and physical hosts — and which three things does the customer retain responsibility for even in SaaS?
4. A workload must execute a snippet of code every time a file lands in storage, with no pre-provisioned servers and billing only for actual execution time. Which Azure service and which service-type category is this?
5. An organization adopts Dynamics 365 for CRM and Microsoft 365 for email. What service type is this, what is the customer still responsible for, and which Microsoft service manages those sign-in identities?

<details>
<summary>Answers</summary>

1. **IaaS** (Azure Virtual Machines on virtual networks with Azure Storage) — a classic **lift-and-shift** migration. The **customer** still patches the guest operating systems; Microsoft manages only the physical hosts, network, datacenter, and hypervisor.
2. **PaaS** — **Azure App Service** for the web application and **Azure SQL Database** for the database. The provider manages the OS, runtime, middleware, and database engine patching/licensing; the team keeps only application code and data.
3. Microsoft owns virtualization and all physical layers in **all three** service types (IaaS, PaaS, and SaaS). Even in SaaS, the customer retains **data, devices, and accounts/identities** (managed via Microsoft Entra ID).
4. **Azure Functions** — **serverless** computing, which falls within the **PaaS** category. Servers still exist, but the provider allocates them on demand and bills per execution.
5. **SaaS** — complete finished products on subscription. The customer remains responsible for its **data, connected devices, and user accounts/identities**, which are managed through **Microsoft Entra ID (formerly Azure Active Directory)**.
