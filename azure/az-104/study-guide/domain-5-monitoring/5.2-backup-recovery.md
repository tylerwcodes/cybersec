# Objective 5.2 — Implement backup and recovery by using Azure Backup and Azure Site Recovery

This objective is tested with sharp, admin-level scenario questions built around a handful of decision points: which **vault type** a workload needs (Recovery Services vault vs. Backup vault — the single most classic trap here), which settings are **locked after the first protected item** (backup storage redundancy), which **policy** delivers a required schedule or retention, which **restore option** matches a stem ("recover one file" vs. "rebuild the whole VM" vs. "restore in another region"), and the correct **order of operations** in a Site Recovery drill (test failover → failover → commit → re-protect → fail back). Memorize the vault-to-workload mapping table, the LRS/GRS/ZRS lock rule, the standard-vs-enhanced policy schedule limits, the five VM restore options, soft delete's 14-day grace period, and the failover sequence — nearly every question in this objective resolves to one of those facts.

## Create a Recovery Services vault

- **What it is:** A **Recovery Services vault** is the classic management container for **Azure Backup** *and* **Azure Site Recovery**. It stores backup data and replication metadata for **Azure VMs**, **SQL Server and SAP HANA running inside Azure VMs**, **Azure Files** shares, and **on-premises backups** sent via the **MARS agent**, **Microsoft Azure Backup Server (MABS)**, or **System Center DPM**.
- **Why it matters:** It is the answer whenever the workload is a VM, an in-VM database, a file share, an on-premises machine — or anything involving **Site Recovery** replication. The vault must be created in the **same region and same subscription** as the VMs it protects; you cannot back up a VM in East US to a vault in West Europe.

The setting the exam loves: **backup storage redundancy**. The vault's storage can be **LRS**, **GRS** (the default), or **ZRS** — and it **must be chosen before the first item is protected**, because it is **locked once anything in the vault is being backed up**. Choosing **GRS** also unlocks **Cross-Region Restore (CRR)**: once enabled, you can restore protected items in the **secondary paired region at any time** (not only during a Microsoft-declared regional outage).

```bash
# Create the vault (same region + subscription as the VMs it will protect)
az backup vault create \
  --resource-group rg-prod --name rsv-prod-eastus --location eastus

# Set redundancy BEFORE protecting anything — locked afterwards
az backup vault backup-properties set \
  --resource-group rg-prod --name rsv-prod-eastus \
  --backup-storage-redundancy GeoRedundant \
  --cross-region-restore-flag True
```

```powershell
$vault = New-AzRecoveryServicesVault -Name rsv-prod-eastus -ResourceGroupName rg-prod -Location eastus
Set-AzRecoveryServicesBackupProperty -Vault $vault -BackupStorageRedundancy GeoRedundant
```

> 💡 **Exam Tip:** Three facts answer most vault questions: (1) the vault must be in the **same region and subscription** as the VMs it protects, (2) redundancy defaults to **GRS** and must be set **before the first backup** — locked afterwards, (3) **Cross-Region Restore requires GRS + CRR enabled** and works anytime, on demand.

> ⚠️ **Common Pitfall:** "The redundancy option is greyed out" is not a permissions problem — the vault already **contains protected items**, so redundancy can no longer change. The fix is a **new vault** with the desired redundancy, then moving/re-protecting the workloads.

## Create an Azure Backup vault

- **What it is:** The newer **Backup vault** (the Data Protection platform) is a separate vault type for the **newer PaaS workloads**: **Azure Blobs**, **Azure Disks**, **Azure Database for PostgreSQL**, and **Azure Kubernetes Service (AKS)**.
- **Why it matters:** Picking the wrong vault type is a classic question. A Backup vault **cannot** protect Azure VMs, and a Recovery Services vault **cannot** protect Blobs, Disks, PostgreSQL, or AKS. Two vault types, two disjoint workload lists — know both cold.

| | **Recovery Services vault** | **Backup vault** |
|---|---|---|
| Workloads | **Azure VMs**, **SQL Server / SAP HANA in Azure VMs**, **Azure Files**, on-prem via **MARS / MABS / DPM** | **Azure Blobs**, **Azure Disks**, **Azure Database for PostgreSQL**, **AKS** |
| Site Recovery | **Yes** — same vault handles ASR replication | No |
| Platform | Classic Azure Backup | Newer Data Protection framework |
| CLI namespace | `az backup ...` | `az dataprotection ...` |
| PowerShell | `Az.RecoveryServices` | `Az.DataProtection` |

```bash
az dataprotection backup-vault create \
  --resource-group rg-prod --vault-name bv-prod-eastus --location eastus \
  --storage-setting "[{type:'LocallyRedundant',datastore-type:'VaultStore'}]"
```

> 💡 **Exam Tip:** Sort by workload noun: "VM / SQL in a VM / SAP HANA / Azure Files / on-premises / Site Recovery" = **Recovery Services vault**. "Blobs / managed Disks / PostgreSQL / AKS" = **Backup vault**. If both appear in one scenario, the answer is **two vaults**.

> ⚠️ **Common Pitfall:** The names are cruelly similar — "Backup vault" sounds like the generic term, but it is a **specific resource type** that does *not* back up VMs. When a stem says "back up an Azure virtual machine," the Backup vault answer choice is the trap.

## Create and configure a backup policy

- **What it is:** A **backup policy** attached to a vault defines two things for the items assigned to it: the **schedule** (when backups run) and the **retention** (how long each recovery point is kept).
- **Why it matters:** Policy questions test the schedule limits of the two Azure VM policy types and the layered retention model — both are pure memorization.

**Schedule — two Azure VM policy tiers:**

| | **Standard policy** | **Enhanced policy** |
|---|---|---|
| Backup frequency | **Once per day** | **Up to every 4 hours** (multiple backups/day) |
| Required for | Most VMs | **Ultra-disk** / Premium SSD v2 VMs (Trusted Launch VMs now support standard *or* enhanced) |
| Snapshot tier retention | 1–5 days (default 2) | 1–30 days |
| Cost | Standard | Higher |

**Retention — grandfather-father-son (GFS):** a policy layers **daily**, **weekly**, **monthly**, and **yearly** retention points, so you can express "keep dailies 30 days, weeklies 12 weeks, monthlies 12 months, yearlies 7 years" in one policy without storing 2,555 daily copies.

**Instant restore:** the policy also sets **snapshot retention of 1–5 days (default 2)** for a standard policy. These local snapshots enable **Instant Restore** — restores from the snapshot tier skip the vault transfer entirely and complete in minutes.

```bash
# Inspect and reuse the default policy, or create your own from JSON
az backup policy list --resource-group rg-prod --vault-name rsv-prod-eastus -o table
az backup policy create --resource-group rg-prod --vault-name rsv-prod-eastus \
  --name DailyGFS --backup-management-type AzureIaasVM --policy @policy.json
```

```powershell
$schedule  = Get-AzRecoveryServicesBackupSchedulePolicyObject  -WorkloadType AzureVM
$retention = Get-AzRecoveryServicesBackupRetentionPolicyObject -WorkloadType AzureVM
New-AzRecoveryServicesBackupProtectionPolicy -Name DailyGFS -WorkloadType AzureVM `
  -SchedulePolicy $schedule -RetentionPolicy $retention -VaultId $vault.ID
```

> 💡 **Exam Tip:** "Back up a VM **more than once per day**" or "back up an **Ultra-disk / Premium SSD v2** VM" = **enhanced policy** (up to every **4 hours**); Trusted Launch VMs can use either policy type. "Keep monthly points for a year and yearly points for seven years" = one policy with **GFS retention**, not multiple policies.

> ⚠️ **Common Pitfall:** Snapshot (instant restore) retention and vault retention are different dials: snapshots live **1–5 days** (default **2**) for fast restores; the vault holds the long-term daily/weekly/monthly/yearly points. Raising snapshot retention speeds restores but raises snapshot storage cost — it does not change how long backups are kept.

## Perform backup and restore operations by using Azure Backup

Enabling protection installs the **backup extension** into the Azure VM agent. Snapshot consistency then depends on the OS: **application-consistent on Windows (via VSS)**, **file-system-consistent on Linux** (application-consistent only if you add **pre/post scripts**), and **crash-consistent** at worst (e.g., a VM that is shut down).

```bash
# Protect a VM, then run an on-demand backup
az backup protection enable-for-vm --resource-group rg-prod \
  --vault-name rsv-prod-eastus --vm vm-web-01 --policy-name DailyGFS
az backup protection backup-now --resource-group rg-prod \
  --vault-name rsv-prod-eastus --container-name vm-web-01 \
  --item-name vm-web-01 --backup-management-type AzureIaasVM --retain-until 15-08-2026
```

**Restore options for an Azure VM** — pick by what the stem asks for:

| Restore option | What happens | When the stem says... |
|---|---|---|
| **Create a new VM** | A new VM is built from the recovery point | "Quickly bring the workload back" |
| **Restore disks** | Only disks are restored (to a staging storage account/resource group); you attach them or build a VM from a template | "Customize the VM / attach the disk elsewhere" |
| **Replace existing** | The **source VM's disks are swapped** with the recovery point's disks (VM must still exist) | "Roll the same VM back in place" |
| **Cross-Region Restore** | Restore in the **secondary paired region** (needs **GRS + CRR**) | "Restore in another region / primary region is down" |
| **File-level recovery** | A downloaded **script mounts the recovery point as local drives** — copy out individual files, then unmount | "Recover a single file/folder, not the whole VM" |

```bash
az backup restore restore-disks --resource-group rg-prod \
  --vault-name rsv-prod-eastus --container-name vm-web-01 --item-name vm-web-01 \
  --rp-name <recoveryPointName> --storage-account stagingsa --target-resource-group rg-restore
```

Two protective behaviors round out operations:

- **Soft delete for backup:** when backup data is deleted, it is retained an extra **14 days at no cost** before permanent deletion (extendable, and can be made **always-on**/irreversible). This is the defense against **ransomware and rogue-admin** deletion of backups.
- **Stop protection** offers two choices: **retain backup data** (backups stop, existing recovery points stay restorable per policy) or **delete backup data** (which is when soft delete's 14-day grace kicks in).

For on-premises machines without MABS/DPM, the **MARS agent** (Microsoft Azure Recovery Services agent) backs up **Windows files, folders, and system state only** — **no Linux support and no full-VM backup** — and can run **up to 3 times per day**.

> 💡 **Exam Tip:** "Recover one deleted file from last Tuesday without restoring the VM" = **file-level recovery** (script mounts the recovery point as drives). "An attacker deleted our backups two days ago" = recover them from **soft delete** — data persists **14 days** after deletion.

> ⚠️ **Common Pitfall:** MARS is narrower than people assume: **files/folders/system state on Windows only** — it cannot back up Linux machines or take full VM images. For full on-prem server/VM backup, the answer is **MABS or DPM** feeding the Recovery Services vault.

## Configure Azure Site Recovery for Azure resources

- **What it is:** **Azure Site Recovery (ASR)** is the **disaster recovery** service: for Azure VMs it **continuously replicates VM disks to a secondary region**, generating **crash-consistent recovery points about every 5 minutes** and **app-consistent points** at a configurable frequency.
- **Why it matters:** Backup and Site Recovery answer different questions. Backup gives **point-in-time restore** with retention measured in days-to-years; ASR gives **continuous replication** with **RTO and RPO far lower** than restoring from backup. "Minimize downtime in a regional outage" = ASR, not Backup.

Configuration flow for Azure VMs (all managed from a **Recovery Services vault** — which must be in a region *different from the source VMs* for ASR):

1. **Enable replication** on the VMs, choosing the **target region** (typically the paired region), target resource group, and target virtual network.
2. ASR deploys the **Site Recovery (Mobility) extension**, creates a **cache storage account** in the source region, and begins **initial replication**, then continuous delta replication.
3. Set the **replication policy**: recovery point retention and **app-consistent snapshot frequency**.
4. Build a **recovery plan**: recovery plans **group VMs, order their startup** (e.g., domain controllers → database tier → app tier → web tier), and can **inject Azure Automation scripts or manual actions** between groups.

```powershell
# Representative Az.RecoveryServices ASR cmdlets (most ASR setup is portal-driven)
Get-AzRecoveryServicesAsrFabric
Get-AzRecoveryServicesAsrReplicationProtectedItem -ProtectionContainer $container
New-AzRecoveryServicesAsrRecoveryPlan -Name rp-tier-order `
  -PrimaryFabric $priFabric -RecoveryFabric $recFabric -ReplicationProtectedItem $rpi
```

> 💡 **Exam Tip:** Keyword split — "restore last week's data / retain for years" = **Azure Backup**; "fail over to another region with minimal downtime / low RPO-RTO / disaster recovery" = **Azure Site Recovery**. Multi-tier startup ordering with scripts = a **recovery plan**.

> ⚠️ **Common Pitfall:** For *backup*, the vault sits in the **same** region as the VM; for *Site Recovery*, the vault must be in a region **other than the source region** (commonly the target region). Same vault resource type, opposite placement rule — a favorite trick.

## Perform a failover to a secondary region by using Site Recovery

The exam expects the **exact sequence**, and the first step is non-negotiable:

1. **Test failover — always run this first.** ASR spins up copies of the VMs in an **isolated test virtual network** in the target region with **zero impact on production or ongoing replication**. Validate the app, then run **cleanup** to delete the test VMs. Best practice: drill regularly.
2. **Failover (real):** choose a **recovery point** — *latest* (lowest data loss, slower to process), *latest processed* (lowest RTO), or *latest app-consistent* — and ASR brings the VMs up in the **target region**.
3. **Commit:** after verifying the failed-over VMs, **commit** the failover, which deletes the other available recovery points.
4. **Re-protect:** once the original region recovers, enable **reverse replication** — the now-primary VMs in the secondary region replicate **back** to the original region.
5. **Fail back:** run a planned failover in the reverse direction to return to the original region, then re-protect again to restore the original replication direction.

```powershell
Start-AzRecoveryServicesAsrTestFailoverJob   -RecoveryPlan $rp -Direction PrimaryToRecovery -AzureVMNetworkId $testVnetId
Start-AzRecoveryServicesAsrTestFailoverCleanupJob -RecoveryPlan $rp
Start-AzRecoveryServicesAsrUnplannedFailoverJob   -RecoveryPlan $rp -Direction PrimaryToRecovery
Start-AzRecoveryServicesAsrCommitFailoverJob      -RecoveryPlan $rp
```

> 💡 **Exam Tip:** Any stem about "validating DR without affecting production" = **test failover** into an **isolated network**. Sequence questions expect: **test failover → failover (pick recovery point) → commit → re-protect (reverse replication) → fail back**.

> ⚠️ **Common Pitfall:** A test failover uses an **isolated test network**, never the production VNet — connecting test VMs to production networks causes IP/name collisions. And failover is not finished at "VMs are running": until you **commit**, the job is incomplete; until you **re-protect**, you have **no DR protection** in the new direction.

## Configure and interpret reports and alerts for backups

- **What they are:** **Backup reports** are historical/analytical views (job success rates, storage consumption, compliance, cost trends); **backup alerts** are near-real-time notifications for failures and destructive operations. Both surface centrally in **Backup center** (the cross-vault management hub).
- **Why they matter:** The setup dependency is the testable fact — reports do not work until diagnostics flow to Log Analytics.

**Reports:** enable the vault's **diagnostic settings** to send backup data to a **Log Analytics workspace**, then open the built-in **Backup Reports** workbook (in the vault or Backup center). One workspace can aggregate **many vaults across subscriptions**, giving a single reporting pane. Expect up to ~24 hours before data appears.

```bash
az monitor diagnostic-settings create \
  --name backup-diag --resource $vaultId \
  --workspace $lawId \
  --logs '[{"categoryGroup":"allLogs","enabled":true}]'
```

**Alerts:** **built-in Azure Monitor alerts** fire automatically — no rules to author — for **backup and restore job failures** and for **destructive operations** (deleting backup data, stopping protection with delete, disabling soft delete). They appear under **Alerts** in Backup center/Azure Monitor; add **alert processing rules + action groups** to route email/SMS/webhook notifications. Custom log-based alerts on the Log Analytics workspace cover anything bespoke (e.g., "no successful backup in 48 hours").

> 💡 **Exam Tip:** "Configure Backup Reports" = two ingredients: **vault diagnostic settings → Log Analytics workspace**, then the **Backup Reports workbook**. "Get notified when a backup job fails or someone deletes backup data" = **built-in Azure Monitor alerts**, surfaced in **Backup center**.

> ⚠️ **Common Pitfall:** Data collection here is a *vault diagnostic setting*, not an agent: the legacy Log Analytics (MMA) agent is retired and the **Azure Monitor Agent (AMA)** story applies to machines — neither is how vault data reaches the workspace. If a question implies installing an agent to get Backup Reports, that answer is wrong.

## How It Fits Together (mental model)

Contoso runs its production VMs in East US and starts by creating a **Recovery Services vault** in the **same region and subscription** as those VMs; before protecting anything, the admin confirms **backup storage redundancy** is **GRS** (the default, versus **LRS**/**ZRS**) and enables **Cross-Region Restore**, knowing the choice is **locked after the first protected item**. She assigns most VMs a **standard policy** (**once-per-day** backups with **GFS retention** — dailies, weeklies, monthlies, yearlies) but the **Trusted Launch** SQL VMs get an **enhanced policy** backing up **every 4 hours**, with **instant restore snapshots** kept the default **2 days**; the **backup extension** takes **application-consistent (VSS)** snapshots on Windows and **file-system-consistent** ones on Linux. The newer platform workloads — **Azure Blobs**, **Azure Disks**, **PostgreSQL**, and an **AKS** cluster — go into a separate **Backup vault**, while a legacy on-prem file server sends files and system state to Azure three times a day via the **MARS agent**. When a developer deletes a VM's backups, **soft delete** keeps the data **14 extra days** and it is recovered untouched; when a user loses one spreadsheet, **file-level recovery** mounts the recovery point as a drive instead of triggering a full **restore** (the other options being a **new VM**, **restore disks**, **replace existing**, or a **Cross-Region Restore** from the secondary). For true disaster recovery, Contoso enables **Azure Site Recovery** to **continuously replicate** the VMs to West US with **crash-consistent points every ~5 minutes**, sequences the tiers in a **recovery plan**, proves it works with a quarterly **test failover** into an **isolated network**, and — when the region really goes down — runs a **failover** to a chosen recovery point, **commits**, later **re-protects** with reverse replication, and **fails back**. Throughout, vault **diagnostic settings** stream to a **Log Analytics workspace** feeding the **Backup Reports** workbook, and **built-in Azure Monitor alerts** in **Backup center** page the team on any **job failure or destructive operation**.
