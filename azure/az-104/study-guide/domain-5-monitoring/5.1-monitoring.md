# Objective 5.1 — Monitor resources in Azure

Monitoring questions on AZ-104 are scenario drills about *plumbing*: which data pillar holds the answer (**metrics** vs. **logs**), what you must configure before data even exists (a **diagnostic setting** for resource logs, the **Azure Monitor Agent** plus a **Data Collection Rule** for VM guest data), which KQL operator produces the requested output, and which alerting object does which job (**alert rule** fires, **action group** notifies/acts, **alert processing rule** suppresses or fans out at scale). Memorize the retention numbers (93 days for metrics, 90 for the Activity Log, 30 default / 730 max interactive for a Log Analytics workspace, archive to 12 years), the four diagnostic-setting destinations, the Sev0–Sev4 scale, and the one-line purpose of every Network Watcher tool — the exam loves "which tool do you use?" stems where each distractor is a real tool that solves a *slightly* different problem.

## Interpret metrics in Azure Monitor

- **What they are:** **Metrics** are one of Azure Monitor's two data pillars — lightweight **numeric time-series** values (CPU percentage, disk IOPS, request count) collected at regular intervals, available in **near-real-time**, and retained for **93 days**.
- **Why they matter:** **Platform metrics are collected automatically** for every Azure resource with **no configuration and no agent** — they are the fastest, cheapest signal you have, and the exam expects you to explore them fluently in **Metrics Explorer**.

The two pillars contrast on every axis the exam tests:

| | **Metrics** | **Logs** |
|---|---|---|
| Shape | Numeric time series | Records/events with rich properties |
| Latency | Near-real-time | Minutes (ingestion delay) |
| Collection | Platform metrics automatic | Must be routed (diagnostic settings, agents) |
| Storage | Azure Monitor time-series database | **Log Analytics workspace** |
| Query | **Metrics Explorer** | **KQL** |
| Retention | **93 days** fixed | 30 days default, configurable (see next section) |

Working in **Metrics Explorer** you build a chart from four choices:

1. **Scope** — the resource (or multiple resources of the same type/region).
2. **Metric** — e.g., `Percentage CPU`, `Transactions`, `Ingress`.
3. **Aggregation** — how samples are rolled up per interval: **Average, Minimum, Maximum, Sum (Total), Count**. Picking the wrong one changes the story — Max CPU shows spikes that Average hides.
4. **Time range and granularity** — the window and the interval each point represents (1 minute to 1 day). Zooming to finer **time granularity** exposes short bursts smoothed away at coarser intervals.

Two features turn a flat line into a diagnosis: **splitting** breaks one metric into a line per **dimension** value (e.g., Transactions split by *API name* or *Response type*), and **filtering** restricts the chart to specific dimension values (only `GetBlob`, only `ServerTimeoutError`). Finished charts can be **pinned to Azure dashboards** (or sent to workbooks) for shared, at-a-glance operations views.

```bash
# CLI: pull a metric with a specific aggregation and interval
az monitor metrics list --resource $VM_ID \
  --metric "Percentage CPU" --aggregation Average --interval PT5M

# List which metrics (and dimensions) a resource exposes
az monitor metrics list-definitions --resource $VM_ID
```

```powershell
# PowerShell equivalent
Get-AzMetric -ResourceId $vmId -MetricName "Percentage CPU" `
  -AggregationType Maximum -TimeGrain 00:05:00
```

> 💡 **Exam Tip:** "See CPU **right now** with no setup" = platform metrics in **Metrics Explorer**. "Break the Transactions chart out **per API operation**" = apply **splitting** on a dimension; "show only failed transactions" = a dimension **filter**. Metrics live **93 days** — longer trend analysis means routing metrics to a Log Analytics workspace via a diagnostic setting.

> ⚠️ **Common Pitfall:** Metrics Explorer shows **host/platform** metrics only. Guest-OS counters — memory in use, logical-disk free space *inside* the VM — are **not** platform metrics for a VM; they require the **Azure Monitor Agent** and a Data Collection Rule (next section). If a stem asks for available memory on a VM and no agent is installed, "just open Metrics Explorer" is the trap.

## Configure log settings in Azure Monitor

- **What it is:** The configuration layer that decides **which log data gets collected and where it lands** — because unlike platform metrics, most log data is **not collected until you ask for it**.
- **Why it matters:** Half of all AZ-104 monitoring stems reduce to "the data isn't there — what's missing?" The answer is almost always a **diagnostic setting**, an **agent + DCR**, or a workspace retention change.

Know the three log sources and how each is enabled:

| Source | Plane | Collected by default? | How you enable collection |
|---|---|---|---|
| **Activity Log** | **Subscription-level control plane** — who created, modified, or deleted what, and when | Yes — kept **90 days free** | Export via a **diagnostic setting** for longer retention/analysis |
| **Resource logs** | **Data plane** — operations *inside* a resource (Key Vault reads, NSG rule hits, storage transactions) | **No** — nothing is captured until configured | Create a **diagnostic setting** per resource, choosing **categories** and destinations |
| **VM guest data** | Guest OS — Windows event logs, Syslog, performance counters | No | Install the **Azure Monitor Agent (AMA)** and associate a **Data Collection Rule (DCR)** |

A **diagnostic setting** picks log categories (and optionally metrics) and sends them to up to four destination types:

| Destination | Use it when... |
|---|---|
| **Log Analytics workspace** | You want to **query with KQL**, correlate, alert — the default choice |
| **Storage account** | Cheap long-term **archive** / audit retention |
| **Event Hubs** | **Stream to an external SIEM** or third-party tool |
| **Partner solutions** | Send directly to an integrated ISV (e.g., Datadog) |

The **Log Analytics workspace** is the destination that matters most: its default **interactive retention is 30 days**, extendable **up to 730 days**, after which data can move to **low-cost archive tiers for a total of up to 12 years** — a favorite compliance-scenario number.

For VMs, the **Azure Monitor Agent (AMA)** is the *only* supported agent — the **legacy Log Analytics agent (MMA/OMS) retired in August 2024**, so any answer built on it is wrong. AMA collects nothing on its own; a **Data Collection Rule (DCR)** defines *what* to collect (event logs, Syslog facilities, performance counters, sample rates) and *where* to send it (which workspace), and is **associated** with one or many VMs — one DCR can drive a whole fleet.

```bash
# Diagnostic setting: route resource logs + metrics to a workspace
az monitor diagnostic-settings create --name toLA \
  --resource $KV_ID --workspace $WORKSPACE_ID \
  --logs '[{"categoryGroup":"audit","enabled":true}]' \
  --metrics '[{"category":"AllMetrics","enabled":true}]'

# Workspace retention
az monitor log-analytics workspace update -g rg-mon \
  --workspace-name law-prod --retention-time 365

# Associate a DCR with a VM
az monitor data-collection rule association create \
  --name vm1-assoc --resource $VM_ID --rule-id $DCR_ID
```

```powershell
New-AzDiagnosticSetting -Name toLA -ResourceId $kvId `
  -WorkspaceId $lawId -Log $logSettings -Metric $metricSettings
```

> 💡 **Exam Tip:** Match the verb to the plane: "**who deleted** the VM?" = **Activity Log** (control plane, free for 90 days). "**Which secrets were read** in Key Vault?" = **resource logs** — and if nobody created a **diagnostic setting** beforehand, that data simply does not exist. "Send logs to a **SIEM**" = **Event Hubs** destination; "**cheap archive**" = storage account; "**query/alert**" = Log Analytics workspace.

> ⚠️ **Common Pitfall:** Diagnostic settings are **not retroactive** — creating one today captures events from today forward. And retention lives in two places: the **Activity Log's 90 days** is fixed platform retention, while the **workspace's 30-day default** is what you raise (to 730, then archive) for long-term needs. Answers that "extend Activity Log retention" directly are wrong — you *export it to a workspace*.

## Query and analyze logs in Azure Monitor

- **What it is:** Interrogating the tables in a **Log Analytics workspace** using **KQL (Kusto Query Language)** — a pipe-based language where data flows left to right through filters, aggregations, and projections.
- **Why it matters:** AZ-104 shows you queries with blanks or asks which query returns a required result; you must read and assemble the core operators without hesitation.

The canonical query shape — always **table first**, then piped operators:

```kusto
Heartbeat
| where TimeGenerated > ago(1h)
| summarize count() by Computer
| top 10 by count_
```

Core operators to lock in:

| Operator | Does | Example |
|---|---|---|
| `where` | Filters rows | `where TimeGenerated > ago(1h)` |
| `summarize` | Aggregates (count, avg, max...) grouped by columns | `summarize avg(CounterValue) by Computer, bin(TimeGenerated, 5m)` |
| `project` | Selects/renames columns | `project Computer, CounterValue` |
| `top` | First N rows by a sort expression | `top 10 by TimeGenerated desc` |
| `sort by` / `order by` | Orders results | `sort by CounterValue desc` |
| `render` | Chart the output | `render timechart` |

Common tables the exam names:

| Table | Contains |
|---|---|
| **Heartbeat** | One record per minute per connected agent — "which VMs are reporting?" |
| **Perf** | Guest performance counters from agents |
| **InsightsMetrics** | Performance data collected by **VM insights** |
| **AzureActivity** | The exported **Activity Log** |
| **Event** | **Windows** event logs |
| **Syslog** | **Linux** Syslog messages |

A worked example — machines low on memory in the last hour:

```kusto
Perf
| where TimeGenerated > ago(1h)
| where ObjectName == "Memory" and CounterName == "Available MBytes"
| summarize avg(CounterValue) by Computer
| where avg_CounterValue < 500
| sort by avg_CounterValue asc
```

Queries can be run in the portal's **Logs** blade, saved and shared, pinned to dashboards, or scripted:

```bash
az monitor log-analytics query -w $WORKSPACE_GUID \
  --analytics-query "Heartbeat | summarize count() by Computer" -t P1D
```

```powershell
Invoke-AzOperationalInsightsQuery -WorkspaceId $wsGuid `
  -Query "AzureActivity | where TimeGenerated > ago(24h) | take 50"
```

> 💡 **Exam Tip:** Read KQL as a pipeline: **filter early** (`where TimeGenerated > ago(...)`), **aggregate** (`summarize ... by`), **shape** (`project`), **limit** (`top N by`). "Count events per computer" = `summarize count() by Computer`. "Windows event logs" = **Event** table; "Linux" = **Syslog**; "is the agent alive?" = **Heartbeat**.

> ⚠️ **Common Pitfall:** Operator order matters — `top 10 by TimeGenerated` *before* a `where` filters differently than after. And don't confuse look-alike tables: **Perf** holds agent-collected counters via classic settings, **InsightsMetrics** is where **VM insights** writes its performance data — a query against the wrong table returns nothing even when collection is healthy.

## Set up alert rules, action groups, and alert processing rules in Azure Monitor

- **What they are:** Three separable objects: an **alert rule** detects a condition, an **action group** defines who gets notified and what runs, and an **alert processing rule** modifies alert behavior at scale after firing.
- **Why they matter:** The exam tests the boundaries — which object holds the email address (action group), which suppresses pages during maintenance (processing rule), and which evaluates the signal (alert rule).

An **alert rule** = **scope** (target resources) + **signal condition** + **severity** + attached action group(s). Signal types:

| Signal type | Evaluates | Behavior |
|---|---|---|
| **Metric alert** | A metric crossing a threshold (static or dynamic) | **Stateful**: fires once, then auto-**resolves** when the condition clears — no re-fire storm |
| **Log search alert** | A KQL query **run on a schedule** (e.g., every 5 minutes over the last 15) | Fires when results meet the threshold; scheduled, not real-time |
| **Activity log alert** | Control-plane events (resource deleted, Service Health incident) | Fires on matching events |

Severity is a five-step scale you must know cold: **Sev0 = Critical, Sev1 = Error, Sev2 = Warning, Sev3 = Informational, Sev4 = Verbose**.

An **action group** is reusable across many alert rules and holds two lists:

- **Notifications:** **email**, **SMS**, **push** (Azure mobile app), **voice** call, and **Email Azure Resource Manager role** (mail everyone holding a role like Owner on the subscription — no hardcoded addresses).
- **Actions:** **Automation runbook**, **Azure Function**, **Event Hub**, **ITSM** connector (create tickets), **Logic App**, **webhook / secure webhook**.

**Alert processing rules** apply *after* alerts fire, across a broad scope (subscription, resource group, tags): the two exam use cases are **suppressing notifications during a planned maintenance window** (alerts still fire and are logged — only the noise stops) and **attaching an action group to many existing alerts at once** without editing each rule.

```bash
# Action group with an email receiver
az monitor action-group create -g rg-mon -n ag-ops \
  --action email oncall ops@contoso.com

# Stateful metric alert: CPU > 80% (Sev2)
az monitor metrics alert create -g rg-mon -n cpu-high \
  --scopes $VM_ID --condition "avg Percentage CPU > 80" \
  --severity 2 --action ag-ops

# Log search alert on a schedule
az monitor scheduled-query create -g rg-mon -n low-disk \
  --scopes $WORKSPACE_ID --condition "count 'LowDisk' > 0" \
  --condition-query LowDisk="Perf | where CounterName == '% Free Space' and CounterValue < 10" \
  --evaluation-frequency 5m --window-size 15m --severity 1 --action-groups $AG_ID
```

```powershell
New-AzActionGroup / New-AzMetricAlertRuleV2 / New-AzScheduledQueryRule   # the Az cmdlet trio
```

> 💡 **Exam Tip:** "Notify **without maintaining an email list** as admins change" = the **Email Azure Resource Manager role** notification. "**Stop pages during the maintenance window** without disabling 50 alert rules" = an **alert processing rule** with a suppression schedule. "Run **remediation automatically**" = an action group **action** (runbook, Function, Logic App).

> ⚠️ **Common Pitfall:** Metric alerts are **stateful** — they don't re-notify every evaluation while the condition persists, and they auto-resolve; **log search alerts run on a schedule**, so they can't be "instant" and each evaluation that matches can fire again. Also: suppression via a processing rule stops **notifications**, not alert **creation** — the alerts still appear in the portal.

## Configure and interpret monitoring of virtual machines, storage accounts, and networks by using Azure Monitor Insights

- **What they are:** **Azure Monitor Insights** are **curated monitoring experiences** — prebuilt, opinionated dashboards per resource type that assemble the right metrics, logs, and visualizations so you don't build them from scratch.
- **Why they matter:** The exam phrase "with **minimal configuration/administrative effort**" is the signal that an Insight — not a hand-built workbook or raw KQL — is the answer.

| Insight | What it shows | Setup notes |
|---|---|---|
| **VM insights** | **Performance** charts (CPU, memory, disk, network across a fleet) + the **Map** feature — a **dependency map** of **processes and TCP connections** per VM | Requires the **Azure Monitor Agent** (and DCR); Map needs the dependency-visualization option enabled; data lands in **InsightsMetrics** |
| **Storage insights** | **Transactions, availability, latency, capacity** across storage accounts | No agent — built on platform metrics/logs |
| **Network insights** | **Topology** view and **health/metrics of network resources** (load balancers, gateways, firewalls, public IPs), connectivity and traffic views | No agent; surfaces Network Watcher data too |

The interpretation skill the exam probes hardest is in **storage insights**: compare **end-to-end latency** (client → Azure → client, the whole round trip) with **server latency** (time Azure Storage itself spent processing). If **server latency is low but end-to-end is high**, the delay is in the **network or the client application** — not the storage service; if **both are high**, the storage service (or its tier/design) is the problem. For **VM insights**, the **Map** answers "what will break if I move this VM?" by showing every process and its inbound/outbound connections — the tool for **discovering application dependencies before a migration**.

```bash
# Network insights topology equivalent
az network watcher show-topology -g rg-app --location eastus
```

> 💡 **Exam Tip:** "Visualize **processes and their connections** / discover dependencies" = **VM insights Map**. "High latency reported by users but **server latency is normal**" = a **client or network** issue — read it straight off **storage insights**. "Single **topology** view of all network resources' health" = **network insights**.

> ⚠️ **Common Pitfall:** VM insights is the *one* Insight with an agent prerequisite — no **AMA + DCR**, no performance or Map data, and the answer to "why is the VM missing from VM insights?" is the agent, not permissions. And remember VM insights writes to **InsightsMetrics**, so KQL follow-up questions must target that table.

## Use Azure Network Watcher and Connection Monitor

- **What it is:** **Network Watcher** is a **per-region** suite of network diagnostic tools, enabled automatically in a region when you create or update a virtual network there.
- **Why it matters:** These are one-line-purpose tools, and the exam hands you a symptom and four of them — precision is everything.

| Tool | Answers the question... | Nature |
|---|---|---|
| **IP flow verify** | "Is this specific packet (5-tuple) **allowed or denied** to/from this VM — and **which NSG rule** decides?" | Point-in-time test |
| **Next hop** | "Where does traffic from this VM **route next** — and via which route table entry?" (catches bad UDRs) | Point-in-time test |
| **Connection troubleshoot** | "Can this VM reach that endpoint **right now**, and where along the path does it fail?" | **Point-in-time** connectivity check |
| **Packet capture** | Record actual traffic on a VM remotely (no RDP/SSH needed) for deep analysis | On-demand capture |
| **VPN troubleshoot** | Diagnose **VPN gateway and connection** health | On-demand diagnostic |
| **NSG diagnostics** | Evaluate all NSGs applied to a flow and show the aggregate allow/deny | Point-in-time test |
| **Flow logs** | Record IP traffic flows for audit/analysis — **VNet flow logs**; the older **NSG flow logs are deprecated** (no new ones since June 2025; full retirement September 2027) | Continuous logging |
| **Connection Monitor** | **Continuous** connectivity, **latency**, and **packet-loss** monitoring between endpoints | **Continuous** monitoring |

**Connection Monitor** deserves its own paragraph because "point-in-time vs. continuous" is the exam's favorite discriminator: it runs **ongoing tests** between **Azure VMs, on-premises hosts, and external endpoints (URLs/IPs)**, measuring reachability, **latency**, and **packet loss** over time. Source machines need the **Network Watcher extension** (Azure VMs) or AMA-based monitoring (Arc/on-prem hosts). Results flow into a **Log Analytics workspace**, so you can query trends with KQL and attach **alert rules** — closing the loop back to the rest of this chapter.

```bash
# Would this packet be allowed? Which NSG rule applies?
az network watcher test-ip-flow --vm vm-web -g rg-app \
  --direction Inbound --protocol TCP \
  --local 10.0.0.4:3389 --remote 203.0.113.10:60000

# Where does traffic go next?
az network watcher show-next-hop --vm vm-web -g rg-app \
  --source-ip 10.0.0.4 --dest-ip 10.1.0.4

# One-time connectivity check
az network watcher test-connectivity -g rg-app \
  --source-resource vm-web --dest-address www.contoso.com --dest-port 443
```

```powershell
Test-AzNetworkWatcherIPFlow / Get-AzNetworkWatcherNextHop / New-AzNetworkWatcherConnectionMonitor
```

> 💡 **Exam Tip:** Symptom → tool: "**blocked by which NSG rule?**" = **IP flow verify**. "Traffic taking the **wrong route** / UDR check" = **next hop**. "Test connectivity **once, now**" = **connection troubleshoot**. "Monitor latency and packet loss **continuously** to an on-prem app or external URL" = **Connection Monitor**. "Inspect the **actual packets** without logging into the VM" = **packet capture**.

> ⚠️ **Common Pitfall:** Two retirements the exam expects you to know: **NSG flow logs are deprecated (no new ones since June 2025; retirement September 2027) — VNet flow logs are the answer** for flow logging, just as **Basic public IPs and Basic load balancers are retired in favor of Standard SKUs**. And Network Watcher is **regional** — diagnosing a VNet requires Network Watcher enabled in *that VNet's region*.

## How It Fits Together (mental model)

Picture Contoso's admin on day one: she opens **Metrics Explorer** and immediately sees **platform metrics** — CPU with **Average** and **Max aggregations**, **split** by instance **dimension** — because **metrics** collect automatically and live **93 days**, and she **pins the charts to a dashboard**. But the "who deleted the test VM?" question sends her to the **Activity Log** (subscription **control-plane** events, **90 days free**), and Key Vault access questions expose the gap: **resource logs** collect nothing until she creates a **diagnostic setting** routing chosen categories to a **Log Analytics workspace** (for **KQL**), a **storage account** (archive), and **Event Hubs** (the SIEM feed), then raises workspace **interactive retention** from the **30-day default toward 730 days** with **archive to 12 years** for compliance. Guest-OS memory counters need the **Azure Monitor Agent** — the legacy **Log Analytics agent retired in August 2024** — associated with a **Data Collection Rule**, after which she queries **Heartbeat**, **Perf**, and **AzureActivity** with `where TimeGenerated > ago(1h)` and `summarize count() by Computer`. She wires an **alert rule** — scope, **signal**, **Sev1** — whose **stateful metric alert** auto-resolves, plus a scheduled **log search alert**, both invoking an **action group** that emails the **Azure Resource Manager role** holders and triggers an **Automation runbook**; a weekend maintenance window is silenced fleet-wide by an **alert processing rule**. For curated views she enables **VM insights** (performance plus the dependency **Map**), reads **storage insights** — **end-to-end vs. server latency** proving a slowdown is client-side — and checks topology in **network insights**. When an app can't reach its database, **Network Watcher**'s **IP flow verify** names the blocking NSG rule, **next hop** validates routing, and **Connection Monitor** begins **continuous latency and packet-loss** tests from Azure VMs and on-prem hosts to the endpoint, streaming results into the same workspace where the story began.
