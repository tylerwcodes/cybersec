# Objective 3.1 — Automate deployment of resources by using ARM templates or Bicep files

Infrastructure-as-code questions on AZ-104 are less about writing templates from scratch and more about *reading* them: the exam shows you a JSON or Bicep snippet and asks what it deploys, what a highlighted expression evaluates to, or what one-line change achieves a goal ("make the location follow the resource group," "make deployment remove resources not in the template"). Memorize the ARM template section names and which one is required, the anatomy of a resource declaration, the handful of template functions the exam reuses constantly (`parameters()`, `variables()`, `resourceGroup().location`, `uniqueString()`, `concat()`), the Bicep keywords (`param`, `var`, `resource`, `module`, `output`), the deployment commands at each scope, the **Incremental vs. Complete** mode distinction, and the export/decompile/build tooling. Almost every question in this objective resolves to one of those facts.

## Interpret an Azure Resource Manager (ARM) template or a Bicep file

- **What it is:** An **ARM template** is a **JSON** file that describes Azure resources **declaratively** — you state the *end state* you want, and **Azure Resource Manager** figures out how to get there. A **Bicep** file is a cleaner **domain-specific language (DSL)** for the same job: it **transpiles to ARM JSON** before deployment, so anything a template can do, Bicep can do with less syntax.
- **Why it matters:** Both are **idempotent** — you can deploy the same file repeatedly and get the same result, with no duplicates and no errors for resources that already exist. That is what makes them safe for automation and CI/CD pipelines, and it is a favorite true/false fact on the exam.

An ARM template has a fixed set of top-level **sections**:

| Section | Required? | Purpose |
|---|---|---|
| **$schema** | **Yes** | URL of the JSON schema that defines the template language version |
| **contentVersion** | **Yes** | Your own version string for the template (e.g., `1.0.0.0`) — Azure doesn't act on the value |
| **parameters** | No | Values supplied **at deployment time** (environment name, SKU, admin credentials) |
| **variables** | No | Values **computed inside the template** to avoid repeating expressions |
| **functions** | No | **User-defined** functions for complex reusable expressions (rarely used) |
| **resources** | **Yes** | The resources to deploy or update |
| **outputs** | No | Values returned after deployment (connection strings, resource IDs, hostnames) |

`$schema`, `contentVersion`, and `resources` are the three mandatory top-level elements. When the exam asks which *section* is required, it means the sections that hold your content — `parameters`, `variables`, `functions`, `resources`, `outputs` — and of those, **`resources` is the only required one**.

Every entry in `resources` shares the same anatomy — recognize these four-plus-one fields on sight:

```json
{
  "type": "Microsoft.Storage/storageAccounts",
  "apiVersion": "2023-05-01",
  "name": "[concat(parameters('prefix'), uniqueString(resourceGroup().id))]",
  "location": "[resourceGroup().location]",
  "properties": { "allowBlobPublicAccess": false },
  "sku": { "name": "Standard_LRS" },
  "kind": "StorageV2"
}
```

- **type** follows the pattern `Microsoft.Provider/resourceType` (e.g., `Microsoft.Compute/virtualMachines`, `Microsoft.Network/virtualNetworks`).
- **apiVersion** pins which version of that provider's REST API the properties are validated against.
- **name** and **location** identify and place the resource; **properties** holds the type-specific configuration.
- Anything inside `"[...]"` is a **template expression**, evaluated at deployment time using **template functions**: `parameters('x')` and `variables('y')` read the corresponding sections, `resourceGroup().location` returns the deployment resource group's region, `uniqueString(resourceGroup().id)` generates a deterministic 13-character hash (the standard trick for globally unique storage account names), and `concat()` glues strings together.

The same resource in **Bicep** shows why the DSL exists:

```bicep
@description('Prefix for the storage account name')
param prefix string

param location string = resourceGroup().location

var storageName = '${prefix}${uniqueString(resourceGroup().id)}'

resource stg 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: storageName
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
  properties: { allowBlobPublicAccess: false }
}

output storageId string = stg.id
```

| Concept | ARM JSON | Bicep |
|---|---|---|
| Parameter | `parameters` section + `[parameters('x')]` | **`param`** keyword, referenced by name |
| Variable | `variables` section + `[variables('y')]` | **`var`** keyword |
| Resource | Object in `resources` array with `type` + `apiVersion` | **`resource` symbolicName `'type@apiVersion'`** |
| Reuse another template | Nested/linked templates (URIs, awkward) | **`module`** keyword pointing at another `.bicep` file |
| Return values | `outputs` section | **`output`** keyword |
| String building | `[concat(...)]` | String **interpolation**: `'${prefix}${suffix}'` |
| Dependencies | Usually needs explicit **`dependsOn`** | **Implicit** through symbolic references |

The dependency difference is the exam's favorite contrast: in Bicep, referencing another resource's **symbolic name** (e.g., a VM's NIC property set to `nic.id`) makes Resource Manager deploy them in the right order automatically — you **rarely need `dependsOn`**. In ARM JSON there are no symbolic names, so ordering **often requires an explicit `dependsOn` array** (or a `reference()`-by-name expression Resource Manager can detect — `resourceId()` alone creates no dependency).

> 💡 **Exam Tip:** If asked which template section is required, the answer is **resources** — the other sections (parameters, variables, functions, outputs) are optional, though a valid template also keeps its `$schema` and `contentVersion` elements. If asked what `[uniqueString(resourceGroup().id)]` is for, it's a **deterministic, globally unique-enough name** (classic for storage accounts). "Declarative" and "idempotent" are the two adjectives the exam wants attached to both formats.

> ⚠️ **Common Pitfall:** The `functions` section is for **user-defined** functions, not built-ins like `concat()` — built-in template functions need no declaration. And Bicep is not a different deployment engine: it **compiles to the same ARM JSON** and hits the same Resource Manager API, so there is nothing Bicep can deploy that a template cannot.

## Modify an existing ARM template

The exam hands you a working template and asks you to change it — the skills are surgical, not creative:

- **Add a parameter:** insert an object into `parameters` with a **`type`** (string, int, bool, object, array, secureString, secureObject), and optionally **`defaultValue`**, **`allowedValues`**, and constraints like `minLength`/`maxLength`. A parameter without a default **must** be supplied at deployment time.

```json
"parameters": {
  "storageSku": {
    "type": "string",
    "defaultValue": "Standard_LRS",
    "allowedValues": [ "Standard_LRS", "Standard_GRS", "Standard_ZRS" ]
  }
}
```

- **Consume it:** replace the hard-coded value with `"[parameters('storageSku')]"` — and remember every expression must sit inside the square brackets, or Resource Manager treats it as a literal string.
- **Promote repetition to a variable:** move a repeated expression into `variables` and reference it with `[variables('name')]` everywhere it was duplicated.
- **Parameterize location correctly:** the house pattern is a `location` parameter whose `defaultValue` is `"[resourceGroup().location]"` — hard-coding a region is the "what's wrong with this template" answer.
- **Add a resource:** append an object to the `resources` array with `type`, `apiVersion`, `name`, `location`, `properties` — and if it must wait for another resource in the same template (a VM waiting for its NIC, an extension waiting for its VM), add an explicit **`dependsOn`** array, typically built with `resourceId()`:

```json
"dependsOn": [
  "[resourceId('Microsoft.Network/networkInterfaces', variables('nicName'))]"
]
```

- **Add an output:** entries in `outputs` have a `type` and a `value` expression — the standard way to surface a resource ID or hostname to a pipeline or a parent template.
- **Secure the secrets:** admin passwords use type **`secureString`** (never plain `string`, never a `defaultValue`), ideally supplied from **Azure Key Vault** via a reference in the parameter file.

> 💡 **Exam Tip:** "Restrict a parameter to specific values" = **`allowedValues`**. "Make the parameter optional" = **`defaultValue`**. "Resource B must be created after resource A" in JSON = **`dependsOn`** with `resourceId()`. Expressions live inside `"[ ]"` — an answer choice missing the brackets is wrong.

> ⚠️ **Common Pitfall:** `dependsOn` accepts resources **in the same template only** — you cannot depend on a resource that already exists outside the deployment (it doesn't need to be waited on anyway). And adding `dependsOn` where none is needed doesn't break the deployment, but the exam's "most efficient" phrasing wants dependencies only where real ordering exists.

## Modify an existing Bicep file

The same tasks in Bicep use keywords and decorators instead of JSON sections:

- **Add a parameter:** `param storageSku string = 'Standard_LRS'` — the `= value` is the default. Constraints are **decorators** placed above the declaration: **`@allowed([...])`**, **`@minLength()`** / **`@maxLength()`**, **`@description('...')`**, and **`@secure()`** for passwords and secrets (the Bicep equivalent of `secureString`).

```bicep
@allowed([ 'Standard_LRS', 'Standard_GRS', 'Standard_ZRS' ])
param storageSku string = 'Standard_LRS'

@secure()
param adminPassword string
```

- **Build strings with interpolation, not concat:** `var vmName = '${prefix}-vm-${env}'` — the linter actively flags `concat()` in Bicep; interpolation is the idiomatic answer.
- **Let references create the order:** to make a subnet's ID flow into a NIC, just write `subnet.id` (the **symbolic name**) — the implicit dependency replaces `dependsOn`. If the exam shows a Bicep file with a `dependsOn` block that merely restates a symbolic reference, "remove the redundant dependsOn" is the improvement.
- **Reference existing resources:** the **`existing`** keyword points a symbolic name at a resource **already deployed** (e.g., a shared Key Vault or VNet) so you can read its properties without redeploying it:

```bicep
resource kv 'Microsoft.KeyVault/vaults@2023-07-01' existing = {
  name: 'corp-shared-kv'
}
```

- **Compose with modules:** a **`module`** declaration deploys another Bicep file as a nested deployment, passing values through `params` and reading its `output` values — the clean replacement for ARM's linked templates:

```bicep
module network 'modules/network.bicep' = {
  name: 'networkDeploy'
  params: {
    location: location
    addressSpace: '10.0.0.0/16'
  }
}
```

- **Repeat with loops:** `[for i in range(0, 3): { ... }]` stamps out multiple copies of a resource — Bicep's version of ARM JSON's `copy` element.

> 💡 **Exam Tip:** Decorator questions are lookup questions: "restrict values" = **`@allowed`**, "hide the password in logs" = **`@secure()`**, "reuse a common Bicep file across deployments" = **`module`**, "read a resource deployed last year" = **`existing`**. And in Bicep, ordering comes free from **symbolic references** — reach for `dependsOn` only when no property reference connects the two resources.

> ⚠️ **Common Pitfall:** `@secure()` parameters cannot have meaningful defaults and their values are excluded from deployment history/logs — supplying a password as a plain `param string` with a default is the "what is wrong here" answer. Also, a module's `name` is the **nested deployment's name** in the Deployments blade, not a resource name — two modules with the same `name` in one deployment collide.

## Deploy resources by using an ARM template or a Bicep file

Deployment is where AZ-104 gets hands-on. The commands differ by **scope** — most deployments target a resource group, but templates can also create resource groups, policies, and role assignments at higher scopes:

| Scope | Azure CLI | Azure PowerShell |
|---|---|---|
| **Resource group** | `az deployment group create` | `New-AzResourceGroupDeployment` |
| **Subscription** | `az deployment sub create` | `New-AzSubscriptionDeployment` |
| **Management group** | `az deployment mg create` | `New-AzManagementGroupDeployment` |
| **Tenant** | `az deployment tenant create` | `New-AzTenantDeployment` |

The bread-and-butter commands (both accept `.json` **or** `.bicep` directly — the Bicep transpile happens automatically):

```bash
az deployment group create \
  --resource-group RG1 \
  --template-file main.bicep \
  --parameters main.bicepparam

# inline parameter override
az deployment group create -g RG1 --template-file azuredeploy.json \
  --parameters azuredeploy.parameters.json --parameters storageSku=Standard_GRS
```

```powershell
New-AzResourceGroupDeployment -ResourceGroupName RG1 `
  -TemplateFile ./azuredeploy.json `
  -TemplateParameterFile ./azuredeploy.parameters.json
```

- **Parameter files** keep per-environment values out of the template: the JSON convention is **`azuredeploy.parameters.json`**; the Bicep-native format is a **`.bicepparam`** file, which starts with `using 'main.bicep'` and assigns `param name = value` pairs with full IntelliSense.
- **Deployment modes** decide the fate of resources that exist in the resource group but **not** in the template:

| Mode | Resources in template | Resources NOT in template | Notes |
|---|---|---|---|
| **Incremental** (default) | Created/updated to match | **Left unchanged** | Safe default for shared resource groups |
| **Complete** | Created/updated to match | **DELETED** | **Resource-group scope only**; enforces the template as the whole truth — use with extreme care |

  Select it with `--mode Complete` / `-Mode Complete`. Complete mode is the exam's "make the resource group contain *only* what the template defines" answer — and its "why did my VM disappear" trap.
- **What-if** previews the diff — Create/Modify/Delete/NoChange per resource — **without deploying anything**: add **`--what-if`** (CLI) or **`-WhatIf`** (PowerShell). `--confirm-with-what-if` / `-Confirm` shows the preview and then asks before proceeding.
- **Template specs** solve template *sharing*: `az ts create --name vmSpec --version 1.0 --template-file main.bicep ...` (or `New-AzTemplateSpec`) stores the template as a **versioned Azure resource**, shared via **RBAC** instead of a storage account SAS URL, and deployable by ID with `--template-spec`.
- Every deployment lands in the resource group's **Deployments blade** with its **inputs, outputs, template, and status** — named after the template file unless you pass `--name`, and this history is what you troubleshoot and re-download from later.

> 💡 **Exam Tip:** Match the noun to the scope command: "create a resource group *from* a template" cannot be a group-scope deployment — that's **`az deployment sub create`** (which needs `--location` for the deployment metadata, since there's no resource group to inherit from). "Preview the changes first" = **`--what-if` / `-WhatIf`**. "Existing resources must not be affected" = **Incremental** (and it's already the default).

> ⚠️ **Common Pitfall:** **Complete mode deletes.** Running a partial template in Complete mode against a shared resource group removes every resource the template doesn't mention — and Complete mode is only valid for **resource-group** deployments. Also note the CLI deploys `.bicep` because Azure CLI installs and updates the Bicep tooling itself, while Azure PowerShell expects the **Bicep CLI** to be installed separately on the machine.

## Export a deployment as an ARM template or convert an ARM template to a Bicep file

Two different questions hide under "export" — *what Azure looks like now* versus *what you actually deployed*:

| Method | What you get | Caveat |
|---|---|---|
| Resource group → **Export template** (portal), `az group export`, `Export-AzResourceGroup` | Generated template of the **current state** of the resources (including portal-made drift) | Best-effort: **may not capture every resource type or setting perfectly** — the portal lists types it couldn't export; expect cleanup |
| **Deployment history** → select deployment → Template (or `az deployment group export --name <deployment>`) | The **exact template** submitted for that deployment, with its parameters | Only reflects that deployment — not changes made since |

```bash
az group export --name RG1 > exported.json          # current state of the RG
az deployment group export -g RG1 -n storageDeploy  # the template a past deployment used
```

Conversion between the two languages is built into the Bicep tooling:

| Direction | Command | Notes |
|---|---|---|
| ARM JSON → Bicep | **`az bicep decompile --file azuredeploy.json`** | Best-effort translation; review and fix warnings, tidy generated names |
| Bicep → ARM JSON | **`az bicep build --file main.bicep`** | Deterministic transpile — the same JSON the deployment commands generate on the fly |

The standard modernization workflow chains them: **export** the resource group (or grab the historical template), **decompile** the JSON into Bicep, refactor the messy generated code into `param`/`var`/`module` structure, run **what-if** to confirm the refactor is a no-op, then publish the polished file as a **template spec** for the rest of the organization.

> 💡 **Exam Tip:** "Capture everything currently in the resource group, including manual portal changes" = **Export template** from the resource group. "Retrieve the template used for a *specific past deployment*" = the **Deployment history**. "Convert JSON to Bicep" = **`az bicep decompile`**; "produce the JSON from a Bicep file" = **`az bicep build`**.

> ⚠️ **Common Pitfall:** An exported resource-group template is a **snapshot, not gospel** — some resource types export incompletely, secrets are omitted, and values arrive hard-coded rather than parameterized. Treat it as a starting point. And don't reverse the verbs: **decompile** goes JSON→Bicep, **build** goes Bicep→JSON.

## How It Fits Together (mental model)

Picture Contoso's Azure admin retiring click-ops. She starts from a resource group built by hand: **Export template** captures its **current state** (with the portal's warning that the export is imperfect), and **`az bicep decompile`** turns that **ARM JSON** into a **Bicep** file she can actually read. She refactors it — hard-coded strings become **`param`** declarations with **`@allowed`** and **`@secure()`** decorators, repeated expressions become **`var`** lines with string **interpolation** instead of **`concat()`**, the storage account name gets its **`uniqueString(resourceGroup().id)`** suffix, `location` defaults to **`resourceGroup().location`**, the networking resources move into a reusable **`module`**, and the redundant **`dependsOn`** entries disappear because Bicep's **symbolic references** create **implicit dependencies**. The old JSON version kept only its required **resources** section honest — every resource carrying its **type**, **apiVersion**, **name**, **location**, and **properties** — with environment values flowing through **parameters** and **outputs** returning the resource IDs. Per environment she writes a **`.bicepparam`** file, then previews with **`--what-if`**: the diff shows no deletes, so she runs **`az deployment group create --resource-group RG --template-file main.bicep`** (her teammate prefers **`New-AzResourceGroupDeployment`**) in the default **Incremental** mode, keeping unrelated resources safe — reserving **Complete** mode for the locked-down resource group where the template must be the whole truth. Because the templates are **declarative** and **idempotent**, the pipeline redeploys them nightly without side effects; new resource groups themselves come from an **`az deployment sub create`** at **subscription scope**. She publishes the final file as a versioned **template spec** shared by RBAC, and when an auditor asks what changed last quarter, the resource group's **Deployments blade** shows every deployment with its inputs, outputs, and the exact template — one **`az bicep build`** away from its JSON form.

## Scenario Keyword Cheat Sheet

| The question says... | The answer is... |
|---|---|
| "The only required section of an ARM template" | `resources` |
| "Deploy the same template repeatedly with the same end result" | Declarative + idempotent (safe to redeploy) |
| "Simpler language that transpiles to ARM JSON" | Bicep |
| "Reference a value supplied at deployment time in JSON" | `[parameters('name')]` |
| "Globally unique storage account name derived from the resource group" | `uniqueString(resourceGroup().id)` |
| "Resource location should default to the resource group's region" | `resourceGroup().location` |
| "In JSON, resource B must be created after resource A" | Explicit `dependsOn` with `resourceId()` |
| "In Bicep, control deployment order" | Implicit dependency via symbolic references (rarely `dependsOn`) |
| "Restrict a parameter to specific values" | `allowedValues` (JSON) / `@allowed` (Bicep) |
| "Password parameter that must not appear in logs" | `secureString` / `@secure()` |
| "Reuse one Bicep file inside another" | `module` |
| "Deploy a template that creates resource groups" | `az deployment sub create` / `New-AzSubscriptionDeployment` |
| "Deploy a Bicep file to an existing resource group" | `az deployment group create --template-file main.bicep` / `New-AzResourceGroupDeployment` |
| "Resources not defined in the template must be deleted" | Complete mode (`--mode Complete`, resource-group scope only) |
| "Existing resources not in the template must be left alone" | Incremental mode (the default) |
| "Preview exactly what will change before deploying" | `--what-if` / `-WhatIf` |
| "Bicep-native parameter file" | `.bicepparam` (starts with `using 'main.bicep'`) |
| "Capture the current state of a resource group as a template" | Export template (`az group export`) — may be imperfect |
| "Get the exact template a past deployment used" | Deployment history in the Deployments blade |
| "Convert an ARM template to Bicep / Bicep to JSON" | `az bicep decompile` / `az bicep build` |
| "Store versioned templates as a shareable Azure resource with RBAC" | Template specs |
