# Objective 3.4 — Create and configure Azure App Service

App Service questions on AZ-104 are tier-gating questions in disguise: almost every scenario hinges on knowing *which pricing tier unlocks which feature* — deployment slots, autoscale, custom backups, Traffic Manager, slot counts — and on the direction of each networking feature (private endpoint = inbound, VNet integration = outbound). Memorize the tier feature matrix cold (Free → Shared → Basic → Standard → Premium → Isolated), the instance and slot limits (3/10/30/100 instances; 5/20 slots), the DNS records for custom domains (CNAME + TXT `asuid` for subdomains, A + TXT for the apex), and the backup prerequisites (Standard+, storage account in the same subscription). Expect drag-and-drop ordering (verify domain → add binding), "minimum tier that supports X" stems, and CLI/PowerShell fill-in-the-blank for slot swaps.

## Provision an App Service plan

- **What it is:** An **App Service plan** is the *compute* underneath your web apps — it defines the **region**, the **operating system** (Windows or Linux), and the **pricing tier (SKU)**, which together determine the VM size, instance limits, and features available.
- **Why it matters:** Every App Service app **must run in a plan**, and **multiple apps can share one plan** — they run on the same VM instances and **scale together**. Consolidating apps onto a plan saves money; separating them isolates performance. The plan, not the app, is where you scale.

| Tier | Compute | Max instances | Key features / limits |
|---|---|---|---|
| **Free (F1)** | **Shared** infrastructure | 1 (shared) | **60 CPU minutes/day**, **no custom domain**, **no SLA** — dev/test only |
| **Shared (D1)** | Shared infrastructure | 1 (shared) | Adds **custom domains**; still metered CPU, no SLA (Windows only) |
| **Basic (B1–B3)** | **Dedicated** VMs | **3** (manual scale) | Custom domains + SNI SSL, **no deployment slots**, **no autoscale** |
| **Standard (S1–S3)** | Dedicated VMs | **10** (autoscale) | **Autoscale**, **5 deployment slots**, **scheduled backups**, **Traffic Manager** support |
| **Premium (P1v2–P3v3)** | Dedicated, faster hardware | **30** | **20 deployment slots**, VNet integration, private endpoints, **zone redundancy (v3)** |
| **Isolated / Isolated v2 (I1–I3v2)** | **App Service Environment** — single-tenant, injected into your VNet | **100** | Maximum scale and network isolation; highest cost |

- Windows and Linux apps cannot share the same plan — the plan's OS is fixed at creation.
- Scaling the plan scales **every app in it**; a runaway app starves its plan-mates. Move a noisy app to its own plan (`az webapp update --plan`), which must be in the **same region and resource group** as the original.

```bash
# CLI — create a Linux Standard plan
az appservice plan create --name plan-web-prod --resource-group rg-web \
  --location eastus --sku S1 --is-linux
```

```powershell
# PowerShell — create a Windows Standard plan
New-AzAppServicePlan -Name plan-web-prod -ResourceGroupName rg-web `
  -Location eastus -Tier Standard -NumberofWorkers 2 -WorkerSize Small
```

> 💡 **Exam Tip:** Learn the tier ladder as *feature unlock points*: custom domain = **Shared**, dedicated compute + SNI SSL = **Basic**, autoscale + slots + backups + Traffic Manager = **Standard**, 20 slots + 30 instances + zone redundancy = **Premium v3**, single-tenant isolation = **Isolated (ASE)**. "Minimum tier that supports deployment slots" = **Standard**, every time.

> ⚠️ **Common Pitfall:** Free and Shared tiers run on **shared multi-tenant infrastructure with daily CPU quotas and no SLA** — Free doesn't even allow a custom domain. And remember apps in one plan **scale together**: scaling out for one busy app also multiplies every other app in that plan.

## Configure scaling settings in an App Service plan

- **What it is:** **Scale up** changes the plan's **tier/SKU** (bigger VMs, more features); **scale out** changes the **instance count** (more VMs running copies of your apps). **Autoscale** (Standard and above) adjusts the instance count automatically via **Azure Monitor autoscale** rules.
- **Why it matters:** Scale up is how you *unlock features* (slots, backups, VNet integration); scale out is how you *handle load*. The exam tests both the vocabulary and the autoscale rule anatomy.

Autoscale rule anatomy:

- **Metric rules** — react to **CPU percentage**, **memory percentage**, or **HTTP queue length** (e.g., "add 1 instance when CPU > 70% for 10 minutes; remove 1 when CPU < 30%"). Always pair a scale-out rule with a scale-in rule.
- **Schedule rules** — set instance counts for **recurring windows** (business hours) or **fixed dates** (product launch).
- **Instance limits** — every autoscale setting has a **minimum**, **maximum**, and **default** count. The maximum is capped by the tier (10 Standard, 30 Premium). The default applies when metrics can't be read.
- **Cooldown** — after a scale action, autoscale waits (default **5 minutes**) before acting again, preventing flapping.

```bash
# Scale up (change tier) and manual scale out
az appservice plan update --name plan-web-prod --resource-group rg-web --sku P1v3
az appservice plan update --name plan-web-prod --resource-group rg-web --number-of-workers 4

# Autoscale: 2–10 instances, add one when CPU > 70%
az monitor autoscale create --resource-group rg-web --name web-autoscale \
  --resource plan-web-prod --resource-type Microsoft.Web/serverfarms \
  --min-count 2 --max-count 10 --count 2
az monitor autoscale rule create --resource-group rg-web --autoscale-name web-autoscale \
  --condition "CpuPercentage > 70 avg 10m" --scale out 1
```

> 💡 **Exam Tip:** "Add instances automatically when CPU exceeds…" = **scale out with autoscale**, and that requires **Standard or higher** — a Basic plan can only scale *manually* to 3 instances. "Need deployment slots / more memory per instance / VNet integration" = **scale up** to a higher tier.

> ⚠️ **Common Pitfall:** Autoscale is configured **on the App Service plan**, not on the individual app — and a scale-out rule without a matching scale-in rule means instances are added but never removed, burning money. Also don't confuse Azure Monitor autoscale with Premium's newer per-app "automatic scaling"; when the exam says rules, metrics, and schedules, it means Azure Monitor autoscale.

## Create an App Service

- **What it is:** The **App Service** (web app) is the application itself — code or container — deployed into a plan. At creation you pick the **globally unique name** (it becomes the default hostname **`<name>.azurewebsites.net`**), the **runtime stack** (.NET, Java, Node.js, Python, PHP) or a **container image**, the **OS**, the **region**, and the **plan**.
- **Why it matters:** The app inherits region and OS from its plan; publish type (code vs. container) and runtime are app-level choices. Deployment sources include GitHub Actions, Azure DevOps, local Git, ZIP deploy, and container registries.

```bash
# CLI — create a web app on an existing plan
az webapp create --name contoso-web-2026 --resource-group rg-web \
  --plan plan-web-prod --runtime "NODE:20-lts"
```

```powershell
# PowerShell
New-AzWebApp -Name contoso-web-2026 -ResourceGroupName rg-web `
  -Location eastus -AppServicePlan plan-web-prod
```

- **App settings** and **connection strings** configured in App Service are injected as environment variables at runtime and **override** values in configuration files — a favorite trick for per-environment config.
- Enable **Always On** (Basic+) to keep the app loaded when idle; without it, apps unload after inactivity and cold-start on the next request.

> 💡 **Exam Tip:** The app name must be **globally unique across Azure** because it forms the public URL `<name>.azurewebsites.net` — same logic as storage account names. Region and OS come from the **plan**, so "create an app in region X" really means "create or pick a plan in region X."

> ⚠️ **Common Pitfall:** You cannot deploy a Linux app to a Windows plan (or vice versa) — the plan's OS is fixed. If a scenario needs both OS types, the answer is **two plans**.

## Configure certificates and Transport Layer Security (TLS) for an App Service

- **What it is:** TLS bindings attach a certificate to a custom hostname so the app serves HTTPS. Azure offers three certificate sources plus platform TLS settings (**HTTPS Only**, **minimum TLS version**).
- **Why it matters:** The exam tests which certificate option fits which constraint (free vs. wildcard vs. exportable) and which binding type costs extra.

| Option | Cost | Key facts |
|---|---|---|
| **App Service managed certificate** | **Free** | Requires the **custom domain already mapped and validated**; **auto-renews**; supports apex (root) domains but **no wildcards**; **cannot be exported** (locked to App Service) |
| **App Service certificate** | Purchased | Bought **through Azure**, issued by a partner CA; **stored in Azure Key Vault**; supports wildcard; renewable/exportable; importable into multiple apps |
| **Bring your own certificate** | Your CA's price | Upload a **PFX** (with private key + password) or import from **Key Vault**; you manage renewal |

Binding types:

- **SNI SSL** — free, unlimited bindings, supported on **Basic and above**; works with all modern browsers.
- **IP-based SSL** — requires **Standard or above**, assigns the app a **dedicated inbound IP address**, and incurs an extra charge; only needed for ancient clients without SNI support (or when you want an app-assigned address).

Platform TLS settings (Configuration → General settings):

- **HTTPS Only** — redirects all HTTP requests to HTTPS.
- **Minimum TLS version** — enforce **1.2** (or 1.3); TLS 1.0/1.1 are deprecated and only exist for legacy compatibility.

```bash
az webapp config ssl create --resource-group rg-web --name contoso-web-2026 \
  --hostname www.contoso.com          # free managed certificate
az webapp config ssl bind --resource-group rg-web --name contoso-web-2026 \
  --certificate-thumbprint <THUMBPRINT> --ssl-type SNI
az webapp update --resource-group rg-web --name contoso-web-2026 --https-only true
```

> 💡 **Exam Tip:** "Free certificate, auto-renews, no admin overhead" = **App Service managed certificate** — but only *after* the custom domain is mapped, and never for a **wildcard** (`*.contoso.com`) or for export to another service. "Certificate purchased in Azure and stored centrally" = **App Service certificate + Key Vault**.

> ⚠️ **Common Pitfall:** SNI SSL vs. IP-based SSL. SNI is **free from Basic tier up**; IP-based SSL needs **Standard+**, adds cost, and gives the app a **dedicated IP** — choose it only when the scenario demands a static app-assigned address or supports pre-SNI clients. Don't reflexively pick IP SSL because it "sounds more dedicated."

## Map an existing custom DNS domain name to an App Service

- **What it is:** Replacing `<name>.azurewebsites.net` with your own domain (e.g., `www.contoso.com`) by creating DNS records at your registrar, **verifying ownership**, then adding the hostname to the app.
- **Why it matters:** The exam tests the exact record types — and that custom domains require **Shared (D1) tier or higher** (Free F1 is excluded).

| Domain type | Record 1 (routing) | Record 2 (verification) |
|---|---|---|
| **Subdomain** (`www.contoso.com`) | **CNAME** `www` → `contoso-web-2026.azurewebsites.net` | **TXT** `asuid.www` → app's **custom domain verification ID** |
| **Apex/root** (`contoso.com`) | **A** record → the app's **inbound IP address** | **TXT** `asuid` → verification ID |

Workflow (order matters): create the DNS records → App Service **validates** them → **add the hostname** to the app → then bind a certificate (previous section).

```bash
# Get the verification ID and inbound IP, then map the domain
az webapp show --name contoso-web-2026 --resource-group rg-web \
  --query customDomainVerificationId
az webapp config hostname add --webapp-name contoso-web-2026 \
  --resource-group rg-web --hostname www.contoso.com
```

- An apex domain **cannot use a CNAME** (DNS standard forbids CNAME at the zone root) — hence the A record. Azure DNS users can alternatively use an **alias record** at the apex.
- The **TXT `asuid` record** proves domain ownership and prevents subdomain takeover; validation fails without it.

> 💡 **Exam Tip:** Drag-and-drop favorite: **CNAME for `www`, A record for the apex, TXT `asuid.*` for verification in both cases — verify first, then add the hostname.** If the stem mentions the root/naked domain, the answer involves an **A record**, never a CNAME.

> ⚠️ **Common Pitfall:** Mapping the domain does **not** make it HTTPS — the certificate binding is a separate step *after* the hostname is added (and the free managed certificate can't even be created until the mapping exists). Also, a Free (F1) plan can't map a custom domain at all; the minimum is **Shared**, with **Basic** needed for SSL bindings.

## Configure backup for an App Service

- **What it is:** The **Backup and Restore** feature snapshots app content, configuration, and optionally **linked databases** to a **storage account container**.
- **Why it matters:** The prerequisites are pure exam bait: custom backups require the **Standard tier or higher** and a **storage account and container in the same subscription** as the app.

Key facts:

- **Custom backups** can run **manually (on demand)** or on a **schedule** (e.g., daily on Standard) with configurable retention, and can include **linked databases** — SQL Database, MySQL, PostgreSQL — referenced by the app's connection strings.
- **Automatic backups** also exist (Basic+): hourly platform snapshots retained 30 days, no configuration and no storage account needed — but no database inclusion and no schedule control. When the exam says "configure backup," it means **custom backups**.
- **Restore** targets: overwrite the existing app, restore to a **new app**, or restore to a **deployment slot** (a safe way to inspect a backup without touching production).
- Backups are full (not incremental) and the app must be **running** for scheduled backups to fire.

```bash
az webapp config backup create --resource-group rg-web --webapp-name contoso-web-2026 \
  --backup-name daily --container-url "<SAS-URL-to-container>"
az webapp config backup update --resource-group rg-web --webapp-name contoso-web-2026 \
  --frequency 1d --retain-one true --retention 30 --container-url "<SAS-URL>"
```

```powershell
New-AzWebAppBackup -ResourceGroupName rg-web -Name contoso-web-2026 `
  -StorageAccountUrl "<SAS-URL>" -BackupName daily
```

> 💡 **Exam Tip:** Two prerequisites, always: **Standard tier or higher** *and* **a storage account + container in the same subscription**. A Basic-tier app that "needs scheduled backups including its database" must first **scale up to Standard**.

> ⚠️ **Common Pitfall:** The storage account is accessed via a **SAS URL to a container** — a scenario pointing at a storage account in a *different subscription* fails. And linked databases are only included if they're defined as **connection strings** in the app's configuration.

## Configure networking settings for an App Service

- **What it is:** App Service is multi-tenant with a public endpoint by default; networking features bolt on **inbound** control and **outbound** reach. The single most-tested fact in this objective is the **direction** of each feature.
- **Why it matters:** Picking the inbound tool for an outbound problem (or vice versa) is the classic wrong answer.

| Direction | Feature | What it does |
|---|---|---|
| **Inbound** | **Access restrictions** | Ordered (priority-numbered) **allow/deny rules** by IP/CIDR, **service tag**, or VNet subnet (service endpoints); adding the first allow rule creates an implicit deny-all below it |
| **Inbound** | **Private endpoint** | Gives the app a **private IP in your VNet** via Private Link, so clients reach it privately; pair with disabling public access |
| **Inbound** | **App-assigned address** | A dedicated inbound IP, obtained via an **IP-based SSL** binding |
| **Outbound** | **Regional VNet integration** | Lets the app **make outbound calls into a VNet** (to VMs, databases, private endpoints of other services) through a **delegated subnet** — provides **no inbound access** to the app |
| **Outbound** | **Hybrid Connections** | **TCP relay** (Azure Relay) from the app to a specific **on-premises host:port**, via the Hybrid Connection Manager agent — no VPN/ExpressRoute required |

- Regional VNet integration requires a **dedicated, delegated subnet** (`Microsoft.Web/serverFarms`) in a VNet in the same region, and a **Basic or higher** plan.
- The fully isolated pattern — **App Service Environment (Isolated v2)** — deploys the entire service *inside* your VNet, covering both directions natively.

```bash
az webapp vnet-integration add --name contoso-web-2026 --resource-group rg-web \
  --vnet vnet-prod --subnet snet-appsvc            # outbound into the VNet
az webapp config access-restriction add --name contoso-web-2026 --resource-group rg-web \
  --rule-name AllowFrontDoor --priority 100 --service-tag AzureFrontDoor.Backend --action Allow
```

> 💡 **Exam Tip:** Say it as a mantra: **private endpoint = traffic coming IN privately; VNet integration = traffic going OUT into the VNet.** "App must reach a database on a private IP" = **VNet integration**. "Users must reach the app only over a private IP" = **private endpoint**. "App must call a TCP port on an on-prem server without a VPN" = **Hybrid Connections**.

> ⚠️ **Common Pitfall:** VNet integration does **not** make the app privately reachable — it changes nothing inbound. Conversely, a private endpoint does nothing for the app's outbound calls. Many scenarios need **both** at once, and that is a legitimate answer.

## Configure deployment slots for an App Service

- **What it is:** **Deployment slots** are live parallel instances of the app (e.g., **staging**) with their **own hostname** (`contoso-web-2026-staging.azurewebsites.net`) and their own content and settings, running in the **same App Service plan**.
- **Why it matters:** Slot **swap** ships new code with **zero downtime** — the platform **warms up** the staging slot (instances are loaded and hit with warm-up requests) *before* exchanging it with production, so there's **no cold start**, and rolling back is just **swapping back**.

| Tier | Slots (besides production) |
|---|---|
| Free / Shared / Basic | **0** |
| **Standard** | **5** |
| **Premium** | **20** |
| Isolated | 20 |

Behavior details:

- A swap **exchanges the content and applicable settings** of two slots. Settings marked **"deployment slot setting" (sticky)** stay with the slot and do **not** travel — e.g., the production database **connection string** stays in production, and a staging flag stays in staging. Custom domains, TLS bindings, and scale settings are always slot-specific.
- **Swap with preview** applies production's settings to staging first so you can validate before completing the swap.
- **Auto swap** — pushing code to a designated slot automatically warms it and swaps it into production; classic CI/CD pattern.
- **Traffic routing** — send a **percentage of production traffic** to a slot (e.g., 10% to staging) for canary testing; users are pinned by cookie.
- Slots share the plan's compute — heavy load tests in staging steal CPU from production.

```bash
az webapp deployment slot create --name contoso-web-2026 --resource-group rg-web \
  --slot staging
az webapp deployment slot swap --name contoso-web-2026 --resource-group rg-web \
  --slot staging                          # staging <-> production
az webapp traffic-routing set --name contoso-web-2026 --resource-group rg-web \
  --distribution staging=10
```

```powershell
Switch-AzWebAppSlot -ResourceGroupName rg-web -Name contoso-web-2026 `
  -SourceSlotName staging -DestinationSlotName production
```

> 💡 **Exam Tip:** Numbers first: **Standard = 5 slots, Premium = 20** — "needs 8 deployment slots" forces **Premium**. "Deploy with no downtime and instant rollback" = **swap** (and rollback = swap back). "Keep the production connection string in production during a swap" = mark it as a **deployment slot setting**.

> ⚠️ **Common Pitfall:** A swap moves **code *and* non-sticky settings** — forgetting to mark a connection string as sticky means staging's string lands in production after the swap. And slots don't exist below Standard: a Basic-tier scenario asking for slots is really a **scale up** question.

## How It Fits Together (mental model)

Contoso launches its storefront by provisioning an **App Service plan** — Linux, East US, **Standard S1** because the team needs **autoscale**, **deployment slots**, **scheduled backups**, and **Traffic Manager** support that **Basic** lacks — and creates the web app with the **globally unique name** `contoso-web-2026.azurewebsites.net`. Marketing wants `www.contoso.com`, so an admin adds a **CNAME** to the default hostname plus a **TXT `asuid.www`** verification record (the apex gets an **A record** to the app's IP), verifies, adds the hostname, then issues a free **App Service managed certificate** — auto-renewing, but **no wildcards** and never exportable — bound via free **SNI SSL**, with **HTTPS Only** on and **minimum TLS version** set to 1.2. Nightly **custom backups**, including the **linked database**, land in a **storage account container in the same subscription**. **Autoscale** rules grow the plan from 2 toward its Standard cap of **10 instances** when **CPU** passes 70%, with a **5-minute cooldown**; Black Friday's projections demand more, so they **scale up** to **Premium v3** — **30 instances**, **20 slots**, **zone redundancy**. Networking is split by direction: a **private endpoint** brings admin traffic **in** on a private IP, **access restrictions** allow only the Front Door **service tag**, **regional VNet integration** lets the app reach the database **outbound** through a delegated subnet, and a **hybrid connection** relays TCP to a legacy on-prem inventory host. Releases deploy to the **staging slot** on its own hostname, take 10% of live traffic via **traffic routing**, then **swap** into production fully **warmed up** — the production connection string stays put because it's a sticky **deployment slot setting** — and when a bug surfaces, rollback is one **swap back**.
