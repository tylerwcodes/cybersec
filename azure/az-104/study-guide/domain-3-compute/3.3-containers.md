# Objective 3.3 — Provision and manage containers in the Azure portal

Container questions on AZ-104 are service-selection and configuration questions in disguise. The exam gives you a workload — a private image store, a one-off batch job, a microservice that must scale on queue length — and expects you to pick the right service (**Azure Container Registry**, **Azure Container Instances**, **Azure Container Apps**, or step up to **AKS**) and then configure it correctly: the right **ACR SKU** for geo-replication or private endpoints, the right **authentication** method for CI/CD, the right **restart policy** for a run-once container, the right **scale rule** to reach zero replicas. Memorize the SKU/feature pairings, the ACI container-group limits (~4 vCPU / 16 GB, no autoscale), the Container Apps scaling triggers (HTTP, KEDA events, CPU/memory — and which of those can scale to zero), and the handful of `az acr` / `az container` / `az containerapp` commands, because command-completion items are common here.

## Create and manage an Azure container registry

- **What it is:** **Azure Container Registry (ACR)** is a managed, **private Docker/OCI registry** for storing and distributing container images (and other OCI artifacts like Helm charts). Every registry gets a **login server** at **`<name>.azurecr.io`**, where the registry name must be **globally unique**, **5–50 alphanumeric characters** (lowercase recommended — it becomes part of a DNS name).
- **Why it matters:** ACI, Container Apps, AKS, App Service, and your CI/CD pipelines all pull images from somewhere; ACR is the Azure-native "somewhere," with Entra-integrated auth and network isolation that Docker Hub can't give you.

### SKUs

| SKU | Storage / throughput | Distinguishing features |
|---|---|---|
| **Basic** | Lowest included storage and image throughput | Same core capabilities (Entra auth, webhooks); cost-optimized for dev/learning |
| **Standard** | More storage and throughput | The default for most production registries |
| **Premium** | Highest storage and throughput by far | **Geo-replication** (one registry, many regions), **private endpoints / Private Link**, **customer-managed keys (CMK)** for encryption, repository-scoped permissions at scale |

The exam pattern: any stem mentioning **geo-replication**, **private endpoint / Private Link**, or **customer-managed keys** forces **Premium** — those features exist in no other SKU. You can upgrade a registry's SKU in place (`az acr update --sku Premium`).

### Authentication options

| Method | Identity | Use when... |
|---|---|---|
| **`az acr login`** | Your **Microsoft Entra ID** identity (token handed to the Docker CLI) | Interactive developer push/pull |
| **Service principal** (or **managed identity**) | An application identity with an RBAC role (**AcrPull**, **AcrPush**) | **CI/CD pipelines** and services pulling images headlessly — the recommended automation path |
| **Admin account** | A **single username/password** shared by anyone who has it | **Disabled by default and discouraged** — no per-user audit trail; only for quick tests or services that demand basic auth |
| **Repository-scoped tokens** | A token bound to specific repositories with specific actions | Granting a partner or system pull access to **one repository**, not the whole registry |

### Building, importing, and automating

```bash
# Create a registry
az acr create --resource-group rg-app --name conregistry01 --sku Premium

# Log in with your Entra identity (wraps 'docker login')
az acr login --name conregistry01

# Build in the cloud from local source and push — no local Docker daemon needed
az acr build --registry conregistry01 --image webapp:v1 .

# Copy an image from another registry (e.g., Docker Hub) without docker pull/push
az acr import --name conregistry01 --source docker.io/library/nginx:latest --image nginx:latest

# Inspect contents
az acr repository list --name conregistry01
```

PowerShell equivalents live in the **Az.ContainerRegistry** module: `New-AzContainerRegistry`, `Connect-AzContainerRegistry`, `Get-AzContainerRegistryRepository`, `Update-AzContainerRegistry`.

- **`az acr build`** runs the build **in Azure** (an ACR Tasks "quick task") and pushes the result to the registry — the answer whenever the stem says "build without Docker installed locally."
- **`az acr import`** copies an existing image **registry-to-registry** — the answer for "get this Docker Hub image into ACR without pulling it locally."
- **ACR Tasks** automate the pipeline: trigger an image build on **source code commit** (GitHub/Azure DevOps) or on **base-image update** (your app image rebuilds automatically when the underlying OS/framework image is patched), plus scheduled and multi-step tasks.

> 💡 **Exam Tip:** Match feature to SKU instantly: **geo-replication, Private Link, customer-managed keys → Premium**. Match auth to scenario: interactive human → `az acr login`; pipeline → **service principal/managed identity with AcrPush/AcrPull**; single-repo access for an outsider → **repository-scoped token**.

> ⚠️ **Common Pitfall:** The **admin account** is disabled by default for a reason — it is one shared credential with full push/pull rights and no individual accountability. If a question asks for the *recommended* way to let a pipeline push images, the answer is a **service principal (or managed identity)**, never "enable the admin user." Also don't confuse `az acr build` (builds from source) with `az acr import` (copies an already-built image).

## Provision a container by using Azure Container Instances

- **What it is:** **Azure Container Instances (ACI)** is the **fastest, simplest serverless way to run a container** in Azure — no VM to create, no orchestrator to manage, **billed per second** for the vCPU and memory you request, from creation to termination.
- **Why it matters:** For single containers, batch/run-once jobs, build agents, and quick task automation, ACI removes every layer between "I have an image" and "it's running with a public IP."

### Container groups

The unit of deployment is the **container group**: one or more containers **scheduled on the same host machine** that share a **lifecycle, network (one IP, one port space), and volumes** — the same idea as a Kubernetes pod. This enables the **sidecar pattern**: an app container plus a logging or monitoring helper deployed and torn down together. **Multi-container groups are Linux-only; Windows containers support only a single container per group.**

### Key configuration at provisioning

| Setting | Options | Notes |
|---|---|---|
| **Resources** | Request **CPU cores** and **memory** per container | Group total capped around **4 vCPU / 16 GB** (standard; exact caps vary by region/OS) |
| **Restart policy** | **Always** (default) / **OnFailure** / **Never** | **Never** = run-once jobs — container runs to completion, stops, is billed only while running |
| **Networking** | **Public IP + DNS name label** (`<label>.<region>.azurecontainer.io`) or deploy into a **VNet** | VNet deployment = private-only workloads reachable from your network |
| **Persistence** | Mount an **Azure Files share** as a volume | Container filesystems are ephemeral; Azure Files survives restarts (Linux containers) |
| **Images** | Any registry; for ACR provide credentials | Typically a service principal or managed identity with **AcrPull** |

```bash
# Public web container with DNS name
az container create --resource-group rg-app --name webinstance \
  --image conregistry01.azurecr.io/webapp:v1 \
  --cpu 1 --memory 1.5 \
  --ip-address Public --dns-name-label webapp-demo --ports 80

# Run-once batch job with an Azure Files mount
az container create --resource-group rg-app --name nightlyjob \
  --image conregistry01.azurecr.io/batch:v2 \
  --restart-policy Never \
  --azure-file-volume-account-name stgapp01 \
  --azure-file-volume-share-name jobs \
  --azure-file-volume-mount-path /mnt/jobs

az container logs --resource-group rg-app --name nightlyjob
az container exec --resource-group rg-app --name webinstance --exec-command "/bin/sh"
```

PowerShell: `New-AzContainerGroup` / `Get-AzContainerGroup` / `Remove-AzContainerGroup` (Az.ContainerInstance module).

Two more provisioning details worth a mark each:

- **Environment variables:** pass configuration with `--environment-variables`, and use `--secure-environment-variables` for secrets — secure values are not shown in the portal or returned by `az container show`.
- **Multi-container groups:** the portal and a basic `az container create` deploy **single-container** groups; to define a multi-container (sidecar) group from the CLI you supply a **YAML file** (`az container create --file group.yaml`) or use an ARM/Bicep template.

> 💡 **Exam Tip:** "Run a container **as quickly/simply as possible**, no orchestration, pay **per second**" = ACI. "Task that runs to completion and should **not** restart" = restart policy **Never**. "Two containers that must share a lifecycle and localhost network" (sidecar) = a **multi-container group — Linux only**.

> ⚠️ **Common Pitfall:** ACI has **no autoscaling** — a container group is a **fixed-size** allocation. If the stem needs automatic scale-out (or scale to zero on demand), ACI is the wrong answer; that's Azure Container Apps. And remember data loss: without an **Azure Files volume mount**, everything written inside the container disappears when it stops.

## Provision a container by using Azure Container Apps

- **What it is:** **Azure Container Apps** is a **serverless container platform** built on **managed Kubernetes** with **KEDA** (event-driven autoscale), **Dapr** (microservice building blocks), and **Envoy** (ingress proxy) built in — you get Kubernetes-grade capabilities with **no cluster to create, patch, or manage** and no direct Kubernetes API access.
- **Why it matters:** It occupies the sweet spot between ACI (too simple for microservices) and AKS (too much operational burden for teams that don't need kubectl): scale-to-zero, versioned deployments, and HTTPS ingress out of the box.

### Core concepts

- **Environment:** the **secure boundary** around a group of container apps — apps in one environment share a **virtual network** and write logs to the same **Log Analytics workspace**. Create the environment first; deploy apps into it.
- **Revisions:** every deployment creates an **immutable revision** (image + configuration snapshot). Run in **single-revision mode** (each update replaces the last) or **multiple-revision mode** with **traffic splitting** — e.g., 90% to the stable revision, 10% to the new one — enabling **blue-green and canary** deployments with no extra infrastructure.
- **Ingress:** enable **external** (internet-facing HTTPS endpoint) or **internal** (reachable only inside the environment/VNet) ingress **without building any load balancer** — Envoy handles TLS termination and traffic splitting for you.
- **Plans:** the **Consumption** plan bills per-second for what replicas use (and nothing at zero); **Dedicated workload profiles** give reserved, larger compute (including specialized sizes) for predictable or resource-hungry apps. One environment can mix both.
- **Dapr integration:** enable **Dapr** per app for service-to-service invocation, state stores, and pub/sub without adding SDK-specific plumbing to your code — it runs as a managed sidecar.
- **Jobs:** alongside always-on apps, **Container Apps jobs** run containers to completion on a **manual**, **scheduled (cron)**, or **event-driven** trigger — the Container Apps answer to finite batch work.

```bash
# 1. Create the environment (shared VNet + Log Analytics boundary)
az containerapp env create --resource-group rg-app --name aca-env --location eastus

# 2. Deploy an app with external ingress and autoscale bounds
az containerapp create --resource-group rg-app --name orders-api \
  --environment aca-env \
  --image conregistry01.azurecr.io/orders:v1 \
  --ingress external --target-port 8080 \
  --min-replicas 0 --max-replicas 10

# 3. Ship v2 and canary it
az containerapp update --resource-group rg-app --name orders-api \
  --image conregistry01.azurecr.io/orders:v2
az containerapp ingress traffic set --resource-group rg-app --name orders-api \
  --revision-weight orders-api--rev1=90 orders-api--rev2=10

az containerapp revision list --resource-group rg-app --name orders-api -o table
```

### Choosing among the three container services

| Service | Pick it when the stem says... |
|---|---|
| **ACI** | Simple single container, batch/run-once job, fastest start, per-second billing, no scaling needed |
| **Container Apps** | **Microservices**, autoscale (including **to zero**), **revisions**/traffic splitting, event-driven processing, managed ingress |
| **AKS** | **Full Kubernetes control** — kubectl access, custom operators/CRDs, complete control of the cluster |

> 💡 **Exam Tip:** The environment is the architectural anchor: "apps must share a **VNet** and a **Log Analytics workspace**" = same **Container Apps environment**. "Route 10% of traffic to the new version" = **multiple revisions + traffic splitting** — no Application Gateway or load balancer required.

> ⚠️ **Common Pitfall:** Container Apps runs *on* Kubernetes but does **not give you the Kubernetes API** — if the scenario demands kubectl, custom resource definitions, or cluster-level control, the answer is **AKS**, not Container Apps. Conversely, don't over-answer with AKS when the requirements are just "microservices that scale on events" — that's Container Apps.

## Manage sizing and scaling for containers, including Azure Container Instances and Azure Container Apps

Sizing and scaling is where the two services diverge most sharply — and where the exam draws its contrast questions:

| | **Azure Container Instances** | **Azure Container Apps** |
|---|---|---|
| Sizing unit | **CPU cores + memory requested per container** at creation | CPU/memory per replica (Consumption combos up to ~**4 vCPU / 8 GiB**; more on **Dedicated workload profiles**) |
| Upper bound | ~**4 vCPU / 16 GB per container group** (standard) | **Min/max replica count** you set per app (max replicas default 10, configurable much higher) |
| Autoscale | **None — fixed size once deployed** | **Yes** — HTTP concurrency, **KEDA event-driven scalers**, CPU/memory |
| Scale to zero | No (a stopped group is just stopped) | **Yes** — zero replicas = **no compute charge** while idle |
| How to scale out | **Deploy more container groups** (manually or via automation), or move to Container Apps | Adjust `--min-replicas` / `--max-replicas` and scale rules |

### ACI: size it right the first time

You request resources per container (`--cpu 2 --memory 4`); the group's total is fixed for its lifetime. To change size, redeploy; to handle more load, **deploy additional container groups** — there is no built-in autoscaler. If a question describes fluctuating demand against ACI, the correct move is usually "use Azure Container Apps instead."

One workaround pattern the exam accepts: an automation trigger (Logic Apps, Azure Functions, or a script) that creates or deletes container groups on a schedule or signal — but that is orchestration you build yourself, not a platform feature.

### Container Apps: declarative scale rules

- **HTTP scaling:** replicas added based on **concurrent HTTP requests** per replica (a concurrency target you set).
- **KEDA event-driven scaling:** dozens of scalers — **Azure Storage/Service Bus queue length**, Event Hubs lag, Kafka, and more — scale on the *backlog*, not on CPU.
- **CPU / memory scaling:** classic utilization-based rules.
- **Scale to zero:** with **HTTP or event-driven (KEDA) rules and `--min-replicas 0`**, an idle app drops to **zero replicas and zero compute cost**. **CPU/memory scale rules cannot scale to zero** — they need at least one running replica to measure, so those apps floor at one.

```bash
# Scale 0→20 replicas on Azure Storage queue length
az containerapp update --resource-group rg-app --name queue-worker \
  --min-replicas 0 --max-replicas 20 \
  --scale-rule-name queue-rule \
  --scale-rule-type azure-queue \
  --scale-rule-metadata "queueName=orders" "queueLength=20" \
  --scale-rule-auth "connection=queue-conn-secret"
```

> 💡 **Exam Tip:** "Costs nothing while idle / scale to **zero**" = **Container Apps** with `min-replicas 0` and an **HTTP or KEDA event** rule. "Scale when the **queue length** grows" = a **KEDA** scaler — not CPU-based autoscale, and never ACI.

> ⚠️ **Common Pitfall:** Two traps in one section: (1) attributing autoscale to **ACI** — a container group is fixed-size, full stop; (2) expecting a **CPU or memory** scale rule to reach zero — it can't; scale-to-zero requires HTTP or event-driven triggers. Also keep the ceilings straight: ~**4 vCPU / 16 GB** is the ACI *container group* cap, while Container Apps limits are per *replica*, multiplied across replicas.

## How It Fits Together (mental model)

Picture a retailer moving its order system to containers. The platform team creates an **Azure Container Registry** named `retailacr` — **globally unique**, reachable at `retailacr.azurecr.io` — on the **Premium** SKU so it can **geo-replicate** images to both operating regions, lock pulls behind a **private endpoint**, and encrypt at rest with **customer-managed keys**. Developers authenticate interactively with **`az acr login`** (their **Entra ID** identities), the CI/CD pipeline pushes with a **service principal** holding **AcrPush** (the shared **admin account** stays **disabled**), and an external auditor gets a **repository-scoped token** for one repository. Builds happen in the cloud with **`az acr build`**, a needed Docker Hub base image is copied in with **`az acr import`**, and **ACR Tasks** rebuild the app automatically on every **source commit** and **base-image update**. The nightly inventory reconciliation runs as an **Azure Container Instances** **container group** — created with **`az container create`**, sized at 2 vCPU / 4 GB (under the ~**4 vCPU / 16 GB** group cap), **restart policy Never** so it runs once and stops, **billed per second**, writing results to an **Azure Files volume mount**; a Linux **sidecar** container in the same group ships logs. The customer-facing APIs, though, need elasticity, so they run in **Azure Container Apps**: an **environment** gives them a shared **VNet** and **Log Analytics workspace**, **Envoy**-backed **external ingress** exposes HTTPS without any load balancer to build, each deployment creates an immutable **revision**, and release day is a **canary** — **traffic splitting** 90/10 between revisions. The queue-processing worker uses a **KEDA** scaler on **queue length** with **min replicas 0**, so it **scales to zero** overnight and costs nothing, while the API scales on **HTTP concurrency** between 1 and 20 replicas on the **Consumption** plan — and when the data-science team later demands raw **kubectl** control for a custom operator, that one workload graduates to **AKS**.
