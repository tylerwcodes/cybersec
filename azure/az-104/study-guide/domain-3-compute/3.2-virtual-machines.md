# Objective 3.2 — Create and configure virtual machines

Virtual machines are the heaviest-weighted single topic on AZ-104, and the exam tests them as an *administrator*, not an architect: it expects you to know which resources a VM deployment actually creates, which `az vm` / `Az` PowerShell commands perform a task, and — above all — the operational side effects of every action (resizing **restarts** the VM, deallocating **wipes the temp disk**, moving a resource **locks both resource groups**). Memorize the size-family letters (B/D/E/F/L/N), the three encryption layers (SSE vs. Azure Disk Encryption vs. encryption at host), the five managed-disk types and which one unlocks the single-VM SLA, and the SLA ladder: single VM with Premium SSD **99.9%** → availability set **99.95%** → availability zones **99.99%**. Questions are scenario-driven ("the new size isn't listed — what do you do first?"), so learn the *why* behind each constraint, not just the fact.

## Create a virtual machine

- **What it is:** An **Azure virtual machine** is IaaS compute: you pick an **image** (platform images from the Marketplace, or your own generalized image in an **Azure Compute Gallery**), a **size**, and a **region**, and Azure provisions the machine on shared hardware while you keep responsibility for the OS and everything above it.
- **Why it matters:** A VM is never deployed alone. Creating one also creates or attaches a **network interface (NIC)** joined to a **virtual network/subnet**, a **managed OS disk**, and optionally a **public IP address** and a **network security group (NSG)** — every one of these is a separate resource that lives on (and bills) independently if you delete only the VM.

The two commands the exam expects you to recognize on sight:

```bash
az vm create \
  --resource-group rg-app-prod \
  --name vm-web01 \
  --image Ubuntu2204 \
  --size Standard_D2s_v5 \
  --admin-username azureadmin \
  --generate-ssh-keys
```

```powershell
New-AzVM -ResourceGroupName "rg-app-prod" -Name "vm-web01" `
  -Image "Ubuntu2204" -Size "Standard_D2s_v5" -Credential (Get-Credential)
```

- Authentication: **SSH keys** are the recommended default for Linux (`--generate-ssh-keys`); Windows VMs take a username/password. Windows names are limited to **15 characters**, Linux to 64.
- Any public IP or load balancer you create today is **Standard SKU** — the **Basic SKUs are retired**; Standard is secure by default (traffic is blocked until an NSG allows it) and is zone-capable.
- **VM extensions** are small agents that run **post-deployment configuration**: the **Custom Script Extension** downloads and executes a script after deployment (install software, configure roles), while **Desired State Configuration** and **Run Command** cover ongoing config and one-off commands.

```bash
az vm extension set --resource-group rg-app-prod --vm-name vm-web01 \
  --name customScript --publisher Microsoft.Azure.Extensions \
  --settings '{"fileUris":["https://.../setup.sh"],"commandToExecute":"./setup.sh"}'
```

- Power states matter for billing: **Stopped** (shut down from inside the OS) still **incurs compute charges** because the hardware is reserved; **Stopped-deallocated** (`az vm deallocate` / `Stop-AzVM`) releases the hardware, **stops compute charges**, but **keeps the managed disks** (which continue to bill) — and releases any dynamic IP.

> 💡 **Exam Tip:** If the stem says "run a script automatically after the VM is deployed," the answer is the **Custom Script Extension**. If it says "stop paying compute charges but keep the VM's disks," the answer is **deallocate**, not stop.

> ⚠️ **Common Pitfall:** Deleting a VM does **not** delete its NIC, disks, or public IP by default — orphaned resources keep billing. And a VM stopped from *inside the guest OS* is only "Stopped," not "Stopped-deallocated," so it still costs money.

## Configure Azure Disk Encryption

Azure encrypts VM disks at up to three distinct layers — the exam loves to make you tell them apart:

| Layer | What encrypts | Where keys live | Enabled by |
|---|---|---|---|
| **Server-side encryption (SSE)** | All managed disks at rest, in the storage service | Platform-managed keys (or customer-managed keys in Key Vault) | **Always on** — cannot be disabled |
| **Azure Disk Encryption (ADE)** | OS + data disk **volumes inside the guest OS** | **Azure Key Vault** — must be in the **same region and subscription** as the VM | You, per VM |
| **Encryption at host** | Data on the **host server** itself, including temp disk and caches | Platform- or customer-managed | You, per VM (subscription feature must be registered) |

- **What it is:** **Azure Disk Encryption** uses **BitLocker** on Windows and **DM-Crypt** on Linux to encrypt the volumes *inside* the VM, with the encryption keys and secrets stored in an **Azure Key Vault** that has the `EnabledForDiskEncryption` access policy set.
- **Why it matters:** Compliance mandates that say "encrypt the disks with keys we control, inside the guest" mean ADE — SSE alone is storage-level and always on, so it can't be the answer to "enable encryption."

```bash
az vm encryption enable --resource-group rg-app-prod --name vm-web01 \
  --disk-encryption-keyvault kv-prod-encrypt
```

```powershell
Set-AzVMDiskEncryptionExtension -ResourceGroupName "rg-app-prod" -VMName "vm-web01" `
  -DiskEncryptionKeyVaultUrl $kv.VaultUri -DiskEncryptionKeyVaultId $kv.ResourceId
```

- ADE is **not supported** on **Basic/A-series sizes** or on VMs with very small memory (less than ~2 GB), nor on Ultra Disks or Premium SSD v2 — for those, use **encryption at host** instead.
- Optionally wrap the encryption key with a **key encryption key (KEK)** in the same vault for an extra layer of control.

> 💡 **Exam Tip:** Match the phrase to the layer: "always on, no action needed" = **SSE**; "BitLocker / DM-Crypt with keys in Key Vault" = **ADE**; "encrypt the temp disk and host caches too" = **encryption at host**. The Key Vault must be in the **same region** as the VM — a vault in another region is a wrong-answer trap.

> ⚠️ **Common Pitfall:** ADE fails on Basic/A-series and low-memory sizes — if the scenario's VM is an A-series and encryption "won't enable," the size is the reason. Also remember SSE is not a substitute: it's always on, so a question asking you to *configure* encryption is never answered "SSE."

## Move a virtual machine to another resource group, subscription, or region

- **What it is:** Moving between **resource groups or subscriptions** is a metadata operation with **`Move-AzResource`** (PowerShell) or **`az resource move`** (CLI); moving between **regions** is a *replication* operation with **Azure Resource Mover** (built on **Azure Site Recovery**) because the underlying data must physically relocate.
- **Why it matters:** Admins reorganize constantly — chargeback restructures, subscription consolidations, data-residency requirements — and the exam tests the constraints, not the clicks.

```bash
az resource move --destination-group rg-app-new --ids $vmId $nicId $diskId
```

```powershell
Move-AzResource -DestinationResourceGroupName "rg-app-new" -ResourceId $vmId, $nicId, $diskId
```

Rules for RG/subscription moves:

- Move the VM **together with its dependent resources** — NIC, managed disks, and (for cross-subscription moves) the virtual network they sit in. A VM cannot move away from its dependencies.
- During the move, **both the source and destination resource groups are locked**: no create, update, or delete operations until the move completes (reads still work).
- The resource's **region does not change** — a VM moved to a resource group "located" in another region stays physically where it was.
- **VMs with ADE-encrypted disks cannot move across subscriptions** (disable ADE first). Cross-subscription moves also require both subscriptions to be in the **same Microsoft Entra tenant**.

Rules for region moves:

- Use **Azure Resource Mover**, which validates dependencies, replicates via **Site Recovery**, lets you test, then commits the move — new resource IDs, new IPs, and (usually) a new virtual network on the other side.

> 💡 **Exam Tip:** Keyword sort: "another resource group / another subscription" = **Move-AzResource / az resource move**; "another region" = **Azure Resource Mover** (or Site Recovery). If the stem mentions the move failing and the VM is encrypted, ADE across subscriptions is the culprit.

> ⚠️ **Common Pitfall:** Moving a VM to a resource group in a different region does **not** move the VM to that region — resource-group location is metadata only. And forgetting that both RGs are **locked mid-move** is a favorite "what happens during the move?" question.

## Manage virtual machine sizes

- **What they are:** VM **sizes** (SKUs like `Standard_D4s_v5`) define vCPU, RAM, temp-disk size, max data disks, max IOPS, and network bandwidth, grouped into **families** identified by their first letter.
- **Why they matter:** The exam gives you a workload adjective and expects the family letter back:

| Family | Optimized for | Typical stem phrase |
|---|---|---|
| **B** | **Burstable** — banks CPU credits while idle, bursts when busy | "Low baseline CPU, occasional spikes, lowest cost" |
| **D** | **General purpose** — balanced CPU:memory | "Production web server, small database, default choice" |
| **E** | **Memory optimized** — high memory-to-CPU ratio | "In-memory cache, SAP, large relational database" |
| **F** | **Compute optimized** — high CPU-to-memory ratio | "Batch processing, gaming servers, analytics compute" |
| **L** | **Storage optimized** — high local disk throughput/IOPS | "Big data, NoSQL like Cassandra, data warehousing" |
| **N** | **GPU** | "Machine-learning training, rendering, video processing" |

Resizing is a routine admin task with sharp edges:

```bash
az vm resize --resource-group rg-app-prod --name vm-web01 --size Standard_E4s_v5
```

```powershell
$vm = Get-AzVM -ResourceGroupName "rg-app-prod" -Name "vm-web01"
$vm.HardwareProfile.VmSize = "Standard_E4s_v5"
Update-AzVM -ResourceGroupName "rg-app-prod" -VM $vm
```

- Resizing **restarts the VM** — plan a maintenance window.
- `az vm list-vm-resize-options` / `Get-AzVMSize -VMName` shows only sizes available on the **current hardware cluster**. If the target size isn't listed, **deallocate the VM first** — a deallocated VM can restart on any cluster in the region that offers the size. (VMs in an availability set must all be deallocated together to move clusters.)
- Downsizing works the same way but can fail if the smaller size supports fewer data disks or NICs than the VM currently uses.

> 💡 **Exam Tip:** "The size I need doesn't appear in the resize list" has a one-word answer: **deallocate** (then resize, then start). And be able to recite the letters cold — B burstable, D general, E memory, F compute, L storage, N GPU.

> ⚠️ **Common Pitfall:** Assuming a resize is non-disruptive. It always **reboots** the VM, and if it requires a cluster change it requires **deallocation** — which releases dynamic public IPs and **erases the temporary disk**.

## Manage virtual machine disks

Every VM has up to three kinds of disk — know them apart before comparing disk *types*:

- **OS disk:** the bootable managed disk created from the image; one per VM.
- **Data disks:** additional managed disks you attach for application data; the maximum count depends on VM size.
- **Temporary disk:** **local storage on the host** (mounted as `D:` on Windows, `/dev/sdb` on Linux) intended for page/swap files — its contents are **lost on deallocate, redeploy, or host maintenance**. **Never store data you need on the temp disk.**

The five **managed disk** types compete on performance and price:

| Disk type | Media | Best for | Notes |
|---|---|---|---|
| **Ultra Disk** | SSD | Extreme IOPS/latency: SAP HANA, top-tier databases | **Data disk only** (cannot be an OS disk); IOPS/throughput tunable independently of size |
| **Premium SSD v2** | SSD | High performance with independently configurable size/IOPS/throughput | Data disk only; cheaper than Ultra for most workloads |
| **Premium SSD** | SSD | Production workloads | Required (on **all** disks) for the **single-instance VM SLA of 99.9%**; needs an s-capable size (e.g., `D4s`) |
| **Standard SSD** | SSD | Dev/test, light web servers | Consistent latency, lower IOPS ceiling |
| **Standard HDD** | HDD | Backups, non-critical, infrequent access | Cheapest |

Operational facts the exam tests directly:

- Disks can be **expanded, never shrunk**. Growing beyond 4 TiB (or without downtime, where supported) may require the VM to be **deallocated** first; after expansion you must also **extend the partition inside the guest OS**.
- A **snapshot** is a point-in-time, read-only copy of a managed disk — the basis for backups, disk export, or creating a new disk/VM from a known state.

```bash
az disk update --resource-group rg-app-prod --name vm-web01-data1 --size-gb 512
az snapshot create --resource-group rg-app-prod --name data1-snap \
  --source vm-web01-data1
```

- **Host caching** per disk (None / ReadOnly / ReadWrite) tunes performance; changing it detaches and re-attaches the disk — and restarts the VM when it is the **OS disk's** cache setting.

> 💡 **Exam Tip:** "Guarantee an SLA for a single VM" = **Premium SSD (or better) on every disk** → **99.9%**. "Highest IOPS, sub-millisecond latency" = **Ultra Disk** — but remember Ultra and Premium SSD v2 are **data disks only**, never OS disks.

> ⚠️ **Common Pitfall:** Two classics: storing data on the **temporary disk** (wiped on deallocate/redeploy) and trying to **shrink** a managed disk (impossible — you'd create a new smaller disk and migrate the data instead).

## Deploy virtual machines to availability zones and availability sets

- **What they are:** The two intra-region resilience constructs. An **availability set** spreads VMs across isolated hardware *within one datacenter*; **availability zones** spread VMs across **physically separate datacenters** in the same region, each with independent power, cooling, and networking.
- **Why they matter:** They set the compute SLA, and the exam expects you to pick the construct — and quote the number — from the failure the scenario must survive.

Availability sets are built from two kinds of domain:

| Domain | Protects against | Count |
|---|---|---|
| **Fault domain (FD)** | Unplanned hardware failure — a shared **rack, power source, and network switch** | **2 or 3** per region |
| **Update domain (UD)** | **Planned maintenance** — Azure reboots **only one UD at a time**, waiting 30 minutes between them | Up to **20**, default **5** |

```bash
az vm availability-set create --resource-group rg-app-prod --name avset-web \
  --platform-fault-domain-count 2 --platform-update-domain-count 5
az vm create --resource-group rg-app-prod --name vm-web02 \
  --availability-set avset-web --image Ubuntu2204 ...
```

- A VM joins an availability set **only at creation** — to add an existing VM you must delete and recreate it (keeping its disks).
- Zonal deployment is just `--zone 1|2|3` on `az vm create`; zone-redundant designs put VM copies in different zones behind a **Standard load balancer** (Standard SKU is zone-redundant; Basic is retired).

The SLA ladder to memorize:

| Deployment | SLA |
|---|---|
| Single VM, **Premium SSD or better on all disks** | **99.9%** |
| **2+ VMs in an availability set** | **99.95%** |
| **2+ VMs across availability zones** | **99.99%** |

> 💡 **Exam Tip:** Map the threat: "rack/power/switch failure" = **fault domains**; "planned maintenance reboots" = **update domains**; "entire datacenter loss" = **availability zones**. Then quote the SLA: 99.9 / 99.95 / 99.99.

> ⚠️ **Common Pitfall:** You cannot combine an availability set with availability zones for the same VM, and you cannot join an **existing** VM to an availability set — both are recreate-the-VM situations. Also, an availability set protects nothing with only **one** VM in it; the 99.95% SLA requires **two or more**.

## Deploy and configure Azure Virtual Machine Scale Sets

- **What it is:** A **Virtual Machine Scale Set (VMSS)** deploys and manages a group of **identical VMs from the same image** that can **autoscale** — automatically adding (**scale out**) or removing (**scale in**) instances — typically behind an optional **Azure Load Balancer** or **Application Gateway**.
- **Why it matters:** VMSS is the answer whenever the stem says "automatically adjust the number of VMs based on demand" — it grows to as many as **1,000 instances** with platform images (600 with custom images), can span **availability zones** for 99.99% resilience, and centralizes image updates across the fleet.

Two **orchestration modes**, chosen at creation:

| Mode | Instances are... | Choose when... |
|---|---|---|
| **Uniform** | Identical, defined by a scale-set model; managed as a group | Classic large-scale, stateless, identical workloads |
| **Flexible** | Full standard VMs (can mix sizes/types) managed by the scale set | Mixed instance types, higher fault-domain flexibility, quorum-based or stateful workloads — the recommended default for new deployments |

```bash
az vmss create --resource-group rg-app-prod --name vmss-web \
  --image Ubuntu2204 --orchestration-mode Flexible \
  --instance-count 3 --zones 1 2 3 --lb lb-web --admin-username azureadmin

az monitor autoscale create --resource-group rg-app-prod \
  --resource vmss-web --resource-type Microsoft.Compute/virtualMachineScaleSets \
  --min-count 2 --max-count 10 --count 3
az monitor autoscale rule create --resource-group rg-app-prod \
  --autoscale-name vmss-web --scale out 2 \
  --condition "Percentage CPU > 75 avg 5m"
```

- **Autoscale rules** trigger on **metrics** (CPU percentage, memory, queue depth, custom Application Insights metrics) or on a **schedule** (business hours, month-end). Every profile sets **minimum, maximum, and default** instance counts, and each rule has a **cooldown** period so a scale action can settle before the next one fires.
- Always pair a scale-out rule with a matching **scale-in** rule, or the set grows and never shrinks.
- **Upgrade policy** controls how instances receive a new model/image: **Automatic** (all at once — brief full outage possible), **Rolling** (in batches with health checks between them), or **Manual** (you upgrade each instance yourself).

> 💡 **Exam Tip:** "Identical VMs that scale automatically on CPU" = **VMSS with a metric autoscale rule**; "predictable Monday-morning load" = **schedule-based profile**. "Update instances in batches without downtime" = **Rolling** upgrade policy. Mixed VM sizes in one set = **Flexible** orchestration.

> ⚠️ **Common Pitfall:** Autoscale never violates the profile's **min/max** bounds — if the set "won't scale past 10," the maximum is set to 10, not a platform limit. And don't confuse the **default** count (used when metrics can't be read) with the minimum.

## How It Fits Together (mental model)

Picture Contoso standing up its web platform. An admin runs **`az vm create`**, and Azure provisions not just the VM but its **NIC**, **managed OS disk**, **Standard-SKU public IP**, and **NSG**; a **Custom Script Extension** then installs the web server post-deployment. The team picks a **D-series** (general purpose) size for the web tier, an **E-series** (memory optimized) for the database, and a cheap **B-series** (burstable) for a monitoring box — knowing that a later `az vm resize` will **restart** each VM, and that if the target size isn't on the current cluster they must **deallocate** first (accepting that **Stopped-deallocated** VMs stop compute billing but keep — and keep paying for — their disks, while their **temporary disks** are wiped). Every disk already has always-on **SSE**, but compliance demands **Azure Disk Encryption** — **BitLocker** in the guest with keys in a **Key Vault in the same region** — which rules out the old **Basic/A-series** test boxes ADE doesn't support. The database VM gets **Premium SSD** on **all** disks to earn the single-instance **99.9% SLA**, a data disk is later **expanded** (never shrunk) after a **snapshot** for safety, and nobody stores anything on the temp disk. When finance restructures, **`Move-AzResource`** shifts the VMs — with their **NICs, disks, and VNet** — to a new subscription while **both resource groups sit locked**, though the ADE-encrypted VM must be decrypted first; the later move to a new region uses **Azure Resource Mover** on **Site Recovery**. For resilience, the two database VMs share an **availability set** — separate **fault domains** (rack/power/switch) and **update domains** (only one rebooted at a time) — for **99.95%**, while the web tier goes further: a **Virtual Machine Scale Set** in **Flexible orchestration** spread across **availability zones** (**99.99%**) behind a **Standard load balancer**, with **autoscale rules** scaling out at 75% CPU between a **minimum** of 2 and a **maximum** of 10 instances, a **cooldown** between actions, and a **Rolling upgrade policy** pushing new images in health-checked batches.
