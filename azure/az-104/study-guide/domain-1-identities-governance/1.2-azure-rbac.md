# Objective 1.2 — Manage access to Azure resources

Azure RBAC is one of the most heavily tested topics on AZ-104, and unlike AZ-900 it is tested *hands-on*: the exam expects you to pick the least-privileged built-in role for a job description, assign it at exactly the right scope, predict the *effective* permissions when multiple assignments overlap, and read a role-definition JSON well enough to say what it does and does not allow. Memorize the anatomy of a role assignment (who + what + where), the four fundamental roles, the scope hierarchy and its downward inheritance, the "assignments are additive" union rule, and the sharp line between control-plane and data-plane access. Expect stems like "a user must manage VMs but not the virtual network — which role, at which scope?" and "the Reader at subscription level also has Contributor on one resource group — what can they do there?"

## Manage built-in Azure roles

**Azure role-based access control (Azure RBAC)** is the authorization system for Azure resources, built on **Azure Resource Manager**. Every grant of access is a **role assignment**, and a role assignment always has exactly three parts:

| Part | What it is | Examples |
|---|---|---|
| **Security principal** | *Who* gets access | **User**, **group**, **service principal**, **managed identity** |
| **Role definition** | *What* they can do — a named collection of permissions | Owner, Contributor, Virtual Machine Contributor, a custom role |
| **Scope** | *Where* the permissions apply | Management group, subscription, resource group, resource |

Azure ships with well over a hundred **built-in roles**, but four **fundamental roles** anchor everything and appear on nearly every exam:

| Role | Can do | Cannot do |
|---|---|---|
| **Owner** | Full access to all resources **including granting access** (creating/deleting role assignments) | — |
| **Contributor** | Full access to create and manage all resource types | **Cannot grant access** — no assigning roles or managing role assignments |
| **Reader** | **View** all resources | Make any change |
| **User Access Administrator** | **Manage user access** to Azure resources (role assignments) plus read | Modify the resources themselves |

The classic split to internalize: **Owner = Contributor + User Access Administrator**. If a stem says "can manage everything *except* permissions," the answer is Contributor; "can manage *only* permissions," User Access Administrator. A newer, more least-privilege alternative to User Access Administrator is **Role Based Access Control Administrator**, which can create role assignments (optionally constrained with conditions to specific roles) without full authorization control.

Beyond the fundamentals, know the common **workload roles** and what they deliberately exclude:

- **Virtual Machine Contributor** — **What it is:** manage virtual machines (create, restart, resize, delete). **Why it matters:** it does **not** grant access to the virtual network or storage account the VM connects to, does not let you sign in to the VM, and cannot assign roles — the exam loves testing these exclusions.
- **Network Contributor** — **What it is:** manage all networking resources (VNets, subnets, NSGs, load balancers, public IPs). **Why it matters:** the pairing partner of VM Contributor — an admin who must also modify the VM's VNet needs *both* roles or a broader one.
- **Storage Account Contributor** — **What it is:** manage storage accounts (create, configure, list access keys). **Why it matters:** it is a **control-plane** role — with Microsoft Entra authentication it grants **no access to the data** inside; it only manages the account object (though listing keys is a side door the exam sometimes probes).
- **Storage Blob Data Reader / Storage Blob Data Contributor** — **What they are:** **data-plane** roles that grant read (Reader) or read/write/delete (Contributor) access to blob containers and blob data when clients authenticate with **Microsoft Entra ID**. **Why they matter:** this is *the* control-plane vs. data-plane trap — Owner or Contributor on a storage account does **not** let a user read blobs via Entra auth; a Data role is required.

Every role is described by a **role definition** in JSON. Learn the properties:

| Property | Meaning |
|---|---|
| **Actions** | Control-plane operations the role **allows** (wildcards like `*` permitted) |
| **NotActions** | Operations **subtracted from Actions** — a scoping subtraction, **NOT a deny** |
| **DataActions** | **Data-plane** operations allowed (e.g., read blob content) |
| **NotDataActions** | Data-plane operations subtracted from DataActions |
| **AssignableScopes** | Scopes at which the role is **available for assignment** |

```json
{
  "Name": "Contributor",
  "IsCustom": false,
  "Description": "Grants full access to manage all resources, but does not allow you to assign roles.",
  "Actions": [ "*" ],
  "NotActions": [
    "Microsoft.Authorization/*/Delete",
    "Microsoft.Authorization/*/Write",
    "Microsoft.Authorization/elevateAccess/Action"
  ],
  "DataActions": [],
  "NotDataActions": [],
  "AssignableScopes": [ "/" ]
}
```

That JSON *is* the Contributor story: `Actions: ["*"]` allows everything, then `NotActions` subtracts the `Microsoft.Authorization` write/delete operations — which is exactly why Contributor cannot grant access. When no built-in role fits, create a **custom role**: author the same JSON (set `"IsCustom": true`, choose least-privilege `Actions`, and set **AssignableScopes** — at least one subscription, resource group, or a single management group). Custom Azure roles are a free RBAC feature — no Entra ID P1/P2 license is needed (a tenant supports up to 5,000 custom roles) — but *creating* one requires `Microsoft.Authorization/roleDefinitions/write`, i.e., Owner or User Access Administrator.

```bash
# List and inspect built-in roles
az role definition list --output table
az role definition list --name "Virtual Machine Contributor"

# Create / update a custom role from JSON
az role definition create --role-definition ./vm-operator.json
az role definition update --role-definition ./vm-operator.json
```

```powershell
Get-AzRoleDefinition | Select-Object Name, IsCustom
Get-AzRoleDefinition "Contributor" | ConvertTo-Json
New-AzRoleDefinition -InputFile ./vm-operator.json
```

Finally, keep the two authorization systems separate in your head: **Azure RBAC** governs Azure *resources*; **Microsoft Entra roles** (Global Administrator, User Administrator, etc.) govern the *directory*. A **Global Administrator has no access to Azure resources by default**. In an emergency (orphaned subscription, lost Owner), a Global Administrator can enable the **"Access management for Azure resources"** toggle (**elevate access**) in Entra ID properties, which grants them **User Access Administrator at root scope (`/`)** — spanning every subscription in the tenant — and should be switched off as soon as the recovery is done.

> 💡 **Exam Tip:** Match the verb to the role: "everything including access" = **Owner**; "everything except access" = **Contributor**; "view only" = **Reader**; "only manage access" = **User Access Administrator**. And whenever a user must *read or write actual data* (blobs, queues) with Entra sign-in, the answer is a **Data** role — never Owner/Contributor alone.

> ⚠️ **Common Pitfall:** **NotActions is not a deny.** It merely subtracts operations from that role's own Actions list. If the same user gains the subtracted permission from *another* role assignment, they have it. Only a **deny assignment** (covered below) actually blocks access.

## Assign roles at different scopes

**Scope** is the *where* of a role assignment, and Azure scopes form a strict four-level hierarchy with **downward inheritance**:

| Level | Scope string format | Assignment inherited by |
|---|---|---|
| **Management group** | `/providers/Microsoft.Management/managementGroups/<mg-id>` | All child subscriptions, RGs, resources |
| **Subscription** | `/subscriptions/<sub-id>` | All resource groups and resources in it |
| **Resource group** | `/subscriptions/<sub-id>/resourceGroups/<rg-name>` | All resources in the group |
| **Resource** | `.../resourceGroups/<rg-name>/providers/Microsoft.Compute/virtualMachines/<vm-name>` | That resource only |

Rules to memorize:

- **Assign at the highest scope that matches the need, and no higher** — Reader on a management group for the audit team, Contributor on one resource group for a project team, a role on a single resource for a narrowly scoped automation identity.
- **Inheritance flows down only.** A role at subscription scope applies to every current *and future* resource group inside it; a role on a resource group says nothing about the rest of the subscription.
- **Assignments are additive.** A principal's effective permissions are the **union** of everything assigned directly or via group membership at that scope or above.
- **Prefer groups over users.** Assigning a role to a **group** once beats maintaining hundreds of per-user assignments — which matters because each subscription supports a limit of roughly **4,000 role assignments** (and about 500 at each management group). Group-based assignment is both the best practice and the exam's favorite answer to "you are approaching the role assignment limit."

The assignment commands are pure muscle memory for this exam:

```bash
# Assign a role (resource-group scope shown)
az role assignment create \
  --assignee "dana@contoso.com" \
  --role "Virtual Machine Contributor" \
  --scope "/subscriptions/<sub-id>/resourceGroups/rg-prod"

# Remove it
az role assignment delete \
  --assignee "dana@contoso.com" \
  --role "Virtual Machine Contributor" \
  --scope "/subscriptions/<sub-id>/resourceGroups/rg-prod"
```

```powershell
# Assign a role — -ResourceGroupName / -Scope selects the scope
New-AzRoleAssignment -SignInName dana@contoso.com `
  -RoleDefinitionName "Virtual Machine Contributor" `
  -ResourceGroupName rg-prod

# Group and service-principal assignments use -ObjectId
New-AzRoleAssignment -ObjectId <group-object-id> `
  -RoleDefinitionName "Reader" `
  -Scope "/subscriptions/<sub-id>"

Remove-AzRoleAssignment -SignInName dana@contoso.com `
  -RoleDefinitionName "Virtual Machine Contributor" -ResourceGroupName rg-prod
```

In the portal, every assignment lives on the resource's/subscription's **Access control (IAM)** blade → **Add role assignment**. Whoever creates assignments needs `Microsoft.Authorization/roleAssignments/write` at that scope — i.e., **Owner**, **User Access Administrator**, or **Role Based Access Control Administrator**; a Contributor cannot do it.

> 💡 **Exam Tip:** "All current **and future** resource groups/subscriptions must get this access" is a scope question, not a role question — assign once at the **subscription** or **management group** level and let **inheritance** do the work. Conversely, "only this one VM" means resource scope, honoring least privilege.

> ⚠️ **Common Pitfall:** You cannot "carve out" an exception below an assignment. Contributor at subscription scope cannot be reduced to Reader on one resource group by adding a Reader assignment there — the union rule keeps them Contributor everywhere. To restrict, you must remove the broad assignment and re-grant at narrower scopes (or rely on Azure Policy/locks for operational guardrails).

## Interpret access assignments

Interpreting access means answering "what can this principal actually do *here*?" — combining every direct, group-based, and inherited assignment into **effective permissions**:

- **Union rule:** effective permissions are the **sum of all role assignments**. A user with **Reader at the subscription** and **Contributor on resource group rg-app** is a Reader everywhere in the subscription *except* inside `rg-app`, where they are a **Contributor** (Contributor already includes everything Reader grants).
- **Group math counts:** an assignment to a group applies to every transitive member, so a user with no direct assignments can still hold significant access. Always check group-derived assignments before declaring someone unprivileged.
- **NotActions math:** within a single role, permissions = (Actions − NotActions) + (DataActions − NotDataActions), evaluated per role and *then* unioned across roles.
- **Deny assignments** — **What they are:** blocks that *prevent* specific actions even when a role assignment grants them; **deny wins over any role assignment**. **Why they matter:** you **cannot create your own** — deny assignments are created only by Azure itself, on resources protected by **Azure managed applications** or **deployment stacks**. If a stem says an Owner "mysteriously cannot delete" a resource, look for a deny assignment (or a resource lock, its Objective-1.3 cousin).

The interpretation toolset:

| Tool | What it shows |
|---|---|
| IAM → **Check access** | Enter a user/group/service principal/managed identity and see their **effective role assignments** at that scope, including inherited and group-based ones — the portal's built-in interpreter |
| IAM → **Role assignments** tab | All assignments *at* this scope plus those **inherited** from above (the "Scope" column reads "Inherited") |
| `az role assignment list` | Scriptable listing; filter by assignee and scope |
| `Get-AzRoleAssignment` | PowerShell equivalent |

```bash
# Everything one principal holds, at every scope in the subscription
az role assignment list --assignee dana@contoso.com --all --output table

# Assignments at a scope, including those inherited from parent scopes
az role assignment list --include-inherited \
  --scope "/subscriptions/<sub-id>/resourceGroups/rg-prod"
```

```powershell
Get-AzRoleAssignment -SignInName dana@contoso.com
Get-AzRoleAssignment -ResourceGroupName rg-prod
Get-AzRoleAssignment -Scope "/subscriptions/<sub-id>"
```

For "who changed access?" questions, role assignments are write operations recorded in the **Activity Log** (`Microsoft.Authorization/roleAssignments/write`), so auditing a suspicious grant is an Activity Log query, not an RBAC blade.

> 💡 **Exam Tip:** When a stem lists two or three assignments and asks what the user can do at a specific resource, compute the **union at that scope**: gather every assignment at that scope and above (including via groups), take the most permissive combination, then subtract nothing — unless a **deny assignment** appears, which overrides everything.

> ⚠️ **Common Pitfall:** Confusing directory with resources. A **Global Administrator** who cannot see any subscriptions is behaving *correctly* — Entra roles grant no Azure resource access. The fix is a proper Azure role assignment, or in a lockout emergency the **elevate access** toggle (User Access Administrator at root `/`) — which should be disabled immediately after use.

## How It Fits Together (mental model)

Picture Contoso onboarding its Azure estate. The platform team holds **Owner** on the production **management group**, so **inheritance** carries their access into every **subscription** and **resource group** below; the audit team gets **Reader** there through a **group** assignment, keeping the ~**4,000-per-subscription role assignment** budget healthy. A VM operations crew receives **Virtual Machine Contributor** on `rg-prod` — they can resize and restart VMs but discover they cannot touch the VNet, so the network team's **Network Contributor** stays cleanly separated. An app's **managed identity** (a **security principal**, like any **user**, **group**, or **service principal**) needs to read blobs, and because **Storage Account Contributor** is only **control plane**, it instead gets the **data-plane** role **Storage Blob Data Reader** at the storage-account **scope** via `az role assignment create`. One engineer holds **Reader** at the subscription plus **Contributor** on `rg-app`; since **assignments are additive**, the IAM **Check access** blade shows her **effective permissions** as full Contributor inside that resource group. When no built-in **role definition** fits, the team authors a **custom role** in JSON — **Actions** minus **NotActions** (a subtraction, **not a deny**), plus **DataActions**, bounded by **AssignableScopes**. A resource deployed through a managed application refuses deletion even for Owners — a **deny assignment**, which Azure alone creates and which **wins over role assignments**. And when the last subscription Owner leaves the company, the **Global Administrator** — who has **no resource access by default** because **Entra roles** and **Azure RBAC** are separate systems — flips **"Access management for Azure resources"**, becomes **User Access Administrator at root scope**, re-grants Owner via **User Access Administrator**-level rights, and turns the toggle back off.

## Quick Contrast Drills

Four pairings the exam loves to blur — rehearse the one-line distinction:

1. **Contributor vs. Owner:** identical resource powers, but only **Owner** can create or delete **role assignments** — "except managing access" always means Contributor.
2. **Storage Account Contributor vs. Storage Blob Data Contributor:** **control plane** (manage the account) vs. **data plane** (touch the blobs) — with Entra auth, only the Data role reads or writes data.
3. **NotActions vs. deny assignment:** NotActions **subtracts from one role's own Actions** and can be overridden by another assignment; a **deny assignment** blocks the action outright and beats every role.
4. **Entra roles vs. Azure RBAC roles:** directory vs. resources — **Global Administrator** manages Entra ID but holds zero Azure resource access until an Azure role is assigned or **elevate access** is used.

And one spanning rule: every "what can this user do here?" stem is the **union** of all assignments at that scope and above (direct + group), minus nothing — unless Azure itself planted a **deny assignment**.

## Key Takeaways

- [ ] A **role assignment** = **security principal** (user, group, service principal, managed identity) + **role definition** + **scope**.
- [ ] Fundamental roles: **Owner** (all incl. access), **Contributor** (all except access), **Reader** (view), **User Access Administrator** (access only); Owner ≈ Contributor + UAA.
- [ ] **Control plane ≠ data plane:** Owner/Contributor/Storage Account Contributor don't grant blob/queue data access under Entra auth — use **Storage Blob Data Reader/Contributor** and friends.
- [ ] Role definition JSON: **Actions**, **NotActions** (a subtraction, not a deny), **DataActions**, **NotDataActions**, **AssignableScopes**; custom roles are free, need `roleDefinitions/write` to create.
- [ ] Scope hierarchy: **management group > subscription > resource group > resource**, inheritance strictly downward; assign to **groups** at the highest appropriate scope; ~**4,000 assignments** per subscription.
- [ ] **Assignments are additive** — effective permissions are the **union**; you cannot narrow inherited access with a lesser role below it.
- [ ] **Deny assignments** are created only by Azure (managed applications, deployment stacks) and **override role assignments**.
- [ ] **Entra roles and Azure RBAC are separate**; Global Administrator gets resource access only via the **elevate access** toggle (UAA at root `/`) — disable it after use.
- [ ] Tooling: `az role assignment create/list/delete`, `New-AzRoleAssignment` / `Get-AzRoleAssignment`, `az role definition list/create`, and the IAM **Check access** blade for effective access.

## Self-Check Questions

1. A support engineer must be able to restart and resize the VMs in resource group `rg-web`, but must not modify the virtual network they use or grant anyone else access. Which built-in role at which scope?
2. An application uses a managed identity with Contributor on a storage account, authenticates to Blob Storage with Microsoft Entra ID, and receives authorization failures reading blobs. Why, and what fixes it?
3. A user has Reader assigned at the subscription and, through a group, Contributor on resource group `rg-data`. Can she delete a VM in `rg-data`? Can she delete one in `rg-web`?
4. Your tenant's Global Administrator must urgently re-assign Owner on a subscription whose only Owner left the company, but she sees no subscriptions at all. What is the supported recovery path?
5. In a custom role, `Actions` contains `"Microsoft.Compute/*"` and `NotActions` contains `"Microsoft.Compute/virtualMachines/delete"`. A user holds this role plus Contributor on the same resource group. Can the user delete VMs there?

<details>
<summary>Answers</summary>

1. **Virtual Machine Contributor** scoped to **resource group `rg-web`**. It manages VMs but deliberately excludes the connected virtual network and storage, and it cannot create role assignments — least privilege satisfied without a custom role.
2. Contributor is a **control-plane** role; with **Microsoft Entra authentication** it grants no data access. Assign a **data-plane** role — **Storage Blob Data Reader** (read) or **Storage Blob Data Contributor** (read/write) — to the managed identity at the storage-account (or container) scope.
3. Yes in `rg-data`: assignments are **additive**, and the union of Reader (inherited) + Contributor (via the group) makes her an effective **Contributor** there. No in `rg-web`: only the subscription-level **Reader** reaches it, and Reader cannot delete anything.
4. Enable **"Access management for Azure resources"** (elevate access) in Entra ID — as Global Administrator she gains **User Access Administrator at root scope (`/`)**, can then create the new Owner assignment on the subscription, and should **disable the toggle immediately afterward**.
5. **Yes.** `NotActions` only subtracts the delete operation from the *custom role's* Actions — it is **not a deny**. Contributor independently grants `Microsoft.Compute/virtualMachines/delete`, and effective permissions are the union of both roles. Only a **deny assignment** could block the delete.
