# Objective 1.1 — Manage Microsoft Entra users and groups

Identity is the front door of AZ-104, and this objective is where the exam checks that you can actually *administer* it, not just describe it. Expect hands-on stems: "bulk-create 200 users — what file format?", "the group must automatically contain everyone in Sales — what membership type and what license?", "a user in a licensed group shows a license error — why?", "guests must reset their own passwords — what do you configure?". The recurring traps are licensing (dynamic groups and group-based licensing both need **Entra ID P1**), the **usageLocation** property (no license assignment without it), and SSPR's special rules for administrators. Memorize the group type × membership type matrix, the Free/P1/P2 feature split, the CSV bulk operations, and the SSPR knobs (None/Selected/All, methods to register vs. reset, 180-day reconfirmation) — most questions are decided by exactly one of those facts.

## Create users and groups

Every identity in a tenant is one of two **user types**:

| User type | Who they are | Sign-in credentials | Default directory permissions |
|---|---|---|---|
| **Member** | Internal users who belong to your organization (created in your tenant or synced from on-premises AD) | An account in *your* tenant | Can read most directory information (users, groups) |
| **Guest** | External collaborators invited through **B2B collaboration** | Their *own* identity (home tenant, Microsoft account, Google, or one-time passcode) | **Limited** — cannot enumerate the full directory by default |

You can create users four ways, and the exam tests all of them:

- **Portal (single):** Microsoft Entra admin center → **Users** → **New user** — supply display name, **user principal name (UPN)** on a verified domain, and an initial password.
- **Portal (bulk):** **Users → Bulk operations** offers **Bulk create**, **Bulk invite**, and **Bulk delete** — each works the same way: **download the CSV template, fill it in, upload it**, and monitor progress under **Bulk operation results**. "Hundreds of users from a spreadsheet" always means the CSV bulk operations, never a script of one-off clicks.
- **PowerShell (Microsoft.Graph module):**

```powershell
Connect-MgGraph -Scopes "User.ReadWrite.All"
$PasswordProfile = @{ Password = "P@ssw0rd!2026"; ForceChangePasswordNextSignIn = $true }
New-MgUser -DisplayName "Dana Reyes" -UserPrincipalName "dana@contoso.com" `
  -MailNickname "dana" -AccountEnabled -PasswordProfile $PasswordProfile
```

- **Azure CLI:**

```bash
az ad user create --display-name "Dana Reyes" \
  --user-principal-name "dana@contoso.com" \
  --password "P@ssw0rd!2026"
```

Groups come in two **group types**, crossed with the membership types covered in the next section:

| | **Security group** | **Microsoft 365 group** |
|---|---|---|
| **Purpose** | Grant access to resources: role assignments, app access, licenses, policies | Collaboration: shared mailbox, calendar, SharePoint site, Teams team |
| **Can contain** | Users, devices, service principals, other groups | Users only |
| **Membership types supported** | Assigned, Dynamic User, **Dynamic Device** | Assigned, Dynamic User (**no** Dynamic Device) |
| **Restore after deletion** | **No** — deletion is permanent | Yes — restorable for 30 days |

```powershell
New-MgGroup -DisplayName "Sales Team" -MailEnabled:$false `
  -MailNickname "salesteam" -SecurityEnabled
```

```bash
az ad group create --display-name "Sales Team" --mail-nickname "salesteam"
```

Deleted **users** are soft-deleted and **restorable for 30 days** (portal: **Users → Deleted users**, or `Restore-MgDirectoryDeletedItem`); after 30 days they are permanently purged along with their licenses and group memberships.

> 💡 **Exam Tip:** "Create/invite/delete many users at once" = **Bulk operations with a CSV template** in the portal. "Scripted, repeatable creation" = **`New-MgUser`** (PowerShell) or **`az ad user create`** (CLI). If the group must contain *devices* or be nested inside another group, it must be a **security group**.

> ⚠️ **Common Pitfall:** The 30-day restore window applies to **users and Microsoft 365 groups — not security groups**. Deleting a security group is permanent, and every role assignment, license, and access grant tied to it dies with it. Also, a UPN must use a **verified domain** in the tenant; `user@contoso.com` fails if only `contoso.onmicrosoft.com` is verified.

## Manage user and group properties

- **What it is:** The day-two work of identity administration — editing user profile attributes (job title, department, contact info, **usageLocation**), transferring group ownership, and choosing how a group's membership is populated.
- **Why it matters:** Properties drive automation: dynamic groups filter on attributes, group-based licensing fails without **usageLocation**, and a wrong department value can silently pull a user out of every group (and license) that depends on it.

The property questions on the exam almost always resolve to the group's **membership type**:

| Membership type | How members get in | License required | Available on |
|---|---|---|---|
| **Assigned** | An owner or admin adds each member manually | Free | Security and Microsoft 365 groups |
| **Dynamic User** | A rule over **user attributes** evaluates automatically | **Entra ID P1** | Security and Microsoft 365 groups |
| **Dynamic Device** | A rule over **device attributes** evaluates automatically | **Entra ID P1** | **Security groups only** |

**Dynamic membership rules** are attribute expressions evaluated continuously by the service — membership updates itself when attributes change, and you **cannot manually add or remove members** of a dynamic group:

```
(user.department -eq "Sales")
(user.department -eq "Sales") -and (user.country -eq "US")
(device.deviceOSType -eq "Windows")
```

A single group's rule targets users **or** devices, never both. Converting a group from Assigned to Dynamic causes the rule to take over — existing manually-added members who don't match the rule are removed on the next evaluation.

Editing properties is routine but scriptable:

```powershell
Update-MgUser -UserId "dana@contoso.com" -Department "Sales" -UsageLocation "US"
Update-MgGroup -GroupId $groupId -Description "US field sales"
```

Finally, **administrative units (AUs)** solve the delegation problem: an AU is a container of users, groups, and devices that **scopes a role assignment to just that subset** of the directory. Assign someone **User Administrator** over the "Seattle" AU and they can reset passwords and edit properties for Seattle users only — not the whole tenant.

> 💡 **Exam Tip:** "Group membership must update automatically based on department/location/job title" = **Dynamic User** membership + a rule like `(user.department -eq "Sales")` + an **Entra ID P1** license. "Help desk should manage only one office's users" = put those users in an **administrative unit** and assign the role scoped to it.

> ⚠️ **Common Pitfall:** **Microsoft 365 groups do not support Dynamic Device membership** — if the scenario auto-groups Windows devices for policy targeting, the answer must be a **security group** with a Dynamic Device rule. And remember dynamic groups are hands-off: a stem that says "the admin adds one extra user to the dynamic group" describes something that isn't possible.

## Manage licenses in Microsoft Entra ID

- **What it is:** Assigning product licenses (Entra ID P1/P2, Microsoft 365, etc.) to users — either directly, or via **group-based licensing**, where a license attached to a group flows to every member automatically.
- **Why it matters:** Licenses gate features the rest of this chapter depends on, and group-based licensing turns joiner/mover/leaver churn into a non-event: join the group, get the license; leave the group, lose it.

First, know which tier unlocks what:

| Feature | **Entra ID Free** | **Entra ID P1** | **Entra ID P2** |
|---|---|---|---|
| User/group management, SSO, basic reports | ✔ | ✔ | ✔ |
| Dynamic groups, group-based licensing | — | ✔ | ✔ |
| SSPR for cloud users / on-prem writeback | — | ✔ | ✔ |
| Conditional Access | — | ✔ | ✔ |
| **Privileged Identity Management (PIM)** | — | — | ✔ |
| **Identity Protection** (risk-based policies) | — | — | ✔ |

Memorize the one-liner: **P2 = P1 + PIM + Identity Protection.**

**Group-based licensing** mechanics the exam tests:

- Requires **Entra ID P1** (or above) — and works best with an **assigned or dynamic security group**.
- Every user receiving a license **must have the `usageLocation` property set** (a two-letter country code) — Microsoft cannot legally provision services without knowing where the user is. Missing usageLocation = the assignment **fails for that user**.
- **License errors surface per user**, not per group. The group's **Licenses → Errors** view lists exactly who failed and why. Common error states:

| Error | Cause | Fix |
|---|---|---|
| **CountViolation** | Not enough purchased licenses for all members | Buy more seats or shrink the group |
| **MutuallyExclusiveViolation** | Conflicting/duplicate service plans from another license | Remove the conflicting direct or inherited license |
| **ProhibitedInUsageLocationViolation** | The product is not available in the user's usageLocation | Correct the usageLocation or choose another SKU |

- A user can hold the **same license both directly and inherited from a group** — removing the direct assignment then leaves the inherited one intact (this is the recommended migration path from direct to group-based licensing).
- Removing a user from the group removes the inherited license (and its service data grace period begins).

```powershell
Update-MgUser -UserId "dana@contoso.com" -UsageLocation "US"
$sku = Get-MgSubscribedSku | Where-Object SkuPartNumber -eq "ENTERPRISEPREMIUM"
Set-MgUserLicense -UserId "dana@contoso.com" `
  -AddLicenses @(@{SkuId = $sku.SkuId}) -RemoveLicenses @()
```

> 💡 **Exam Tip:** "Users hired into the Sales department should automatically receive Microsoft 365 licenses" = a **dynamic security group** on `(user.department -eq "Sales")` with **group-based licensing** — both features together require **P1**. If a stem mentions a license assignment failing for *one* member of a licensed group, check **usageLocation** first.

> ⚠️ **Common Pitfall:** Group-based licensing failures are **per user and silent** — the group assignment "succeeds" while individual members sit in an error state until you open the errors blade. Don't pick answers that claim the whole group assignment is rejected; Azure assigns to everyone it can and flags the rest.

## Manage external users

- **What it is:** **B2B collaboration** — inviting partners, vendors, and consultants into your tenant as **guest users** identified by their **email address**, so they authenticate with their *own* credentials while you govern what they can touch.
- **Why it matters:** No shadow accounts, no password sprawl: the partner's home organization keeps the credential and its lifecycle, while your tenant keeps the access control.

The lifecycle the exam expects you to know:

1. **Invite:** Portal (**Users → New user → Invite external user**), **Bulk invite** via the CSV template for many guests at once, or programmatically:

```powershell
New-MgInvitation -InvitedUserEmailAddress "pat@fabrikam.com" `
  -InviteRedirectUrl "https://myapps.microsoft.com" -SendInvitationMessage
```

2. **Redemption:** The guest receives the invitation email and completes the **redemption process** — consenting to your organization's terms and signing in with their home tenant account, Microsoft account, federated Google identity, or an emailed **one-time passcode** if they have none of those. Until redemption, the guest object shows a pending acceptance state.
3. **Use:** The redeemed guest appears in your directory with **UserType = Guest** (the UPN contains `#EXT#`), can be added to groups, assigned to apps, and included in Conditional Access and access reviews.

Governance controls to remember:

- **Guests get limited default permissions:** they can see their own profile and objects they're granted, but **cannot enumerate users, groups, or apps** in the directory. Guest access restrictions can be tightened further (or relaxed) tenant-wide.
- **External collaboration settings** control *who may invite* (everyone, members, only admins and the **Guest Inviter** role, or no one) and impose **allow/deny lists of collaboration domains** (e.g., allow only `fabrikam.com`).
- Find them fast: `az ad user list --filter "userType eq 'Guest'"`.

> 💡 **Exam Tip:** "External partner must access an app using **their own credentials**" = **B2B collaboration guest invitation**. "Only allow invitations to specific partner domains" = **external collaboration settings** with a domain allowlist. Bulk partner onboarding = **Bulk invite + CSV**.

> ⚠️ **Common Pitfall:** Inviting a guest does **not** grant access to anything — redemption only creates the guest object; you must still add them to groups or apps. And don't confuse the *guest's* limited **directory** permissions with resource permissions: a guest added to a group with a role assignment gets that role's full power on those resources.

## Configure self-service password reset (SSPR)

- **What it is:** A policy that lets users **reset their own forgotten passwords** (and unlock accounts) after proving their identity with pre-registered **authentication methods** — no help desk ticket required.
- **Why it matters:** Password resets are the classic #1 help desk cost; SSPR eliminates them, and the exam tests every knob on its configuration blade.

**Enablement** (Entra admin center → **Password reset → Properties**) has exactly three settings:

| Setting | Effect |
|---|---|
| **None** | SSPR disabled for regular users (default) |
| **Selected** | Enabled only for members of one specific group you choose (pilot pattern) |
| **All** | Enabled for every user in the tenant |

Licensing: **SSPR for cloud users requires Entra ID P1**, and hybrid **on-premises password writeback** (via Entra Connect, so a cloud reset updates on-prem AD) **also requires P1**.

**Authentication methods** users can register, and the two counts you configure:

- Methods: **mobile app notification** (Authenticator push), **mobile app code** (verification code), **email**, **mobile phone** (SMS/call), **office phone**, and **security questions** — with the hard rule that **security questions are never available to administrator accounts**.
- **Number of methods required to register** vs. **number required to reset**: you set how many a user must have on file, and separately whether a reset demands **one or two** of them. Two-gate resets (e.g., app code *and* SMS) are the security-conscious answer.

**Registration:** with "Require users to register when signing in" enabled, unregistered users are **prompted at sign-in** and periodically asked to **reconfirm their methods — default every 180 days** (settable 0–730; 0 disables reconfirmation).

**Notifications:** two switches — **notify users on their own password resets** (an email to the user, so a hijacked reset doesn't go unnoticed), and optionally **notify all admins when another admin resets their own password**.

**Administrator accounts are special:** admins get SSPR **enforced automatically with a two-method (two-gate) policy regardless of the None/Selected/All setting**, and the weaker methods (security questions, office phone) are off the table for them.

> 💡 **Exam Tip:** "Pilot SSPR for one department first" = **Selected** + that department's group. "Users must re-verify their methods twice a year" = the **reconfirmation period**, default **180 days**. "A cloud password reset must update on-premises AD" = **password writeback** (Entra Connect + **P1**).

> ⚠️ **Common Pitfall:** Setting SSPR to **None** does *not* exempt administrators — admin accounts always have SSPR with **two methods enforced**, and **security questions can never be one of them**. Conversely, don't hand "All users can use security questions" to a stem involving Global Admins; the platform will refuse.

## How It Fits Together (mental model)

Contoso onboards a 300-person sales acquisition in one morning: HR exports a spreadsheet, an admin runs **Bulk create** with the **CSV template** (scripting the stragglers with **`New-MgUser`** and **`az ad user create`**), and every new **member** user lands in the tenant with `department = Sales` and **usageLocation** set to US. A **security group** with **Dynamic User** membership — rule `(user.department -eq "Sales")`, which requires **Entra ID P1** — picks them up automatically, and because the tenant runs **P2** (adding **PIM** and **Identity Protection** on top of P1), **group-based licensing** on that group flows Microsoft 365 licenses to each member, with the two hires whose **usageLocation** was missed surfacing as **per-user license errors** in the group's error blade. A second security group with a **Dynamic Device** rule (something a **Microsoft 365 group** could never do) sweeps their Windows laptops into policy scope, while an **administrative unit** for the Sales region lets the regional help desk hold **User Administrator** rights over only those users. The acquisition's outside consultants aren't given accounts at all — they're **B2B collaboration guests**, **bulk-invited** by email against a **domain allowlist**, completing the **redemption process** with their own credentials and receiving only **limited default directory permissions**. Finally IT flips **SSPR** from **Selected** (the pilot group) to **All**: users register **two authentication methods** at sign-in, reconfirm every **180 days**, get **notified of their own resets**, and the admins — whose accounts have **two-gate SSPR enforced regardless**, with **security questions barred** — enable **password writeback** so resets flow back to on-prem AD. When someone fat-fingers a **Bulk delete**, the affected users are calmly restored from the **30-day deleted-users window** — a safety net the permanently-deleted security group they also removed did not enjoy.
