# Objective 1.3 — Manage Azure subscriptions and governance

Governance questions on AZ-104 are less about definitions and more about *choosing the right control for the job* — and knowing exactly what each control can and cannot do. The exam repeatedly probes three boundary lines: **Azure Policy** controls *what* can be deployed (regardless of who), **RBAC** controls *who* can do what, and **resource locks** stop *everyone* — even Owners — from a specific operation. Around those, memorize the hard numbers (50 tags per resource, 6 levels of management-group depth, 10,000 management groups per directory), the behaviors that surprise people (budgets alert but never stop spending; tags are not inherited; a ReadOnly lock breaks operations that are secretly writes), and the CLI/PowerShell verbs for each task — AZ-104 is a hands-on admin exam and drag-the-command questions are common.

## Implement and manage Azure Policy

- **What it is:** **Azure Policy** is the governance service that evaluates resources against **policy definitions** — JSON **if/then rules** ("*if* a resource matches these conditions, *then* apply this effect") — and reports or enforces **compliance** at scale.
- **Why it matters:** It is how an administrator guarantees standards ("only these regions," "every resource must carry a CostCenter tag," "no public IPs") across hundreds of subscriptions without reviewing each deployment by hand.

Each definition ends in exactly one **effect**:

| Effect | What it does | Needs managed identity? |
|---|---|---|
| **Deny** | Blocks the create/update request outright | No |
| **Audit** | Allows the operation but flags the resource **non-compliant** in the activity/compliance view | No |
| **Append** | Adds fields to the resource during creation/update (e.g., add allowed IP ranges to a storage account) | No |
| **Modify** | Adds, updates, or removes properties **or tags** during creation/update — and on existing resources via remediation | **Yes** |
| **AuditIfNotExists** | Flags a resource non-compliant if a *related* resource (e.g., a diagnostic setting) is missing | No |
| **DeployIfNotExists** | Deploys the missing related resource after creation (e.g., install an extension, create a diagnostic setting) | **Yes** |
| **Disabled** | Turns evaluation off — useful for testing a definition without enforcing it | No |

- An **initiative** (also called a **policy set definition**) is a **group of policy definitions assigned together** as a single unit — assign one initiative (e.g., a regulatory-compliance baseline) instead of dozens of individual policies, and track one compliance score.
- **Assignments** apply a definition or initiative at a **scope**: a **management group**, a **subscription**, or a **resource group**. You can carve out **exclusions** (sub-scopes the assignment never touches) and grant **exemptions** (time-boxed, documented waivers for specific resources that stay visible in compliance reporting).
- **DeployIfNotExists** and **Modify** perform actions on your behalf, so their assignments require a **managed identity** with the right RBAC roles; to fix resources that *already existed* before the assignment, you must run a **remediation task** — policy does not retroactively change anything on its own.
- Existing resources that violate a new **Deny** policy are only **flagged non-compliant** — Azure Policy **never deletes or alters existing resources** unless you explicitly remediate with Modify/DeployIfNotExists.
- The dividing line the exam loves: **Policy controls WHAT can be deployed regardless of who is deploying; RBAC controls WHO can perform which actions.** A user with Owner rights is still blocked by a Deny policy.

```bash
# Assign a built-in policy (require a tag) at a resource group, with parameters
az policy assignment create --name require-costcenter \
  --policy "Require a tag on resources" \
  --scope "/subscriptions/<sub-id>/resourceGroups/rg-prod" \
  --params '{ "tagName": { "value": "CostCenter" } }'

# Remediate existing resources under a DeployIfNotExists/Modify assignment
az policy remediation create --name fix-tags \
  --policy-assignment require-costcenter --resource-group rg-prod
```

```powershell
New-AzPolicyAssignment -Name require-costcenter -PolicyDefinition $def -Scope $rgId
Start-AzPolicyRemediation -Name fix-tags -PolicyAssignmentId $assignment.PolicyAssignmentId
```

> 💡 **Exam Tip:** Match the verb in the stem to the effect: "prevent/block" = **Deny**, "report/flag only" = **Audit**, "automatically install/create the missing X" = **DeployIfNotExists**, "automatically add or fix a tag/property" = **Modify**, "check that a related resource exists" = **AuditIfNotExists**. "Assign multiple policies as one unit" = **initiative**. And if the effect *does* something (Modify, DeployIfNotExists), the answer almost always also needs a **managed identity** and a **remediation task**.

> ⚠️ **Common Pitfall:** Assigning a Deny policy does **not** delete or break the resources that already violate it — they are only marked **non-compliant**. Conversely, don't reach for RBAC when the requirement is "no one — regardless of role — may create resource type X": that's Policy. RBAC can't express "what," only "who."

## Configure resource locks

- **What they are:** **Resource locks** are safety switches applied at a subscription, resource group, or resource that block destructive operations **for everyone — including Owners** — until the lock is removed.
- **Why they matter:** RBAC can't protect a resource from an authorized user's mistake; a lock can. They are the standard answer to "prevent accidental deletion."

| Lock level | Portal name | Blocks | Still allowed |
|---|---|---|---|
| **CanNotDelete** | **Delete** lock | Delete operations | Read and modify |
| **ReadOnly** | Read-only lock | Delete **and** any modify/write | Read only |

- Locks are **inherited by child scopes**: a lock on a resource group protects every resource inside it; a lock on a subscription protects everything below. The **most restrictive** lock in the inheritance chain wins.
- Locks apply **regardless of RBAC role** — an Owner who needs to delete a locked resource must first **remove the lock**, then delete. Managing locks requires `Microsoft.Authorization/locks/*` permissions, held by **Owner** and **User Access Administrator** (or a custom role).
- **ReadOnly** is sneakier than it sounds: it blocks every request Azure classifies as a write, and some "read-looking" operations are really **POST** calls. The classic example: **listing storage account keys is a POST operation**, so a ReadOnly lock on a storage account breaks key listing (and therefore any tool that authenticates with keys). ReadOnly locks can similarly break VM restarts, disk operations, and App Service tooling.

```bash
az lock create --name NoDelete --lock-type CanNotDelete --resource-group rg-prod
az lock list --resource-group rg-prod --output table
az lock delete --name NoDelete --resource-group rg-prod
```

```powershell
New-AzResourceLock -LockName NoDelete -LockLevel CanNotDelete -ResourceGroupName rg-prod
Remove-AzResourceLock -LockName NoDelete -ResourceGroupName rg-prod
```

> 💡 **Exam Tip:** "Prevent accidental **deletion** but still allow changes" = **CanNotDelete**. "Prevent **any** change" = **ReadOnly**. "An Owner cannot delete resource X — why?" = a lock exists somewhere up the scope chain and must be **removed first**. Locks beat RBAC every time.

> ⚠️ **Common Pitfall:** A ReadOnly lock is not harmless observation mode — because operations like **listing storage account keys are POSTs**, ReadOnly can break running workloads. If a stem says "after applying a lock, the app can no longer retrieve storage keys," the answer is the **ReadOnly** lock, not a permissions problem.

## Apply and manage tags on resources

- **What they are:** **Tags** are **name/value pairs** (e.g., `CostCenter = 1234`, `Env = Prod`) attached to resources, resource groups, and subscriptions to add organizational metadata — up to **50 tags per resource or resource group**.
- **Why they matter:** Tags are the backbone of cost reporting and operational filtering: **Cost Management** can **group and filter costs by tag**, and automation can target resources by tag instead of by name.

- Tags are **NOT inherited** from the resource group or subscription by default — tagging `rg-prod` does nothing to the VMs inside it. To propagate tags downward, assign a built-in **Azure Policy with the Modify effect** (e.g., "Inherit a tag from the resource group"), plus a **remediation task** for existing resources.
- Tag names are case-insensitive for operations (values are stored as provided), and not every resource type supports tags. Applying tags requires write access to the resource — or the narrowly scoped **Tag Contributor** built-in role, which can tag without other permissions.
- The command-line trap: some update commands **replace** the entire tag set, wiping tags you didn't mention. Use a **Merge** operation to add without destroying.

```bash
# Merge (add/update) tags without erasing existing ones
az tag update --resource-id $id --operation Merge --tags Env=Prod CostCenter=1234

# Careful: this REPLACES all tags on the group with just this one
az group update --name rg-prod --tags Env=Prod
```

```powershell
Update-AzTag -ResourceId $id -Tag @{ Env = "Prod"; CostCenter = "1234" } -Operation Merge
```

> 💡 **Exam Tip:** The numbers to know: **50 tags per resource**, name/value pairs, grouped in **Cost Management cost analysis** for chargeback. "Make child resources automatically receive the resource group's tag" = **Policy Modify effect** ("Inherit a tag...") with a **remediation task** — never "tags inherit automatically."

> ⚠️ **Common Pitfall:** Assuming tag inheritance. Tags on a resource group or subscription do **not** flow to the resources inside — the exam presents this as "the VM shows no CostCenter tag even though its resource group has one," and the fix is a Modify policy, not re-tagging by hand.

## Manage resource groups

- **What they are:** A **resource group (RG)** is the **lifecycle container** for resources: everything inside is deployed, managed, secured, and — critically — **deleted together**.
- **Why they matter:** RG design determines the blast radius of a delete, the natural scope for RBAC/Policy/locks, and how easily you can tear down or move an environment.

- **Deleting a resource group deletes every resource inside it** — the single most-tested RG fact. There is no undo.
- The RG's **location only stores its metadata**; the resources inside can live in **any region**. A resource group in East US can happily contain VMs in West Europe.
- Every resource belongs to **exactly one** resource group, but resources can be **moved** between resource groups — and between **subscriptions** — with `az resource move` / `Move-AzResource`:
  - During the move, **both the source and destination resource groups are locked** — no add/update/delete operations in either group until the move completes (reads still work).
  - **Some resource types cannot move** (check the move-support matrix; classic examples include certain networking and Entra-integrated resources), and cross-subscription moves require both subscriptions in the same Entra tenant. Use the **validate move** operation to test before committing.
  - Moving a resource does **not** change its region — only its management container.

```bash
az group create --name rg-prod --location eastus
az resource move --destination-group rg-archive --ids $resourceId
az resource move --destination-group rg-new --destination-subscription-id $sub2 --ids $resourceId
az group delete --name rg-old --yes --no-wait
```

```powershell
New-AzResourceGroup -Name rg-prod -Location eastus
Move-AzResource -DestinationResourceGroupName rg-archive -ResourceId $resourceId
Remove-AzResourceGroup -Name rg-old -Force
```

> 💡 **Exam Tip:** "Delete an entire environment in one operation" = delete the **resource group**. "Can a resource in West Europe live in an RG located in East US?" = **yes** — RG location is **metadata only**. "During a move, can you modify resources in the source group?" = **no** — both source **and destination** groups are locked for writes.

> ⚠️ **Common Pitfall:** Assuming everything can move. Not all resource types support `move`, and moving between subscriptions has extra constraints (same tenant, dependent resources often must move together). Validate first — and remember a move never relocates the resource to a different *region*.

## Manage subscriptions

- **What it is:** A **subscription** is a **billing boundary and an access-management boundary**: costs accrue per subscription, and it is a top-level scope for RBAC and Policy beneath management groups.
- **Why it matters:** Subscriptions are how admins separate environments (prod vs. dev), teams, and invoices — and they are the unit you place into a management-group hierarchy.

- A subscription trusts exactly one Microsoft Entra tenant, and sits under **exactly one management group parent** at a time (the **tenant root management group** by default until you move it).
- Subscriptions can be **transferred** — billing ownership to another account, or the subscription to a different Entra directory — without redeploying resources. Common offer types include Enterprise Agreement, Pay-As-You-Go, and CSP; limits/quotas (e.g., vCPU quotas) are tracked **per subscription, per region** and raised via support request.
- Day-to-day admin work: list subscriptions, switch the active context, and move a subscription between management groups.

```bash
az account list --output table
az account set --subscription "Production"
az account management-group subscription add --name mg-corp --subscription $subId
```

```powershell
Get-AzSubscription
Set-AzContext -Subscription "Production"
New-AzManagementGroupSubscription -GroupName mg-corp -SubscriptionId $subId
```

> 💡 **Exam Tip:** Subscription = **billing + access boundary**. When a scenario needs separate invoices, separate quota pools, or a hard blast-radius wall between environments, the answer is **separate subscriptions** — resource groups alone don't separate billing. A subscription always has **one** management-group parent.

> ⚠️ **Common Pitfall:** Confusing scopes: management group > subscription > resource group > resource. RBAC and Policy can be assigned at any of them, but *billing* rolls up per **subscription** — you cannot split an invoice by resource group without using **tags/cost analysis** to break it down.

## Manage costs by using alerts, budgets, and Azure Advisor recommendations

- **What it is:** **Microsoft Cost Management** provides **cost analysis** (explore and break down actual spend), **budgets** (thresholds with alerts), and **cost alerts**; **Azure Advisor** layers on personalized recommendations.
- **Why it matters:** The admin exam tests whether you know which tool *observes*, which *alerts*, and which *recommends* — and that none of them silently stops spending.

- **Budgets** are set per scope (management group, subscription, or resource group) with alert **thresholds** based on **actual** cost ("we have spent 80%") or **forecasted** cost ("we are projected to exceed 100%"). Crossing a threshold fires notifications (email, and **action groups** on supported scopes) — but a budget **never stops or throttles spending on its own**. To take hard action (shut down VMs, disable a subscription's deployments), pair the budget alert with an **action group** triggering **Azure Automation runbooks**, **Logic Apps**, or **Functions**.
- **Cost analysis** slices accumulated and forecasted costs **by tag, resource group, service, subscription, region**, and more — this is where tags pay off for chargeback/showback. Exports can push daily cost data to a storage account for external tooling.
- **Azure Advisor** analyzes your usage and gives free recommendations across five categories: **Cost** (e.g., right-size or shut down underutilized VMs, buy reservations), **Security**, **Reliability**, **Operational excellence**, and **Performance**. Cost questions ("how do you identify underutilized VMs?") point at Advisor, not Cost Management.

```bash
az consumption budget create --budget-name monthly-prod --amount 5000 \
  --category cost --time-grain monthly \
  --start-date 2026-08-01 --end-date 2027-07-31
az advisor recommendation list --category Cost --output table
```

```powershell
New-AzConsumptionBudget -Name monthly-prod -Amount 5000 -Category Cost -TimeGrain Monthly `
  -StartDate 2026-08-01 -EndDate 2027-07-31
Get-AzAdvisorRecommendation -Category Cost
```

> 💡 **Exam Tip:** Sort the stems: "alert me at 80% of planned spend" = **budget** with a threshold (choose **forecasted** if it says "projected/expected to exceed"); "break down last month's spend by department" = **cost analysis grouped by tag**; "recommend cheaper VM sizes / identify idle resources" = **Azure Advisor (Cost)**. Advisor's five categories — **Cost, Security, Reliability, Operational excellence, Performance** — are fair game as a list question.

> ⚠️ **Common Pitfall:** Believing a budget enforces a cap. Budgets are **alert-only** — spending sails right past 100% unless *you* wired an **action group + automation** to react. Any answer implying "the budget stopped the deployment" is wrong.

## Configure management groups

- **What they are:** **Management groups (MGs)** are containers **above subscriptions** that let you apply governance — **RBAC role assignments and Azure Policy** — once, and have it **inherit down to every subscription** (and everything inside them) below.
- **Why they matter:** With tens or hundreds of subscriptions, per-subscription assignments don't scale; the MG hierarchy is the enterprise-scale answer.

| Fact | Value |
|---|---|
| Top of the hierarchy | **Tenant root management group** (above all other MGs; cannot be deleted or moved) |
| Maximum depth | **Six levels** — *not counting* the tenant root or the subscription level |
| Parents | Each MG and each subscription has **exactly one parent** |
| Scale | Up to **10,000 management groups** per Microsoft Entra directory |
| Inheritance | **RBAC + Policy assigned at an MG apply to every subscription (and resource) beneath it** |

- A common design: tenant root → `mg-platform` / `mg-landing-zones` → per-department or per-environment MGs → subscriptions. Assign broad guardrails (allowed regions, required tags, security baselines) high, and looser or team-specific policy lower.
- Because assignments inherit, granting **Owner** at an MG makes someone Owner of *every* subscription below — treat high-level MG assignments as crown jewels. By default, working with MGs may require elevating access or holding roles at the root (a Global Administrator can elevate to **User Access Administrator** at root scope when locked out).

```bash
az account management-group create --name mg-corp --display-name "Corp" --parent mg-root
az account management-group subscription add --name mg-corp --subscription $subId
az account management-group list --output table
```

```powershell
New-AzManagementGroup -GroupName mg-corp -DisplayName "Corp" -ParentId $rootId
New-AzManagementGroupSubscription -GroupName mg-corp -SubscriptionId $subId
```

> 💡 **Exam Tip:** "Apply a policy/role assignment to **many subscriptions at once**" = assign it at a **management group** — inheritance does the rest. Memorize the trio of numbers: **six levels deep** (excluding root and subscriptions), **one parent** each, **10,000 MGs** per directory, all under the **tenant root management group**.

> ⚠️ **Common Pitfall:** Counting the depth wrong. The six-level limit does **not** include the tenant root MG at the top or the subscription level at the bottom. And a subscription cannot live in two MGs "for two policy sets" — it has exactly **one parent**; layer policy via the hierarchy instead.

## How It Fits Together (mental model)

Picture Contoso onboarding fifty teams to Azure. Under the **tenant root management group**, admins build a **management group** hierarchy (well inside the **six-level** limit), because **RBAC** and **Azure Policy** assigned at an MG **inherit to every subscription** below — each **subscription** being its own **billing and access boundary** with **exactly one parent** MG. At the top they assign an **initiative** bundling **policy definitions**: a **Deny** effect blocks disallowed regions no matter *who* deploys (Policy governs **what**; **RBAC** governs **who**), an **Audit** effect flags legacy resources as **non-compliant** without touching them, and a **Modify** effect — running as a **managed identity** with a **remediation task** — makes every resource **inherit the CostCenter tag** from its **resource group**, since **tags** (name/value pairs, **50 per resource**) are **not inherited by default**. Each team gets a **resource group** as its **lifecycle container** — its **location is metadata only** — knowing that **deleting the RG deletes everything inside**, which is why production carries a **CanNotDelete** lock (and one storage account learned that a **ReadOnly** lock breaks **listing storage keys**, a POST). When a project migrates, `az resource move` shifts resources to another subscription while **both source and destination groups are locked**. Finance sets **budgets** with **actual and forecasted thresholds** — which **alert but never stop spending**, so an **action group** triggers automation for hard stops — slices spend **by tag** in **cost analysis**, and works through **Azure Advisor** recommendations across **Cost, Security, Reliability, Operational excellence, and Performance**.
