# Objective 2.3 — Configure Azure Files and Azure Blob Storage

This objective is where AZ-104 stops asking "what is storage?" and starts asking "you are the admin — make it work." Expect scenarios about a file share that won't mount (port **445** blocked), a public container that stays private no matter what you click (account-level anonymous access disabled), an archived blob a user needs *today* (rehydration priority), and lifecycle rules that must tier data down on a schedule without breaking retention minimums. Memorize the numbers cold: SMB port 445, 100 TiB standard share limit, 200 snapshots per share, 1–365 day soft-delete retention windows, the 30/90/180-day tier minimums, and the 15-hour vs. under-1-hour rehydration priorities. Then know which knob lives at the *account* level (default tier, versioning, soft delete, anonymous access) versus the *share/container/blob* level (share tier, container access level, per-blob tier, snapshots) — misplacing the setting is how the exam catches you.

## Create and configure a file share in Azure Storage

- **What it is:** An **Azure Files** share is a fully managed cloud file share inside a storage account, mountable over **SMB** or **NFS 4.1** like a traditional network drive — no file server to build or patch.
- **Why it matters:** It's the lift-and-shift answer for apps that expect a mapped drive, and the AZ-104 exam drills the operational details: protocols, ports, quotas, tiers, and mount commands.

Key configuration facts:

- **Protocols:** **SMB** (Windows/Linux/macOS) travels over **TCP port 445**. **NFS 4.1** is supported **only on premium (FileStorage) accounts** and only from trusted networks (no encryption in transit over the public internet), and an NFS share cannot also be SMB — the protocol is chosen at share creation.
- **Port 445 is the classic troubleshooting question:** many ISPs and corporate firewalls **block outbound 445**, so a share that mounts fine from an Azure VM fails from home or the office. Fixes: open 445, or tunnel over **VPN/ExpressRoute/private endpoint**.
- **Size and performance:** **standard** shares (GPv2 accounts) scale up to **100 TiB** (large file shares are standard on new accounts) with pay-as-you-go billing; **premium** shares (FileStorage accounts) use a **provisioned** model — you provision capacity/IOPS/throughput up front and pay for what you provision, not what you store.
- **Standard file share access tiers** (set *per share*, changeable later): **transaction optimized** (heavy churn — highest storage price, lowest transaction price), **hot**, and **cool** (team shares and archival — cheaper storage, pricier transactions). Premium is its own SSD-backed tier, chosen by account type, not a dropdown.
- **Quota:** each share has a quota (GiB) capping its size — raise it with no downtime.

Create and mount:

```bash
# CLI — create a share via the management plane (share-rm) with a tier and quota
az storage share-rm create \
  --resource-group rg-files --storage-account stcontosofiles \
  --name finance --quota 1024 --access-tier TransactionOptimized

# Change the tier later
az storage share-rm update --resource-group rg-files \
  --storage-account stcontosofiles --name finance --access-tier Cool
```

```powershell
# PowerShell equivalent
New-AzRmStorageShare -ResourceGroupName rg-files -StorageAccountName stcontosofiles `
  -Name finance -QuotaGiB 1024 -AccessTier TransactionOptimized
```

Mounting: the portal's **Connect** blade generates a ready-made script per OS. On Windows it wraps **`net use`** (or `New-PSDrive`); on Linux it uses **`mount.cifs`**:

```
# Windows — storage account key as the credential
net use Z: \\stcontosofiles.file.core.windows.net\finance /user:localhost\stcontosofiles <account-key>

# Linux
sudo mount -t cifs //stcontosofiles.file.core.windows.net/finance /mnt/finance \
  -o vers=3.1.1,username=stcontosofiles,password=<account-key>,serverino
```

Identity-based authentication (Microsoft Entra Domain Services, on-prem AD DS, or Entra Kerberos) replaces the storage key for user-level NTFS-style permissions — the key always grants full-share access.

> 💡 **Exam Tip:** "Users can mount the share from Azure VMs but not from the on-premises office/home" = **outbound TCP 445 is blocked** by the ISP or firewall. The answer is open 445 or use a **VPN/private endpoint** — not regenerating keys or changing tiers.

> ⚠️ **Common Pitfall:** **NFS 4.1 requires a premium FileStorage account.** If the scenario demands an NFS share on a Standard GPv2 account, that's the flaw — you must create a premium account. Also, a share is SMB *or* NFS, never both.

## Create and configure a container in Blob Storage

- **What it is:** A **container** is the folder-like grouping for **blobs** inside a storage account's blob service — every blob lives in exactly one container.
- **Why it matters:** The exam tests naming rules, the three **anonymous public access levels**, and the account-level switch that gates all of them.

Rules and settings:

- **Naming:** container names are **3–63 characters**, **lowercase** letters, numbers, and hyphens, starting with a letter or number. `MyContainer` is invalid — a favorite trick.
- **Anonymous access levels** (set per container):

| Level | Anonymous users can... | Typical use |
|---|---|---|
| **Private** (default) | Nothing — authentication required | Everything sensitive |
| **Blob** | Read **individual blobs** if they know the URL; **cannot list** the container | Public website images |
| **Container** | Read blobs **and enumerate (list)** the container's contents | Fully public datasets |

- **The account-level gate:** every container-level setting is subordinate to the storage account's **"Allow blob anonymous access"** property. It is **disabled by default on new accounts** — while disabled, all containers behave as Private no matter what level they're set to. This two-layer design is a prime exam scenario: "the container is set to Blob but anonymous requests fail — why?"
- **Blob types**, chosen at upload and not changeable afterward: **block blobs** (the default — documents, images, backups, uploaded in blocks), **append blobs** (optimized for append-only writes — logs, audit trails), and **page blobs** (512-byte pages for random read/write — the format behind **VHDs/unmanaged disks**). **Access tiers apply to block blobs only.**

```bash
# Allow anonymous access at the account, then create a public-read container
az storage account update --name stcontosoweb --resource-group rg-web \
  --allow-blob-public-access true

az storage container create --account-name stcontosoweb \
  --name images --public-access blob --auth-mode login
```

```powershell
New-AzStorageContainer -Name images -Context $ctx -Permission Blob
```

> 💡 **Exam Tip:** "Anonymous users must download blobs by URL but must **not** be able to list what's in the container" = access level **Blob**. If they must browse/enumerate, that's **Container**. And any "public access isn't working" stem = check the **account-level Allow blob anonymous access** switch first.

> ⚠️ **Common Pitfall:** Choosing the blob type wrong is permanent — you **cannot convert** an append blob to a block blob later; you re-upload. Logs = **append**, VHD/disk = **page**, everything else = **block**.

## Configure storage tiers

- **What they are:** Per-blob (block blobs only) **access tiers** trading storage price against access price and latency: **hot**, **cool**, **cold**, **archive**.
- **Why they matter:** AZ-104 goes beyond AZ-900's definitions into the admin mechanics — minimum durations, early-deletion fees, the account default, and **rehydration**.

| Tier | Minimum storage duration | Online? | Profile |
|---|---|---|---|
| **Hot** | none | Online | Highest storage cost, lowest access cost |
| **Cool** | **30 days** | Online | Infrequent access, instantly readable |
| **Cold** | **90 days** | Online | Rarer access, still instant |
| **Archive** | **180 days** | **Offline** | Cheapest storage; must **rehydrate** before reading |

- **Early deletion/tier-change fees:** delete a blob or move it to a different tier before its minimum (30/90/180 days) and you're billed a prorated **early deletion charge** for the remaining days. The exam frames this as "what is the cost consequence of moving a cool blob after 10 days?"
- **Account default tier:** the storage account's default access tier setting can be any **online tier — hot, cool, or cold** — but **archive is a per-blob (or per-lifecycle-rule) setting**, never the account default. Blobs uploaded without an explicit tier inherit the account default.
- **Archive is offline:** reads and downloads fail until the blob is **rehydrated** to an online tier. Two rehydration methods: **Set Blob Tier** back to hot/cool/cold (changes the blob in place), or **Copy Blob** to a *new* blob in an online tier (leaves the archived original untouched — no early-deletion fee on the source). Two priorities: **Standard** (may take **up to 15 hours**) and **High** (typically **under 1 hour for blobs under 10 GB**, at a premium price).

```bash
# Set a blob's tier / archive it
az storage blob set-tier --account-name stcontoso --container-name backups \
  --name db-2025.bak --tier Archive

# Rehydrate with high priority
az storage blob set-tier --account-name stcontoso --container-name backups \
  --name db-2025.bak --tier Hot --rehydrate-priority High

# Change the account default tier (an online tier — Hot, Cool, or Cold; never Archive)
az storage account update --name stcontoso --resource-group rg-data --access-tier Cool
```

> 💡 **Exam Tip:** "The archived blob is needed within the hour" = rehydrate with **High priority** (blob < 10 GB). "Read the data but keep the archived copy where it is" = **Copy Blob** to an online tier rather than Set Blob Tier.

> ⚠️ **Common Pitfall:** The account **default** access tier offers only the online tiers — **Hot, Cool, or Cold**. If an answer choice sets the account default to **Archive**, it's wrong — archive exists only per blob or via lifecycle rules.

## Configure snapshots and soft delete

- **What they are:** Two complementary recovery nets. **Snapshots** are **read-only point-in-time copies** you (or a tool) take deliberately; **soft delete** keeps deleted data recoverable for a retention window.
- **Why they matter:** "A user deleted/overwrote X — recover it" is a guaranteed exam scenario; the answer depends on *which* protection was enabled and *where*.

**Azure Files — share snapshots:**

- Read-only, point-in-time copies of an entire share, **up to 200 snapshots per share**; incremental (you're billed only for the differential).
- Restore **individual files** — from the portal, or on Windows straight from the **Previous Versions** tab of a mounted share.
- Azure Backup for Azure Files is built on share snapshots and adds scheduling and retention policies.

**Azure Files — soft delete for file shares:**

- Protects **the share itself** from deletion: retention **1–365 days**, and it is **enabled by default at 7 days** on new storage accounts. A soft-deleted share can be undeleted with all contents and snapshots intact.

**Blob snapshots vs. blob soft delete:**

- A **blob snapshot** is a **manual, per-blob** read-only copy tied to the base blob (contrast with versioning below, which is automatic).
- **Blob soft delete** retains deleted or overwritten blobs for **1–365 days**; undelete restores the blob **and its snapshots**. **Container soft delete is a separate setting** with its own 1–365 day retention — blob soft delete alone will *not* bring back a deleted container.

```bash
# Snapshot a file share / a blob
az storage share snapshot --account-name stcontosofiles --name finance
az storage blob snapshot --account-name stcontoso --container-name docs --name plan.docx

# Blob soft delete + container soft delete (account-level blob service properties)
az storage account blob-service-properties update \
  --account-name stcontoso --resource-group rg-data \
  --enable-delete-retention true --delete-retention-days 14 \
  --enable-container-delete-retention true --container-delete-retention-days 14

# File share soft delete
az storage account file-service-properties update \
  --account-name stcontosofiles --resource-group rg-files \
  --enable-delete-retention true --delete-retention-days 30
```

```powershell
Enable-AzStorageBlobDeleteRetentionPolicy -ResourceGroupName rg-data `
  -StorageAccountName stcontoso -RetentionDays 14
```

> 💡 **Exam Tip:** Map the loss to the protection: single file inside a share = **share snapshot** (Previous Versions); the whole share deleted = **file share soft delete**; a blob deleted = **blob soft delete**; a whole **container** deleted = **container soft delete** — each is its own checkbox.

> ⚠️ **Common Pitfall:** Retention windows are **1–365 days** everywhere, but only **file share soft delete is on by default (7 days)** for new accounts — blob and container soft delete must be enabled. And soft delete is time-boxed recovery, not backup: once retention lapses, the data is gone.

## Configure blob lifecycle management

- **What it is:** A rule-based policy engine (a **JSON** document of rules on the storage account) that automatically **tiers down or deletes** block blobs as they age.
- **Why it matters:** It's how the 30/90/180-day tier economics get enforced without an admin touching anything — and the exam loves asking you to read or assemble a rule.

Anatomy of a rule:

- **Filters:** **blob type** (blockBlob/appendBlob), name **prefix** (e.g., `logs/`), and **blob index tags**.
- **Actions:** **tierToCool**, **tierToCold**, **tierToArchive**, **delete** — applicable to base blobs, **previous versions, and snapshots** (so lifecycle rules are also the cleanup mechanism for versioning and snapshots).
- **Conditions:** **`daysAfterModificationGreaterThan`** (base blobs), **`daysAfterCreationGreaterThan`** (versions/snapshots), and **`daysAfterLastAccessTimeGreaterThan`** — the last-access condition **requires access tracking (last access time tracking) to be enabled** on the account first.
- **Timing:** the platform runs the policy **automatically, roughly once a day** — a new or changed policy can take **up to 24–48 hours** to take effect. "The rule was created but nothing moved yet" = wait; nothing is broken.

```json
{
  "rules": [{
    "name": "age-out-logs",
    "enabled": true,
    "type": "Lifecycle",
    "definition": {
      "filters": { "blobTypes": ["blockBlob"], "prefixMatch": ["logs/"] },
      "actions": {
        "baseBlob": {
          "tierToCool":    { "daysAfterModificationGreaterThan": 30 },
          "tierToArchive": { "daysAfterModificationGreaterThan": 180 },
          "delete":        { "daysAfterModificationGreaterThan": 2555 }
        },
        "snapshot": { "delete": { "daysAfterCreationGreaterThan": 90 } }
      }
    }
  }]
}
```

```bash
az storage account management-policy create --account-name stcontoso \
  --resource-group rg-data --policy @policy.json
```

> 💡 **Exam Tip:** "Tier blobs that haven't been **read** in 90 days" = `daysAfterLastAccessTimeGreaterThan` — and the trap is the prerequisite: **enable access tracking** on the account or the condition can't be used. "Haven't been **modified**" = `daysAfterModificationGreaterThan`, no prerequisite.

> ⚠️ **Common Pitfall:** Keep the tier minimums in mind when authoring rules: a rule that moves blobs to cool at day 5 and to archive at day 15 racks up **early tier-change fees** against the 30-day cool minimum. Align rule day-counts with the 30/90/180-day floors.

## Configure blob versioning

- **What it is:** **Blob versioning** automatically captures a **previous version of a blob on every overwrite or delete** — no manual step, unlike snapshots.
- **Why it matters:** It's the strongest built-in defense against accidental overwrite and ransomware-style corruption of blobs, and the exam contrasts it directly with snapshots and soft delete.

| Capability | **Blob snapshot** | **Blob versioning** |
|---|---|---|
| Trigger | **Manual** (you call snapshot) | **Automatic** on every write/delete |
| Scope | Per blob, on demand | All blobs in the account once enabled |
| Restore | Copy/promote the snapshot | Promote any previous version to current |
| Cleanup | Manual or lifecycle rules | Lifecycle rules on **previous versions** |

- Enabled at the **storage account** level; from then on, every overwrite preserves the prior state as a read-only **previous version** with a version ID, and deleting a blob keeps its versions.
- **Versioning + soft delete together** is Microsoft's recommended data-protection baseline: versioning preserves history; soft delete protects the versions themselves from permanent deletion during the retention window.
- Old versions bill as normal (tiereable) data — pair versioning with a **lifecycle rule** that tiers or deletes previous versions (`daysAfterCreationGreaterThan`) or costs balloon silently.

```bash
az storage account blob-service-properties update \
  --account-name stcontoso --resource-group rg-data --enable-versioning true
```

```powershell
Update-AzStorageBlobServiceProperty -ResourceGroupName rg-data `
  -StorageAccountName stcontoso -IsVersioningEnabled $true
```

> 💡 **Exam Tip:** "Automatically retain prior states of blobs whenever they are overwritten, with no admin action per blob" = **blob versioning**. If the stem says "point-in-time copy created on demand / by a script," that's a **snapshot**.

> ⚠️ **Common Pitfall:** Versioning is a **blob** feature — Azure **Files has no versioning**; its equivalents are **share snapshots** (up to 200) and soft delete. Cross-applying blob features to Files (or vice versa) is a standard wrong-answer pattern.

## How It Fits Together (mental model)

Picture Contoso's migration week. The admin creates a premium **FileStorage** account for the engineering **NFS 4.1** share and a Standard GPv2 account whose 100-TiB-capable **Azure Files** SMB share holds the finance drive on the **transaction optimized** tier; office users mount it via the portal-generated **net use** script — after the firewall team opens outbound **port 445**, which the ISP had blocked — while a Linux box uses **mount.cifs**. Nightly automation takes **share snapshots** (well under the **200-per-share** cap) so any file can be restored from **Previous Versions**, and **file share soft delete**, already on by default at **7 days**, is stretched to 30. On the blob side, a lowercase-named **container** called `images` gets access level **Blob** so the website can serve pictures anonymously — but only after flipping the account's **Allow blob anonymous access** switch, disabled by default. Logs land in **append blobs**, VHDs in **page blobs**, and everything else in **block blobs**, which start **hot** (the account **default access tier**), then a **lifecycle management** JSON rule — filtered by the `logs/` **prefix** — applies **tierToCool** at 30 days, **tierToCold** at 90, and **tierToArchive** at 180, honoring every minimum-duration floor and kicking in within the policy's daily run. When legal needs an archived blob, the admin **rehydrates** it with **high priority** and has it back **in under an hour**. Meanwhile **blob versioning** silently keeps a **previous version** on every overwrite, **blob soft delete** (and its separate sibling, **container soft delete**) holds deletions for 14 days, and the same lifecycle policy prunes old versions and **snapshots** so the safety nets never outgrow the budget.
