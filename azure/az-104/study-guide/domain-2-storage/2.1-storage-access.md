# Objective 2.1 — Configure access to storage

AZ-104 tests storage access as a layered defense problem: first the *network* layer (can the packet even reach the account?), then the *authorization* layer (what credential proves the request is allowed?). Expect scenario questions that make you pick between the three **public network access** modes, decide whether a subnet needs a **service endpoint** or a **private endpoint**, choose the right **SAS** type for a delegation requirement ("least privilege, revocable, no account key" is a giveaway), and sequence the three permission layers for **identity-based Azure Files** access (enable a source → RBAC on the share → NTFS ACLs on files). Memorize the SAS comparison table cold — account vs. service vs. user delegation is the single most-asked distinction in this objective — plus the revocation rules (regenerate the key, or edit the stored access policy) and the exact RBAC role names for SMB shares. Because this is a hands-on admin exam, also know the `az storage` commands that perform each action.

## Configure Azure Storage firewalls and virtual networks

- **What it is:** The **Azure Storage firewall** is a per-account network ACL that decides which sources may reach the account's **public endpoint**, controlled by the **public network access** setting plus lists of **virtual network rules** and **IP rules**.
- **Why it matters:** By default a new account answers to the entire Internet (authorization still required, but the door is reachable). Locking the network layer down is step one of least privilege — and the exam loves the side effects (locked-out portals, private IPs rejected, trusted services exceptions).

The **public network access** setting has three modes:

| Mode | Who can reach the public endpoint | Typical use |
|---|---|---|
| **Enabled from all networks** | Any source on the Internet (auth still required) | Default; public content, dev/test |
| **Enabled from selected virtual networks and IP addresses** | Only subnets and IP ranges you list, plus configured exceptions | Standard production posture |
| **Disabled** | No one — the public endpoint refuses all traffic | Private-endpoint-only designs |

Key mechanics of the "selected networks" mode:

- **Virtual network rules** grant access to specific **subnets**, and they ride on **service endpoints**: the subnet must have the **`Microsoft.Storage`** service endpoint enabled, which routes the subnet's storage traffic over the Azure backbone and presents its VNet/subnet identity to the firewall.
- **IP network rules** accept **public Internet IPv4 addresses or CIDR ranges only** — you cannot add private (RFC 1918) addresses like `10.0.0.0/8`, because traffic from inside Azure or over a service endpoint doesn't arrive with a private source IP the firewall could match. Private address rules are rejected.
- **Exceptions** can punch controlled holes: **"Allow Azure services on the trusted services list to access this storage account"** lets first-party services (Azure Backup, Azure Site Recovery, Log Analytics, and other trusted-list services) through even when their IPs aren't listed; a second exception allows read access to storage **logging and metrics** from any network.
- A **private endpoint** (Azure Private Link) gives the account a **private IP inside your VNet** and **bypasses the public firewall entirely** — firewall rules apply only to the public endpoint. The maximum-lockdown pattern is *public network access Disabled + private endpoints only*.

```bash
# Default-deny the public endpoint, then allow one subnet and one office IP range
az storage account update -g rg1 -n stacct1 --default-action Deny
az network vnet subnet update -g rg1 --vnet-name vnet1 -n subnet1 \
    --service-endpoints Microsoft.Storage
az storage account network-rule add -g rg1 --account-name stacct1 \
    --vnet-name vnet1 --subnet subnet1
az storage account network-rule add -g rg1 --account-name stacct1 \
    --ip-address 203.0.113.0/24
az storage account update -g rg1 -n stacct1 --bypass AzureServices
```

```powershell
Update-AzStorageAccountNetworkRuleSet -ResourceGroupName rg1 -Name stacct1 -DefaultAction Deny
Add-AzStorageAccountNetworkRule -ResourceGroupName rg1 -Name stacct1 `
    -VirtualNetworkResourceId $subnet.Id
Add-AzStorageAccountNetworkRule -ResourceGroupName rg1 -Name stacct1 -IPAddressOrRange "203.0.113.0/24"
```

> 💡 **Exam Tip:** Match the phrase to the mechanism: "allow only a specific **subnet**" = VNet rule + **Microsoft.Storage service endpoint** on that subnet; "allow the **office's public IP**" = IP rule; "Azure Backup must still work with the firewall on" = the **trusted services** exception; "no public exposure at all" = **Disabled** + **private endpoint**.

> ⚠️ **Common Pitfall:** Two classic traps. (1) IP rules take **public** ranges only — an answer adding `10.1.0.0/16` to the firewall is always wrong; use a VNet rule or private endpoint instead. (2) After you default-deny, *you* are outside the wall too: portal browsing of blobs and tools like Storage Explorer fail from unlisted networks. And remember a **private endpoint ignores the public firewall** — deny-all does not block private-endpoint traffic.

## Create and use shared access signature (SAS) tokens

- **What it is:** A **shared access signature (SAS)** is a signed URI query string that delegates limited, time-boxed access to storage resources without handing out the account keys — the token itself encodes exactly what the bearer may do.
- **Why it matters:** SAS is Azure's answer to "give this partner/app/customer access to *this* data, with *these* permissions, until *this* time" — and the exam tests which of the **three SAS types** fits a scenario and how (or whether) each can be revoked.

| | **Account SAS** | **Service SAS** | **User delegation SAS** |
|---|---|---|---|
| Signed with | **Storage account key** | Storage account key | **Microsoft Entra credentials** (a user delegation key) |
| Scope | Can span **Blob, File, Queue, Table** services and service-level operations | **One service** — a single blob, container, file, share, queue, or table | **Blob service only** (blobs and containers) |
| Stored access policy | Not supported | **Supported** — can be tied to a policy | Not supported |
| Max lifetime | Whatever expiry you set | Whatever expiry you set (unbounded when tied to a policy) | **7 days maximum** |
| Revocation | Regenerate the signing account key | Regenerate the key, **or** edit/delete its stored access policy | Revoke the user delegation key, or wait out ≤ 7 days |
| Security posture | Broadest blast radius | Narrower | **Most secure — no account key involved**; Microsoft's recommendation |

Every SAS specifies its grant in the token's query parameters:

- **Allowed services** (blob/file/queue/table — account SAS only) and **allowed resource types** (service, container, object).
- **Permissions** — the `racwdl` set: **read, add, create, write, delete, list** (plus service-specific extras like tag or filter operations).
- **Start and expiry times** (`st`/`se`) — keep windows short; clock skew means a start time of "now" can fail, so start a few minutes in the past.
- **Allowed IP addresses or range** (`sip`) and **allowed protocol** (`spr`) — require **HTTPS only** in practice.
- The **signature** (`sig`) — computed with one of the two account keys (key1 or key2); the token doesn't name the signing key, but *which* key signed it matters for rotation, below.

The hard rule the exam returns to repeatedly: **a SAS cannot be revoked directly**. It is a self-contained signed token — the service just validates the signature. Your only levers are:

1. **Regenerate the signing account key** — instantly invalidates **every** SAS signed with that key (a blunt instrument).
2. For a **service SAS tied to a stored access policy** — modify or delete the policy (surgical; next section).
3. For a **user delegation SAS** — revoke the user delegation key, or rely on the built-in **7-day cap** and the fact that removing the signer's RBAC permissions also cuts off access.

```bash
# Account SAS: blob+file services, read/list on containers and objects, 1 day, HTTPS only
az storage account generate-sas --account-name stacct1 --services bf \
    --resource-types co --permissions rl --expiry 2026-07-27T00:00Z --https-only

# Service SAS on one container, referencing a stored access policy
az storage container generate-sas --account-name stacct1 -n contracts --policy-name partner-read

# User delegation SAS (signed with your Entra login, not a key)
az storage blob generate-sas --account-name stacct1 -c contracts -n deal.pdf \
    --permissions r --expiry 2026-07-27T00:00Z --auth-mode login --as-user
```

PowerShell equivalents: `New-AzStorageAccountSASToken`, `New-AzStorageContainerSASToken`, and `New-AzStorageBlobSASToken` (pass a context created with `-UseConnectedAccount` for a user delegation SAS).

> 💡 **Exam Tip:** Decode the stem: "span multiple services" = **account SAS**; "single container, must be revocable later" = **service SAS + stored access policy**; "most secure / avoid storing account keys / Entra-signed" = **user delegation SAS** — and remember it is **blob-only** with a **7-day** ceiling.

> ⚠️ **Common Pitfall:** There is no "revoke SAS" button. If a token leaks and it wasn't policy-backed, your only remedy is **regenerating the account key that signed it** — which also kills every *legitimate* SAS signed with that key. That collateral damage is exactly why exam answers favor stored access policies and user delegation SAS.

## Configure stored access policies

- **What it is:** A **stored access policy** is a named set of SAS parameters (start, expiry, permissions) defined **on the resource itself** — a blob **container**, file **share**, **queue**, or **table** — that a **service SAS** references by identifier instead of embedding those values in the token.
- **Why it matters:** It converts an irrevocable token into a managed one: because the service re-reads the policy on every request, **changing the policy's expiry or permissions — or deleting it — immediately affects every SAS tied to it**, giving you after-the-fact control.

Mechanics to memorize:

- Up to **5 stored access policies per container** (the same limit applies per share, queue, and table).
- A service SAS may take each parameter from the policy or from the token, but **not both** — a token that duplicates a field the policy defines is invalid.
- To **revoke** issued tokens: delete the policy, or rename its identifier, or set its expiry to the past. To *extend or trim* access: edit the policy in place — no re-issuing required.
- Only **service SAS** can reference a policy; account SAS and user delegation SAS cannot.
- Policy changes can take **up to about 30 seconds** to propagate — tokens may work briefly after revocation.

```bash
# Create a policy on a container, issue a SAS against it, later revoke by deleting the policy
az storage container policy create --account-name stacct1 -c contracts \
    -n partner-read --permissions rl --expiry 2026-08-31T00:00Z
az storage container generate-sas --account-name stacct1 -n contracts --policy-name partner-read
az storage container policy delete --account-name stacct1 -c contracts -n partner-read
```

```powershell
New-AzStorageContainerStoredAccessPolicy -Container contracts -Policy partner-read `
    -Permission rl -ExpiryTime "2026-08-31" -Context $ctx
Set-AzStorageContainerStoredAccessPolicy -Container contracts -Policy partner-read `
    -ExpiryTime "2026-07-26" -Context $ctx   # shorten to now = revoke
```

> 💡 **Exam Tip:** Any stem shaped like "you must be able to **revoke or modify** access **after** the SAS URLs have already been distributed, **without regenerating account keys**" has one answer: issue **service SAS tokens tied to a stored access policy**, then edit or delete the policy.

> ⚠️ **Common Pitfall:** The **5-per-container** limit and the type restriction both get tested: you cannot attach a stored access policy to an **account SAS** or a **user delegation SAS**. If the scenario demands policy-based revocation, the SAS type in the answer must be a **service SAS**.

## Manage access keys

- **What they are:** Every storage account has **two 512-bit access keys — key1 and key2** — either of which grants full **Shared Key** authorization to everything in the account: data plane, all services, no scoping.
- **Why they matter:** The keys are **root-level access** to your data, they sign account and service SAS tokens, and the exam tests the zero-downtime rotation dance plus the modern guidance to minimize or disable key use altogether.

Why *two* keys? **Zero-downtime rotation.** The pattern:

1. Applications currently use **key1**. Point them at **key2**.
2. **Regenerate key1** (now nothing depends on it — no outage).
3. At the next rotation cycle, swap back: move apps to the fresh key1, regenerate key2.

```bash
az storage account keys list -g rg1 -n stacct1
az storage account keys renew -g rg1 -n stacct1 --key key1     # regenerate key1
```

```powershell
Get-AzStorageAccountKey -ResourceGroupName rg1 -Name stacct1
New-AzStorageAccountKey -ResourceGroupName rg1 -Name stacct1 -KeyName key1
```

Management options layered on top:

- **Key expiration policy / rotation reminders:** set a maximum key age on the account and Azure surfaces portal reminders (and a policy-auditable compliance signal) when keys go stale (`az storage account update --key-exp-days 90`).
- **Azure Key Vault–managed keys:** register the storage account with **Key Vault**, which stores and **automatically regenerates the keys on a schedule** — applications fetch keys (or Key Vault–issued SAS tokens) from the vault and never hard-code them.
- **Disable Shared Key entirely:** the account-level **"Allow storage account key access"** setting (`az storage account update --allow-shared-key-access false`) rejects *all* requests authorized with the keys — including account and service SAS tokens signed by them — forcing **Microsoft Entra** authorization. This is the endgame for security-hardened accounts.

Remember the ripple effect: regenerating a key invalidates **every account SAS and service SAS signed with that key**, and any app or script still holding the old key starts failing immediately.

> 💡 **Exam Tip:** "Rotate keys with **no application downtime**" = the two-key swap (migrate to key2 → renew key1). "Keys must rotate **automatically** without app changes" = **Key Vault–managed** storage keys. "Ensure nobody can use Shared Key auth at all" = set **Allow storage account key access** to Disabled.

> ⚠️ **Common Pitfall:** Access keys cannot be scoped, and RBAC does not constrain them — anyone holding a key has **full data access regardless of their Azure roles**. Also, disabling shared key access breaks anything still using keys or key-signed SAS (a common "why did the app break" stem) — **user delegation SAS** keeps working because it never touched a key.

## Configure identity-based access for Azure Files

- **What it is:** **Identity-based authentication** for Azure Files lets users access **SMB** file shares with their directory identities via **Kerberos**, instead of everyone sharing the storage account key — enforced through three stacked permission layers.
- **Why it matters:** It's how a cloud file share behaves like a proper corporate file server — per-user permissions, auditable access — and the exam tests both the choice of identity **source** and the strict **order of the layers**.

**Step 1 — choose and enable one identity source on the storage account** (only one at a time):

| Identity source | Directory | Best when... |
|---|---|---|
| **On-premises AD DS** | Your Active Directory domain (account is domain-joined via the **AzFilesHybrid** module / `Join-AzStorageAccount`) | Traditional domain-joined clients with **line of sight to on-prem domain controllers**; identities synced to Entra ID |
| **Microsoft Entra Domain Services** | The managed domain in Azure | Cloud-only environments with no on-prem AD; VMs joined to the managed domain |
| **Microsoft Entra Kerberos** | Entra ID issues Kerberos tickets directly for **hybrid identities** (users synced from AD DS) | Entra-joined or hybrid-joined clients (e.g., remote laptops, Azure Virtual Desktop) that **can't reach a domain controller** |

```bash
az storage account update -g rg1 -n stacct1 --enable-files-aadds   # Entra Domain Services
az storage account update -g rg1 -n stacct1 --enable-files-aadkerb # Entra Kerberos
```

**Step 2 — share-level permissions via Azure RBAC.** Assign one of three built-in roles on the share (or account) to users/groups:

| Role | Grants |
|---|---|
| **Storage File Data SMB Share Reader** | Read files and directories |
| **Storage File Data SMB Share Contributor** | Read, write, delete |
| **Storage File Data SMB Share Elevated Contributor** | Read, write, delete **and modify Windows ACLs** |

**Step 3 — file/directory-level permissions via Windows ACLs.** Standard **NTFS-style ACLs** on folders and files, managed with **`icacls`** or File Explorer's Security tab from a mounted client. The *effective* permission is the **intersection** of the share-level RBAC role and the NTFS ACL — RBAC is the ceiling, ACLs refine below it.

And the superuser caveat: the **storage account key bypasses all three layers**. Mounting with the key gives unrestricted superuser access to the entire share, ignoring RBAC and ACLs alike — which is why hardened designs disable shared key access once identity-based auth is proven.

> 💡 **Exam Tip:** Pick the source by the clients: "domain-joined, can reach DCs" = **AD DS**; "no on-prem AD at all" = **Entra Domain Services**; "hybrid users on Entra-joined devices with **no line of sight to a DC**" = **Entra Kerberos**. Then recite the order — **enable source → share-level RBAC → NTFS ACLs (icacls)** — and note that editing ACLs over SMB requires the **Elevated Contributor** role (or the account key).

> ⚠️ **Common Pitfall:** Entra Kerberos supports **hybrid identities only** — cloud-only Entra users cannot authenticate to Azure Files with it. And an RBAC role alone isn't enough for fine-grained control (NTFS ACLs still apply), while the **account key ignores both layers** — "a user without any role assignment accessed every file" means someone mounted with the key.

## How It Fits Together (mental model)

Picture Contoso hardening the storage account behind its contract-management app. The admin flips **public network access** to **Enabled from selected virtual networks and IP addresses**, enables the **Microsoft.Storage service endpoint** on the app's subnet so a **virtual network rule** can admit it, adds one **IP network rule** for the office's public range (the intern's attempt to add `10.0.0.0/16` is rejected — **private IPs aren't allowed**), and checks **"Allow Azure services on the trusted services list"** so **Azure Backup** keeps working; the finance system instead reaches the account through a **private endpoint**, which **bypasses the public firewall entirely**. To share documents externally, the team stops emailing the **account keys** — those are **root-level access** — and issues a **service SAS** on the contracts container, tied to a **stored access policy** (one of at most **5 per container**) so legal can later shrink the **expiry** or **revoke** every distributed link by deleting the policy, while internal apps use short-lived **user delegation SAS** tokens signed with **Microsoft Entra** credentials — **blob-only, 7-day max, no key involved**. Quarterly, ops rotates credentials with zero downtime by moving apps to **key2**, running `az storage account keys renew` on **key1**, and letting **Key Vault** and a **key expiration policy** nag about the next cycle — knowing a renewal also invalidates every **account SAS** that key signed. Finally, the corporate file share on **Azure Files** gets **identity-based access**: the account enables **Microsoft Entra Kerberos** for its **hybrid identities**, HR gets **Storage File Data SMB Share Reader** while IT gets **Elevated Contributor**, folder permissions are tightened with **icacls** NTFS ACLs — and once everything authenticates via Kerberos, the admin sets **Allow storage account key access** to Disabled, closing the superuser back door for good.
