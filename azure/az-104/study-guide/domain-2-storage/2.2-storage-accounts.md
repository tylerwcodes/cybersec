# Objective 2.2 — Configure and manage storage accounts

Where AZ-900 asked you to *describe* storage, AZ-104 expects you to *build and operate* it. Questions here are administrator tasks: "you must meet requirement X — which account type / redundancy SKU / setting do you configure, and what must be enabled first?" The high-yield memorization: which settings are locked at account creation (performance tier, infrastructure encryption) versus changeable later (redundancy, tiers, keys); the redundancy ladder with copy counts and durability nines (LRS 11 → ZRS 12 → GRS/GZRS 16); the object replication prerequisites (blob versioning on **both** accounts, change feed on the source — the exam's favorite trap in this objective); the three key-management models for encryption; and the AzCopy syntax (`copy`, one-way `sync`, resumable `jobs`). Expect the answers to be exact CLI/PowerShell parameters, not just concepts.

## Create and configure storage accounts

- **What it is:** A **storage account** is the top-level Azure resource that contains your blobs, files, queues, and tables, and the object where you set performance, redundancy, networking, and encryption for everything inside it.
- **Why it matters:** Almost every setting in this objective is configured *on the account*, and several are decided *at creation and can never be changed* — the exam loves asking which ones.

The **account type** (kind + performance tier) determines what the account can hold and how fast it is:

| Account type | Backing media | Supported services | Redundancy options | Choose when... |
|---|---|---|---|---|
| **Standard general-purpose v2** | HDD-based | **Blobs, Files, Queues, Tables** | LRS, ZRS, GRS, GZRS, RA-GRS, RA-GZRS | The **default choice** for most workloads |
| **Premium block blobs** | **SSD** | Block blobs (and append blobs) | **LRS, ZRS only** | High transaction rates, small objects, consistently low latency |
| **Premium file shares** | **SSD** | Azure Files (SMB **and NFS**) | **LRS, ZRS only** | Enterprise/performance-critical file shares; NFS shares require premium |
| **Premium page blobs** | **SSD** | Page blobs | **LRS only** | Random read/write page-blob workloads (e.g., unmanaged disk-style data) |

**Naming rules** — a favorite gotcha: the account name must be **3–24 characters**, **lowercase letters and numbers only**, and **globally unique across all of Azure**, because it becomes the DNS prefix of the account's public **endpoints**:

```text
https://<account>.blob.core.windows.net    # Blob
https://<account>.file.core.windows.net    # Files
https://<account>.queue.core.windows.net   # Queues
https://<account>.table.core.windows.net   # Tables
https://<account>.dfs.core.windows.net     # Data Lake Storage (hierarchical namespace)
```

Know what is **fixed at creation** versus **changeable later**:

| Setting | Changeable after creation? |
|---|---|
| **Performance tier** (Standard vs. Premium) | **No** — migrate data to a new account to switch |
| **Infrastructure (double) encryption** | **No** — creation-time only |
| Account name / region | No (name is permanent; region requires migration) |
| **Redundancy** (LRS ↔ GRS, etc.) | **Yes** — some paths need a conversion (next section) |
| Default **access tier** (Hot/Cool/Cold), networking rules, TLS minimum, encryption keys | Yes |

Create an account with the CLI or PowerShell (the redundancy is expressed as the **SKU**, e.g. `Standard_LRS`, `Standard_GZRS`, `Premium_LRS`):

```bash
az storage account create \
  --name contosodata001 \
  --resource-group rg-storage \
  --location eastus \
  --kind StorageV2 \
  --sku Standard_GZRS \
  --access-tier Hot \
  --min-tls-version TLS1_2
```

```powershell
New-AzStorageAccount -ResourceGroupName rg-storage -Name contosodata001 `
  -Location eastus -Kind StorageV2 -SkuName Standard_GZRS `
  -AccessTier Hot -MinimumTlsVersion TLS1_2
```

> 💡 **Exam Tip:** Unless the scenario demands SSD-class latency, the answer is **Standard general-purpose v2**. If it does, match the data shape: block blobs → **Premium block blobs**, SMB/NFS shares → **Premium file shares**, page blobs → **Premium page blobs** — and remember premium accounts top out at **LRS/ZRS** (no geo-redundancy).

> ⚠️ **Common Pitfall:** The **performance tier cannot be changed after creation**. If a question says "the Standard account must become Premium," the only valid answer is *create a new Premium account and copy the data* (AzCopy). Also watch for invalid names — `Contoso-Storage` fails twice: uppercase letters and a hyphen.

## Configure Azure Storage redundancy

- **What it is:** The account's replication setting — how many **copies** of the data exist and whether they live in one datacenter, across **availability zones**, or in a paired **secondary region**.
- **Why it matters:** AZ-104 tests the exact copy counts, the **durability** figures, and the operational mechanics of *changing* redundancy and *failing over* — not just the definitions.

| Option | Layout | Copies | Durability (nines) | Survives |
|---|---|---|---|---|
| **LRS** | 3 synchronous copies in **one datacenter** | 3 | **11 nines** (99.999999999%) | Drive/rack failure |
| **ZRS** | 3 copies across **3 availability zones** | 3 | **12 nines** | Entire zone/datacenter loss |
| **GRS** | LRS in primary **+ asynchronous** LRS in secondary region | **6** | **16 nines** | Regional disaster |
| **GZRS** | **ZRS in primary + LRS in secondary** region | 6 | **16 nines** | Zone **and** regional failure |
| **RA-GRS / RA-GZRS** | Same as GRS/GZRS | 6 | 16 nines | Same — plus an **always-readable secondary** endpoint (`<account>-secondary.blob.core.windows.net`) |

**Changing redundancy** is allowed, but not every path is a simple switch:

- LRS ↔ GRS/RA-GRS (adding or removing geo-replication, no zones involved): a direct update.
- Any path **into or out of ZRS** (LRS → ZRS, GRS → GZRS): requires a **conversion** — either a **customer-initiated conversion** (portal/CLI, Azure moves the data in place) or a **manual migration** (copy to a new account with AzCopy when you need it done on your schedule).

```bash
az storage account update --name contosodata001 --resource-group rg-storage \
  --sku Standard_RAGRS          # simple redundancy change
```

**Customer-initiated account failover** promotes the secondary region to primary when the primary is down. Because geo-replication is **asynchronous**, any writes not yet replicated at failover time are **lost** — check the account's **Last Sync Time** property to measure the exposure before pulling the trigger. After failover the account is **LRS** in the new primary; re-enable GRS/GZRS afterwards to restore geo-protection.

```bash
az storage account show --name contosodata001 --expand geoReplicationStats \
  --query geoReplicationStats.lastSyncTime      # check potential data loss first
az storage account failover --name contosodata001
```

```powershell
Get-AzStorageAccount -ResourceGroupName rg-storage -Name contosodata001 `
  -IncludeGeoReplicationStats
Invoke-AzStorageAccountFailover -ResourceGroupName rg-storage -Name contosodata001
```

> 💡 **Exam Tip:** Anchor the numbers: **3 copies** stay in-region (LRS/ZRS), **6 copies** span two regions (GRS/GZRS); durability climbs **11 → 12 → 16 nines**. "Read from the secondary without failing over" = **RA-** prefix. "How much data could a failover lose?" = **Last Sync Time**.

> ⚠️ **Common Pitfall:** GZRS is **ZRS in the primary + LRS in the secondary** — the secondary region is *not* zone-redundant. And a customer-initiated failover is not free: un-replicated writes since Last Sync Time are gone, and the account drops to LRS until you re-enable geo-redundancy.

## Configure object replication

- **What it is:** **Object replication** asynchronously copies **block blobs** from containers in a **source storage account** to containers in a **destination storage account** — in another region or the same one — according to **rules** you define.
- **Why it matters:** It is the answer when a scenario wants blob data *itself* available in multiple accounts/regions during normal operations — to **reduce read latency** for users near the destination region, or to let **compute workloads process local copies** instead of reaching across regions.

Hard requirements the exam tests verbatim:

- **Blobs only** — specifically **block blobs**. Not Azure Files, queues, tables, page blobs, or accounts with a hierarchical namespace (Data Lake Storage) enabled.
- **Blob versioning** must be enabled on **both the source and the destination** accounts.
- **Change feed** must be enabled on the **source** account (it is how replication detects writes).
- Replication is **asynchronous** with no SLA on replication lag; check a blob's **replication status** on the source to confirm completion.

**Rules** pair a source container with a destination container and can **filter by blob prefix** (e.g., only `logs/`). Each rule also sets a copy scope: everything, only new objects, or objects created after a custom date. A source account can replicate to a maximum of **two destination accounts**.

```bash
# Prerequisites on both accounts (change feed needed on the source)
az storage account blob-service-properties update \
  --account-name contosodata001 --resource-group rg-storage \
  --enable-versioning true --enable-change-feed true

# Create the policy (destination side first, then it is applied to the source)
az storage account or-policy create \
  --account-name contosodest001 --resource-group rg-storage \
  --source-account contosodata001 --destination-account contosodest001 \
  --source-container media --destination-container media \
  --prefix-match video/
```

```powershell
$rule = New-AzStorageObjectReplicationPolicyRule -SourceContainer media `
  -DestinationContainer media -PrefixMatch video/
Set-AzStorageObjectReplicationPolicy -ResourceGroupName rg-storage `
  -StorageAccountName contosodest001 -PolicyId default `
  -SourceAccount contosodata001 -Rule $rule
```

> 💡 **Exam Tip:** The prerequisite triad is the question: **versioning on source + versioning on destination + change feed on source**. If a stem says "object replication fails to configure," the missing piece is almost always one of those three.

> ⚠️ **Common Pitfall:** Object replication is not geo-redundancy and not backup. GRS replicates *within one account* to a hidden secondary; object replication copies between **two distinct accounts** with independently readable data — and deletes/overwrites replicate too, so it does not protect against accidental deletion. It also is **blob-only**: any scenario involving file shares rules it out.

## Configure storage account encryption

- **What it is:** **Storage Service Encryption (SSE)** — server-side encryption of all data written to any Azure Storage service using **256-bit AES**.
- **Why it matters:** SSE is **always on and cannot be disabled**; the configurable part — and what AZ-104 tests — is *who manages the keys* and the creation-time extras.

| Key management model | Keys live in | Managed by | Notes |
|---|---|---|---|
| **Microsoft-managed keys** | Microsoft's infrastructure | Microsoft | The **default**; zero configuration |
| **Customer-managed keys (CMK)** | **Azure Key Vault** or Key Vault Managed HSM | You (rotation, access policy, revocation) | The account needs a **managed identity** with permission to wrap/unwrap keys in the vault; vault should have soft delete + purge protection |
| **Customer-provided keys** | Supplied by the client **on each request** | You, per-operation | **Blob storage only**, via REST headers — Azure never stores the key |

Two more encryption features, both scenario magnets:

- **Infrastructure encryption** (**double encryption**) adds a second, independent layer of encryption at the infrastructure level. It **must be enabled when the account is created** — it cannot be turned on later.
- **Encryption scopes** create secure boundaries *within* one account: you define a scope (with a Microsoft-managed or customer-managed key) and apply it **per container or per individual blob**, isolating different customers' or projects' data under different keys without separate accounts.

```bash
# Infrastructure (double) encryption — creation-time only
az storage account create --name contososec001 --resource-group rg-storage \
  --location eastus --kind StorageV2 --sku Standard_LRS \
  --require-infrastructure-encryption

# Switch to customer-managed keys in Key Vault
az storage account update --name contosodata001 --resource-group rg-storage \
  --assign-identity   # managed identity the vault will trust
az storage account update --name contosodata001 --resource-group rg-storage \
  --encryption-key-source Microsoft.Keyvault \
  --encryption-key-vault https://contoso-kv.vault.azure.net \
  --encryption-key-name storage-cmk
```

```powershell
Set-AzStorageAccount -ResourceGroupName rg-storage -Name contosodata001 `
  -KeyvaultEncryption -KeyVaultUri https://contoso-kv.vault.azure.net `
  -KeyName storage-cmk
```

> 💡 **Exam Tip:** Map the requirement to the model: "meet compliance with no effort" = **Microsoft-managed keys**; "we must control rotation/revocation in Key Vault" = **customer-managed keys** (and the follow-up answer is grant the account's **managed identity** access to the vault); "the key is supplied with each request" = **customer-provided keys**; "different keys for different containers in one account" = **encryption scopes**.

> ⚠️ **Common Pitfall:** Two absolutes trip people: SSE **cannot be disabled** — any answer choice offering to "turn off storage encryption" is wrong — and **infrastructure encryption cannot be added to an existing account**; if double encryption is required, you must create a new account with the flag set.

## Manage data by using Azure Storage Explorer and AzCopy

- **What they are:** **Azure Storage Explorer** is a **free, cross-platform GUI** (Windows, macOS, Linux) for browsing and managing storage accounts; **AzCopy** is the **command-line** utility for high-performance, scriptable data transfer. Storage Explorer actually **uses AzCopy under the hood** for its transfers.
- **Why they matter:** AZ-104 tests tool selection (GUI vs. script), the authentication options for each, and exact AzCopy syntax.

**Storage Explorer** connects to storage several ways — pick per scenario:

| Connection method | Use when... |
|---|---|
| **Microsoft Entra sign-in** | You have RBAC data-plane roles (e.g., **Storage Blob Data Contributor**) — the recommended default |
| **Account name + key** | Full access with the shared key; works when RBAC isn't set up |
| **SAS** (URI or connection string) | Delegated, time-limited, scoped access — no credentials shared |
| **Local emulator (Azurite)** | Development and testing without an Azure subscription |

**AzCopy** authenticates via `azcopy login` (Microsoft Entra ID) or by appending a **SAS token** to each URL, and works against both **blob and file endpoints**:

```bash
azcopy login                                   # Entra ID sign-in (or use SAS URLs)

# Upload a local folder to a container, including subfolders
azcopy copy ./data "https://contosodata001.blob.core.windows.net/backups" --recursive

# Server-to-server copy between two accounts (SAS on each URL)
azcopy copy "https://src.blob.core.windows.net/media?<SAS>" \
            "https://dst.blob.core.windows.net/media?<SAS>" --recursive

# One-directional sync: makes DESTINATION match SOURCE (deltas only)
azcopy sync ./data "https://contosodata001.blob.core.windows.net/backups" \
            --delete-destination=true

# Transfers are resumable jobs
azcopy jobs list
azcopy jobs resume <job-id>
```

The critical behavioral fact: **`azcopy sync` is one-directional** — it copies changes from source to destination only. It is *not* Azure File Sync (the bi-directional Windows Server caching service) and it will never pull destination changes back. Interrupted transfers pick up where they left off with **`azcopy jobs resume`**, which is why AzCopy is the answer for large, unreliable, or scheduled transfers.

> 💡 **Exam Tip:** "Graphical / browse / ad-hoc" = **Storage Explorer**; "script / automate / bulk / resume an interrupted transfer" = **AzCopy**. For Entra-based access with either tool, the account also needs a **data-plane RBAC role** like Storage Blob Data Contributor — Owner/Contributor alone govern the management plane, not the data.

> ⚠️ **Common Pitfall:** `azcopy sync` deletes nothing and mirrors nothing *backwards* — and with `--delete-destination=true` it will **delete destination blobs that no longer exist at the source**. Read the direction in the stem carefully: source → destination, always.

## How It Fits Together (mental model)

Contoso's admin creates a **Standard general-purpose v2** **storage account** named `contosodata001` — **3–24 lowercase letters and numbers**, **globally unique** because it becomes the `contosodata001.blob.core.windows.net` **endpoint** — choosing the Standard **performance tier** carefully because it **cannot be changed later**, and checking **infrastructure encryption** at creation for the compliance team since that flag is also creation-time only (a separate **Premium file shares** account backs the latency-sensitive NFS share, accepting its **LRS/ZRS-only** limit). The account starts on **ZRS** (3 copies, 3 **availability zones**, **12 nines**), then a DR mandate drives a **conversion** to **RA-GZRS** — **ZRS primary + LRS secondary, 6 copies, 16 nines** — so reports read from the **always-readable secondary**; the runbook for a **customer-initiated failover** starts with checking **Last Sync Time**, because **asynchronous** geo-replication means un-synced writes are lost. To serve European customers locally, the admin configures **object replication** of the `media` container to a second account in West Europe — first enabling **blob versioning on both accounts** and **change feed on the source**, then a **rule** filtering the `video/` **prefix** — cutting **read latency** and letting a Europe-based compute job process its **local copy**. All of it is encrypted by **SSE** with **AES-256** (always on, never disable-able); the admin moves from **Microsoft-managed keys** to **customer-managed keys** in **Key Vault**, granting the account's **managed identity** access to the vault, and adds **encryption scopes** so two tenants' containers use different keys inside one account. Day to day, the team browses with **Storage Explorer** (signed in via **Entra** with Storage Blob Data Contributor, falling back to **SAS** for a contractor) while the nightly pipeline runs **`azcopy sync`** — **one-directional**, source to destination — and a failed 2 TB upload simply continues with **`azcopy jobs resume`**.

| The question says... | The answer is... |
|---|---|
| "Default account type for blobs, files, queues, and tables" | Standard general-purpose v2 |

| "NFS file share / performance-critical SMB share" | Premium file shares account |
| "Account name is rejected" | 3–24 chars, lowercase letters + numbers, globally unique |
| "Change a Standard account to Premium" | Impossible — create a new account and copy with AzCopy |
| "Cheapest redundancy, 11 nines, single datacenter" | LRS |
| "Survive a zone outage, stay in one region" | ZRS (12 nines) |
| "Survive a regional disaster, 6 copies, 16 nines" | GRS (or GZRS with zone redundancy in the primary) |
| "Read from the secondary region during normal operations" | RA-GRS / RA-GZRS |
| "How much data would a failover lose?" | Check Last Sync Time (geo-replication is asynchronous) |
| "Move LRS to ZRS" | Redundancy conversion (customer-initiated) or manual migration |
| "Copy blobs between two storage accounts automatically, filtered by prefix" | Object replication |
| "Object replication won't configure" | Enable versioning on both accounts + change feed on the source |
| "Reduce blob read latency for users in another region, without failover" | Object replication to an account in that region |
| "Disable storage encryption" | Impossible — SSE (AES-256) is always on |
| "Company must control key rotation and revocation" | Customer-managed keys in Key Vault + managed identity |
| "Double encryption at the infrastructure layer" | Enable infrastructure encryption at account creation (only) |
| "Different encryption keys per container or blob in one account" | Encryption scopes |

| "Keep a destination container matching a source, one direction only" | `azcopy sync` |
