# Objective 4.3 — Configure name resolution and load balancing

This objective is tested in two hands-on flavors. For DNS, the exam checks whether you know what Azure DNS *is* (a hosting service, not a registrar), how to **delegate** a domain with the four assigned name servers, when an **alias record** beats a plain A/CNAME, and how **private DNS zones** resolve names inside VNets via links and auto-registration — plus the magic IP **168.63.129.16**. For load balancing, it drills the anatomy of an **Azure Load Balancer** (frontend, backend pool, probe, rule, NAT rule), the **Standard vs. Basic** SKU story (Basic is retired — Standard is always the answer), **public vs. internal**, session persistence tuples, and why a backend shows *unhealthy* (almost always an **NSG** blocking the probe). Memorize the component names, the tuple counts (5/3/2), the probe source IP, and the four-way "choose the right balancer" matrix — those four things answer most questions here.

## Configure Azure DNS

- **What it is:** **Azure DNS** is a hosting service for DNS zones that answers queries for your domain records from Azure's global anycast name-server network, managed with the same Azure tooling (portal, CLI, PowerShell, RBAC) as everything else.
- **Why it matters:** It is *not* a **domain registrar** — you cannot buy `contoso.com` in Azure DNS. Purchase the domain from a third-party registrar (or via **App Service domains**), then host its records in an Azure DNS zone. The exam loves this distinction.

### Public zones and delegation

Creating a **public DNS zone** (e.g., `contoso.com`) assigns it **four Azure name servers** (visible in the zone's **NS** and **SOA** records, e.g., `ns1-01.azure-dns.com`). **Delegation** means going to your registrar and replacing the domain's NS records with those exact four name servers. Until you delegate, the Internet never asks Azure for your records — a classic "created the zone but nothing resolves" scenario.

You can verify delegation and records from anywhere with standard tooling:

```bash
nslookup -type=SOA contoso.com          # should return an Azure name server as authoritative
nslookup www.contoso.com ns1-01.azure-dns.com   # query the zone's own name server directly
```

### Record sets

Records live in **record sets** — a collection of records sharing the same name and type, with one **TTL** (time to live, in seconds) controlling how long resolvers cache the answer. Azure DNS zones are managed with **RBAC** like any resource, so record changes can be scoped and audited via the activity log:

| Type | Maps | Typical use |
|---|---|---|
| **A** | Name → IPv4 address | Point `www` at a web server's IP |
| **AAAA** | Name → IPv6 address | IPv6 endpoints |
| **CNAME** | Name → another name | `www` → `contoso.azurewebsites.net`; **forbidden at the zone apex** |
| **MX** | Mail routing (with priority) | Point the domain at Exchange Online / mail hosts |
| **NS** | Delegation to name servers | The four Azure name servers; child-zone delegation |
| **PTR** | IP → name (reverse lookup) | Reverse DNS zones |
| **SRV** | Service location (priority, weight, port, target) | SIP, LDAP, service discovery |
| **TXT** | Arbitrary text | Domain verification (Microsoft 365, custom domains), SPF/DKIM |
| **SOA** | Zone authority metadata | Created automatically with the zone; one per zone |

### Alias record sets

- **What they are:** An **alias record set** (available for **A, AAAA, and CNAME** types) points at an **Azure resource** — a **public IP address**, a **Traffic Manager profile**, or an **Azure CDN / Front Door endpoint** — instead of at a hard-coded value.
- **Why they matter:** The record **tracks the resource automatically**: if the public IP changes, the alias updates itself, and if the target resource is deleted the record is cleaned up rather than left dangling. Crucially, an alias **A** record gives **"CNAME-like" behavior at the zone apex** (`contoso.com` itself), where DNS standards forbid a real CNAME — the only supported way to point a naked domain at Traffic Manager or Front Door.

### Private DNS zones

- **What they are:** **Private DNS zones** (e.g., `internal.contoso.com`) provide name resolution **inside virtual networks**, invisible to the Internet. A zone does nothing until you create **virtual network links** attaching VNets to it.
- **Why they matter:** A link can enable **auto-registration**, making the zone automatically create and delete **A records for VMs** as they are deployed and removed in that VNet. A linked VNet is either a **registration VNet** (auto-registration on) or a **resolution VNet** (query-only) — and a VNet can be a registration VNet for **only one** private zone, though it can resolve against many. Because the same zone name can exist publicly and privately with different answers, private zones enable **split-horizon** DNS: internal clients get private IPs, the Internet gets public ones.

### Default and custom name resolution

By default, VMs in a VNet use **Azure-provided DNS** at the virtual IP **168.63.129.16** — zero-configuration resolution of VM names within the VNet (plus recursion to the Internet). To use your own DNS servers (e.g., on-prem AD DNS for hybrid resolution), set **custom DNS server IPs on the VNet** (or override per NIC). VMs receive DNS settings via DHCP, so after changing them you must **restart the VM or renew its DHCP lease** before the new servers take effect.

Common commands:

```bash
# Public zone + a record set
az network dns zone create -g rg-dns -n contoso.com
az network dns record-set a add-record -g rg-dns -z contoso.com -n www -a 20.50.1.10

# Private zone linked to a VNet with auto-registration
az network private-dns zone create -g rg-dns -n internal.contoso.com
az network private-dns link vnet create -g rg-dns -z internal.contoso.com \
  -n link-hub --virtual-network vnet-hub --registration-enabled true

# Custom DNS servers on a VNet
az network vnet update -g rg-net -n vnet-hub --dns-servers 10.0.0.4 10.0.0.5
```

```powershell
New-AzDnsZone -ResourceGroupName rg-dns -Name contoso.com
New-AzDnsRecordSet -ResourceGroupName rg-dns -ZoneName contoso.com -Name www `
  -RecordType A -Ttl 3600 -DnsRecords (New-AzDnsRecordConfig -Ipv4Address 20.50.1.10)
New-AzPrivateDnsZone -ResourceGroupName rg-dns -Name internal.contoso.com
New-AzPrivateDnsVirtualNetworkLink -ResourceGroupName rg-dns -ZoneName internal.contoso.com `
  -Name link-hub -VirtualNetworkId $vnet.Id -EnableRegistration
```

> 💡 **Exam Tip:** "Point the apex/root domain (`contoso.com`) at Traffic Manager / Front Door / a public IP" = **alias record set** — a real CNAME is illegal at the apex. "VM names resolve automatically across a VNet with no servers to manage" = **private DNS zone with an auto-registration-enabled link**. "Zone created but the domain doesn't resolve from the Internet" = **delegation not done at the registrar** (copy the four NS values).

> ⚠️ **Common Pitfall:** Azure DNS does not sell domains — buy at a registrar or via App Service domains, then host the zone. And after setting **custom DNS servers on a VNet**, running VMs keep the old setting until they **restart or renew DHCP** — "changed DNS but VMs still use 168.63.129.16" is a configuration-propagation question, not a broken-zone question.

## Configure an internal or public load balancer

- **What it is:** **Azure Load Balancer** is a **layer 4 (TCP/UDP)** load balancer that distributes inbound flows arriving at its **frontend** across healthy VMs in its **backend pool**, with **zone-redundant** frontends available for resilience across availability zones.
- **Why it matters:** Layer 4 means it balances *connections*, not HTTP requests — it never inspects URLs, cookies, or **TLS** (no termination). When the scenario needs HTTP-aware features, the answer is a different service (table below).

### SKUs

| | **Standard** (the answer) | **Basic** |
|---|---|---|
| Status | Current, recommended | **Retired September 30, 2025** |
| SLA | **99.99%** | None |
| Security | **Secure by default** — traffic is blocked until an **NSG explicitly allows** it | Open by default |
| Frontend | Static public IP options, **zone-redundant or zonal** | Dynamic or static, no zones |
| Backend pool | Up to 5,000 instances; any VM/VMSS in the VNet | 300; single availability set/VMSS |
| Extras | **HA ports**, **outbound rules**, TCP reset on idle | Not available |

On the current exam, any SKU question resolves to **Standard** — Basic Load Balancer (and Basic public IPs) are retired.

### Public vs. internal

- **Public load balancer:** frontend is a **public IP** — balances **Internet** traffic to your VMs and can provide **outbound** connectivity (SNAT) for the backend pool.
- **Internal (private) load balancer:** frontend is a **private IP** inside the VNet — balances traffic **only from internal sources** (VNet, peered VNets, on-prem via VPN/ExpressRoute). The classic pattern: public LB in front of the web tier, **internal LB** in front of the middle/business tier so it is never Internet-exposed.

### Components

| Component | What it does |
|---|---|
| **Frontend IP configuration** | The IP(s) clients connect to — public or private; a LB can have several |
| **Backend pool** | The VMs / **VMSS** instances (by NIC) that receive traffic |
| **Health probe** | **TCP** or **HTTP/HTTPS** check that decides which instances get new flows; probes originate from **168.63.129.16**; an HTTP(S) probe must receive **HTTP 200** within the timeout or the instance is pulled out of rotation |
| **Load-balancing rule** | Maps a frontend port + protocol to a backend port across the *whole pool* (e.g., frontend TCP 443 → backend 443) |
| **Inbound NAT rule** | Port-forwards a frontend port to **one specific VM** (e.g., frontend 50001 → VM1:3389, 50002 → VM2:3389 for per-VM **RDP**) |
| **Outbound rule** | Explicit **SNAT** configuration giving backend VMs outbound Internet access through the public frontend |

An **HA ports** rule (internal Standard LB only, frontend/backend port **0**, protocol **All**) balances **all ports and protocols** in one rule — the required pattern for highly available **network virtual appliances** (firewall NVAs).

### Distribution and session persistence

The hash that picks a backend instance defines "stickiness":

| Session persistence setting | Hash | Behavior |
|---|---|---|
| **None** (default) | **5-tuple** (source IP, source port, dest IP, dest port, protocol) | Best spread; a client's *next connection* may land elsewhere |
| **Client IP** | **2-tuple** | All traffic from one source IP → same instance (**source IP affinity**) |
| **Client IP and protocol** | **3-tuple** | Same source IP + protocol → same instance |

**Floating IP** (direct server return) makes the backend see the *frontend* IP as the destination, letting multiple rules share a port — required for **SQL Server Always On availability group listeners**.

```bash
az network lb create -g rg-app -n lb-web --sku Standard \
  --frontend-ip-name fe-web --backend-pool-name bp-web --public-ip-address pip-lb
az network lb probe create -g rg-app --lb-name lb-web -n probe-http \
  --protocol Http --port 80 --path /health
az network lb rule create -g rg-app --lb-name lb-web -n rule-http \
  --protocol Tcp --frontend-port 80 --backend-port 80 \
  --frontend-ip-name fe-web --backend-pool-name bp-web --probe-name probe-http
az network lb inbound-nat-rule create -g rg-app --lb-name lb-web -n nat-rdp-vm1 \
  --protocol Tcp --frontend-port 50001 --backend-port 3389 --frontend-ip-name fe-web
```

```powershell
$probe = New-AzLoadBalancerProbeConfig -Name probe-http -Protocol Http -Port 80 `
  -RequestPath /health -IntervalInSeconds 15 -ProbeCount 2
$rule  = New-AzLoadBalancerRuleConfig -Name rule-http -Protocol Tcp `
  -FrontendPort 80 -BackendPort 80 -FrontendIpConfiguration $fe -BackendAddressPool $bp -Probe $probe
New-AzLoadBalancer -ResourceGroupName rg-app -Name lb-web -Location eastus -Sku Standard `
  -FrontendIpConfiguration $fe -BackendAddressPool $bp -Probe $probe -LoadBalancingRule $rule
```

### Choose the right load-balancing service

| Service | Layer | Scope | Signature features |
|---|---|---|---|
| **Azure Load Balancer** | **L4** TCP/UDP | Regional | Ultra-low latency, HA ports, NAT rules — any TCP/UDP workload |
| **Application Gateway** | **L7** HTTP(S) | Regional | **URL-path-based routing**, host headers, **WAF**, cookie affinity, TLS termination |
| **Traffic Manager** | **DNS-based** | Global | Routes by returning endpoints in DNS: **performance / priority / weighted / geographic** |
| **Azure Front Door** | **L7** HTTP(S) | Global (**anycast** edge) | Global HTTP acceleration, **WAF**, caching, path routing across regions |

> 💡 **Exam Tip:** Read the tier and the protocol. "Middle tier must not be reachable from the Internet" = **internal load balancer**. "RDP to a *specific* VM behind the LB" = **inbound NAT rule** (a load-balancing rule cannot target one VM). "NVA cluster must forward every port" = **HA ports**. "Client must stay on the same server" = **Client IP** (2-tuple) session persistence. "URL path routing / WAF" = Application Gateway; "global DNS routing" = Traffic Manager; "global HTTP with caching at the edge" = Front Door.

> ⚠️ **Common Pitfall:** Standard LB is **secure by default**: with no NSG rule allowing the traffic, *nothing* reaches the backend even though the LB is configured perfectly — the #1 "it doesn't work" cause in labs and questions. Also, Load Balancer is layer 4: it cannot terminate TLS, read cookies, or route by URL — picking it for those requirements is always wrong.

## Troubleshoot load balancing

- **What it is:** Diagnosing why traffic through a load balancer fails or backends show **unhealthy**, using probe logic, NSG review, and **Azure Monitor** / Load Balancer **Insights** metrics (health probe status, data path availability).
- **Why it matters:** Nearly every troubleshooting stem here reduces to one question — *why is the health probe failing?* — because an instance that fails its probe receives **no new flows** at all.

Work the checklist in order when a backend is unhealthy or connections fail:

1. **NSG blocking the probe or the traffic.** Probes originate from **168.63.129.16**; the built-in **AzureLoadBalancer service tag** covers it in default rules. If a custom NSG rule denies that source — or simply doesn't allow the probe/data port inbound on the subnet or NIC — the instance goes unhealthy or clients time out. Fix: allow the **AzureLoadBalancer** service tag and the application port.
2. **Wrong probe configuration.** Probe port doesn't match the port the app listens on; HTTP probe path is wrong (`/health` vs `/healthz`); probe protocol mismatched (TCP probe passing while the app's HTTP endpoint is broken, or an HTTP probe against a TLS-only site).
3. **The application itself.** Service stopped or not listening on the probed port (`netstat`/`ss` inside the VM), host firewall (Windows Firewall) blocking it, or the health endpoint returning **anything other than 200** (301/302 redirects and 403s count as *failures*).
4. **Pool membership.** The VM's NIC was never added to the **backend pool**, or the VM lives in a VNet the LB can't use. No pool membership, no traffic — regardless of probes.
5. **Rule mismatches.** Frontend/backend ports transposed, wrong frontend IP configuration on the rule, or **floating IP** enabled/disabled inconsistently with what the backend (e.g., a SQL listener) expects.
6. **Outbound/SNAT issues.** Backend VMs failing *outbound* calls behind a Standard public LB usually means missing **outbound rules** or **SNAT port exhaustion** — add outbound rules with more allocated ports or front the subnet with a **NAT Gateway**.

Useful checks:

```bash
az network lb show -g rg-app -n lb-web --query "backendAddressPools[].loadBalancerBackendAddresses"
az network nic show -g rg-app -n vm1-nic --query "ipConfigurations[].loadBalancerBackendAddressPools"
az network nsg rule list -g rg-app --nsg-name nsg-web -o table
az network watcher test-connectivity -g rg-app --source-resource vm-jump --dest-address 10.0.2.10 --dest-port 80
```

```powershell
Get-AzLoadBalancer -ResourceGroupName rg-app -Name lb-web |
  Select-Object -ExpandProperty Probes            # confirm probe port/path/protocol
(Get-AzNetworkInterface -ResourceGroupName rg-app -Name vm1-nic).IpConfigurations |
  Select-Object -ExpandProperty LoadBalancerBackendAddressPools   # confirm pool membership
```

**Load Balancer Insights** (Azure Monitor) gives a prebuilt topology and metrics dashboard — watch **Health Probe Status** (per-instance probe pass rate) and **Data Path Availability** (is the Azure data path to the frontend working at all). If Data Path Availability is healthy but Health Probe Status is low, the platform is fine and the problem is inside your VMs or NSGs.

And remember what the LB *cannot* be blamed for: it does **not terminate TLS** (certificate errors are the backend's or App Gateway's problem), it does not retry or buffer requests, and it does not health-check at the HTTP-content level unless you gave it an HTTP(S) probe.

> 💡 **Exam Tip:** "All backend instances show unhealthy immediately after adding an NSG" = the NSG blocks **168.63.129.16 / the AzureLoadBalancer service tag** or the probe port — fix the NSG, not the LB. "Probe is TCP and succeeds, but users get errors" = switch to an **HTTP probe against a real health path** so app failures are detected.

> ⚠️ **Common Pitfall:** An HTTP(S) probe requires exactly **HTTP 200** within the timeout — a 302 redirect to HTTPS or a login page marks the instance *down*, a subtle trap when the health path sits behind authentication or HTTP→HTTPS redirection. And don't chase LB settings when the VM was simply never added to the **backend pool** — verify membership first.

## How It Fits Together (mental model)

Contoso buys `contoso.com` at a registrar (because **Azure DNS** hosts zones but is **not a registrar**), creates a **public DNS zone**, and completes **delegation** by copying the **four Azure name servers** into the registrar's **NS records**. `www` gets a **CNAME**, mail gets **MX** and **TXT** (SPF) **record sets** with sensible **TTLs**, and the apex `contoso.com` — where a CNAME is forbidden — uses an **alias record set** pointing at the **Front Door** endpoint, which will track any IP change automatically. Inside Azure, a **private DNS zone** `internal.contoso.com` is attached to the hub VNet by a **virtual network link** with **auto-registration**, so every VM's **A record** appears on deploy (the hub can be the **registration VNet** for only this one zone), giving **split-horizon** resolution while spoke VMs otherwise rely on **Azure-provided DNS** at **168.63.129.16** — except the hybrid spoke, which sets **custom DNS servers** on the VNet and **restarts its VMs** to pick them up. Traffic arrives at a **Standard** SKU (Basic is **retired**) **public Azure Load Balancer** — **layer 4**, **zone-redundant**, **99.99% SLA** — whose **load-balancing rule** maps frontend 443 to the web tier's **backend pool**, with an **HTTP health probe** (from **168.63.129.16**, expecting a **200**) and an **NSG** rule allowing the **AzureLoadBalancer service tag** because Standard is **secure by default**; admins reach individual VMs through **inbound NAT rules** (50001→VM1:3389), and **outbound rules** handle **SNAT**. The web tier calls the business tier through an **internal load balancer** with a **private frontend IP**, the firewall NVAs sit behind an **HA ports** rule, the SQL **Always On listener** uses **floating IP**, and the kiosk app that must stay on one server uses **Client IP** (2-tuple) **session persistence** instead of the default **5-tuple** hash. When a backend later shows **unhealthy**, the on-call engineer checks the **NSG**, the **probe port and path**, the app's **200** response, and **backend-pool membership** — in that order — and for URL-path routing and **WAF** they know to reach for **Application Gateway**, for global DNS steering **Traffic Manager**, and for global anycast HTTP **Front Door**, not the L4 Load Balancer.
