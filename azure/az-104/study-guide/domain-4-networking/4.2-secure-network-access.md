# Objective 4.2 — Configure secure access to virtual networks

This objective is where AZ-104 tests whether you can actually *reason about traffic* — not just name services. Expect rule-evaluation questions ("given these NSG rules on the subnet and NIC, does the packet get through?"), where you must apply the priority order (lower number wins, first match stops) and remember that **inbound traffic hits the subnet NSG first, then the NIC NSG — and both must allow it**. Expect at least one fact-recall item on **Azure Bastion** (the `AzureBastionSubnet` name and its **/26** minimum are near-guaranteed), and count on the exam's favorite discriminator: **service endpoint vs. private endpoint**. Memorize the default rule priorities (65000/65001/65500), the load-balancer probe IP **168.63.129.16**, the Bastion SKU ladder, and the one-line difference between the two PaaS access patterns — traffic *from* a public endpoint over the backbone (service endpoint) versus a **private IP in your subnet** (private endpoint).

## Create and configure network security groups (NSGs) and application security groups (ASGs)

- **What it is:** A **network security group (NSG)** is a stateful packet filter containing security rules that **allow or deny** traffic. Each rule is a **5-tuple**: **source, source port, destination, destination port, protocol** (TCP/UDP/ICMP/Any).
- **Why it matters:** NSGs are the primary east-west and north-south traffic control inside a VNet — nearly every "can VM A reach VM B on port X?" exam question is an NSG question in disguise.

Rule processing is strictly by **priority**, a number from **100 to 4096** for custom rules:

- The **lower the number, the higher the priority** — a Deny at 100 beats an Allow at 200.
- Rules are evaluated in priority order and **processing stops at the first match**; nothing after the matching rule is considered.
- Every NSG ships with **default rules** at priorities 65000–65500 that **cannot be deleted** — you override them by creating custom rules with lower (i.e., stronger) priority numbers.

| Direction | Priority | Default rule | Effect |
|---|---|---|---|
| Inbound | **65000** | **AllowVnetInBound** | Allow all traffic from within the VNet (and peered VNets) |
| Inbound | **65001** | **AllowAzureLoadBalancerInBound** | Allow Azure Load Balancer health probes (source **168.63.129.16**) |
| Inbound | **65500** | **DenyAllInBound** | Deny everything else |
| Outbound | **65000** | **AllowVnetOutBound** | Allow all traffic to the VNet |
| Outbound | **65001** | **AllowInternetOutBound** | Allow all traffic to the Internet |
| Outbound | **65500** | **DenyAllOutBound** | Deny everything else |

**Association and evaluation order** — an NSG can be associated to **subnets and/or NICs**, and **one NSG can serve many subnets and NICs** (a reuse pattern the exam rewards):

- **Inbound:** evaluated by the **subnet NSG first, then the NIC NSG** — traffic must be allowed by **both** to arrive.
- **Outbound:** evaluated by the **NIC NSG first, then the subnet NSG** — again, both must allow.
- NSG rules are **stateful**: if a flow is allowed in one direction, the **reply traffic is automatically allowed** — you never write a rule for return packets.

**Service tags** replace hand-maintained IP ranges in rules. Microsoft keeps the underlying prefixes current:

| Service tag | Represents |
|---|---|
| **Internet** | All public IP space outside Azure (plus Azure public IPs) |
| **VirtualNetwork** | The VNet address space, connected/peered networks, and routes advertised to it |
| **AzureLoadBalancer** | The platform load balancer health probe source — **168.63.129.16** |
| **Storage** / **Sql** | Public endpoints of Azure Storage / Azure SQL (regional variants like `Storage.EastUS` exist) |
| **AzureCloud** | All Azure datacenter public IPs |

- **What it is:** An **application security group (ASG)** is a **named group of VM NICs** that you use as the **source or destination of an NSG rule** instead of IP addresses.
- **Why it matters:** ASGs let you write app-tier rules like "**webservers** can reach **dbservers** on **1433**" and never touch the rule again as VMs are added — you simply **join each NIC to the ASG**. The constraint to memorize: **all ASGs referenced in a single rule must contain NICs in the same VNet**.

```bash
# NSG + rule + ASG (CLI)
az network nsg create -g rg-net -n nsg-web
az network nsg rule create -g rg-net --nsg-name nsg-web -n Allow-HTTPS \
  --priority 200 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes Internet --destination-port-ranges 443
az network asg create -g rg-net -n asg-web
az network nic ip-config update -g rg-net --nic-name vm-web1-nic \
  -n ipconfig1 --application-security-groups asg-web
az network vnet subnet update -g rg-net --vnet-name vnet-hub \
  -n snet-web --network-security-group nsg-web
```

```powershell
# Same flow in PowerShell (Az module)
$rule = New-AzNetworkSecurityRuleConfig -Name Allow-HTTPS -Priority 200 `
  -Direction Inbound -Access Allow -Protocol Tcp -SourceAddressPrefix Internet `
  -SourcePortRange * -DestinationAddressPrefix * -DestinationPortRange 443
New-AzNetworkSecurityGroup -ResourceGroupName rg-net -Name nsg-web `
  -Location eastus -SecurityRules $rule
New-AzApplicationSecurityGroup -ResourceGroupName rg-net -Name asg-web -Location eastus
```

> 💡 **Exam Tip:** When a question lists rules, sort by priority and walk down — **lowest number first, stop at the first match**. Then repeat for the *other* NSG in the path: inbound = subnet → NIC, outbound = NIC → subnet, and **both must say Allow**. "Health probes are failing" almost always means someone blocked **AzureLoadBalancer** / **168.63.129.16**.

> ⚠️ **Common Pitfall:** Default rules can't be deleted, but they *can* be overridden — a custom **DenyAllInBound-style rule is unnecessary** (65500 already does it), while blocking VNet traffic requires a custom Deny *below* 65000. Also, ASGs don't filter anything by themselves — they are just NIC groupings that only take effect when **referenced in an NSG rule**.

## Evaluate effective security rules in NSGs

- **What it is:** **Effective security rules** is a read-only view that merges the subnet NSG and the NIC NSG (plus default rules) into the **combined result actually applied** to a network interface.
- **Why it matters:** With two NSGs in the path, portal rule lists lie by omission — a rule that looks fine on the NIC can be silently pre-empted by a subnet deny. Effective rules is the admin's ground truth for "why can't this VM be reached?"

Where to look and what to run:

| Method | How |
|---|---|
| Portal (NIC blade) | VM → **Networking** → NIC → **Effective security rules** |
| Portal (**Network Watcher**) | Network Watcher → **Effective security rules** (pick VM/NIC) |
| Azure CLI | `az network nic list-effective-nsg -g rg-net -n vm-web1-nic` |
| PowerShell | `Get-AzEffectiveNetworkSecurityGroup -NetworkInterfaceName vm-web1-nic -ResourceGroupName rg-net` |

- The VM must be **running** — effective rules are computed from the live data path, so a deallocated VM returns an error.
- Pair it with Network Watcher's **IP flow verify**, which answers a single 5-tuple question ("would TCP 3389 from 203.0.113.5 be allowed?") and names the exact rule that allowed or denied it.

> 💡 **Exam Tip:** "View the *combined* rules applied to a VM's NIC" = **Effective security rules**. "Test whether a *specific* packet would be allowed and identify the rule responsible" = **IP flow verify**. Both live under **Network Watcher**.

> ⚠️ **Common Pitfall:** Troubleshooting by reading only one NSG. If the subnet NSG denies inbound traffic, no NIC-level Allow can save it — the subnet is evaluated **first** on inbound, and effective rules is the only view that shows the merged outcome.

## Implement Azure Bastion

- **What it is:** **Azure Bastion** is a **managed jump service** deployed into a dedicated subnet that provides **RDP and SSH in the browser over TLS on port 443** through the Azure portal.
- **Why it matters:** Your VMs need **no public IP at all**, and NSGs can **block 3389/22 from the Internet entirely** — Bastion connects to VMs over their **private IPs** from inside the VNet, eliminating the classic exposed-RDP attack surface.

Deployment facts to memorize:

- The subnet must be named exactly **`AzureBastionSubnet`** and be at least **/26** — no NSG-attached VMs live in it, only the Bastion hosts.
- The Bastion resource needs a **Standard SKU public IP** (Basic public IPs are retired); users reach it at `https://portal.azure.com` — no client software, no agent on the VMs.
- Bastion reaches peered VNets, so one Bastion in a **hub VNet** can serve VMs in spoke VNets.

| SKU | Defining features |
|---|---|
| **Developer** | **Free**, connects to **one VM at a time**, limited regions, no dedicated subnet — for dev/test |
| **Basic** | Dedicated deployment, browser RDP/SSH, fixed instance count |
| **Standard** | **Scales host instances** (2–50), **native client** support (`az network bastion rdp/ssh/tunnel`), file transfer, shareable links, IP-based connections |
| **Premium** | Everything in Standard plus **session recording** and private-only deployment |

```bash
az network vnet subnet create -g rg-net --vnet-name vnet-hub \
  -n AzureBastionSubnet --address-prefixes 10.0.255.0/26
az network public-ip create -g rg-net -n pip-bastion --sku Standard
az network bastion create -g rg-net -n bas-hub --vnet-name vnet-hub \
  --public-ip-address pip-bastion --sku Standard

# Native-client connections (Standard SKU or higher)
az network bastion rdp --name bas-hub -g rg-net --target-resource-id <vm-id>
az network bastion ssh --name bas-hub -g rg-net --target-resource-id <vm-id> --auth-type ssh-key --username azureuser --ssh-key ~/.ssh/id_rsa
az network bastion tunnel --name bas-hub -g rg-net --target-resource-id <vm-id> --resource-port 22 --port 2222
```

> 💡 **Exam Tip:** The two rote facts appear constantly: subnet name **AzureBastionSubnet** (exact spelling, no NSG customization games) and minimum size **/26**. "Connect with the native RDP/SSH client instead of the browser" or "az network bastion tunnel" = **Standard** SKU or higher; "record sessions" = **Premium**; "free for a single VM" = **Developer**.

> ⚠️ **Common Pitfall:** Bastion removes the need for a public IP **on the VMs**, not on Bastion itself — the Bastion host requires a **Standard public IP** (except the Developer SKU). And Bastion is not a VPN: it gives interactive RDP/SSH sessions, not network-layer connectivity for applications.

## Configure service endpoints for Azure PaaS services

- **What it is:** A **service endpoint** is a **per-subnet switch** that extends your **VNet identity** to an Azure PaaS service (Storage, SQL, Key Vault, etc.) over the **Azure backbone**, so the service's firewall can then **allow that specific subnet**.
- **Why it matters:** It is the **free**, low-friction way to lock a PaaS resource down to "only my subnet" — no NAT, no appliances, and traffic never rides the public Internet even though the service keeps its public address.

How it works, step by step:

1. Enable the endpoint on the subnet (e.g., `Microsoft.Storage`); the subnet's outbound route to that service now goes directly onto the backbone.
2. On the PaaS resource, set the firewall to **deny public access** and **allow the VNet/subnet**.
3. Traffic sourced from the subnet is identified by its **VNet/subnet identity** (not a public NAT IP), so the firewall rule matches.

The critical properties the exam probes:

- The service **keeps its public endpoint** — the same `mystorage.blob.core.windows.net` name resolves to a **public IP**; what changes is that traffic *from your subnet* gets private, identity-tagged treatment and the firewall shuts everyone else out.
- Service endpoints work **only from within Azure VNets** — **on-premises clients cannot use them**, because your datacenter has no Azure subnet identity. On-prem traffic must be allowed by public IP or moved to a private endpoint.
- **No extra cost** — service endpoints are free.

```bash
az network vnet subnet update -g rg-net --vnet-name vnet-hub -n snet-app \
  --service-endpoints Microsoft.Storage Microsoft.Sql

az storage account network-rule add -g rg-data --account-name stcontoso \
  --vnet-name vnet-hub --subnet snet-app
az storage account update -g rg-data -n stcontoso --default-action Deny
```

> 💡 **Exam Tip:** "Restrict the storage account to a subnet, at **no additional cost**" = **service endpoint**. Remember it's a two-sided configuration: the **subnet** turns the endpoint on, and the **PaaS firewall** allows the subnet — enabling only one side either changes nothing or locks everyone out.

> ⚠️ **Common Pitfall:** A service endpoint does **not** give the service a private IP and does **not** help on-premises users — the resource still answers on its public endpoint. If the requirement says "no public endpoint," "reachable from on-premises over VPN/ExpressRoute," or "private IP address," a service endpoint is the wrong answer; that's a private endpoint.

## Configure private endpoints for Azure PaaS services

- **What it is:** A **private endpoint** (the **Azure Private Link** technology) is a **NIC with a private IP address from your subnet** mapped to **one specific PaaS resource** (one storage account, one SQL server, one Key Vault).
- **Why it matters:** Traffic stays **fully private** end to end; the resource is reachable from **peered VNets** and from **on-premises over VPN or ExpressRoute**, and you can **disable the public endpoint entirely** — the strongest PaaS isolation Azure offers.

The piece candidates forget is **DNS**. The service's public name must resolve to the private IP *inside* your network:

- Create the matching **`privatelink.*` private DNS zone** — e.g., **`privatelink.blob.core.windows.net`** for blob storage, `privatelink.database.windows.net` for Azure SQL — and **link it to the VNet**.
- Azure adds a CNAME: `stcontoso.blob.core.windows.net` → `stcontoso.privatelink.blob.core.windows.net` → the endpoint's private IP (e.g., 10.0.2.5). Outside the network, the same name still resolves publicly (and gets refused if you disabled public access).
- Unlike service endpoints, private endpoints **cost money**: an **hourly charge per endpoint plus a per-GB** data-processing charge.

```bash
az network private-endpoint create -g rg-net -n pe-stcontoso \
  --vnet-name vnet-hub --subnet snet-app \
  --private-connection-resource-id $(az storage account show -g rg-data -n stcontoso --query id -o tsv) \
  --group-id blob --connection-name conn-stcontoso

az network private-dns zone create -g rg-net -n privatelink.blob.core.windows.net
az network private-dns link vnet create -g rg-net \
  --zone-name privatelink.blob.core.windows.net -n dnslink-hub \
  --virtual-network vnet-hub --registration-enabled false
az network private-endpoint dns-zone-group create -g rg-net \
  --endpoint-name pe-stcontoso -n default \
  --private-dns-zone privatelink.blob.core.windows.net --zone-name blob
```

The discrimination table — a **guaranteed exam item**:

| | **Service endpoint** | **Private endpoint (Private Link)** |
|---|---|---|
| What the service gets | Keeps its **public IP**; subnet traffic tagged with VNet identity | A **private IP in your subnet** via a dedicated NIC |
| Scope | The **whole service type** for a subnet (firewall narrows it) | **One specific resource** (one storage account, one SQL server) |
| From on-premises (VPN/ER) | **No** | **Yes** |
| From peered VNets | Only if the peered subnet enables its own endpoint | **Yes** |
| Disable public endpoint | No — public endpoint remains | **Yes** — public access can be turned off entirely |
| DNS changes needed | None | **privatelink.\*** private DNS zones linked to the VNet |
| Cost | **Free** | **Hourly + per-GB** |

> 💡 **Exam Tip:** Sort by the requirement's strongest word. "Private IP address," "no public endpoint," "accessible from on-premises," or "data must never traverse a public endpoint" = **private endpoint**. "Cheapest / no cost way to restrict to a subnet" = **service endpoint**. If storage works by IP but fails by name after adding a private endpoint, the missing piece is the **private DNS zone**.

> ⚠️ **Common Pitfall:** Creating the private endpoint but skipping DNS. Clients keep resolving the public IP, and connections fail once public access is disabled — the fix is the **privatelink zone + VNet link** (or a DNS forwarder for on-prem resolution), not more firewall rules. Also remember granularity: a private endpoint maps to **one resource**, so ten storage accounts need ten endpoints.

## How It Fits Together (mental model)

Picture Contoso hardening its three-tier app. The admin creates one **NSG** for the web subnet and reuses another across both back-end subnets — remembering that **one NSG can serve many subnets and NICs** — and writes **5-tuple** rules with **priorities from 100 to 4096**, knowing the **lowest number wins and processing stops at the first match**, while the built-in **65000/65001/65500 default rules** (which **cannot be deleted**, only overridden) quietly allow **VirtualNetwork** traffic and the **AzureLoadBalancer** health probes from **168.63.129.16** before **DenyAllInBound** drops the rest. Instead of chasing IP addresses, she joins each web NIC to a **webservers ASG** and each database NIC to a **dbservers ASG** (all in the same VNet, as required) and writes one rule: webservers → dbservers on 1433 — **stateful** flow tracking handles the replies. When a developer reports a blocked connection, she opens **effective security rules** on the NIC (via **Network Watcher**) and sees the **subnet NSG** denying inbound before the **NIC NSG** ever gets a vote. For admin access she deploys **Azure Bastion** — **Standard SKU** for the native `az network bastion rdp` client — into the **AzureBastionSubnet** (**/26**), strips every **public IP** off the VMs, and blocks **3389/22** from the **Internet** tag outright, since Bastion delivers RDP/SSH **over TLS 443** in the browser. The app's storage account is first locked to the app subnet with a free **service endpoint** — but because the auditors demand **no public endpoint** and access from on-premises over **ExpressRoute**, she replaces it with a **private endpoint**: a NIC holding a **private IP** mapped to that one storage account, made resolvable by a **privatelink.blob.core.windows.net** private DNS zone linked to the VNet.

## Scenario Keyword Cheat Sheet

| The question says... | The answer is... |
|---|---|
| "Filter traffic by source, port, destination, port, protocol" | NSG 5-tuple rule |
| "Two rules conflict — which applies?" | The **lower priority number**; evaluation stops at first match |
| "Delete the DenyAllInBound default rule" | Impossible — override it with a lower-numbered custom rule |
| "Inbound traffic blocked despite an Allow on the NIC NSG" | Subnet NSG evaluated first — both must allow |
| "Load balancer health probes failing after NSG change" | Allow **AzureLoadBalancer** tag (168.63.129.16) |
| "Rule should follow app roles, not IP addresses" | Application security groups (ASGs) |
| "ASGs in one rule from different VNets" | Not allowed — same VNet only |
| "Do I need a rule for the reply traffic?" | No — NSGs are stateful |
| "See the combined subnet + NIC rules applied to a VM" | Effective security rules (NIC blade / Network Watcher) |
| "Test whether a specific packet would be allowed" | Network Watcher IP flow verify |
| "RDP/SSH without public IPs on VMs, via the portal over 443" | Azure Bastion |
| "Subnet name and minimum size for Bastion" | **AzureBastionSubnet**, **/26** |
| "Native client / az network bastion tunnel / file transfer" | Bastion **Standard** SKU (or higher) |
| "Session recording for privileged access" | Bastion **Premium** SKU |
| "Free way to restrict a storage account to one subnet" | Service endpoint |
| "PaaS access needed from on-premises over VPN/ExpressRoute" | Private endpoint (service endpoints don't work from on-prem) |
| "Give the PaaS resource a private IP; disable its public endpoint" | Private endpoint (Private Link) |
| "Private endpoint reachable by IP but not by name" | Missing **privatelink.\*** private DNS zone linked to the VNet |
