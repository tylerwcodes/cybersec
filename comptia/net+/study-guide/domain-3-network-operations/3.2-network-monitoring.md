# Objective 3.2 — Given a scenario, use network monitoring technologies.

You can't manage what you can't see. Objective 3.2 covers the *methods* used to collect network telemetry — SNMP, flow data, packet captures, logs, APIs, port mirroring — and the *solutions* built on top of them: discovery, traffic analysis, and performance/availability/configuration monitoring. Because this is a "given a scenario" objective, the exam gives you a symptom or a goal ("we need to know *who* is consuming WAN bandwidth," "we need the *contents* of the packets," "we need alerts when a router's CPU spikes") and asks which technology fits. The high-yield facts are the SNMP port numbers and version differences, the syslog severity levels 0–7, and knowing the depth-of-visibility ladder: SNMP counters → flow metadata → full packet capture.

## Methods

### SNMP (Simple Network Management Protocol)

SNMP is the classic protocol for monitoring (and optionally configuring) network devices. Architecture:

- **Manager** — the network management station (NMS) that collects data (e.g., PRTG, SolarWinds, LibreNMS).
- **Agent** — software running on each managed device (switch, router, printer, UPS, server) that answers queries and sends notifications.
- The manager **polls** agents with **GET** requests (and can change settings with **SET** requests) on **UDP port 161**.
- Agents send unsolicited **traps** to the manager on **UDP port 162**.

#### Traps

A trap is an **agent-initiated, unsolicited** notification sent the moment an event occurs — interface down, high temperature, fan failure — without waiting for the next poll. Traps give real-time awareness; polling gives regular trend data. (SNMP *informs* are acknowledged traps.) Well-run environments use both: scheduled polling for graphs/baselines, traps for immediate event alerts.

| | Polling (GET) | Traps |
|---|---|---|
| Initiated by | Manager | Agent |
| Timing | Fixed interval (e.g., every 5 min) | Immediately when event occurs |
| Port | UDP 161 (on the agent) | UDP 162 (on the manager) |
| Best for | Trends, graphs, baselines | Real-time event notification |

#### Management Information Base (MIB)

The **MIB** is the structured database of everything an agent can report — a hierarchical tree of variables, each identified by an **OID (Object Identifier)**, a dotted numeric path such as `1.3.6.1.2.1.2.2.1.10` (interface inbound octets). Standard MIBs (MIB-II) cover common data like interface counters and uptime; vendors publish private MIBs for device-specific data. The manager loads MIB files so it can translate numeric OIDs into human-readable names and know what to poll.

#### Versions: v2c vs. v3

| Feature | SNMPv1 | SNMPv2c | SNMPv3 |
|---|---|---|---|
| Authentication | Community string | Community string | Username + HMAC authentication (MD5/SHA) |
| Encryption | None | None | Yes — privacy via DES/AES |
| Credentials on the wire | Plaintext | **Plaintext** | Protected |
| Extras | — | Bulk retrieval (GetBulk), 64-bit counters | Security levels: noAuthNoPriv / authNoPriv / **authPriv** |

- **v2c** added efficiency (GetBulk, 64-bit counters) but kept the v1 security model: a **community string** sent in **plaintext**.
- **v3** is the only version with real security: **user-based authentication** (proves the message source and integrity) and **encryption/privacy** (hides the contents). Its three security levels are noAuthNoPriv, authNoPriv, and authPriv (authentication + privacy — use this one).

#### Community Strings

A community string is a shared password used by SNMPv1/v2c — typically a **read-only** string (default `public`) and a **read-write** string (default `private`). Because they cross the network unencrypted, anyone sniffing the wire can capture them; a captured read-write string allows reconfiguration of devices. Minimum hardening: change the defaults, use read-only wherever possible, restrict by ACL — but the real fix is SNMPv3.

#### Authentication

SNMPv3 replaces community strings with per-user credentials: authentication (HMAC-MD5/HMAC-SHA) verifies the sender and message integrity, and the privacy option encrypts the payload (DES/AES). 

> 💡 **Exam Tip:** Port pairs to memorize: agents listen for queries on **UDP 161**; managers receive traps on **UDP 162**. Version security: **v2c = plaintext community strings, no encryption; v3 = authentication + encryption (authPriv)**. If a scenario mentions "credentials visible in a packet capture" of monitoring traffic, the fix is SNMPv3.

### Flow Data

Flow technologies (**NetFlow** — Cisco, **sFlow** — sampled, multi-vendor, **IPFIX** — the IETF standard derived from NetFlow v9) export **metadata about traffic conversations, not the packets themselves**. A flow record summarizes: source/destination IP, source/destination port, protocol, byte and packet counts, timestamps, interface. A flow **exporter** on the router/switch sends records to a **collector** for analysis.

- Answers: *Who is talking to whom? Which application/host is consuming the bandwidth? When?*
- Does **not** capture payloads — you can see that Host A moved 4 GB to Host B on port 443, but not what the data was.
- Far lighter-weight than packet capture, so it can run continuously network-wide. (sFlow specifically *samples* 1-in-N packets rather than accounting for every flow, trading accuracy for scale.)

> 💡 **Exam Tip:** "The WAN link is saturated — identify which user/application is responsible" → **flow data (NetFlow)**. "We must inspect the actual contents/payload of the traffic" → **packet capture**. This flow-vs-capture distinction is one of the most reliably tested points in 3.2.

### Packet Capture

Packet capture (protocol analysis) records **complete packets — headers and full payload** — for deep inspection with tools like **Wireshark** (GUI) or **tcpdump** (CLI). It is the maximum-fidelity view: you can decode protocol handshakes, read unencrypted contents, measure retransmissions and handshake timing, and prove exactly what crossed the wire. Costs: enormous storage at scale and privacy/security implications, so captures are typically targeted (specific segment, host, or timeframe) rather than continuous. To capture traffic that isn't addressed to your analyzer, you need **port mirroring/SPAN** or a hardware **tap**, and a NIC in promiscuous mode.

Visibility ladder (memorize): **SNMP** = device health counters → **Flow data** = conversation metadata (who/what/when/how much) → **Packet capture** = full contents (exactly what was sent).

### Baseline Metrics

A **baseline** is a documented record of normal network behavior — typical bandwidth utilization, CPU/memory, latency, error rates — captured over time under normal conditions. Baselines matter because raw numbers are meaningless without context: is 70% CPU a problem? Only the baseline knows. Baselines are re-captured after major changes and used for capacity planning ("utilization grows 5%/month; the link saturates in Q3").

#### Anomaly Alerting / Notification

Monitoring systems compare live metrics against the baseline (or configured thresholds) and generate **alerts/notifications** — email, SMS, dashboard, ticket — when values deviate abnormally: a traffic spike at 3 a.m., interface errors climbing, CPU pinned. Anomaly-based alerting catches problems that fixed thresholds miss, but thresholds must be tuned to avoid **alert fatigue** (so many false alarms that real ones are ignored).

### Log Aggregation

Every device produces logs. Log aggregation centralizes them so events can be searched, correlated across devices, retained per policy, and preserved even if the originating device is compromised or fails.

#### Syslog Collector

**Syslog** is the standard protocol for sending log messages to a central **syslog collector/server**, traditionally over **UDP port 514** (TCP 514 and TLS 6514 variants exist for reliability/security). Each message carries a facility (source category) and a **severity level 0–7** — memorize all eight, in order:

| Level | Name | Meaning |
|---|---|---|
| 0 | **Emergency** | System is unusable |
| 1 | **Alert** | Action must be taken immediately |
| 2 | **Critical** | Critical conditions |
| 3 | **Error** | Error conditions |
| 4 | **Warning** | Warning conditions |
| 5 | **Notice** | Normal but significant condition |
| 6 | **Informational** | Informational messages |
| 7 | **Debug** | Debug-level messages |

**Lower number = more severe.** Configuring a device to log "at level 4" means it sends levels 0–4 (Warning and everything more severe). Mnemonic: **E**very **A**wesome **C**isco **E**ngineer **W**ill **N**eed **I**ce cream **D**aily.

> ⚠️ **Common Pitfall:** Students invert the scale. **0 is the WORST (Emergency), 7 is the least severe (Debug).** Also don't confuse the ports: syslog = UDP **514**; SNMP = UDP **161/162**.

#### Security Information and Event Management (SIEM)

A **SIEM** ingests logs and events from many sources (syslog, Windows events, firewalls, IDS/IPS, applications, cloud) and adds intelligence on top of plain aggregation:

- **Correlation** — links related events across devices into one detected incident (e.g., 500 failed logins on the VPN + a success + unusual outbound transfer = likely breach).
- **Real-time alerting** on correlation rules and behavioral analytics.
- **Dashboards, reporting, and forensic search** for investigations.
- **Long-term retention** of normalized logs for compliance (PCI DSS, HIPAA) and after-the-fact investigation.

A syslog collector *stores* logs; a SIEM *analyzes and correlates* them and raises security alerts. Scenario keyword "correlate events from multiple sources" → SIEM.

### API Integration

Modern monitoring platforms expose and consume **APIs** (typically **REST**, exchanging **JSON** over HTTPS). API integration lets tools interoperate and enables automation that SNMP can't do well: a monitoring system can push alerts into a ticketing system automatically, pull device state from an SD-WAN controller, feed dashboards, or trigger automated remediation scripts. APIs are also how you monitor cloud services and controllers that don't speak SNMP. Compared with SNMP, REST APIs are firewall-friendly (HTTPS), return structured JSON, and support configuration as well as monitoring.

### Port Mirroring

**Port mirroring** (Cisco: **SPAN** — Switched Port Analyzer) configures a switch to **copy traffic** from one or more source ports or VLANs to a designated destination port where an analyzer or IDS listens. It exists because switches, by design, only forward frames to the destination port — so a passively attached analyzer would otherwise see almost nothing. Mirroring is how you feed packet-capture tools and intrusion-detection sensors without interrupting traffic. Limits: the mirror port can be oversubscribed (mirroring ten 1G ports into one 1G port drops packets), and mirroring adds load to the switch. The alternative is a dedicated hardware **tap** placed inline.

> 💡 **Exam Tip:** "A technician connects a laptop running Wireshark to a switch port but sees only broadcasts and their own traffic — what must be configured?" → **Port mirroring/SPAN** on the switch.

## Solutions

The "solutions" bullets are the operational capabilities you build from the methods above.

### Network Discovery

Discovery finds what's actually on the network — via ping sweeps, SNMP walks, ARP tables, LLDP/CDP neighbor data — and builds/updates inventory and topology maps. Discovery finds undocumented and **rogue devices** and keeps documentation honest.

- **Ad hoc discovery** — run **on demand**, at a point in time: after a change, during troubleshooting, when investigating a suspicious device, or during an initial site assessment.
- **Scheduled discovery** — runs **automatically at regular intervals** (nightly/weekly), continuously reconciling reality against the asset inventory and alerting on new/missing devices.

### Traffic Analysis

Traffic analysis examines *what kind of traffic* is flowing and *how*: top talkers, protocol/application mix, conversation patterns, bandwidth trends. Inputs are typically **flow data** (broad, continuous) and **packet captures** (deep, targeted). Uses: justify upgrades with utilization data, enforce policy (spotting unauthorized applications), detect anomalies (data exfiltration, scanning, DDoS patterns), and plan QoS.

### Performance Monitoring

Performance monitoring tracks *how well* the network is working: bandwidth utilization, **latency, jitter, packet loss**, interface errors/discards, device CPU and memory. Data comes from SNMP polling, flow data, and synthetic tests; results are graphed against the **baseline** and drive threshold alerts and capacity planning. Jitter and loss monitoring is especially critical for VoIP/video.

### Availability Monitoring

Availability monitoring answers the binary question: **is it up?** Techniques: ICMP ping (reachability), TCP port checks (is the service listening?), HTTP/application checks (does it respond correctly?), and SNMP status polls, at regular intervals with alerting on failure. Availability monitoring produces the **uptime percentages** used to verify SLA compliance (99.9%, 99.999%, etc.). Distinguish it from performance monitoring: availability = up or down; performance = how well it works while up.

### Configuration Monitoring

Configuration monitoring watches device **configurations** rather than traffic: it backs up configs on schedule, **diffs** them against the previous backup and the **baseline/golden configuration**, alerts on unauthorized or out-of-window changes (configuration drift), and supports compliance audits and one-click restore. Scenario keyword "detect unauthorized changes to router configs" → configuration monitoring.

| Solution | Question it answers | Primary data sources |
|---|---|---|
| Network discovery | What devices exist? | Ping sweeps, SNMP, ARP, LLDP/CDP |
| Traffic analysis | What traffic is flowing, who are the top talkers? | Flow data, packet capture |
| Performance monitoring | How well is it performing? | SNMP counters, flow, synthetic tests |
| Availability monitoring | Is it up? What's our uptime %? | Ping, port/service checks |
| Configuration monitoring | Did the config change? Does it match the standard? | Config backups, diffs vs. golden config |

## Key Takeaways

- [ ] SNMP: manager polls agents with GET/SET on UDP 161; agents send traps to the manager on UDP 162.
- [ ] Traps are agent-initiated and immediate; polling is manager-initiated and interval-based.
- [ ] The MIB is the hierarchical database of manageable variables; each variable is addressed by a numeric OID.
- [ ] SNMPv2c = plaintext community strings (default `public`/`private`), GetBulk, 64-bit counters, no security; SNMPv3 = user authentication + encryption (authPriv).
- [ ] Flow data (NetFlow/sFlow/IPFIX) = conversation metadata — who/what/when/how much, no payloads; packet capture (Wireshark/tcpdump) = full headers + payloads.
- [ ] Baselines define "normal"; anomaly alerting notifies when live metrics deviate from baseline/thresholds.
- [ ] Syslog: UDP 514 to a central collector; severities 0 Emergency, 1 Alert, 2 Critical, 3 Error, 4 Warning, 5 Notice, 6 Informational, 7 Debug — lower = worse.
- [ ] SIEM = aggregation + correlation + real-time security alerting + long-term retention; a syslog collector alone just stores.
- [ ] API integration (REST/JSON over HTTPS) connects monitoring to ticketing/automation and covers devices/clouds SNMP can't.
- [ ] Port mirroring/SPAN copies switch traffic to an analyzer port — required for packet capture/IDS on switched networks.
- [ ] Discovery: ad hoc = on demand; scheduled = recurring automatic scans that catch rogue/undocumented devices.
- [ ] Performance = how well; availability = up/down and uptime %; configuration monitoring = config backup, diff, and drift detection.

## Self-Check Questions

1. A network manager wants an immediate notification the instant a switch interface goes down, rather than waiting up to five minutes for the next poll. Which SNMP mechanism, and to which port does it go?
2. Security policy requires that monitoring traffic be both authenticated and encrypted. Which SNMP version and security level satisfy this?
3. The Internet circuit hits 100% utilization every afternoon. Which technology identifies which hosts and applications are responsible without capturing packet contents?
4. Place these syslog severities from MOST to LEAST severe: Warning, Emergency, Debug, Critical, Informational.
5. An analyst plugs a Wireshark laptop into an access port to troubleshoot another VLAN's server traffic but captures nothing useful. What switch feature is missing, and what is Cisco's name for it?

<details>
<summary>Answers</summary>

1. An **SNMP trap** — sent by the agent, unsolicited, to the manager on **UDP port 162**. Polling (UDP 161) is interval-based and would delay awareness.
2. **SNMPv3** at the **authPriv** security level — authentication (HMAC-SHA/MD5) plus privacy (AES/DES encryption). v1/v2c send community strings in plaintext with no encryption.
3. **Flow data** — NetFlow/sFlow/IPFIX exported to a collector shows top talkers, applications, and byte counts (metadata only, no payloads).
4. **Emergency (0) → Critical (2) → Warning (4) → Informational (6) → Debug (7)**. Lower numbers are more severe.
5. **Port mirroring** — the switch must copy the target traffic to the analyzer's port. Cisco calls it **SPAN** (Switched Port Analyzer). Without it, a switch only delivers frames destined for that port (plus broadcast/flooded traffic).
