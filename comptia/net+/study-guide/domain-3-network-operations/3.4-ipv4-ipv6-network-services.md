# Objective 3.4 — Given a scenario, implement IPv4 and IPv6 network services.

Three service families make modern networks usable: **dynamic addressing** (DHCP and SLAAC hand out addresses so humans don't), **name resolution** (DNS turns names into addresses), and **time synchronization** (NTP/PTP/NTS keep every clock aligned so authentication, logging, and certificates work). This is a "given a scenario" objective, so expect applied questions: a client stuck with a 169.254.x.x address, a printer that needs the same IP every day, VoIP phones that can't find their boot server across a subnet boundary, a record type to pick for mail routing, or a protocol to pick for sub-microsecond timestamps on a trading floor. This chapter is fact-dense — DORA, lease timers, option numbers, record types, ports 53/123/443/853 — and nearly every fact in it is exam bait.

## Dynamic Addressing

### DHCP (Dynamic Host Configuration Protocol)

DHCP automatically supplies clients with an IP address, subnet mask, default gateway, DNS servers, lease duration, and more. Server listens on **UDP 67**, client on **UDP 68**. Without DHCP (or when it's unreachable), Windows/macOS clients self-assign an **APIPA/link-local address 169.254.x.x** — the classic symptom of "DHCP server down or unreachable."

#### The DORA Process

A new client leases an address in four messages — memorize **D-O-R-A**:

1. **Discover** — client **broadcasts** "any DHCP servers out there?" (it has no IP yet, so it must broadcast from 0.0.0.0 to 255.255.255.255).
2. **Offer** — a server responds, offering an available address plus configuration.
3. **Request** — client **broadcasts** its acceptance of one specific offer (broadcast so all other offering servers know their offers were declined).
4. **Acknowledge (ACK)** — the chosen server confirms and finalizes the lease.

> 💡 **Exam Tip:** DORA order questions are near-guaranteed. Also remember that the initial exchange is **broadcast-based** — which is exactly why DHCP breaks across routers (routers don't forward broadcasts) and why relay agents exist.

#### Scope

A **scope** is the pool of addresses a DHCP server may lease on one subnet — e.g., 192.168.10.100–192.168.10.200 with mask, gateway, DNS, and lease time. One scope per subnet served.

#### Exclusions

An **exclusion range** carves addresses *out of the scope* that the server must never lease — reserved for statically configured devices (routers, servers, printers) that live inside the scope's range. Exclusions prevent the server from handing a client an address that a static device already uses (duplicate-IP conflict).

#### Reservations

A **reservation** maps a specific client's **MAC address to a fixed IP address**: the client still uses DHCP, but always receives the same address (and centrally managed options). Ideal for printers, cameras, and servers that need stable addresses *with* central management.

> ⚠️ **Common Pitfall:** Exclusion vs. reservation: an **exclusion** means "DHCP, never hand these out" (device is configured statically); a **reservation** means "DHCP, always hand this specific address to this specific MAC." If the question says the device should keep getting its address *from DHCP*, the answer is a reservation.

#### Lease Time

Leases are temporary. At **50% of the lease time (T1)** the client **unicasts** a renewal Request to the original server; if it gets an ACK, the lease timer resets. If renewal fails by **87.5% (T2)**, the client broadcasts to *any* server (rebinding). If the lease fully expires, the client must restart DORA. Short leases (e.g., 1 hour) suit guest Wi-Fi with high device turnover; long leases (days) suit stable office LANs and reduce DHCP traffic.

#### Options

DHCP **options** are numbered parameters delivered with the lease. Know these numbers:

| Option | Provides |
|---|---|
| **3** | Default gateway (router) |
| **6** | DNS server(s) |
| 15 | DNS domain name |
| 51 | Lease time |
| **66** | TFTP/boot server name (VoIP phone provisioning) |
| **67** | Bootfile name |
| 150 | TFTP server IP (Cisco VoIP phones) |

Scenario cue: **VoIP phones that must download firmware/config at boot need option 66/67 (or 150)** pointing at the TFTP/provisioning server.

#### Relay / IP Helper

DHCP Discover messages are broadcasts, and **routers do not forward broadcasts** — so by default a client can't reach a DHCP server on another subnet. A **DHCP relay agent** (Cisco: `ip helper-address` on the client subnet's router interface) listens for client broadcasts, converts them to **unicast**, and forwards them to the DHCP server's IP, stamping in the **GIADDR** (gateway address) so the server knows *which subnet's scope* to allocate from. One central DHCP server can thus serve dozens of subnets.

> 💡 **Exam Tip:** "Clients on the new VLAN get 169.254.x.x addresses; clients on other VLANs are fine; the DHCP server is on a different subnet" → configure a **DHCP relay / IP helper address** on the new VLAN's router interface.

### SLAAC (Stateless Address Autoconfiguration)

IPv6 hosts can configure themselves with **no DHCP server at all**:

1. Host self-generates a **link-local address** (fe80::/10) and verifies uniqueness with Duplicate Address Detection (DAD).
2. Host sends a **Router Solicitation (RS)** (ICMPv6 type 133) asking local routers to identify themselves.
3. Router replies (or periodically multicasts) a **Router Advertisement (RA)** (ICMPv6 type 134) containing the **64-bit network prefix**, default-router (the RA sender), and flags.
4. Host forms a global address = **advertised prefix (64 bits) + self-generated interface identifier (64 bits)**.

The interface ID can come from **EUI-64** — take the interface's 48-bit MAC, insert **FFFE** in the middle, and **flip the 7th bit** (universal/local bit) — or, for privacy (since EUI-64 embeds the trackable MAC), from randomly generated **privacy extensions**, which modern OSs use by default. "Stateless" means no server tracks who has which address; DHCPv6 ("stateful") exists when central control or extra options are needed, and RAs can also point SLAAC hosts at DNS servers (RDNSS) or tell them to fetch options via stateless DHCPv6.

> ⚠️ **Common Pitfall:** SLAAC uses **Router Advertisements from a router**, not a DHCP server. If an IPv6 question involves autoconfiguration via RS/RA and prefix + interface ID, it's SLAAC; if a server leases the address and records it, it's DHCPv6.

## Name Resolution

### DNS (Domain Name System)

DNS resolves names (`www.example.com`) to addresses and much more, using a global **hierarchy**: the **root** servers (`.`) → **top-level domain (TLD)** servers (`.com`, `.org`, `.uk`) → **authoritative name servers** for each domain (holding the actual records). DNS queries use **port 53** (UDP for most queries; TCP for zone transfers and large responses).

#### Recursive Resolution Walkthrough

When you browse to `www.example.com`:

1. Client checks its **local cache** (and the **hosts file** — see below), then queries its configured **recursive resolver** (ISP or corporate DNS, 8.8.8.8, 1.1.1.1...).
2. If the resolver has no cached answer, it queries a **root** server → referred to the **.com TLD** servers.
3. Resolver queries the TLD server → referred to `example.com`'s **authoritative** name servers.
4. Resolver queries the authoritative server → receives the A/AAAA record.
5. Resolver **caches** the answer (for the record's TTL) and returns it to the client.

The resolver does the legwork (**recursive** query on behalf of the client); its exchanges with root/TLD/authoritative servers are **iterative** (each server answers or refers, never chases the answer itself).

#### Record Types

| Record | Maps / purpose | Notes |
|---|---|---|
| **A** | Hostname → **IPv4** address | The workhorse record |
| **AAAA** | Hostname → **IPv6** address | "Quad-A" |
| **CNAME** | Alias → canonical hostname | Points a name at another *name*, never an IP |
| **MX** | Domain → **mail server** hostname | Has a **preference number: lower = higher priority** |
| **TXT** | Arbitrary text | Carries **SPF** (authorized mail senders) and **DKIM** (mail signing keys), domain verification |
| **NS** | Domain → its authoritative **name servers** | Delegation glue of the hierarchy |
| **PTR** | IP address → hostname (**reverse** lookup) | Lives in reverse zones; mail servers check PTRs |

> 💡 **Exam Tip:** High-yield record facts: **MX = mail, lowest preference wins**; **CNAME = alias to another name**; **PTR = reverse (IP→name)**; **SPF/DKIM live in TXT records**; **AAAA = IPv6**. A question about "verifying which servers may send email for the domain" = SPF in a **TXT** record.

#### Zone Types: Forward and Reverse

- **Forward zone**: name → IP resolution (contains A, AAAA, CNAME, MX, TXT, NS...). "What's the IP of `mail.example.com`?"
- **Reverse zone**: IP → name resolution using **PTR** records, under the special domain **`in-addr.arpa`** (IPv4; octets reversed — 10.20.30.40 → `40.30.20.10.in-addr.arpa`) or **`ip6.arpa`** (IPv6). Used by mail anti-spam checks, logging, and troubleshooting tools that display names.

#### Authoritative vs. Non-Authoritative

- An **authoritative** answer comes from a name server that *hosts the zone* — the source of truth for that domain.
- A **non-authoritative** answer comes from a resolver's **cache** — a copy of a previous answer, served until its TTL expires. `nslookup` labels these "Non-authoritative answer." Cached answers are fast but can be **stale** (a recent record change may not be visible until TTL expiry — why DNS changes "take time to propagate").

#### Primary vs. Secondary

- The **primary** name server holds the **writable master copy** of the zone file — all record changes are made here.
- **Secondary** servers hold **read-only copies** obtained via **zone transfer** (AXFR/IXFR, over **TCP 53**), refreshed per the zone's SOA timers or NOTIFY messages. Secondaries provide redundancy and load distribution — and both primary and secondary are **authoritative** for the zone.

> ⚠️ **Common Pitfall:** Primary vs. secondary is about *where the zone is edited* (write vs. read-only replica) — **both are authoritative**. Authoritative vs. non-authoritative is about *zone owner vs. cache*. These are two different axes; the exam mixes them deliberately.

#### DNSSEC (Domain Name Security Extensions)

DNSSEC adds **digital signatures** to DNS records (RRSIG, DNSKEY, DS records forming a chain of trust from the root down). Resolvers validate the signatures to guarantee **origin authenticity and integrity** — the answer really came from the zone owner and wasn't altered — which defeats **DNS spoofing/cache poisoning**. Crucial nuance: **DNSSEC does NOT encrypt anything**; queries and answers remain readable on the wire. Integrity ✔, confidentiality ✘.

#### DoH and DoT

**DNS over HTTPS (DoH)** and **DNS over TLS (DoT)** encrypt the *transport* of DNS queries between client and resolver, providing the **privacy/confidentiality** DNSSEC doesn't:

| | DoT | DoH |
|---|---|---|
| Port | **TCP 853** (dedicated) | **TCP 443** (HTTPS) |
| Visibility to network admins | Identifiable as DNS traffic (own port) — easy to see/filter | Blends into ordinary HTTPS — hard to distinguish or block |
| Encrypts queries? | Yes (TLS) | Yes (inside HTTPS) |

> 💡 **Exam Tip:** Memorize **DoT = 853, DoH = 443**, and the roles: **DNSSEC = integrity/authenticity via signatures (no encryption); DoH/DoT = encryption/privacy of queries (no record signing).** They are complementary, not competing.

### Hosts File

Before DNS existed there was a static text file mapping names to IPs — and it still exists on every OS: **`/etc/hosts`** (Linux/macOS), **`C:\Windows\System32\drivers\etc\hosts`** (Windows). The OS checks the hosts file **before querying DNS**, and its entries **override DNS answers**. Legitimate uses: testing a server before changing public DNS, lab name resolution, ad-blocking. Risks: it's a malware target (redirecting banking sites) and a classic troubleshooting culprit — "one machine resolves the name to the wrong address, every other machine is fine" → check the hosts file.

## Time Protocols

Accurate time matters more than students expect: Kerberos authentication tolerates only ~5 minutes of skew, TLS certificates have validity windows, and log correlation/forensics is impossible when device clocks disagree.

### NTP (Network Time Protocol)

NTP synchronizes clocks over the network on **UDP port 123**, typically achieving millisecond-level accuracy on a LAN. NTP organizes time sources in **strata**:

- **Stratum 0** — the reference clocks themselves: atomic clocks, GPS receivers. (Not on the network directly.)
- **Stratum 1** — servers directly connected to a stratum-0 source.
- **Stratum 2** — servers that sync from stratum 1; **stratum 3** syncs from 2, and so on (each hop adds a stratum).
- **Stratum 16** means unsynchronized/unusable.

Lower stratum = closer to the reference = generally more accurate. Enterprises typically point internal devices at a couple of internal stratum-2/3 servers, which sync upstream to public stratum-1 pools — keeping WAN NTP traffic minimal and time consistent inside.

### PTP (Precision Time Protocol)

**PTP, IEEE 1588**, is for when milliseconds aren't good enough: it achieves **sub-microsecond** (nanosecond-class) synchronization by using **hardware timestamping** — timestamps applied by the NIC/switch hardware at the moment a packet hits the wire, eliminating OS/software delay — plus PTP-aware network elements (boundary/transparent clocks) that compensate for switch residence time. A **grandmaster clock** is the authoritative source. Use cases: **financial trading** (regulatory timestamp requirements), **industrial automation**, power utilities/substations, telecom (5G), and professional broadcast/audio-video. NTP = general IT, milliseconds; PTP = specialized, sub-microsecond, needs hardware support.

### NTS (Network Time Security)

Plain NTP is unauthenticated — an on-path attacker can spoof responses and shift a victim's clock (breaking certificate validation, Kerberos, and log integrity). **NTS (RFC 8915) adds cryptographic security to NTP**: a **TLS**-based key-establishment phase (NTS-KE) hands the client cookies and keys, after which NTP packets carry authenticated extension fields. The result: **authentication and integrity for time sync — the client knows responses genuinely came from the intended server and weren't tampered with**. Note the pattern echo: like DNSSEC for DNS, NTS is about *authenticity/integrity* of the time data (the timestamp itself isn't secret).

| Protocol | Port / standard | Accuracy | Security | Typical use |
|---|---|---|---|---|
| **NTP** | UDP 123 | Milliseconds | None natively | General IT clock sync |
| **PTP** | IEEE 1588 | Sub-microsecond | — | Trading, industrial, broadcast (hardware timestamps) |
| **NTS** | TLS-secured NTP (RFC 8915) | Same as NTP | Authentication + integrity | Trustworthy time over untrusted networks |

## Key Takeaways

- [ ] DORA: Discover → Offer → Request → Acknowledge; initial exchange is broadcast (client UDP 68, server UDP 67); no DHCP reachable → APIPA 169.254.x.x.
- [ ] Scope = leasable pool per subnet; exclusion = never lease (static devices); reservation = MAC always gets the same IP via DHCP.
- [ ] Lease renewal: unicast to the original server at 50% (T1); rebind broadcast at 87.5% (T2); full expiry → DORA again.
- [ ] Options: 3 = default gateway, 6 = DNS, 66/67 = TFTP boot server/bootfile (VoIP provisioning).
- [ ] Relay agent / IP helper converts client DHCP broadcasts to unicast so one server can serve remote subnets.
- [ ] SLAAC: RS → RA delivers the /64 prefix; host appends an interface ID (EUI-64 = MAC + FFFE + flipped 7th bit, or random privacy address); no server state.
- [ ] DNS hierarchy: root → TLD → authoritative; recursive resolver walks it, caches by TTL; hosts file is checked before DNS and overrides it.
- [ ] Records: A = IPv4, AAAA = IPv6, CNAME = alias→name, MX = mail (lowest preference wins), TXT = SPF/DKIM, NS = name servers, PTR = reverse.
- [ ] Forward zone = name→IP; reverse zone = IP→name via PTR under in-addr.arpa / ip6.arpa.
- [ ] Authoritative = from the zone's own servers; non-authoritative = from a resolver's cache. Primary = writable master; secondary = read-only zone-transfer copy (both authoritative).
- [ ] DNSSEC = signatures → integrity/authenticity, **no encryption**; DoT = TCP 853; DoH = TCP 443 (hides inside HTTPS).
- [ ] NTP = UDP 123, stratum 0 (reference) / 1 / 2...; PTP = IEEE 1588, hardware timestamps, sub-microsecond (finance/industrial); NTS = TLS-based authentication for NTP.

## Self-Check Questions

1. List the four DHCP lease messages in order, and state which are broadcast during initial acquisition.
2. A networked printer must always be reachable at 10.1.5.25, but the admin wants its address centrally managed by DHCP. Exclusion or reservation — and why?
3. VoIP phones on VLAN 40 boot but never retrieve their configuration files. The provisioning (TFTP) server is on VLAN 10. Which two DHCP mechanisms are likely involved in the fix?
4. Your company changed a web server's A record an hour ago; some users still reach the old address, and `nslookup` shows "Non-authoritative answer." Explain what's happening.
5. A brokerage must timestamp trades with sub-microsecond precision, and separately wants its office NTP clients protected from spoofed time responses. Which protocol answers each need?

<summary>Answers</summary>

1. **Discover, Offer, Request, Acknowledge.** Discover and Request are **broadcast** by the client during initial acquisition (Request is broadcast so all offering servers learn the client's choice); renewal Requests are later sent **unicast** at T1 (50% of lease).
2. A **reservation** — it binds the printer's MAC to 10.1.5.25 while keeping the address under DHCP's central management. An exclusion would require configuring the printer statically, taking it out of DHCP entirely.
3. **DHCP relay / IP helper** on VLAN 40's router interface (so the phones' DHCP broadcasts reach the server on another subnet) and **DHCP options 66/67** (or Cisco option 150) so the lease tells phones the TFTP server name and bootfile to download.
4. Users' recursive resolvers are serving the **cached (non-authoritative)** old record until its **TTL** expires. Only after the cache entry ages out will resolvers re-query the authoritative servers and return the new address — this is normal propagation delay, not an outage.
