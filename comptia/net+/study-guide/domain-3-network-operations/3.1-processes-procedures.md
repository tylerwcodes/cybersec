# Objective 3.1 — Explain the purpose of organizational processes and procedures.

Networks are only as manageable as the paperwork behind them. Objective 3.1 covers the documentation, life-cycle, change, and configuration practices that keep a network understandable, auditable, and recoverable. On the exam this material shows up as "which document would you consult?" and "what is the FIRST/NEXT step?" style questions: you'll be given a scenario (a failed upgrade, an aging switch, a new technician who needs to trace a cable) and asked to pick the correct process artifact — a logical diagram vs. a physical one, an EOL notice vs. an EOS notice, a rollback plan vs. a backup configuration. The distinctions are subtle and heavily tested, so learn precisely what each document or process is *for*, not just what it is.

## Documentation

Documentation is the institutional memory of the network. Good documentation shortens troubleshooting, supports audits and compliance, enables capacity planning, and lets new staff work safely without tribal knowledge. Every artifact below answers a different question about the network.

### Physical vs. Logical Diagrams

- **Physical diagram**: shows *where things actually are* — real devices, physical cable runs, ports, rack positions, rooms, and buildings. Use it to answer "which port on which switch does this wall jack connect to?" or "what will lose power if I shut down this rack?"
- **Logical diagram**: shows *how data flows* — subnets, VLANs, IP addressing, routing relationships, and traffic paths, independent of physical location. Two devices adjacent in a logical diagram might be in different buildings.

| Aspect | Physical diagram | Logical diagram |
|---|---|---|
| Depicts | Actual hardware, cables, ports, locations | IP subnets, VLANs, routing, data flow |
| Answers | "Where is it? What is it plugged into?" | "How does traffic get from A to B?" |
| Typical use | Cabling work, hardware moves, rack planning | Troubleshooting routing/VLAN issues, design |
| Changes when | Equipment is physically moved/recabled | Addressing, VLANs, or routing changes |

> 💡 **Exam Tip:** If the scenario involves *tracing a cable, finding a device, or planning physical work*, the answer is a **physical** diagram (or a cable map/rack diagram). If it involves *subnets, VLANs, or routing paths*, the answer is a **logical** diagram.

### Rack Diagrams

A rack diagram (rack elevation) documents the front/rear layout of an equipment rack, showing each device's position measured in **rack units (U)** — 1U = 1.75 inches. It records what is installed at which U position, power connections, and free space. Rack diagrams are essential when planning new installations (is there space? enough power? airflow?), when directing remote-hands technicians ("remove the server at U12 in rack B4"), and for weight/power/cooling capacity planning.

### Cable Maps and Diagrams

Cable maps document the physical cabling plant: which wall jack connects to which patch-panel port, which patch panel port connects to which switch port, cable types, and cable run paths. Individual cables and both ends of every run should be **labeled** consistently. Without a cable map, tracing a single connection can require a toner probe and hours of work; with one, it takes seconds. Cable documentation should be updated *every time* a cable is added, moved, or removed — stale cable maps are worse than none because they mislead.

### Network Diagrams (Layer 1 / Layer 2 / Layer 3)

Network diagrams are often drawn per OSI layer, and the exam expects you to know what belongs on each:

| Diagram | Shows | Example contents |
|---|---|---|
| **Layer 1 (physical)** | Physical connectivity | Cables, cable types (fiber/copper), ports, patch panels, physical device locations |
| **Layer 2 (data link)** | Switching topology | Switches, VLANs, trunk/access links, link aggregation (LACP), spanning-tree relationships, MAC-level connectivity |
| **Layer 3 (network)** | Routing topology | Routers, firewalls, IP subnets and addresses, routing protocols, gateways, VPN tunnels |

> ⚠️ **Common Pitfall:** VLANs appear on the **Layer 2** diagram (they are a switching construct), while the *subnets mapped to those VLANs* appear on the **Layer 3** diagram. Exam questions probe exactly this boundary.

### Asset Inventory

An asset inventory is a database of everything the organization owns and runs. It supports budgeting, security (you can't patch what you don't know you have), audits, and loss prevention. Track four categories:

- **Hardware**: every physical device — make, model, serial number, asset tag, location, owner, purchase date.
- **Software**: every installed application and version — critical for vulnerability management and patch planning.
- **Licensing**: what licenses are owned, how many seats are in use, and expiration/renewal dates. Prevents both compliance violations (using more than you bought) and waste (paying for unused seats).
- **Warranty support**: coverage terms and expiration dates for each device. Determines whether a failed device gets vendor-repaired for free or must be replaced at cost, and drives refresh planning.

### IP Address Management (IPAM)

IPAM is software (or at minimum a maintained document) that tracks IP address allocation: which subnets exist, which addresses are assigned, to what, and which are free. Modern IPAM tools integrate with **DHCP and DNS** (the combination is sometimes called DDI: DNS, DHCP, IPAM) to automatically discover assignments, detect conflicts and unauthorized devices, and forecast subnet exhaustion. Without IPAM, organizations get duplicate-IP outages and "mystery subnets" nobody remembers allocating.

### Service-Level Agreement (SLA)

An SLA is a contract between a service provider and a customer that defines **measurable service commitments** — most famously uptime/availability, but also throughput, latency, time-to-respond, and time-to-repair — plus the remedies (usually service credits) if the provider misses them. SLAs set expectations and give customers recourse.

Memorize the availability table ("counting nines"):

| Availability | Nickname | Max downtime per year |
|---|---|---|
| 99% | "two nines" | ~3.65 days |
| 99.9% | "three nines" | ~8.76 hours |
| 99.99% | "four nines" | ~52.6 minutes |
| 99.999% | "five nines" | ~5.26 minutes |
| 99.9999% | "six nines" | ~31.5 seconds |

> 💡 **Exam Tip:** **"Five nines" (99.999%) ≈ about 5 minutes of downtime per year.** This exact conversion is a classic exam question. Also remember: an SLA defines *what* is promised (e.g., 99.99% uptime, 4-hour repair), and MTTR/RTO-type metrics often appear inside SLAs.

### Wireless Survey / Heat Map

A wireless site survey measures RF conditions throughout a facility; its visual output is a **heat map** — a floor plan color-coded by signal strength (and often noise, interference, and channel overlap). Surveys are performed **before** deployment (predictive/pre-installation survey to plan AP placement and count), **after** deployment (validation survey), and when users report coverage or performance problems (find dead zones, co-channel interference, rogue APs). If the exam scenario says "users in the northeast corner have weak Wi-Fi," the tool to reach for is a wireless survey/heat map.

## Life-Cycle Management

Every product moves through a life cycle: introduction → general availability → end-of-sale → **end-of-life** → **end-of-support**. Life-cycle management means tracking where each asset sits on that curve and planning budget and migrations *before* the cliff, not after.

### End-of-Life (EOL)

**EOL** means the vendor has stopped **selling and actively developing** the product. No new features are added; the product may still receive limited support and security patches for a defined period. EOL is the signal to *start planning replacement*.

### End-of-Support (EOS)

**EOS** (also end-of-service-life, EOSL) is the harder deadline: the vendor **no longer provides any support, patches, or security updates**. Running EOS equipment or software means new vulnerabilities will never be fixed — a serious security and compliance risk (auditors flag EOS systems). EOS is the point where the asset *must* be replaced or isolated.

> ⚠️ **Common Pitfall:** EOL comes **first** and means "no longer sold/developed (support may continue for a while)." EOS comes **later** and means "no support or security patches at all." The exam loves to swap these definitions. Security risk is the key consequence of **EOS**.

### Software Management

Keeping software current is a continuous operational process across three layers:

- **Patches and bug fixes**: small targeted updates that fix defects and security vulnerabilities. Should be evaluated, tested in a non-production environment, then deployed on a schedule (with emergency out-of-band deployment for critical vulnerabilities).
- **Operating system (OS)**: OS versions and updates on servers, clients, and network operating systems on switches/routers. Major OS upgrades go through change management.
- **Firmware**: low-level software embedded in hardware (switch/router firmware, NIC firmware, drive firmware, BIOS/UEFI). Firmware updates fix hardware-level bugs and vulnerabilities but carry higher risk — a failed firmware update can brick a device — so they demand maintenance windows and rollback plans.

### Decommissioning

Decommissioning is the formal retirement of an asset, and it is much more than unplugging it:

1. Remove the device from production (update diagrams, IPAM, monitoring, and the asset inventory).
2. **Data sanitization**: securely erase all data and configurations — wipe drives (secure erase/overwrite), clear device configs, remove credentials, certificates, SNMP strings, and license keys. For high-sensitivity data, physical destruction (shredding, degaussing) may be required.
3. **Asset disposal**: dispose of hardware properly — resale, donation, recycling per e-waste regulations — and record the disposition in the asset inventory.

> 💡 **Exam Tip:** The #1 decommissioning test point: **sanitize data before disposal**. A scenario about a retired router or server appearing on eBay with the old config intact is a data-sanitization failure.

## Change Management

Change management is the formal process ensuring changes to production are **planned, approved, tested, communicated, and reversible** — because most outages are caused not by failures but by changes. A typical change process:

1. **Request** — the change is documented in a tracking system: what, why, risk, impact, affected systems.
2. **Approval** — a change advisory board (CAB) or approver reviews business justification, risk, and scheduling and authorizes (or rejects) the change.
3. **Planning** — test the change in a lab/staging environment; write the implementation steps and a **rollback plan** (exact steps to restore the previous state if the change fails — you must have this *before* you start).
4. **Maintenance window** — the change executes during a pre-approved low-impact time period; affected users are notified in advance.
5. **Implementation and validation** — perform the change, verify success against defined criteria; if validation fails, execute the rollback plan.
6. **Documentation** — update diagrams, baselines, and the asset inventory to reflect the new state; close the change record.

### Request Process Tracking / Service Request

Changes and user requests are tracked in a **ticketing/ITSM system** (service requests). Tracking creates an auditable history: who requested what, who approved it, when it happened, and what the outcome was. When something breaks at 2 a.m., the first troubleshooting question is "what changed recently?" — the change log answers it. Standard, low-risk, pre-approved changes are often handled as routine **service requests**, while higher-risk changes get full CAB review.

> 💡 **Exam Tip:** Scenario: "A technician needs to upgrade firmware on a core switch. What should be done FIRST?" Answer: **submit a change request** (and have an approved rollback plan and maintenance window before touching anything).

## Configuration Management

Configuration management tracks and controls the settings of every network device so that any device can be audited, compared, and rebuilt. Three configuration artifacts matter:

### Production Configuration

The configuration **currently running** on the live device (on Cisco gear, the running-config). It is the real state of the network right now — and it can drift from what was intended if undocumented changes are made.

### Backup Configuration

A **saved copy** of a device's configuration stored off the device (config-management server, version-controlled repository). Backups are taken on a schedule and before/after every change. If a device fails or a change goes wrong, you restore the backup rather than rebuilding by hand. Automated tools can also **diff** the running config against the last backup to detect unauthorized changes (configuration drift).

### Baseline / Golden Configuration

The **approved, standardized template** configuration for a device role — the "known-good" starting point containing the organization's required settings (hardening, SNMP/logging, NTP, AAA, banner, etc.). New devices are deployed from the golden config; existing devices are periodically compared against it, and deviations are flagged for remediation.

| Artifact | What it is | Primary use |
|---|---|---|
| Production config | What's running right now | Live operation; source of truth for current state |
| Backup config | Saved copy of a device's config | Restore after failure or failed change |
| Baseline/golden config | Approved standard template | Deploy new devices; audit for drift |

> ⚠️ **Common Pitfall:** A *backup* config is a snapshot of one specific device's settings; the *golden/baseline* config is the standardized template a device **should** match. Restoring service after a failed change uses the **backup**; auditing for unauthorized deviation compares against the **baseline/golden**.

## Key Takeaways

- [ ] Physical diagrams = where things are and how they're cabled; logical diagrams = subnets/VLANs/routing and data flow.
- [ ] Layer 1 diagram = cabling/ports; Layer 2 = switches/VLANs/trunks; Layer 3 = routers/subnets/routing.
- [ ] Rack diagrams document rack layouts in rack units (1U = 1.75"); cable maps document jack → patch panel → switch port paths.
- [ ] Asset inventory covers hardware, software, licensing, and warranty support — you can't secure, patch, or budget for what you haven't inventoried.
- [ ] IPAM tracks IP allocation and integrates with DHCP/DNS; prevents duplicate-IP conflicts and subnet exhaustion.
- [ ] SLA = contractual, measurable service commitments; five nines = 99.999% ≈ 5.26 minutes of downtime/year.
- [ ] Wireless survey/heat map plans and validates Wi-Fi coverage and finds dead zones/interference.
- [ ] EOL = no longer sold/developed (comes first); EOS = no support or security patches at all (comes later; major security risk).
- [ ] Software management spans patches/bug fixes, OS updates, and firmware — test before deploying; firmware changes need maintenance windows.
- [ ] Decommissioning = remove from service, update records, **sanitize data**, then dispose of the asset properly.
- [ ] Change management: request → approval → rollback plan → maintenance window → implement/validate → document.
- [ ] Production config = running now; backup config = saved restore copy; baseline/golden config = approved standard template for deployment and drift auditing.

## Self-Check Questions

1. A technician must determine which switch port serves wall jack 3B-14 in a conference room. Which two documents are most useful?
2. Your SLA guarantees "five nines" of availability. Approximately how much downtime per year is permitted?
3. A vendor announces that a switch model will no longer receive security patches or technical assistance of any kind. Is this EOL or EOS, and what is the primary risk of continuing to use it?
4. Before a core-router IOS upgrade, what document must exist so the team can restore service if the upgrade fails — and which saved artifact would they actually restore?
5. An auditor asks you to prove that no unauthorized settings exist on your branch routers. Which configuration artifact do you compare each router against?

<details>
<summary>Answers</summary>

1. The **cable map/diagram** (jack → patch panel → switch port) and the **physical network diagram** (or rack diagram to locate the switch). Logical diagrams won't show physical cabling.
2. **About 5.26 minutes per year** (99.999% availability). Four nines ≈ 52.6 minutes; three nines ≈ 8.76 hours.
3. **EOS (end-of-support)** — no more patches or support of any kind. The primary risk is **security**: newly discovered vulnerabilities will never be fixed, so the device must be replaced or isolated. (EOL only means no longer sold/developed.)
4. A **rollback plan** must be written and approved as part of the change request before the work begins. The artifact actually restored is the **backup configuration** (and the prior IOS image).
5. The **baseline/golden configuration** — the approved standard template. Deviations between a device's production config and the golden config indicate drift or unauthorized change.
