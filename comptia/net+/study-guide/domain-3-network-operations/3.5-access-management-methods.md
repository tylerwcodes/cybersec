# Objective 3.5 — Compare and contrast network access and management methods.

Administrators and remote users need ways *into* the network — securely, and ideally in ways that still work when the network itself is broken. Objective 3.5 is explicitly a "compare and contrast" objective, so the exam tests pairs: site-to-site **vs.** client-to-site VPN, split **vs.** full tunnel, SSH **vs.** console **vs.** GUI **vs.** API, in-band **vs.** out-of-band management. Scenario cues decide everything: "two offices permanently connected" vs. "traveling employee," "only corporate traffic through the tunnel" vs. "all traffic inspected," "the WAN is down and we still need to reach the router" (out-of-band), "one hardened entry point into the server VLAN" (jump box). Learn the discriminating keywords and this objective becomes pattern matching.

## Site-to-Site VPN

A **site-to-site VPN** permanently connects two (or more) *networks* — say, HQ and a branch office — through an encrypted tunnel over the Internet, typically **IPsec**, terminated on **routers or firewalls** at each end. Properties:

- **Always-on**: the tunnel is established between gateway devices and stays up; it is infrastructure, not a user action.
- **Transparent to users**: employees at the branch reach HQ resources as if on one WAN — **no VPN client software on end devices**, no login prompt.
- Cost-effective replacement for leased lines/MPLS between offices.

Scenario cue: "connect the new branch office network to headquarters over the Internet" → site-to-site VPN between the sites' edge firewalls/routers.

## Client-to-Site VPN

A **client-to-site VPN** (remote-access VPN) connects an *individual device* — a laptop at home, a hotel, a coffee shop — to the corporate network. The user runs **VPN client software** (or the OS's built-in client), authenticates (ideally with MFA), and receives an encrypted tunnel (IPsec or, very commonly, TLS/SSL-based) to a **VPN concentrator/firewall** at the edge. The tunnel exists only while that user is connected.

| | Site-to-site | Client-to-site |
|---|---|---|
| Connects | Network ↔ network | One device ↔ network |
| Endpoints | Routers/firewalls at each site | User device ↔ VPN concentrator |
| Duration | Always-on, permanent | Per-session, user-initiated |
| Client software | None on user devices | VPN client (or clientless portal) |
| Typical user | Branch offices | Remote/traveling workers |

### Clientless VPN

A **clientless VPN** provides remote access through a **standard web browser using TLS/HTTPS** — no installed VPN client at all. The user logs into a secure **web portal** on the VPN gateway and accesses published internal applications (web apps, file shares, sometimes RDP/SSH rendered in the browser). Trade-offs: works from any device including unmanaged/BYOD machines and kiosks (nothing to install, no admin rights needed), but access is generally **limited to the applications the portal publishes** — it does not place the full device onto the network the way a client tunnel does.

> 💡 **Exam Tip:** "Remote users must reach an internal web app from unmanaged devices with **no software installation**" → **clientless (browser/TLS portal) VPN**.

### Split Tunnel vs. Full Tunnel

Once a client VPN is up, where does the user's *other* traffic go?

| | Split tunnel | Full tunnel |
|---|---|---|
| Corporate-bound traffic | Through the VPN | Through the VPN |
| Internet-bound traffic (Netflix, general browsing) | **Directly out the local Internet connection** | **Also through the VPN**, out the corporate edge |
| Bandwidth load on VPN/HQ | Low | High (all user traffic hauled in) |
| Security control | Less — Internet traffic bypasses corporate inspection/filters | More — all traffic passes corporate security stack |
| Performance for user's personal traffic | Better (no detour) | Slower (hairpin through HQ) |

- **Split tunnel**: only traffic destined for corporate networks enters the tunnel; everything else uses the local ISP directly. Saves VPN bandwidth and improves performance, but the company cannot inspect or filter the user's Internet traffic, and the simultaneously-bridged position is a security consideration.
- **Full tunnel**: **all** traffic is forced through the VPN and egresses through corporate security (firewall, proxy, DLP, content filtering). Maximum visibility and policy control at the cost of bandwidth and latency.

> ⚠️ **Common Pitfall:** Match the driver to the design: "reduce VPN bandwidth consumption / users complain video calls are slow through HQ" → **split** tunnel. "Security requires all remote traffic be inspected/filtered by corporate controls" → **full** tunnel. Don't reverse them under time pressure.

## Connection Methods

How an administrator actually touches a device:

### SSH (Secure Shell)

**Encrypted command-line access on TCP port 22** — the standard for remote CLI management of routers, switches, firewalls, and servers. Replaces Telnet (TCP 23), which sends everything **including credentials in plaintext** and should never be used. SSH supports password authentication and, better, **public-key authentication** (key pairs; the private key never crosses the wire), plus secure file transfer via SCP/SFTP. Scenario cue: "securely manage a switch's CLI over the network" → SSH.

### Graphical User Interface (GUI)

Management via a visual interface — most commonly a device's **web-based GUI (use HTTPS, never HTTP)**, a vendor management application, or a controller dashboard (e.g., wireless LAN controllers, firewall managers). GUIs lower the learning curve, visualize status well, and suit occasional administration; they can be slower for bulk/repetitive work and historically expose more attack surface than a hardened CLI. Windows server equivalents include RDP (TCP 3389); VNC is a cross-platform remote-desktop option.

### API (Application Programming Interface)

Programmatic management — typically **REST APIs over HTTPS exchanging JSON** — used by scripts (Python), automation/orchestration platforms (Ansible, Terraform), and controllers (SDN, cloud). APIs are the method for **automation at scale**: push a configuration change to 500 switches identically, integrate the network with CI/CD or ticketing, and eliminate the typos of hand-typed CLI. Consistency and speed are the selling points; authentication uses tokens/keys and must be protected like any credential.

### Console

**Direct physical connection to a device's console (serial) port** using a **console/rollover cable** (classically RJ45-to-DB9 or USB) and terminal-emulator software (PuTTY, screen) — traditionally at 9600 baud, 8-N-1. The console works **without any network connectivity or IP configuration**, making it the method for:

- **Initial configuration** of a brand-new device (it has no IP yet).
- **Recovery** when the device is misconfigured off the network, or for password/ROMMON recovery.

The console is inherently **out-of-band** — it does not depend on the production network at all.

| Method | Interface | Transport | Best for |
|---|---|---|---|
| SSH | CLI | Network, TCP 22, encrypted | Day-to-day secure remote CLI |
| GUI | Graphical/web | Network, HTTPS | Visual admin, dashboards, occasional tasks |
| API | Programmatic (REST/JSON) | Network, HTTPS | Automation, scale, integration |
| Console | CLI | **Physical serial — no network needed** | Initial setup, recovery, emergencies |

> 💡 **Exam Tip:** "A brand-new switch has no IP address — how do you configure it?" → **console cable**. "Apply the same change to hundreds of devices automatically" → **API**. "Encrypted remote CLI" → **SSH (22)**; Telnet (23) is the insecure wrong answer planted next to it.

## Jump Box / Host

A **jump box** (jump host/jump server, or richer "bastion" appliances) is a **hardened intermediary system** that serves as the **single controlled entry point** into a secured network segment — a server VLAN, a DMZ, an OT/SCADA network, or cloud subnets. Administrators first connect (SSH/RDP) to the jump box, then from it into the protected systems; firewall rules allow management traffic into the segment **only from the jump box**.

Why it's valuable:

- **Reduced attack surface**: protected systems accept management connections from exactly one origin.
- **Choke point for control**: MFA enforced at the jump box; every session **logged/recorded** for audit; access revocable in one place.
- **Isolation**: admin workstations (email, browsing, malware exposure) never touch sensitive systems directly.

The jump box must itself be rigorously hardened, patched, MFA-protected, and monitored — it is a high-value target precisely because it holds the keys.

> ⚠️ **Common Pitfall:** A jump box is not a VPN and not a proxy for users — it is an **administrative stepping-stone into a restricted segment**. Cue words: "single hardened entry point," "administrators must first connect to an intermediary," "management access to the secure VLAN only from one host."

## In-Band vs. Out-of-Band Management

The final comparison: does management traffic share the network it manages?

### In-Band Management

Management traffic (SSH, HTTPS GUI, SNMP, API) flows over the **same production network** as user data — you SSH to the switch across the very links that carry business traffic. It's convenient and needs no extra infrastructure, but has a fatal flaw: **when the network is down, so is your access to fix it**. A misconfigured uplink or routing loop can lock you out of the device you need to repair. In-band management should at least be segregated onto a **management VLAN** and restricted by ACLs.

### Out-of-Band (OOB) Management

Management access travels a **separate, dedicated path** that does not depend on the production network:

- A physically **separate management network** connecting devices' dedicated management ports.
- **Console servers / terminal servers**: a box wired to the console ports of many devices, reachable via its own connection.
- Backup links for the management path: **cellular/LTE modems** or analog/ISDN lines — reachable even when the site's primary WAN is dead.
- Server-class equivalents: iDRAC/iLO/IPMI lights-out ports.

OOB works **during outages** — the exact moment you need it most — and keeps management traffic isolated from attackers on the production network. Costs: extra hardware, cabling/circuits, and an OOB network that itself must be secured (an unsecured OOB path is a backdoor).

| | In-band | Out-of-band |
|---|---|---|
| Path | Production network | Dedicated management network / console server / cellular |
| Works during network outage? | **No** | **Yes** |
| Cost / complexity | Low | Higher (extra infrastructure) |
| Security posture | Shares fate & exposure with production | Isolated from production traffic |
| Examples | SSH/HTTPS/SNMP over user VLANs | Console server + LTE, management-only VLAN/ports, iLO/iDRAC |

> 💡 **Exam Tip:** "The WAN link to the remote site failed and admins can still reach the router to fix it — how?" → **out-of-band management** (console server with cellular backup is the classic build). Any answer that depends on the production network is in-band and fails exactly when needed.

## Key Takeaways

- [ ] Site-to-site VPN: always-on IPsec tunnel between routers/firewalls joining whole networks; no client software on user devices.
- [ ] Client-to-site VPN: per-user, per-session encrypted tunnel from an individual device to a VPN concentrator; needs a client (unless clientless).
- [ ] Clientless VPN: browser-based TLS portal — no installed software, works from unmanaged devices, limited to published apps.
- [ ] Split tunnel: only corporate-destined traffic uses the VPN (saves bandwidth, less inspection); full tunnel: ALL traffic through the VPN (full corporate control/inspection, more load).
- [ ] SSH: encrypted CLI on TCP 22 with optional key-based auth — replaces plaintext Telnet (23).
- [ ] GUI: web/HTTPS or app-based visual management — approachable, less automatable.
- [ ] API: REST/JSON programmatic management — the choice for automation, scale, and integration.
- [ ] Console: physical serial access via rollover cable — no network/IP required; the method for initial configuration and recovery.
- [ ] Jump box: hardened intermediary host that is the single, logged, MFA-protected entry point for administration of a secure segment.
- [ ] In-band = management over the production network (fails with it); out-of-band = dedicated management network/console server/cellular that works during outages.
- [ ] Compare-and-contrast cues decide answers: who connects (site vs. user), what's installed (client vs. browser), where traffic flows (split vs. full), and whether the path survives an outage (in-band vs. OOB).

## Self-Check Questions

1. A company opens a second office and wants its network permanently linked to HQ over the Internet with no software on employee PCs. Which VPN type, and which devices terminate it?
2. Remote employees stream video heavily, saturating the VPN concentrator. Security agrees that only traffic to corporate subnets needs protection. What change fixes the load?
3. A contractor using a personal tablet needs temporary access to one internal web application. Which access method requires nothing installed?
4. You unbox a new core switch with no IP configuration. Which connection method must you use first, and with what cable?
5. Auditors require that all administrative sessions into the PCI server segment originate from one hardened, MFA-protected, session-recorded host — and that admins can still reach network devices if the production network fails. Which two designs satisfy these requirements?

<details>
<summary>Answers</summary>

1. A **site-to-site VPN** — an always-on (typically IPsec) tunnel terminated on the **edge routers/firewalls** at each site. Users need no VPN client; the sites simply route to each other.
2. Switch remote users from full tunnel to **split tunneling** — only corporate-destined traffic traverses the VPN; personal/Internet traffic exits the users' local connections, unloading the concentrator. Trade-off: that Internet traffic is no longer inspected by corporate controls.
3. A **clientless VPN** — a browser-based TLS/HTTPS portal publishing the web application. Nothing to install, works from unmanaged BYOD devices, and exposes only the published app rather than the whole network.
4. The **console** connection — a rollover/console cable (RJ45↔DB9 or USB) and a terminal emulator. The console requires no network or IP, which is why it's the method for initial configuration (and later for recovery).
5. A **jump box/host** as the sole permitted origin for admin sessions into the segment (hardened, MFA, logging/session recording), plus **out-of-band management** (dedicated management network or console server, often with cellular backup) so device access survives production-network outages.
