# Objective 1.4 — Explain common networking ports, protocols, services, and traffic types

This is the highest-yield memorization objective on the exam. You **will** see straight recall questions ("Which port does RDP use?"), scenario questions ("A technician must transfer files securely using an encrypted protocol — which port?"), and firewall/ACL questions ("Which port must be opened to allow secure LDAP?"). Beyond ports, this objective covers the IP protocol types (ICMP, TCP, UDP, GRE, IPSec with AH/ESP/IKE) and the four traffic types (unicast, multicast, anycast, broadcast). Drill the port table until it is automatic — these are the cheapest points on the exam — then make sure you can pair every insecure protocol with its secure replacement.

## The Official Port Table (memorize cold)

| Protocol | Port(s) | Transport | Purpose |
|---|---|---|---|
| File Transfer Protocol (FTP) | **20/21** | TCP | File transfers — port 21 control/commands, port 20 data (active mode). Credentials and data in cleartext. |
| Secure File Transfer Protocol (SFTP) | **22** | TCP | Encrypted file transfer as a subsystem of SSH — inherits SSH's port. |
| Secure Shell (SSH) | **22** | TCP | Encrypted remote command-line administration; secure replacement for Telnet; also tunnels (SFTP/SCP, port forwarding). |
| Telnet | **23** | TCP | Legacy remote CLI — **cleartext**, no encryption; should not be used. |
| Simple Mail Transfer Protocol (SMTP) | **25** | TCP | Sending/relaying email between servers (unencrypted). |
| Domain Name System (DNS) | **53** | UDP & TCP | Resolves names ↔ IP addresses. UDP 53 for normal queries; TCP 53 for zone transfers and large responses. |
| Dynamic Host Configuration Protocol (DHCP) | **67/68** | UDP | Automatic IP configuration — **server listens on 67, client on 68** (DORA: Discover, Offer, Request, Acknowledge). |
| Trivial File Transfer Protocol (TFTP) | **69** | UDP | Minimal, connectionless file transfer — no authentication; used for firmware/config transfers and PXE boot. |
| Hypertext Transfer Protocol (HTTP) | **80** | TCP | Unencrypted web traffic. |
| Network Time Protocol (NTP) | **123** | UDP | Clock synchronization across devices (stratum hierarchy). |
| Simple Network Management Protocol (SNMP) | **161/162** | UDP | Device monitoring/management — **manager polls agents on 161; agents send unsolicited traps to the manager on 162**. |
| Lightweight Directory Access Protocol (LDAP) | **389** | TCP (also UDP) | Querying/modifying directory services (e.g., Active Directory) — unencrypted. |
| Hypertext Transfer Protocol Secure (HTTPS) | **443** | TCP | Web traffic encrypted with TLS. (HTTP/3-QUIC uses UDP 443 — recognize, don't overthink.) |
| Server Message Block (SMB) | **445** | TCP | Windows file and printer sharing; also used by NAS appliances. |
| Syslog | **514** | UDP | Sending event/log messages to a central log collector. |
| SMTP Secure (SMTPS) | **587** | TCP | Authenticated, TLS-encrypted mail **submission** from clients to servers (STARTTLS). |
| LDAP over SSL (LDAPS) | **636** | TCP | Encrypted directory services. |
| Structured Query Language (SQL) Server | **1433** | TCP | Microsoft SQL Server database connections. |
| Remote Desktop Protocol (RDP) | **3389** | TCP (and UDP) | Graphical remote control of Windows systems. |
| Session Initiation Protocol (SIP) | **5060/5061** | TCP/UDP | Sets up/tears down VoIP calls — **5060 unencrypted, 5061 TLS-encrypted**. |

> 💡 **Exam Tip:** Memory anchors for the paired ports: FTP **20 data / 21 control** ("data before control alphabetically and numerically"); DHCP **67 server / 68 client** ("server answers first, lower number"); SNMP **161 poll / 162 trap** ("the trap is one more"); SIP **5060 clear / 5061 secure** ("secure is one more, like 80→443's idea"). SFTP and SSH share **22** because SFTP runs *inside* SSH.

> ⚠️ **Common Pitfall:** Don't confuse **SFTP (port 22, SSH-based)** with **FTPS (FTP over TLS, ports 990/21)** — the exam objective lists SFTP. Also don't confuse **TFTP (UDP 69)** with **FTP (TCP 20/21)**: TFTP is connectionless, unauthenticated, and used for device firmware/PXE, not user file transfer.

## Secure vs. Insecure Protocol Pairs

Firewall-hardening and "choose the secure alternative" questions come straight from this table:

| Insecure (cleartext) | Port | Secure replacement | Port | Encryption |
|---|---|---|---|---|
| Telnet | 23 | SSH | 22 | SSH |
| HTTP | 80 | HTTPS | 443 | TLS |
| FTP | 20/21 | SFTP | 22 | SSH |
| LDAP | 389 | LDAPS | 636 | TLS/SSL |
| SMTP | 25 | SMTPS (submission) | 587 | TLS (STARTTLS) |
| SNMPv1/v2c (community strings) | 161/162 | SNMPv3 (same ports) | 161/162 | Auth + encryption |
| SIP | 5060 | SIP over TLS | 5061 | TLS |

> 💡 **Exam Tip:** "A technician sees credentials in cleartext in a packet capture of a remote admin session — what should replace the current protocol?" Telnet (23) → **SSH (22)**. Same pattern for HTTP→HTTPS, FTP→SFTP, LDAP→LDAPS, SMTP→SMTPS.

## Internet Protocol (IP) types

These ride directly inside IP packets, identified by the **IP protocol number** field (not TCP/UDP ports):

| Protocol | IP protocol # | Role |
|---|---|---|
| ICMP | 1 | Diagnostics and error reporting |
| TCP | 6 | Reliable, connection-oriented transport |
| UDP | 17 | Fast, connectionless transport |
| GRE | 47 | Generic tunneling/encapsulation |
| ESP (IPSec) | 50 | Encryption + integrity |
| AH (IPSec) | 51 | Integrity/authentication only |

### Internet Control Message Protocol (ICMP)

- **What it is:** The network's diagnostic and error-reporting protocol, operating at **Layer 3** alongside IP (IP protocol 1). It carries **no user data** and uses **no ports** — which is why you can't "open a port" for ping.
- **Key message types:**
  - **Echo Request (Type 8) / Echo Reply (Type 0):** the mechanism behind **ping** — reachability and round-trip time.
  - **Destination Unreachable (Type 3):** a router or host cannot deliver the packet (codes include network unreachable, host unreachable, **port unreachable** — which is how UDP-based traceroute learns it reached the destination).
  - **Time Exceeded (Type 11):** a packet's **TTL hit 0** in transit — the message **traceroute** relies on to reveal each hop.
  - Also recognize: Redirect (Type 5).
- **Why it matters:** ping and traceroute are the first tools in almost every troubleshooting scenario; ICMP is also abused (ping floods, ICMP tunneling), so firewalls often rate-limit or block it — explaining "host is up but doesn't answer ping."

> 💡 **Exam Tip:** Match tool → ICMP messages: **ping = Echo Request/Reply (8/0)**; **traceroute = Time Exceeded (11)** from each intermediate router (plus a final Unreachable/Echo Reply from the destination).

### Transmission Control Protocol (TCP)

- **What it is:** The **connection-oriented, reliable** transport protocol (Layer 4, IP protocol 6). PDU = **segment**.
- **Three-way handshake** (connection establishment):
  1. Client → Server: **SYN** (synchronize; proposes initial sequence number)
  2. Server → Client: **SYN-ACK** (acknowledges client's SYN, sends its own)
  3. Client → Server: **ACK** — connection established.
  - Graceful teardown uses **FIN/ACK** exchanges (reset via RST).
- **Reliability mechanisms:**
  - **Sequence numbers** order segments and detect loss/duplication; receivers reassemble in order.
  - **Acknowledgments (ACKs)** confirm receipt; unacknowledged segments are **retransmitted**.
  - **Flow control — sliding window:** the receiver advertises a window (how many bytes it can buffer); the sender may not exceed it. The window slides forward as ACKs arrive, and shrinks when the receiver is overwhelmed.
  - **Congestion control** (slow start, etc.) throttles senders when the network itself is congested.
- **Used by:** anything needing accuracy over speed — HTTP/HTTPS, FTP/SFTP/SSH, SMTP, RDP, SMB, SQL, LDAP.

### User Datagram Protocol (UDP)

- **What it is:** The **connectionless, best-effort** transport protocol (Layer 4, IP protocol 17). PDU = **datagram**.
- **Traits:** No handshake, no sequencing, no acknowledgments, no retransmission, no flow control — just an 8-byte header (vs. TCP's 20+). "Fire and forget": minimal overhead and latency; any reliability must come from the application.
- **Used by:** real-time and lightweight traffic where a late packet is worse than a lost one — VoIP/video (RTP), DNS queries, DHCP, TFTP, NTP, SNMP, Syslog, streaming/gaming.

| | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented (3-way handshake) | Connectionless |
| Reliability | Guaranteed: sequencing, ACKs, retransmission | Best-effort, none |
| Flow control | Yes (sliding window) | No |
| Overhead/speed | Higher / slower | Minimal / faster |
| PDU | Segment | Datagram |
| Typical uses | Web, email, file transfer, remote desktop | VoIP, streaming, DNS, DHCP, TFTP, NTP, SNMP, Syslog |

> ⚠️ **Common Pitfall:** DNS uses **UDP 53 for ordinary queries** but **TCP 53 for zone transfers** and responses too large for UDP. If a question involves replicating zone data between DNS servers, the answer is TCP 53.

### Generic Routing Encapsulation (GRE)

- **What it is:** A lightweight **tunneling protocol** (IP protocol **47**) developed by Cisco that **encapsulates one protocol's packets inside another IP packet**, creating a virtual point-to-point tunnel across an intervening network.
- **What it can carry:** almost anything — IPv4, IPv6, multicast, routing-protocol traffic — which plain IPSec cannot easily carry.
- **The catch:** GRE provides **no encryption or authentication whatsoever**. It's a plain envelope, not a locked one.
- **Common pairing:** **GRE over IPSec** — GRE provides the flexible tunnel (including multicast/routing protocols), IPSec provides the encryption.

> 💡 **Exam Tip:** "A tunnel that can encapsulate multicast/routing protocol traffic but provides no confidentiality" = **GRE**. "Make that tunnel secure" = wrap it in **IPSec**.

### Internet Protocol Security (IPSec)

IPSec is a **framework/suite** (not a single protocol) that secures IP traffic at **Layer 3** with authentication, integrity, and encryption. It underpins most site-to-site and many client VPNs. Three components are named in the objectives:

#### Authentication Header (AH) — IP protocol 51
- Provides **integrity and origin authentication** (a cryptographic hash over the packet, including immutable IP header fields) and anti-replay protection.
- **Provides NO encryption** — the payload remains readable.
- Because AH hashes header fields, it **breaks through NAT** (NAT rewrites the fields AH protects), which is one reason ESP dominates in practice.

#### Encapsulating Security Payload (ESP) — IP protocol 50
- Provides **encryption (confidentiality)** of the payload **plus** integrity, authentication, and anti-replay.
- The workhorse of real IPSec VPNs — if data must be private, you need ESP.

#### Internet Key Exchange (IKE) — UDP port 500
- The negotiation protocol: authenticates the two peers and **negotiates/establishes the Security Associations (SAs)** — agreeing on algorithms and generating session keys (using Diffie-Hellman) before AH/ESP data flows. Two phases: Phase 1 builds the secure management channel (ISAKMP SA); Phase 2 negotiates the IPSec SAs.
- **NAT Traversal (NAT-T):** when NAT is detected, ESP is encapsulated in **UDP 4500**.

#### Transport mode vs. tunnel mode

| | Transport mode | Tunnel mode |
|---|---|---|
| What is protected | **Payload only** — original IP header stays visible | **Entire original packet** (header + payload), wrapped in a new IP header |
| Endpoints | Host-to-host (end devices) | Gateway-to-gateway (site-to-site VPN routers/firewalls) |
| Typical use | Securing traffic between two servers | Site-to-site VPNs across the Internet |

> 💡 **Exam Tip:** The three IPSec numbers to memorize: **AH = protocol 51 (integrity only, no encryption)**, **ESP = protocol 50 (encryption + integrity)**, **IKE = UDP 500** (key exchange/SA negotiation; NAT-T on UDP 4500). A firewall passing IPSec must permit protocols 50/51 and UDP 500 — these are IP protocol numbers, **not TCP/UDP ports**.

> ⚠️ **Common Pitfall:** "Which IPSec protocol encrypts the data?" — **ESP**, never AH. AH = **A**uthentication only ("AH = All Hash, no hiding"). And tunnel mode hides the original IP header; transport mode does not.

## Traffic types

How many receivers does a transmission target?

### Unicast
- **One-to-one:** a single sender to a single specific receiver — one source IP to one destination IP.
- The vast majority of traffic: web browsing, SSH, file transfers, email.

### Multicast
- **One-to-many (subscribers only):** one stream delivered simultaneously to the group of hosts that **joined** a multicast group — the network duplicates packets only where paths diverge, saving enormous bandwidth vs. many unicasts.
- **Addressing:** IPv4 **Class D — 224.0.0.0/4 (224.0.0.0 – 239.255.255.255)**; IPv6 uses **ff00::/8**.
- **Group management:** hosts join/leave groups using **IGMP** (Internet Group Management Protocol); switches use IGMP snooping to forward streams only to interested ports.
- **Uses:** IPTV/video streaming to many viewers, stock tickers, OS imaging (one image to many PCs), routing protocols (OSPF uses 224.0.0.5/224.0.0.6).

### Anycast
- **One-to-nearest:** the **same IP address is assigned to multiple servers** in different locations; routing automatically delivers each packet to the **topologically nearest** instance.
- **Uses:** **DNS root servers** (13 root addresses, hundreds of physical servers worldwide), CDNs, DDoS absorption. Native to IPv6, implemented in IPv4 via BGP.
- **Benefits:** low latency (nearest node answers), load distribution, resilience — if one instance dies, routing converges to the next nearest.

### Broadcast
- **One-to-all:** delivered to **every host on the local network segment/broadcast domain**.
- **Addressing:** limited broadcast **255.255.255.255** (never routed), or the subnet's directed broadcast (e.g., 192.168.1.255 for /24); Layer 2 broadcast MAC **FF:FF:FF:FF:FF:FF**.
- **Uses:** ARP requests, DHCP Discover.
- **Boundaries:** routers do **not** forward broadcasts — broadcasts define the broadcast domain.
- **IPv6 has NO broadcast** — it replaces broadcast with multicast (e.g., all-nodes ff02::1) and solicited-node multicast for neighbor discovery.

| Type | Pattern | Example |
|---|---|---|
| Unicast | One → one | Loading a web page |
| Multicast | One → many subscribed | IPTV stream, OSPF hellos (224.0.0.0/4, IGMP) |
| Anycast | One → nearest of many | DNS root servers, CDN nodes |
| Broadcast | One → all on segment | ARP request, DHCP Discover (255.255.255.255) |

> 💡 **Exam Tip:** Keyword mapping — "all devices on the subnet" = broadcast; "only devices that subscribed/joined a group" = multicast (IGMP, 224.0.0.0/4); "nearest of several servers sharing one IP" = anycast; "one specific destination" = unicast. And remember: **IPv6 eliminates broadcast entirely**.

## Ports Grouped for Faster Memorization

Grouping beats brute force. Learn the table in these clusters:

**By function:**
- **Remote access:** Telnet 23 (clear) → SSH 22 (secure); RDP 3389 (graphical).
- **File transfer:** FTP 20/21 (clear) → SFTP 22 (secure); TFTP 69 (trivial, UDP); SMB 445 (Windows shares).
- **Web:** HTTP 80 → HTTPS 443.
- **Email:** SMTP 25 (server-to-server) → SMTPS 587 (client submission, TLS).
- **Directory:** LDAP 389 → LDAPS 636.
- **Infrastructure services:** DNS 53, DHCP 67/68, NTP 123.
- **Monitoring/logging:** SNMP 161/162, Syslog 514.
- **Voice/database:** SIP 5060/5061, SQL Server 1433.

**By transport (the UDP shortlist):** the objective's UDP protocols are **DNS (queries), DHCP, TFTP, NTP, SNMP, Syslog** — memorize this short list and default everything else to TCP. Mnemonic: "**D**on't **D**rop **T**hose **N**oisy **S**yslog **S**treams."

**The "one-off numbers":** 445 SMB, 514 Syslog, 587 SMTPS, 636 LDAPS, 1433 SQL, 3389 RDP — flashcard these six; the rest follow patterns (20/21, 22/23, 67/68, 161/162, 5060/5061).

> 💡 **Exam Tip:** Performance-based questions may show a firewall rule table and ask you to fix it. Work protocol-by-protocol: identify the service required by the scenario, recall its port AND transport, then check both the rule's port number and its TCP/UDP designation — a rule allowing "TCP 69" for TFTP is wrong twice.

## Key Takeaways

- [ ] I can recall every port instantly: FTP 20/21, SFTP/SSH 22, Telnet 23, SMTP 25, DNS 53, DHCP 67/68, TFTP 69, HTTP 80, NTP 123, SNMP 161/162, LDAP 389, HTTPS 443, SMB 445, Syslog 514, SMTPS 587, LDAPS 636, SQL Server 1433, RDP 3389, SIP 5060/5061.
- [ ] I know each protocol's transport: UDP for DNS queries, DHCP, TFTP, NTP, SNMP, Syslog; TCP for FTP, SSH/SFTP, Telnet, SMTP(S), HTTP(S), LDAP(S), SMB, SQL, RDP; DNS zone transfers use TCP 53.
- [ ] Secure swaps: Telnet→SSH (23→22), HTTP→HTTPS (80→443), FTP→SFTP (20/21→22), LDAP→LDAPS (389→636), SMTP→SMTPS (25→587).
- [ ] ICMP (IP proto 1, no ports): Echo Request/Reply 8/0 = ping; Destination Unreachable = Type 3; Time Exceeded = Type 11 (TTL=0, traceroute).
- [ ] TCP: 3-way handshake SYN → SYN-ACK → ACK; reliability via sequencing/ACKs/retransmission; flow control via sliding window. UDP: connectionless, no guarantees, minimal overhead for real-time traffic.
- [ ] GRE (proto 47) tunnels anything—including multicast/routing protocols—but encrypts nothing; pair with IPSec for security.
- [ ] IPSec: AH = proto 51, integrity only; ESP = proto 50, encryption + integrity; IKE = UDP 500 negotiates SAs (NAT-T UDP 4500); transport mode protects payload only, tunnel mode wraps the whole packet (site-to-site VPNs).
- [ ] Traffic types: unicast one-to-one; multicast one-to-group (224.0.0.0/4, IGMP); anycast one-to-nearest (DNS root, CDNs); broadcast one-to-all (255.255.255.255, FF:FF:FF:FF:FF:FF, stopped by routers, absent from IPv6).

## Self-Check Questions

1. A firewall administrator must allow secure directory lookups and secure web traffic while blocking their insecure equivalents. Which ports are opened and which are blocked?
2. During a packet capture you see SYN, SYN-ACK, ACK between two hosts. What just happened, which protocol is in use, and what PDU does it produce?
3. A site-to-site VPN must encrypt entire original packets, including their IP headers, between two office firewalls. Which IPSec protocol and mode are required, and which protocol negotiates the keys on which port?
4. A university streams a live lecture to 400 subscribed campus PCs using a single transmission. Which traffic type is this, what IPv4 address range does it use, and what protocol manages group membership?
5. Which two well-known port pairs use "adjacent" numbers for server/client or poll/trap roles, and which side uses which number?

<details>
<summary>Answers</summary>

1. Open **LDAPS TCP 636** and **HTTPS TCP 443**; block **LDAP 389** and **HTTP 80**.
2. The **TCP three-way handshake** established a connection: the client sent SYN, the server answered SYN-ACK, the client confirmed with ACK. TCP is connection-oriented and reliable; its Layer 4 PDU is the **segment**.
3. **ESP (IP protocol 50)** in **tunnel mode** — ESP provides encryption, and tunnel mode encapsulates the entire original packet inside a new IP header (AH, protocol 51, would provide only integrity). **IKE over UDP 500** authenticates the peers and negotiates the security associations/keys.
4. **Multicast** — one stream delivered only to hosts that joined the group. IPv4 multicast uses **224.0.0.0/4 (224.0.0.0–239.255.255.255, Class D)**, with membership managed by **IGMP**.
5. **DHCP: server = UDP 67, client = UDP 68** and **SNMP: manager polls agents on UDP 161, agents send traps to the manager on UDP 162**. (SIP's 5060/5061 pair is unencrypted vs. TLS, another adjacent pair worth knowing.)
