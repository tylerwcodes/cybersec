# Objective 1.8 — Summarize evolving use cases for modern network environments

Networks have shifted from manually configured, hardware-centric designs to software-defined, cloud-integrated, automated environments. This objective is a "summarize" objective — the exam wants you to recognize each technology, its purpose, and its defining characteristics rather than configure it. Expect definition-matching questions (SDN vs. SD-WAN, SASE vs. SSE), "which technology solves this problem" scenarios (VLAN exhaustion → VXLAN; IPv4 exhaustion → IPv6; branch WAN over mixed circuits → SD-WAN), and IPv6 address-type identification. These concepts also anchor Domain 4 security topics (zero trust) and Domain 3 automation topics (IaC), so time invested here pays off across the exam.

## Software-defined network (SDN) and software-defined wide area network (SD-WAN)

**SDN** separates the network's **control plane** (the brains — decisions about where traffic goes) from the **data/forwarding plane** (the muscle — actually moving packets). A centralized **SDN controller** holds the network-wide view and pushes forwarding policy down to switches/routers via southbound APIs (e.g., OpenFlow), while administrators and applications talk to the controller via northbound APIs. The result: the network is programmable and managed as one system instead of box-by-box CLI.

Three SDN planes to know:

| Plane | Role |
|---|---|
| Management plane | Configuring/monitoring the network (APIs, dashboards) |
| Control plane | Path decisions — routing logic, centralized in the controller |
| Data (forwarding) plane | Moves user packets per the control plane's instructions |

**SD-WAN** applies SDN principles to wide-area networks. Instead of every branch needing an expensive dedicated MPLS circuit back to headquarters, an SD-WAN edge device at each site builds encrypted tunnels over *whatever* transports are available and intelligently steers traffic per application and real-time link quality.

### Application aware

SD-WAN identifies traffic **by application** (not just port/IP) and applies per-app policy: send Zoom/VoIP over the lowest-latency path, let bulk backups use cheap broadband, route Office 365 straight to the internet instead of hairpinning through HQ. If a link's latency/jitter/loss degrades, the edge moves sensitive apps to a better path automatically.

### Zero-touch provisioning

A new branch appliance is drop-shipped to the site; a non-technical person plugs in power and WAN. The device phones home to the orchestrator, authenticates, and **pulls its full configuration automatically** — no on-site engineer, no manual CLI. This slashes branch deployment time and configuration errors.

### Transport agnostic

SD-WAN doesn't care what the underlying circuit is — **MPLS, broadband cable/fiber, DSL, 4G/5G LTE, satellite** — it abstracts them all into one virtual WAN and can bond or fail over among them. Organizations mix a cheap broadband link with (or instead of) MPLS and let the software pick paths.

### Central policy management

Policy is defined **once** in the central controller/orchestrator and pushed to **every** site. Need to prioritize a new app or block a category at 200 branches? One change, propagated everywhere — versus logging into 200 routers.

> 💡 **Exam Tip:** The one-line definitions the exam wants: **SDN = separation of control plane from data plane with centralized control.** **SD-WAN = SDN applied to the WAN**, with the four hallmark features: application aware, zero-touch provisioning, transport agnostic, central policy management.

## Virtual Extensible Local Area Network (VXLAN)

VXLAN is an **overlay/tunneling** technology that stretches Layer 2 segments across a Layer 3 (routed) network. It solves two problems with traditional VLANs in large data centers and clouds:

1. **Scale**: 802.1Q VLAN IDs are 12 bits → only ~4,094 usable VLANs. VXLAN's **VNI (VXLAN Network Identifier) is 24 bits → ~16.7 million segments**, enough for massive multi-tenant clouds.
2. **Reach**: VLANs can't natively cross a routed boundary; VXLAN tunnels L2 over any IP network.

How it works: a **VTEP (VXLAN Tunnel Endpoint)** — a switch or hypervisor — takes the original Ethernet frame and encapsulates it (**MAC-in-UDP**, UDP port 4789) inside an IP packet, sends it across the routed underlay, and the far-end VTEP strips the wrapper and delivers the original frame. Hosts think they're on the same LAN.

### Data center interconnect (DCI)

VXLAN is a leading DCI technology: it **extends Layer 2 segments between separate data centers** over any IP/WAN connection. Use cases: live VM migration (e.g., vMotion, which historically wanted the same L2 segment at both ends), active/active data centers, disaster recovery — without stretching fragile spanning-tree domains across sites.

### Layer 2 encapsulation

The core mechanism: **encapsulating Layer 2 Ethernet frames inside Layer 3/4 (IP/UDP) packets** so L2 adjacency can exist anywhere the IP underlay reaches. This is what people mean by "L2 overlay over an L3 underlay" — commonly a spine-and-leaf IP fabric underneath with VXLAN segments on top.

> ⚠️ **Common Pitfall:** VLAN vs. VXLAN numbers: VLAN ID = **12 bits ≈ 4K segments**; VXLAN VNI = **24 bits ≈ 16 million segments**. If the question mentions "running out of VLANs" in a multi-tenant environment or "extend Layer 2 between data centers," the answer is VXLAN.

## Zero trust architecture (ZTA)

Traditional "castle-and-moat" security trusted anything inside the perimeter. Zero trust replaces that with **"never trust, always verify"**: no user, device, or flow is trusted by default because of its network location — every access request is authenticated, authorized, and encrypted, every time, whether it originates inside or outside the network. Zero trust assumes breach: attackers may already be inside, so lateral (east-west) movement must be constrained (microsegmentation).

### Policy-based authentication

Access decisions come from a **policy engine** that evaluates identity plus context on every request: who the user is (MFA-verified), device health/compliance posture, location, time, behavior anomalies. Authentication is **continuous and adaptive**, not a one-time login at the perimeter — a risk change (new country, non-compliant device) can trigger re-authentication or denial mid-session.

### Authorization

After identity is proven, authorization determines **what that identity may actually do** — evaluated per resource and per request. Being authenticated to the network no longer implies access to everything on it; each application/resource access is separately authorized against policy.

### Least privilege access

Every user, device, and service gets the **minimum access required to do its job — and nothing more**, often granted just-in-time and scoped just-enough. If an account is compromised, the blast radius is limited because that account couldn't reach much beyond its role's needs.

> 💡 **Exam Tip:** Zero trust keywords: "never trust, always verify," "assume breach," "verify explicitly every request," "least privilege," "microsegmentation." A question describing users on the internal LAN still having to authenticate to each internal application = zero trust architecture.

## Secure Access Service Edge (SASE) / Security Service Edge (SSE)

**SASE** (pronounced "sassy") converges **networking + security into a single cloud-delivered service**. Instead of backhauling branch/remote-user traffic to a data-center security stack, users connect to the nearest cloud point of presence, where both connectivity and security policy are applied.

SASE = **SD-WAN (the networking half) + a cloud security stack (the SSE half)**, typically including:

- **SWG** — Secure Web Gateway (web filtering, malware inspection)
- **CASB** — Cloud Access Security Broker (visibility/control over SaaS use)
- **ZTNA** — Zero Trust Network Access (per-app remote access replacing broad VPN tunnels)
- **FWaaS** — Firewall as a Service

**SSE** is the **security services subset only — SASE minus SD-WAN**. An organization that keeps its existing WAN but moves security enforcement to the cloud is deploying SSE.

| | SASE | SSE |
|---|---|---|
| SD-WAN networking | ✅ Included | ❌ Not included |
| SWG / CASB / ZTNA / FWaaS | ✅ | ✅ |
| Summary | Network + security, one cloud service | Cloud security stack only |

> ⚠️ **Common Pitfall:** The only difference the exam cares about: **SASE includes SD-WAN; SSE is the same security stack without the networking**. If the scenario says "we already have a WAN, we just want cloud-delivered security," that's SSE.

## Infrastructure as code (IaC)

IaC manages network/infrastructure configuration through **machine-readable definition files (code)** rather than manual CLI/GUI work. Tools: Ansible, Terraform, Puppet, Chef. The desired state is written once, versioned like software, and applied automatically — making deployments **fast, repeatable, consistent, and auditable**. The same file that builds one switch builds five hundred identically.

### Automation

#### Playbooks/templates/reusable tasks

- **Playbooks** (Ansible term): ordered task lists ("create VLAN 30, configure OSPF, apply ACL") executed against many devices.
- **Templates**: parameterized config skeletons — one standard switch template plus per-device variables (hostname, IPs) renders every device's config.
- **Reusable tasks/roles/modules**: build a task once (e.g., "harden SSH"), reuse it across every playbook and project.

#### Configuration drift/compliance

**Drift** = devices slowly diverging from the approved baseline as engineers make one-off manual changes. IaC tools continuously **compare actual state to the defined desired state**, report non-compliant devices, and can automatically **remediate** by re-applying the code. This also produces audit evidence for compliance frameworks.

#### Upgrades

Automation performs OS/firmware upgrades **at scale and consistently**: pre-checks (backup config, verify space/hash), staged rollouts during maintenance windows, post-checks, and rollback on failure — across hundreds of devices without a human babysitting each one.

#### Dynamic inventories

Instead of a hand-maintained static list of devices, a **dynamic inventory** is generated in real time by querying sources of truth (cloud provider APIs, VM managers, IPAM/CMDB). New instances are discovered and managed automatically — essential in cloud environments where servers appear and disappear constantly.

### Source control

Infrastructure code lives in a **version control system** — in practice, **Git** — gaining software-development discipline:

#### Version control

Every change is a **commit** with author, timestamp, and message — full history of *who changed what, when, and why*, with one-command **rollback** to any known-good prior version after a bad change.

#### Central repository

A shared server-side repo (GitHub, GitLab, Bitbucket) is the **single source of truth**. Everyone clones from and pushes to it, so the team always works from the same authoritative configs — no more "latest copy is on Bob's laptop."

#### Conflict identification

When two engineers modify the **same lines of the same file**, the system detects the **merge conflict** and forces a human to review and reconcile the changes before merging — preventing one person's work from silently overwriting another's.

#### Branching

A **branch** is an isolated line of development: build and test a change (say, a new QoS policy) on a feature branch without touching the stable **main** branch, submit it for **peer review** (pull/merge request), then merge once approved. Infrastructure changes get code review before touching production.

> 💡 **Exam Tip:** Map problem → IaC feature: "devices no longer match the standard build" = configuration drift; "deploy the same config to 300 switches" = playbooks/templates; "cloud VMs come and go" = dynamic inventory; "who changed this and can we roll back?" = version control; "two admins edited the same file" = conflict identification; "test changes without affecting production configs" = branching.

## IPv6 addressing

IPv6 uses **128-bit addresses** (vs. IPv4's 32-bit) — about 3.4 × 10^38 addresses. Written as **eight hextets** (groups of four hex digits) separated by colons: `2001:0db8:0000:0000:0000:ff00:0042:8329`.

Two compression rules:

1. Drop leading zeros in each hextet: `0db8` → `db8`.
2. Replace one (and only one) consecutive run of all-zero hextets with `::` — so the example becomes `2001:db8::ff00:42:8329`.

Address types to recognize on sight:

| Type | Prefix | Notes |
|---|---|---|
| Global unicast | 2000::/3 (starts 2 or 3) | Public, internet-routable — IPv6's "public address" |
| Link-local | fe80::/10 | Auto-configured on every IPv6 interface; valid only on the local link (IPv6's analog to APIPA, but always present, by design) |
| Unique local (ULA) | fc00::/7 (in practice fd00::/8) | Private addressing, IPv6's analog to RFC 1918 |
| Multicast | ff00::/8 | One-to-many (e.g., ff02::1 all-nodes, ff02::2 all-routers) |
| Loopback | ::1/128 | The IPv6 localhost (one address, not a whole /8) |

**There is no broadcast in IPv6** — its roles are replaced by multicast (and anycast). A typical LAN interface uses a /64 prefix, and hosts can self-configure via **SLAAC** (stateless address autoconfiguration) without DHCP.

### Mitigating address exhaustion

IPv4's ~4.3 billion addresses are exhausted (regional registries ran out starting in 2011). Stopgaps — NAT/PAT, RFC 1918 private addressing, CIDR — stretched IPv4 but add complexity and break end-to-end connectivity. **IPv6 is the permanent fix**: its 128-bit space is effectively inexhaustible, every device can have a globally unique address, and NAT is no longer required for address conservation.

### Compatibility requirements

IPv4 and IPv6 are **not directly compatible** — an IPv4-only host cannot natively talk to an IPv6-only host — so transition mechanisms bridge the long coexistence period:

#### Dual stack

Devices run **IPv4 and IPv6 simultaneously**, each interface holding both address types. The host uses whichever protocol the destination supports (preferring IPv6). This is the **preferred/cleanest** transition approach — no translation, native performance for both — at the cost of managing two addressing plans at once.

#### Tunneling

**Encapsulates IPv6 packets inside IPv4 packets** (or vice versa) so one protocol can cross an island of the other. Concept examples: **6to4** (automatic IPv6-in-IPv4 using 2002::/16), **ISATAP** (intra-site tunneling within an organization's IPv4 network), **Teredo** (tunnels IPv6 in IPv4 **UDP** so it can traverse NAT), and manually configured 6in4/GRE tunnels. Know them as "IPv6-over-IPv4 tunneling mechanisms" — the exam tests the concept more than per-protocol detail.

#### NAT64

A translation gateway that lets **IPv6-only clients reach IPv4-only servers**: it rewrites IPv6 packets into IPv4 packets (stateful translation). Its partner **DNS64** synthesizes AAAA records — embedding the server's IPv4 address into a special IPv6 prefix (64:ff9b::/96) — so the IPv6 client has an IPv6 destination to send to. Common in mobile carrier networks that run IPv6-only internally.

> 💡 **Exam Tip:** Transition-mechanism selection: run **both protocols** everywhere = dual stack (preferred); cross an **IPv4-only span** with IPv6 traffic = tunneling (6to4/ISATAP/Teredo); let an **IPv6-only network reach IPv4 content** = NAT64 (+DNS64). And memorize the prefixes: 2000::/3 global unicast, fe80::/10 link-local, fc00::/7 unique local, ff00::/8 multicast, ::1 loopback.

> ⚠️ **Common Pitfall:** An fe80:: address on an interface is **normal** — every IPv6 interface always has a link-local address, even when it also has a global address. Unlike IPv4's APIPA (which signals DHCP failure), a link-local IPv6 address is not an error symptom by itself. The problem sign is having *only* fe80:: when a global address was expected.

## Key Takeaways

- [ ] SDN separates the control plane (centralized controller) from the data plane (forwarding hardware); the network becomes programmable via APIs.
- [ ] SD-WAN = SDN for the WAN: application aware, zero-touch provisioning, transport agnostic (MPLS/broadband/LTE/satellite), central policy management.
- [ ] VXLAN: 24-bit VNI ≈ 16.7 M segments (vs. 4,094 VLANs); VTEPs encapsulate MAC-in-UDP (port 4789) to stretch L2 over L3 — key for data center interconnect.
- [ ] Zero trust: never trust/always verify, continuous policy-based authentication, per-request authorization, least privilege, assume breach/microsegmentation.
- [ ] SASE = SD-WAN + cloud security stack (SWG, CASB, ZTNA, FWaaS); SSE = that security stack **without** SD-WAN.
- [ ] IaC automation: playbooks/templates/reusable tasks, drift detection and compliance, automated upgrades, dynamic inventories.
- [ ] Source control: version history/rollback, central repository as source of truth, merge-conflict identification, branching for isolated change + review.
- [ ] IPv6: 128-bit; compress with leading-zero removal and one `::`; 2000::/3 global, fe80::/10 link-local, fc00::/7 ULA, ff00::/8 multicast, ::1 loopback; no broadcast.
- [ ] Transition: dual stack (preferred), tunneling (6to4/ISATAP/Teredo — IPv6 inside IPv4), NAT64 + DNS64 (IPv6-only → IPv4 servers).

3. What is the difference between SASE and SSE?
4. An auditor finds 40 switches whose running configs differ from the approved baseline. What is this called, and which practice detects and fixes it automatically?
5. An IPv6-only mobile network must let subscribers reach IPv4-only websites. Which two technologies work together to make this happen, and what does each do?
