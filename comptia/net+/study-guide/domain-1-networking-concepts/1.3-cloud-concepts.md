# Objective 1.3 — Summarize cloud concepts and connectivity options

Modern networks extend into the cloud, and N10-009 significantly expanded cloud coverage compared with earlier exams. This objective tests whether you can translate familiar on-premises concepts (routers, firewalls, private networks, leased lines) into their cloud equivalents (route tables, security groups, VPCs, Direct Connect). Exam questions are usually definitional ("Which gateway allows outbound-only Internet access?") or scenario-based ("A company needs its own isolated network in a public cloud — what should it deploy?"). Learn each term, its closest on-prem analogy, and the one or two attributes that distinguish it from its neighbors (security groups vs. security lists, scalability vs. elasticity, VPN vs. Direct Connect).

## Network functions virtualization (NFV)

- **What it is:** An architecture that replaces dedicated physical network appliances (routers, firewalls, load balancers, IDS/IPS) with **software running on standard/commodity server hardware** — typically as virtual machines or containers on a hypervisor.
- **How it works:** The network *function* is decoupled from the *hardware*. A "virtual network function" (VNF) — e.g., a virtual firewall image — can be deployed, cloned, scaled, and moved like any VM.
- **Why it matters:** Faster provisioning (minutes vs. weeks of hardware procurement), lower cost, scaling on demand, and it is the foundation of cloud networking — every "router" or "firewall" in a public cloud is NFV.
- **Related but distinct:** **SDN** (software-defined networking, Objective 1.8) separates the control plane from the data plane to centralize *control*; **NFV** virtualizes the *devices themselves*. They complement each other.

> 💡 **Exam Tip:** Keyword mapping — "replacing hardware appliances with virtual/software versions on commodity servers" = **NFV**. "Centralized controller separating control plane from data plane" = SDN.

## Virtual private cloud (VPC)

- **What it is:** A **logically isolated, private virtual network** that you define inside a public cloud provider's infrastructure (AWS/Google call it VPC; Azure calls it a Virtual Network/VNet). It is *your own* network in *their* cloud.
- **What you control:** your private IP address range (CIDR block, typically RFC 1918 space), **subnets** (public and private, often spread across availability zones), **route tables**, gateways, and security filtering (security groups / network ACLs).
- **Typical design:** public subnets hold Internet-facing resources (web servers behind an internet gateway); private subnets hold databases/app tiers with no direct Internet exposure, reaching out only through a NAT gateway.
- **Why it matters:** The VPC is the container for nearly everything else in this objective — gateways attach to it, security groups/lists filter within it, and VPN/Direct Connect terminate at it.

> 💡 **Exam Tip:** "A company wants an isolated private network within a public cloud provider where it defines its own subnets and IP ranges" = **VPC**. Multiple tenants' VPCs run on the same physical infrastructure but cannot see each other — isolation is logical (see Multitenancy).

## Network security groups and network security lists

Both are virtual firewalls filtering traffic in the cloud with allow/deny rules (source/destination, protocol, port). The exam wants the **scope** distinction:

| | Network security group (NSG) | Network security list (NSL) |
|---|---|---|
| Applies to | **Individual resource/instance level** — a VM's virtual NIC (vNIC) | **Subnet level** — every instance in the subnet |
| Granularity | Fine-grained, per-workload rules | Broad, baseline rules for the whole subnet |
| Analogy | Host-based firewall on each server | ACL on the subnet's router interface |
| Typical use | "Only the app tier may reach this DB VM on 1433" | "No Telnet into any host in this subnet" |
| Cloud examples | AWS Security Groups, Azure NSGs | OCI Security Lists; AWS Network ACLs are the equivalent subnet-level construct |

They stack: traffic entering an instance may be filtered first by the subnet's security list, then by the instance's security group. Security groups in AWS are **stateful** (return traffic automatically allowed), while network ACLs/lists are typically **stateless** (need explicit rules both directions) — a nice differentiator to know.

> ⚠️ **Common Pitfall:** The names sound interchangeable. Anchor on scope: **group = per-instance/vNIC**, **list = per-subnet**. If the question says a rule must apply "to all resources in the subnet," it's a network security list.

## Cloud gateways

### Internet gateway

- **What it is:** A VPC component that connects the VPC to the **public Internet**, enabling **bidirectional** traffic — resources with public IPs can be reached *from* the Internet and can initiate traffic *to* it.
- **Use case:** public-facing web servers, load balancers, bastion hosts in **public subnets**. A subnet is "public" precisely because its route table sends 0.0.0.0/0 to the internet gateway.

### Network address translation (NAT) gateway

- **What it is:** A managed gateway that lets instances in **private subnets initiate outbound** connections to the Internet (updates, patches, API calls) **while blocking unsolicited inbound** connections from the Internet.
- **How it works:** Like PAT at home — it translates many private source IPs to its own public IP, tracking sessions so only *return* traffic for established outbound flows comes back in.
- **Use case:** database and application servers that must download patches but must never be directly reachable from the Internet. The NAT gateway itself sits in a public subnet and uses the internet gateway.

| | Internet gateway | NAT gateway |
|---|---|---|
| Direction | Inbound **and** outbound | **Outbound-only** (plus replies) |
| Used by | Public subnets / public IPs | Private subnets / private IPs |
| Inbound connections from Internet | Allowed (subject to security rules) | Blocked — never initiated inbound |
| Typical resources | Web servers, public load balancers | DB/app servers needing updates |

> 💡 **Exam Tip:** The phrase to burn in: **NAT gateway = outbound-only Internet access for private subnets**. Any scenario with "servers must download updates but must not be reachable from the Internet" is a NAT gateway question.

## Cloud connectivity options

How does your on-premises network reach your VPC?

### VPN (cloud/site-to-site VPN)

- **What it is:** An **IPSec-encrypted tunnel over the public Internet** between your on-prem edge device (router/firewall) and a virtual VPN gateway attached to your VPC.
- **Traits:** Quick and cheap to set up (hours), uses existing Internet connections, encrypted end to end — but performance/latency are at the mercy of the public Internet (variable bandwidth, jitter), and throughput is typically limited (~1–2 Gbps per tunnel).
- **Use case:** small/medium workloads, backup connectivity, temporary or rapid deployments.

### Direct Connect (dedicated private connection)

- **What it is:** A **dedicated, private physical circuit** from your premises (or a colocation/partner facility) directly into the cloud provider's network, **bypassing the public Internet entirely**. "Direct Connect" is AWS's name; Azure's is ExpressRoute, Google's is Cloud Interconnect — the exam uses the generic/AWS term.
- **Traits:** Consistent low latency, high dedicated bandwidth (commonly 1–100 Gbps), predictable performance, private by design (not encrypted by default — add VPN/MACsec if encryption is required), higher cost and weeks-long provisioning lead time.
- **Use case:** large data transfers, latency-sensitive/production hybrid workloads, compliance requirements to avoid the public Internet.

| | Cloud VPN | Direct Connect |
|---|---|---|
| Path | Public Internet (encrypted tunnel) | Dedicated private circuit |
| Setup time | Hours | Weeks (physical provisioning) |
| Cost | Low | High |
| Bandwidth/latency | Variable, Internet-dependent | High, consistent, guaranteed |
| Encryption | Built in (IPSec) | Not inherent (private path; encrypt on top if needed) |
| Best for | Quick, low-cost, backup links | Production hybrid, big data, compliance |

> 💡 **Exam Tip:** Many enterprises deploy **both**: Direct Connect as primary, VPN as failover. "Consistent, predictable performance not dependent on the Internet" = Direct Connect. "Fast to set up over existing Internet" = VPN.

## Deployment models

| Model | Who uses the infrastructure | Traits | Example scenario |
|---|---|---|---|
| **Public** | Many organizations share a provider's infrastructure (multitenant) | Pay-as-you-go, huge scale, provider manages hardware, least direct control | Startup runs everything in AWS/Azure/GCP |
| **Private** | One organization exclusively (on-prem or hosted) | Maximum control/customization/security posture, highest cost, you carry the capex | Bank runs its own VMware/OpenStack cloud for regulated data |
| **Hybrid** | Mix of private + public, integrated and orchestrated | Keep sensitive/steady workloads private, burst or expand into public; requires connectivity (VPN/Direct Connect) | Retailer keeps its DB on-prem, bursts web tier to public cloud on Black Friday ("cloud bursting") |

(Community cloud — shared by organizations with common requirements — occasionally appears as a distractor.)

> ⚠️ **Common Pitfall:** "Private cloud" does **not** have to be on-premises — it can be hosted by a third party. What makes it private is **single-organization dedicated use**, not physical location.

## Service models

The three service models differ in **how much the provider manages vs. how much you manage** (the shared responsibility model):

| You manage → | On-premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Applications | You | **You** | **You** | Provider |
| Data | You | **You** | **You** | Provider (you own content/access) |
| Runtime/middleware | You | **You** | Provider | Provider |
| Operating system | You | **You** | Provider | Provider |
| Virtualization | You | Provider | Provider | Provider |
| Servers/storage | You | Provider | Provider | Provider |
| Networking/data center | You | Provider | Provider | Provider |

### Software as a service (SaaS)
- **What:** Complete, ready-to-use applications delivered over the Internet, usually via browser. You manage nothing but your data, users, and settings.
- **Examples:** Microsoft 365, Google Workspace, Salesforce, Zoom, Dropbox.
- **Shared responsibility example:** Provider patches the app, OS, and infrastructure; **you** control user accounts, MFA, and data classification.

### Infrastructure as a service (IaaS)
- **What:** Raw building blocks — virtual machines, virtual networks, storage. The provider manages hardware and hypervisor; **you** manage OS, patches, middleware, apps, data.
- **Examples:** Amazon EC2, Azure Virtual Machines, Google Compute Engine.
- **Shared responsibility example:** If a VM is compromised via a missing OS patch, that's on **you** — OS patching is the customer's job in IaaS.

### Platform as a service (PaaS)
- **What:** A managed platform for developing and running applications — the provider manages OS, runtime, middleware, databases; **you** manage only your application code and data.
- **Examples:** Azure App Service, Google App Engine, AWS Elastic Beanstalk, managed databases (RDS), Heroku.
- **Shared responsibility example:** Provider patches the runtime and OS; **you** are responsible for secure application code and the data it handles.

> 💡 **Exam Tip:** Ladder of control: **IaaS (most customer management: OS and up) → PaaS (just code + data) → SaaS (just use it)**. Scenario keywords: "developers want to deploy code without managing servers/OS" = PaaS; "full control of the OS on rented VMs" = IaaS; "subscription email/CRM in a browser" = SaaS.

## Scalability

- **What it is:** A system's ability to **handle growth** by adding resources. It answers "can we get bigger?"
- **Vertical scaling (scale up):** add power to one node — more CPU/RAM on a VM. Simple, but has a ceiling and usually requires downtime.
- **Horizontal scaling (scale out):** add more nodes — more web servers behind a load balancer. Nearly limitless, adds redundancy; requires apps designed for it.
- Scaling is often a **planned, longer-term** capacity decision.

## Elasticity

- **What it is:** The ability to scale **automatically and dynamically in BOTH directions** — grow when demand spikes, and **shrink back when demand falls** — typically via auto-scaling rules, so you pay only for what you use at any moment.
- **Example:** an e-commerce site auto-scales from 4 to 40 web instances during a flash sale, then back to 4 overnight.

| | Scalability | Elasticity |
|---|---|---|
| Question answered | Can it grow to meet demand? | Does it grow **and shrink automatically** with demand? |
| Direction | Primarily up/out | Both up/out **and** down/in |
| Trigger | Often planned/manual capacity change | Automatic, real-time (auto-scaling) |
| Time horizon | Long-term growth | Moment-to-moment fluctuation |
| Cost angle | Capacity for the future | Pay-as-you-go efficiency |

> ⚠️ **Common Pitfall:** All elastic systems are scalable, but not all scalable systems are elastic. The word that signals **elasticity** is *automatic* + *both directions* (expand **and contract**). If resources only grow (or a human adds them), that's scalability.

## Multitenancy

- **What it is:** A single instance of infrastructure or software serving **multiple customers ("tenants")**, whose data and traffic are **logically isolated** from one another even though they share the same physical hardware.
- **Where you see it:** the entire public cloud (your VPC shares physical hosts with strangers' VPCs), SaaS apps (one Salesforce serves thousands of companies), shared storage/network fabric.
- **Trade-offs:** massive cost efficiency and utilization for the provider (which is why cloud is cheap) vs. the theoretical risk of isolation failure ("noisy neighbor" performance effects, side-channel concerns). Strong logical isolation (hypervisor separation, VPCs, encryption, tenant IDs) is the mitigation.
- **Contrast:** single-tenant/dedicated hosting — one customer per physical host — costlier, used for strict compliance.

> 💡 **Exam Tip:** "Multiple organizations share the same physical infrastructure while remaining logically separated" is the textbook definition of **multitenancy** — it is the defining economic property of the **public** cloud deployment model.

## How It Fits Together (mental model)

A typical hybrid design touching every bullet in this objective: your company builds a **VPC** (public deployment model) with public and private subnets. Web servers in the public subnet reach the Internet through the **internet gateway**; database servers in the private subnet get updates through the **NAT gateway** (outbound-only). A **network security list** blocks Telnet across each subnet; **network security groups** allow only the web tier to hit the DB tier on 1433. The virtual firewall and load balancer are **NFV** appliances. The office connects via **Direct Connect** with a **VPN** as backup (**hybrid** model). The web tier **auto-scales** with demand (**elasticity**) on infrastructure shared with other customers (**multitenancy**), the VMs are **IaaS**, the managed database is **PaaS**, and the company's email is **SaaS**.

## Quick Contrast Drills

Three pairings the exam loves to blur — rehearse the one-line distinction:

1. **Internet gateway vs. NAT gateway:** both connect a VPC toward the Internet, but the internet gateway is **bidirectional** (public subnets) while the NAT gateway is **outbound-only** (private subnets).
2. **Security group vs. security list:** both are rule sets, but the group guards **one instance's vNIC** while the list guards **an entire subnet**.
3. **Scalability vs. elasticity:** both are about capacity, but scalability is the **ability to grow**, elasticity is **automatic growth and shrinkage** tracking live demand.

And one more that spans objectives: **VPN vs. Direct Connect** is really **encrypted-over-shared-Internet vs. unencrypted-over-private-circuit** — pick based on whether the scenario stresses *speed of deployment/cost* (VPN) or *guaranteed performance/avoiding the Internet* (Direct Connect).

## Key Takeaways

- [ ] NFV runs network functions (routers, firewalls, LBs) as software on commodity hardware — the foundation of all cloud networking; distinct from SDN (control/data-plane separation).
- [ ] A VPC is your logically isolated private network within a public cloud: you define CIDR ranges, subnets, route tables, and gateways.
- [ ] Network security **groups** filter at the **instance/vNIC** level (fine-grained, typically stateful); network security **lists** filter at the **subnet** level (broad, typically stateless).
- [ ] Internet gateway = bidirectional Internet access for public subnets; **NAT gateway = outbound-only** access for private subnets (updates yes, inbound connections no).
- [ ] Cloud VPN = encrypted tunnel over the Internet, fast/cheap/variable; **Direct Connect = dedicated private circuit**, consistent/high-bandwidth/expensive/slow to provision; often paired (DX primary, VPN backup).
- [ ] Deployment models: public (shared provider infrastructure), private (single organization, any location), hybrid (integrated mix, enables cloud bursting).
- [ ] Service models by what YOU manage: IaaS = OS and up; PaaS = code + data only; SaaS = just configure and use. Shared responsibility: OS patching is yours in IaaS, the provider's in PaaS/SaaS.
- [ ] Scalability = ability to grow (up/vertical or out/horizontal); **elasticity = automatic growth AND shrinkage** matched to real-time demand.
- [ ] Multitenancy = many logically isolated customers on shared physical infrastructure — the economics behind public cloud.

## Self-Check Questions

1. Servers in a private subnet must download OS updates from the Internet, but the security team requires that no connection can ever be initiated from the Internet to those servers. Which cloud component satisfies this?
2. Your company needs guaranteed bandwidth and consistent low latency to its cloud provider for a production ERP system, and traffic must not traverse the public Internet. Which connectivity option should it choose?
3. What is the scope difference between a network security group and a network security list?
4. A developer team wants to deploy application code without managing operating systems, patching, or runtimes. Which service model fits, and who patches the OS?
5. An online ticketing platform automatically spins up 30 extra instances during a big on-sale and terminates them an hour later. Which cloud characteristic does this best demonstrate — scalability or elasticity — and why?

1. A **NAT gateway** — it permits instances in private subnets to initiate **outbound-only** connections (with return traffic allowed for those sessions) while blocking all unsolicited inbound connections.
