# Objective 1.6 — Compare and contrast network topologies, architectures, and types

A topology describes how nodes are interconnected — both the physical cabling layout and the logical data paths. Architecture goes a level higher: how an entire enterprise or data-center network is organized into layers and how traffic flows through it. The N10-009 exam tests this objective with "identify the topology from a description or diagram" questions, link-count math for mesh networks, and scenario questions about which design fits a given organization (three-tier vs. collapsed core, spine-and-leaf for data centers). Understanding traffic-flow direction (north-south vs. east-west) also underpins later objectives on data-center design and security monitoring.

Two framing ideas before the specifics:

- **Physical vs. logical topology**: the physical topology is where the cables actually run; the logical topology is how data flows. They can differ — legacy Token Ring was wired as a physical star but operated as a logical ring, and a Wi-Fi network is physically wireless but behaves like a logical star centered on the AP.
- **Redundancy vs. cost** is the axis every topology question turns on: more links = more fault tolerance = more money. Full mesh and point-to-point sit at opposite ends; everything else is a compromise.

**Topologies at a glance:**

| Topology | Shape | Redundancy | Cost/Links | Typical Use |
|---|---|---|---|---|
| Full mesh | Everyone ↔ everyone | Highest | n(n−1)/2 links — highest | Small sets of critical WAN sites; internet core |
| Partial mesh | Key nodes richly linked | High where it matters | Moderate | Regional WANs, wireless mesh |
| Star | All nodes → central switch | Low (center = SPOF) | n links — low | Nearly every LAN |
| Hub and spoke | Branches → central hub site | Low (hub = SPOF) | n − 1 circuits — lowest WAN cost | Branch-office WANs |
| Spine and leaf | Every leaf ↔ every spine | High (lose a spine, lose only capacity) | Moderate-high | Modern data centers |
| Point-to-point | Two nodes, one link | None | 1 link | WAN circuits, wireless bridges |
| Hybrid | Mix of the above | Varies | Varies | Almost every real network |

## Mesh

In a mesh topology, nodes interconnect with multiple redundant paths, so the failure of one link (or node) does not partition the network.

### Full mesh vs. partial mesh

- **Full mesh**: every node has a direct link to every other node. Maximum redundancy, maximum cost.
- **Partial mesh**: only some nodes are fully interconnected; others connect to one or two neighbors. A practical compromise — critical sites get redundancy, minor sites don't.

The number of links in a full mesh of *n* nodes:

**Links = n(n − 1) / 2**

| Nodes (n) | Full-mesh links |
|---|---|
| 4 | 6 |
| 5 | 10 |
| 6 | 15 |
| 10 | 45 |

Worked example: a full mesh of 8 sites needs 8 × 7 / 2 = **28** links. Add a 9th site and you need 9 × 8 / 2 = 36 — eight new circuits just for one site. This quadratic growth is why full mesh doesn't scale and partial mesh (or hub-and-spoke) is used instead.

Where you see mesh: WAN designs between major sites, wireless mesh networks (each AP relays for its neighbors — handy for coverage where cabling every AP is impractical), and the internet's core routing fabric (a giant partial mesh).

Trade-off summary:

| | Advantages | Disadvantages |
|---|---|---|
| Full mesh | Survives multiple link/node failures; optimal direct paths; no single point of failure | Quadratic link growth; highest circuit and management cost |
| Partial mesh | Redundancy where it matters at a fraction of full-mesh cost | Some site pairs still depend on intermediate nodes; design requires judgment about which sites deserve extra links |

> 💡 **Exam Tip:** Expect a straight calculation: "How many links to fully mesh N sites?" Apply n(n−1)/2. Also know the trade-off vocabulary: full mesh = best fault tolerance, worst cost/complexity; partial mesh = the practical compromise.

## Hybrid

A hybrid topology combines two or more basic topologies into one network. Almost every real-world network is hybrid. Classic example: each floor of a building is a **star** (hosts to an access switch), and the access switches uplink to a distribution/core layer — a "star of stars," sometimes with redundant (partial-mesh) links between switches. If a diagram shows a star hanging off a bus, or stars interconnected in a ring, the answer is "hybrid."

## Star / hub and spoke

- **Star**: every node connects to a single central device (today, a switch; historically, a hub). The dominant LAN topology.
  - Pros: easy to add/remove nodes, a single cable fault isolates only that node, simple troubleshooting (test the one cable and the one port).
  - Con: the central device is a **single point of failure** — if the switch dies, the whole star goes down. Enterprise designs mitigate this with redundant central switches (which technically turns the star into a hybrid).
- **Hub and spoke**: the same shape applied to WANs — a central site (headquarters/data center = hub) with branch offices (spokes) connecting only to the hub. Spoke-to-spoke traffic must transit the hub, adding latency, but circuit count stays low (**n − 1 links** for n sites vs. n(n−1)/2 for full mesh). Classic hub-and-spoke examples: branch offices with VPN tunnels to headquarters, airline route maps, and traditional MPLS WANs homed to a central data center.

Cost comparison for 10 sites: hub-and-spoke needs **9** circuits; full mesh needs **45**. That 5× difference is the entire argument for hub-and-spoke — accepted in exchange for hub dependence (hub down = every spoke isolated) and extra latency on spoke-to-spoke paths.

> ⚠️ **Common Pitfall:** "Hub and spoke" has nothing to do with the legacy Ethernet hub device — it is a WAN topology term. Don't let the word "hub" fool you into thinking half-duplex hubs or collision domains.

## Spine and leaf

Spine-and-leaf is the modern **data-center** switching architecture, designed for heavy east-west (server-to-server) traffic.

```
        [Spine 1]      [Spine 2]        <- backbone tier (no servers,
        /  |    \  \   /  /  |  \          no spine-to-spine links)
       /   |     \  \ /  /   |   \
  [Leaf 1] [Leaf 2] [Leaf 3] [Leaf 4]   <- every leaf uplinks to EVERY spine
     |        |        |        |          (no leaf-to-leaf links)
  servers  servers  servers  servers    <- endpoints attach to leaves only
```

Rules of the fabric:

- **Every leaf switch connects to every spine switch** (a full mesh between the two tiers).
- **Leaf switches never connect to other leaves; spine switches never connect to other spines.**
- Servers/endpoints connect only to **leaf** switches (often deployed as top-of-rack switches); the **spine** is purely a backbone that forwards between leaves.

Properties that flow from those rules:

- **Predictable, consistent latency**: any server to any other server is always exactly two hops — leaf → spine → leaf.
- **Massive bandwidth and ECMP load balancing**: traffic spreads across all spines simultaneously.
- **Horizontal scalability**: need more server ports? Add a leaf. Need more fabric bandwidth? Add a spine.
- **Redundancy**: losing one spine only reduces capacity; it never isolates a leaf.

| Aspect | Three-tier hierarchical | Spine-and-leaf |
|---|---|---|
| Optimized for | North-south traffic (campus/enterprise) | East-west traffic (data center) |
| Hops between servers | Variable (depends on path) | Always leaf–spine–leaf (uniform) |
| Layers | Core, distribution, access | Spine, leaf (two tiers) |
| Typical home | Campus/enterprise LAN | Data center / cloud fabric |

> 💡 **Exam Tip:** Trigger phrases for spine-and-leaf: "data center," "east-west traffic," "predictable/consistent latency," "every leaf connects to every spine." And remember what it *forbids*: no leaf-to-leaf and no spine-to-spine links.

## Point to point

A point-to-point topology is a single direct link between exactly two nodes — the simplest possible topology. Examples: a WAN circuit between two offices, a wireless bridge between two buildings, a fiber run between two switches, or a serial link between two routers. Because only two devices share the link, there is no contention and configuration is trivial — but there's no redundancy (one link cut = outage), and dedicated links between every pair of many sites quickly becomes a full-mesh cost problem.

Addressing note that connects to objective 1.7: point-to-point router links are traditionally numbered from a **/30 subnet** (exactly two usable addresses) or a /31 on modern gear — the subnet size matches the topology.

## Three-tier hierarchical model

Cisco's classic campus/enterprise design divides the network into three layers, each with a distinct job:

```
              [ Core ]  ==  [ Core ]        <- fast, redundant backbone
              /      \      /      \
        [Distrib A]    [Distrib B]          <- aggregation + routing + policy
         /   |   \       /   |   \
      [Acc][Acc][Acc] [Acc][Acc][Acc]       <- access switches in the closets
        |    |    |     |    |    |
       PCs phones APs  PCs printers cameras <- end devices (PoE from access)
```

| Layer | Role | Typical functions |
|---|---|---|
| Core | High-speed backbone | Fast switching between distribution blocks; redundancy; **no policy processing** (no ACLs/filtering that slow it down) |
| Distribution | Aggregation and policy | Aggregates access switches; inter-VLAN routing; ACLs, QoS marking, security policy; boundary between L2 and L3 |
| Access | Edge/user connectivity | Connects end devices (PCs, phones, printers, APs); PoE for phones/APs/cameras; port security; VLAN assignment |

### Core

The core is engineered for **speed and availability only**. It interconnects distribution-layer blocks (and the data center/WAN edge) with high-bandwidth, redundant links. Design mantra: *the core forwards packets as fast as possible — policy belongs elsewhere.*

### Distribution

The distribution (aggregation) layer sits between access and core. It aggregates the many access switches, performs **routing between VLANs**, and enforces **policy** — access control lists, QoS, redistribution. It typically marks the boundary between the Layer 2 access domain and the Layer 3 routed core.

### Access

The access (edge) layer is where **end devices plug in**. Features live here that touch users directly: **Power over Ethernet (PoE)** for IP phones, wireless APs, and cameras; port security; 802.1X authentication; VLAN membership.

> 💡 **Exam Tip:** Match function to layer instantly: "connects end-user devices / provides PoE" = access; "ACLs, QoS, inter-VLAN routing, aggregates closets" = distribution; "high-speed backbone, no policy" = core.

## Collapsed core

A collapsed-core (two-tier) design **merges the core and distribution layers into a single layer** of switches, keeping a separate access layer. The same devices provide backbone switching *and* aggregation/policy.

- Why: small-to-medium organizations don't have enough traffic or enough distribution blocks to justify three tiers — a full three-tier build wastes money and adds complexity.
- Trade-off: cheaper and simpler, but less scalable; as the network grows, the combined layer can become a bottleneck and the design may need to be split back into three tiers.

> ⚠️ **Common Pitfall:** Collapsed core does **not** eliminate the access layer — end devices still connect to access switches. It collapses **core + distribution** into one tier. "Two-tier design for a smaller organization" = collapsed core.

## Traffic flows

Traffic-flow direction describes movement relative to the data center, matching the way network diagrams are drawn (core/exit at the top, servers at the bottom).

### North-south

Traffic that **enters or leaves** the data center (or network) — client requests coming in from the internet or campus, and responses going back out. It crosses the perimeter, so it passes through firewalls, load balancers, and edge routers. Traditional three-tier designs were optimized for this vertical, client-to-server pattern.

### East-west

Traffic that moves **laterally between servers/devices inside** the same data center — web tier to application tier to database tier, VM-to-VM, storage replication, microservice-to-microservice calls. In modern virtualized data centers, east-west traffic dominates (often ~70%+ of total), which is exactly why spine-and-leaf fabrics (uniform two-hop paths between any two leaves) replaced three-tier designs in the data center. East-west traffic also matters for security: it often bypasses perimeter firewalls, motivating microsegmentation and zero-trust designs.

> 💡 **Exam Tip:** North-south = in/out of the data center (client ↔ server, crosses the perimeter firewall). East-west = server ↔ server within the data center. "Which architecture best handles heavy east-west traffic?" → spine-and-leaf.

## Key Takeaways

- [ ] Full mesh links = n(n−1)/2; full mesh = max redundancy/max cost; partial mesh = compromise.
- [ ] Hybrid = combination of basic topologies (nearly all real networks).
- [ ] Star = LAN with central switch (single point of failure); hub-and-spoke = same shape as a WAN, spokes talk via the hub.
- [ ] Spine-and-leaf: every leaf ↔ every spine, no leaf-leaf or spine-spine links, uniform two-hop latency, built for east-west data-center traffic; scale out by adding leaves (ports) or spines (bandwidth).
- [ ] Point-to-point = one dedicated link between exactly two nodes.
- [ ] Three-tier: core (fast backbone, no policy) / distribution (aggregation, inter-VLAN routing, ACLs/QoS) / access (end devices, PoE, port security).
- [ ] Collapsed core = core + distribution merged into one tier; right-sized for smaller organizations.
- [ ] North-south = traffic in/out of the data center; east-west = lateral server-to-server traffic inside it.
