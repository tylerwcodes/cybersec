# Objective 2.2 — Given a scenario, configure switching technologies and features

Switches are the workhorses of the LAN, and this objective is a "given a scenario" objective — expect performance-based and scenario questions, not just definitions: "users on VLAN 20 can't reach VLAN 10," "the new phone won't get its voice VLAN," "two switches connected with two cables created a broadcast storm." You must know how VLANs segment broadcast domains, how access/trunk/native/voice VLAN interface settings interact, how 802.1Q tags frames, how link aggregation and speed/duplex settings must match on both ends, how spanning tree prevents Layer 2 loops, and when jumbo frames help (and hurt).

## Virtual Local Area Network (VLAN)

A VLAN logically segments one physical switch (or a whole switched network) into multiple **broadcast domains**. Each VLAN behaves like a separate switch: broadcasts, ARP, and unknown-unicast flooding stay inside the VLAN. Benefits: security segmentation (HR separated from guests), smaller broadcast domains (better performance), and logical grouping independent of physical location.

Key facts:

- VLAN IDs range **1–4094** (the 12-bit 802.1Q field gives 4096 values; 0 and 4095 are reserved).
- **VLAN 1 is the default VLAN** — every switch port belongs to it out of the box. Best practice: don't use VLAN 1 for user or management traffic.
- Traffic cannot pass between VLANs without a **Layer 3 device** (router or Layer 3 switch) — that separation is the whole point.

> 💡 **Exam Tip:** VLAN = broadcast domain at Layer 2. "How many broadcast domains?" = number of VLANs (plus any routed links). "How many collision domains?" = number of switch ports.

### VLAN Database

The **VLAN database** is the switch's stored list of VLANs — each VLAN's ID, name, and state. On Cisco switches this historically lives in `vlan.dat` in flash (separate from the running config, a classic gotcha when erasing configs). A VLAN must exist in the database before ports can be assigned to it; assigning a port to a nonexistent VLAN (or a VLAN that exists on one switch but not its neighbor) is a common cause of "user in the right port but wrong network" scenarios.

### Switch Virtual Interface (SVI)

An **SVI** is a virtual Layer 3 interface bound to a VLAN on a switch — `interface vlan 10` with an IP address. Two uses:

- **Management:** even a Layer 2 switch has one SVI (traditionally VLAN 1, better on a dedicated management VLAN) so you can SSH to it.
- **Inter-VLAN routing on a Layer 3 switch:** create one SVI per VLAN, give each an IP, enable IP routing — the switch now routes between VLANs internally at wire speed. Hosts use their VLAN's SVI address as their default gateway. This replaces router-on-a-stick in modern networks.

> 💡 **Exam Tip:** SVI on a Layer 3 switch = the modern answer for inter-VLAN routing. Router-on-a-stick with subinterfaces (Objective 2.1) is the legacy/low-cost alternative.

## Interface Configuration

### Access vs. Trunk Ports (context for everything below)

- **Access port:** belongs to exactly one data VLAN; frames on it are **untagged**. Used for end devices (PCs, printers).
- **Trunk port:** carries **multiple VLANs** between switches (or switch-to-router/hypervisor), using **802.1Q tags** to identify each frame's VLAN.

### Native VLAN

The **native VLAN** is the one VLAN on an 802.1Q trunk whose frames are sent **untagged**. Any untagged frame arriving on the trunk is assumed to belong to the native VLAN.

- Default native VLAN is **VLAN 1**.
- **Must match on both ends of the trunk.** A native VLAN mismatch merges two VLANs' untagged traffic (and triggers CDP/STP warnings) — traffic "leaks" between VLANs.
- **Security best practice:** change the native VLAN from VLAN 1 to an unused VLAN and don't assign hosts to it. This mitigates **VLAN hopping** (double-tagging) attacks.

> ⚠️ **Common Pitfall:** Native VLAN questions almost always hinge on either (a) "untagged frames on a trunk" — that's the definition — or (b) a mismatch between the two ends causing cross-VLAN leakage.

### Voice VLAN

A **voice VLAN** lets one switch port serve both an IP phone and the PC daisy-chained through the phone's built-in mini switch:

- The port carries the **data VLAN untagged** (for the PC) and the **voice VLAN tagged** (for the phone) — effectively a mini-trunk.
- The switch tells the phone its voice VLAN via CDP/LLDP-MED.
- Voice traffic can then be prioritized with QoS/**CoS (Class of Service, 802.1p priority bits in the 802.1Q tag)** so calls don't break up under data load — voice is latency- and jitter-sensitive.

### 802.1Q Tagging

**IEEE 802.1Q** is the open standard for VLAN tagging on trunks:

- Inserts a **4-byte tag** into the Ethernet frame *between the source MAC and EtherType fields* (it does not encapsulate the whole frame; the FCS is recalculated).
- The tag contains a 16-bit TPID (0x8100), **3 bits of priority (PCP/CoS)**, 1 DEI bit, and a **12-bit VLAN ID** (hence 4094 usable VLANs).
- Receiving switch reads the tag, strips it before delivering the frame out an access port in that VLAN.
- Native VLAN frames traverse the trunk with no tag at all.

> 💡 **Exam Tip:** 802.1Q numbers to memorize: **4-byte tag, 12-bit VLAN ID, VLANs 1–4094, 3-bit priority (CoS)**. Also remember 802.1Q slightly enlarges frames (1518 → 1522 bytes max) — "baby giants."

### Link Aggregation

**Link aggregation** bundles multiple physical links between two devices into one logical link (an EtherChannel / port channel / LAG):

- Standard: **IEEE 802.3ad**, which defines **LACP (Link Aggregation Control Protocol)**; the standard was later republished as 802.1AX, but the exam associates LACP with 802.3ad.
- Benefits: **increased aggregate bandwidth** (e.g., 4 × 1 Gbps = 4 Gbps logical) and **redundancy** (one member link fails, the bundle keeps forwarding), plus STP treats the bundle as a single link (no blocked members).
- Traffic is distributed per-flow by a hash (src/dst MAC/IP/port) — a single flow still maxes out at one member link's speed.
- **Configuration must match on both ends and across member ports:** same speed, duplex, VLANs/trunk mode, and compatible LACP modes (active/passive — at least one side active). Mismatches cause the bundle to fail or ports to be suspended/err-disabled.

### Speed

Ethernet interfaces can run at fixed speeds (10/100/1000 Mbps, 10 Gbps, etc.) or **autonegotiate**, in which both ends advertise capabilities and agree on the highest common speed. Speed must match on both ends of a link: a hard-coded 1000 on one side and 100 on the other simply won't link up (or falls back badly). Best practice today: leave both sides on auto, or hard-code **both** sides identically.

### Duplex

- **Full duplex:** send and receive simultaneously — no collisions; the norm on all modern switched links.
- **Half duplex:** one direction at a time (legacy hubs/CSMA-CD).
- **Duplex mismatch** — one side full, one side half — is the classic autonegotiation failure: it happens when one side is hard-coded and the other is left on auto (the auto side can't sense duplex and falls back to **half**). The link *works* but performs terribly under load.
- **Symptoms of a duplex mismatch:** slow throughput, and on the half-duplex side **late collisions**; **CRC/FCS errors** and runts on the full-duplex side. Late collisions on a switched network almost always mean duplex mismatch (or an out-of-spec cable length).

> ⚠️ **Common Pitfall:** "Intermittently slow link, interface counters show late collisions and CRC errors" = **duplex mismatch**. Fix by setting both ends to autonegotiate or hard-coding both identically.

## Spanning Tree

Redundant links between switches are good for fault tolerance but create **Layer 2 loops**. Ethernet frames have no TTL, so a looped broadcast circulates forever, multiplying into a **broadcast storm** that saturates links and CPUs, along with MAC address table instability (the same MAC flapping between ports) and duplicate frame delivery. **Spanning Tree Protocol (STP)** prevents this by logically blocking redundant paths, leaving a single loop-free tree — and unblocking them automatically if an active link fails.

- **802.1D** — original STP: reliable but slow (30–50 seconds to converge).
- **802.1w** — **Rapid Spanning Tree (RSTP)**: same idea, convergence in a few seconds or less; backward compatible with 802.1D.
- Switches exchange **BPDUs** (Bridge Protocol Data Units) to build the tree.

### Root Bridge Election

- All switches elect one **root bridge**: the switch with the **lowest bridge ID** wins.
- Bridge ID = **priority (default 32768) + MAC address**. Lowest priority wins; if priorities tie, the **lowest MAC address** wins.
- Best practice: set a low priority (e.g., 4096 or 0) on your core switch so the root is deterministic — otherwise the oldest switch (lowest MAC) may become root by accident.

### Port Roles

| Role | Meaning |
|---|---|
| **Root port** | The one port on each non-root switch with the lowest path cost toward the root bridge |
| **Designated port** | The forwarding port on each segment closest to the root (all ports on the root bridge are designated) |
| **Blocked / non-designated** (RSTP: alternate/backup) | Ports logically disabled to break the loop; still listen to BPDUs, ready to take over |

### Port States

| 802.1D STP state | Forwards data? | Learns MACs? | Notes |
|---|---|---|---|
| Blocking | No | No | Listens to BPDUs only |
| Listening | No | No | Transitional (15 s forward delay) |
| Learning | No | **Yes** | Transitional (15 s) — builds MAC table |
| Forwarding | **Yes** | Yes | Normal operation |
| (Disabled) | No | No | Administratively down |

**RSTP (802.1w)** collapses these to three states: **discarding, learning, forwarding** (blocking/listening/disabled all become "discarding"), and uses a proposal/agreement handshake instead of timers — hence the rapid convergence.

### STP Enhancements

- **PortFast (edge port):** access ports connected to end hosts skip listening/learning and go straight to forwarding — prevents DHCP timeouts when PCs boot. Never enable on switch-to-switch links.
- **BPDU guard:** if a BPDU ever arrives on a PortFast/edge port (meaning someone plugged in a switch), the port is shut down (err-disabled). Protects the STP topology from rogue or accidental switches.

> 💡 **Exam Tip:** Symptom set "network-wide slowdown, flooding, MAC table instability right after someone connected two switch ports together" = Layer 2 loop / broadcast storm = STP missing or misconfigured. And know the pairings cold: STP = 802.1D, RSTP = 802.1w, VLAN tagging = 802.1Q, LACP = 802.3ad.

## Maximum Transmission Unit (MTU)

The MTU is the largest payload (in bytes) an interface will send in one frame. **Standard Ethernet MTU = 1500 bytes** (the IP packet size; the Ethernet frame adds 18 bytes of header/FCS, 1518 total, 1522 with an 802.1Q tag). Packets larger than the egress MTU must be fragmented (IPv4, if DF isn't set) or dropped with an ICMP "fragmentation needed" message — mismatched MTUs along a path cause black holes for large packets, a classic "ping works but the app hangs" symptom.

### Jumbo Frames

**Jumbo frames** raise the MTU to roughly **9000 bytes** (commonly 9000–9216 depending on hardware):

- **Why:** each frame carries ~6× the data with the same per-frame header and processing overhead — fewer frames, fewer interrupts, higher throughput and lower CPU for bulk data.
- **Where:** storage and data-center traffic — **iSCSI/SAN**, NAS, backups, vMotion, east-west server traffic.
- **The rule:** jumbo frames must be enabled **consistently end-to-end** — every switch, router interface, and NIC in the path. A single 1500-byte hop fragments or silently drops jumbo traffic.

> ⚠️ **Common Pitfall:** "Storage performance is poor / iSCSI sessions fail after enabling jumbo frames on the servers" — some device in the path (often a switch uplink) is still at MTU 1500. Jumbo frames are all-or-nothing along the path.

## Key Takeaways

- [ ] VLAN = Layer 2 broadcast domain segmentation; IDs 1–4094; VLAN 1 is the default; inter-VLAN traffic requires a Layer 3 device.
- [ ] VLAN database stores VLAN IDs/names (vlan.dat); a VLAN must exist before ports can use it.
- [ ] SVI = Layer 3 interface for a VLAN; on an L3 switch, SVIs perform inter-VLAN routing and serve as host gateways.
- [ ] Access port = one VLAN, untagged; trunk = many VLANs, 802.1Q tagged.
- [ ] Native VLAN = untagged VLAN on a trunk; must match both ends; change it off VLAN 1 for security.
- [ ] Voice VLAN: one port carries tagged voice + untagged data; phone learns it via CDP/LLDP; CoS prioritizes voice.
- [ ] 802.1Q inserts a 4-byte tag with a 12-bit VLAN ID and 3-bit priority.
- [ ] Link aggregation (LACP/802.3ad) bundles links for bandwidth + redundancy; settings must match on both ends.
- [ ] Duplex mismatch (one side auto→half, other hard-coded full) → late collisions, CRC errors, slow link.
- [ ] STP (802.1D) blocks redundant paths to stop L2 loops/broadcast storms; RSTP (802.1w) converges much faster.
- [ ] Root bridge = lowest bridge ID (priority, then MAC); roles: root/designated/blocked; states: blocking-listening-learning-forwarding (RSTP: discarding-learning-forwarding).
- [ ] PortFast for host ports; BPDU guard shuts a port that receives a BPDU.
- [ ] MTU default 1500; jumbo frames ≈9000 for storage/iSCSI, must be consistent end-to-end.

## Self-Check Questions

1. A user's PC is on switch port 12, which was assigned to VLAN 30, but VLAN 30 was never created on the switch. What behavior results, and what concept does this illustrate?
2. Untagged frames arriving on an 802.1Q trunk are placed into which VLAN, and what is the security recommendation for it?
3. One end of a server link is hard-coded to 100/full; the other is left on autonegotiate. What duplex does the auto side choose, and what symptoms appear?
4. Two switches were joined with a second patch cable "for redundancy" and the whole network slowed to a crawl with the same MAC addresses appearing on multiple ports. What happened, and which protocols (with IEEE numbers) prevent it?
5. In an STP election, Switch A has priority 32768 and MAC 00:AA:..., Switch B has priority 32768 and MAC 00:0B:..., Switch C has priority 28672 and MAC 00:FF:.... Which becomes root and why?

1. The port is assigned to a nonexistent VLAN, so the user's traffic goes nowhere (on Cisco gear the VLAN may be auto-created or the port left inactive depending on mode, but exam-level: the user has link but no connectivity). It illustrates the **VLAN database** — VLANs must exist in the database before port assignments work, and must exist consistently across switches.
2. The **native VLAN** (default VLAN 1). Best practice: change the native VLAN to an unused ID, don't put hosts in it, and ensure it matches on both trunk ends — this mitigates VLAN-hopping/double-tagging attacks and prevents cross-VLAN leakage.
3. The autonegotiating side cannot detect duplex and falls back to **half duplex**, creating a duplex mismatch. Symptoms: poor throughput, **late collisions** on the half-duplex side, **CRC/FCS errors** on the full-duplex side.
4. A **Layer 2 loop** caused a **broadcast storm** and MAC address table instability (frames have no TTL, so they circulate forever). **STP (802.1D)** and **RSTP (802.1w)** prevent it by blocking redundant paths until needed.
