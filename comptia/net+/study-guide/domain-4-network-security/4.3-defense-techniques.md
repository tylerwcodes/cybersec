# Objective 4.3 — Given a scenario, apply network security features, defense techniques, and solutions

Objective 4.3 is a **"given a scenario"** objective, which means the exam won't just ask what port security *is* — it will describe a situation ("an attacker unplugged a VoIP phone and connected a laptop...") and ask **which feature you apply and how you configure it**. This chapter is the mirror image of 4.2: nearly every attack there has its countermeasure here. The highest-yield material is **802.1X's three roles**, **port security violation behavior**, **ACL logic (ordered evaluation, implicit deny)**, and the **screened subnet** design. Study these as attack→defense pairs: MAC flooding → port security; rogue devices → NAC/802.1X; unauthorized access → hardening; untrusted traffic → zones and ACLs.

## Device Hardening

Hardening reduces a device's **attack surface** — the sum of every way in — by removing or locking down anything not strictly required. Every router, switch, AP, firewall, server, and printer ships in a convenience-first configuration that must be tightened before production.

### Disable unused ports and services

"Ports" here means **both** meanings, and both matter:

- **Physical switch ports:** administratively shut down every unused switch interface (`shutdown`) and assign unused ports to an unused "black-hole" VLAN. This stops anyone who wanders into a conference room or lobby from plugging in a rogue laptop, AP, or DHCP server and instantly joining the LAN.
- **Logical service ports / services:** disable every service and daemon the device doesn't need — Telnet (use SSH), HTTP management (use HTTPS), FTP, SNMPv1/v2c (use SNMPv3), unused APIs, echo/discard, UPnP. Each open service is code listening on the network that can contain vulnerabilities. Run a port scan against your own device to verify what's actually exposed.

> 💡 **Exam Tip:** A scenario about "a visitor plugged into an unused wall jack and got network access" has two acceptable hardening answers: **disable unused switch ports** (this section) and/or require authentication via **802.1X/NAC** (below). Watch which options the question offers.

### Change default passwords

Every device ships with **default credentials** (admin/admin, admin/password) that are published in vendor manuals and aggregated in public lists that attackers and botnets automatically try. Change them **before** the device touches the network. Broader default-configuration hygiene the exam groups here:

- Change/disable default **accounts and usernames** where possible (rename admin, disable guest).
- Change default **SNMP community strings** (public/private are the "default passwords" of SNMP).
- Change default **SSIDs** and wireless admin passwords.
- Use strong, unique passwords per device — centralize with **TACACS+/RADIUS** so admin accounts aren't locally scattered.
- Keep **firmware/OS updated**: patches close the vulnerabilities exploits target; an unpatched device with a strong password is still vulnerable.

> ⚠️ **Common Pitfall:** The Mirai botnet built a massive DDoS army almost entirely from IoT devices using **unchanged default credentials**. If a question asks the *first* step when deploying a new device (camera, AP, router), "change the default password" is almost always the intended answer.

## Network Access Control (NAC)

NAC decides **whether a device may join the network at all, and with what access** — enforcement at the point of connection instead of after. Full NAC solutions perform **posture assessment** (health checks): is the endpoint's OS patched? Antivirus running and updated? Disk encrypted? Compliant devices get network access; non-compliant ones are **quarantined** into a remediation VLAN with just enough access to get fixed. Posture can be checked by an installed **agent** (persistent or dissolvable) or **agentless** scanning. NAC is the enforcement backbone for BYOD and guest onboarding policies from 4.1. The N10-009 blueprint lists three NAC-related mechanisms:

### Port security

Port security is a **switch feature** that limits which and how many **MAC addresses** may be seen on an access port:

- **Maximum MAC addresses per port** — e.g., 1 (or 2 for a phone + PC). Prevents MAC flooding, since thousands of bogus source MACs immediately exceed the limit; also blocks unauthorized hubs/APs multiplying devices on one jack.
- **How allowed MACs are defined:** statically configured, dynamically learned (first N seen), or **sticky MAC** — dynamically learned addresses are saved into the running configuration so they persist and become the permanently allowed set.
- **Violation actions** when an unauthorized MAC appears:

| Action | Traffic from violator | Port state | Counter/log/SNMP alert |
|---|---|---|---|
| **Shutdown** (default) | Dropped | Port goes **err-disabled** (down) — admin must re-enable (or auto-recovery) | Yes |
| **Restrict** | Dropped | Port stays up for allowed MACs | **Yes** — violations counted and alerted |
| **Protect** | Dropped | Port stays up for allowed MACs | **No notification** — silently drops |

> 💡 **Exam Tip:** Restrict vs. protect is a favorite: both drop offending traffic and keep the port up, but **restrict logs/alerts and protect stays silent**. Shutdown is the default and the most secure — the whole port is disabled (err-disabled) until an administrator intervenes.

### 802.1X

**IEEE 802.1X is port-based network access control**: a switch port (or wireless association) passes **no user traffic** until the connecting device authenticates. Three roles — memorize them:

| Role | What it is | Example |
|---|---|---|
| **Supplicant** | The **client device/software** requesting access | Laptop's 802.1X client, phone's Wi-Fi enterprise profile |
| **Authenticator** | The **network device** controlling the port; blocks everything except authentication traffic and relays credentials | The **switch** or **wireless AP/controller** |
| **Authentication server** | The server that validates credentials and tells the authenticator to open or keep blocking the port | A **RADIUS** server (often checking Active Directory) |

The supplicant and authenticator exchange **EAP over LAN (EAPoL)** frames; the authenticator repackages the EAP conversation inside **RADIUS** to the authentication server. Until success, the port allows only EAPoL. On success, the server can also assign the session to a specific **VLAN** or apply ACLs (dynamic authorization). 802.1X on wireless is what makes **WPA2/WPA3-Enterprise** "enterprise." It defeats the rogue-device and unauthorized-user problems of 4.2 at the port level.

> ⚠️ **Common Pitfall:** The **authenticator does not check credentials** — it's a middleman that blocks the port and relays EAP to the RADIUS server, which makes the actual decision. On the exam, "switch = authenticator, RADIUS = authentication server, client = supplicant." Also don't confuse 802.1X (authentication) with 802.1Q (VLAN tagging) — one character, completely different function.

### MAC filtering

MAC filtering permits or denies devices based on their **MAC address** against an allow list (or deny list) — configured on switches or, most commonly, wireless APs. It's trivial to administer for tiny networks but is a **weak control**: MAC addresses are transmitted **in cleartext in every frame** (even on encrypted Wi-Fi, the header MACs are visible), so an attacker just sniffs a legitimate client's MAC and **spoofs** it — changing a MAC is a one-line command in most operating systems. Treat MAC filtering as a layer of defense-in-depth or housekeeping, never as primary security.

> 💡 **Exam Tip:** If a question asks *why* MAC filtering is insufficient, the answer is **MAC addresses can be easily spoofed** (and are visible in cleartext). If it asks for a *strong* port-admission control instead, the answer is **802.1X**.

## Key Management

Cryptography is only as strong as the handling of its keys. Key management covers the **full lifecycle** of cryptographic keys and secrets (and by extension certificates, covered in 4.1):

- **Generation:** create keys of adequate length with strong randomness (e.g., AES-256, RSA 2048+).
- **Distribution/exchange:** get keys to parties securely — asymmetric techniques (e.g., Diffie-Hellman, PKI) bootstrap symmetric session keys; never send keys over cleartext channels.
- **Storage:** protect private keys at rest — hardware security modules (**HSMs**), TPM chips, encrypted key vaults; never hard-code keys in scripts/configs or leave them world-readable.
- **Rotation:** replace keys on a schedule and immediately upon suspected compromise or personnel departure. Regular rotation limits how much data any single compromised key exposes.
- **Escrow:** a trusted third party (or internal authority) holds copies of keys so encrypted data remains recoverable if the key holder leaves, dies, or loses the key — essential for full-disk encryption in enterprises (e.g., recovery keys held by IT).
- **Revocation/destruction:** retire compromised or expired keys (and revoke associated certificates via CRL/OCSP); securely destroy old key material.

> ⚠️ **Common Pitfall:** Losing the only copy of a data-at-rest encryption key means the data is **gone** — self-inflicted ransomware. That's the problem **key escrow** solves; it trades a little confidentiality risk (someone else holds a copy) for recoverability.

## Security Rules

Security rules are the configured policies that decide which traffic and content may pass — from Layer 3/4 packet rules up to Layer 7 content decisions.

### Access control list (ACL)

An ACL is an **ordered list of permit/deny rules** applied to router/firewall/switch interfaces (and to Wi-Fi controllers, cloud security groups, etc.). Rules typically match on **source/destination IP, protocol (TCP/UDP/ICMP), and port numbers**. Core mechanics the exam tests:

1. **Processed top-down, first match wins.** The device evaluates rules in order and applies the **first** rule that matches the packet — later rules are never reached for that packet. Rule **order matters**: put specific rules above general ones. A common bug: a broad `permit any` placed above a specific `deny` renders the deny dead.
2. **Implicit deny at the end.** Anything not explicitly permitted by some rule is **dropped by the invisible implicit deny all** at the bottom of every ACL. An ACL containing only deny statements therefore blocks *everything*.
3. **Applied to an interface in a direction** — inbound or outbound. The same ACL behaves differently depending on where and which direction it's applied.

ACLs implement **least privilege for traffic**: permit exactly what's needed (e.g., permit TCP 443 to the web server), let the implicit deny drop the rest. They also perform **anti-spoofing filtering** (e.g., drop packets arriving from the Internet claiming internal source addresses).

> 💡 **Exam Tip:** Two evergreen ACL questions: (1) "Traffic that should be blocked is getting through" → a broader **permit rule earlier in the list** matches first — reorder the rules. (2) "We only added permits for A and B; why is C blocked?" → the **implicit deny** dropped it. If you want to *log* denied traffic, add an explicit `deny any log` at the end (the implicit deny doesn't log).

### URL filtering

URL filtering controls web access by **web address** — blocking or allowing specific URLs, domains, or URL categories (gambling, malware, social media) via proxy servers, next-gen firewalls, or DNS-layer filtering. It works on **where the user is going**: the request to `badsite.example` is blocked before any content loads. Uses: blocking known-malicious/phishing domains, enforcing acceptable-use policy, regulatory compliance.

### Content filtering

Content filtering inspects **what the traffic actually contains** — scanning payloads, pages, files, and email bodies for prohibited or dangerous content regardless of the URL it came from: malware in downloads, inappropriate material by keyword/image analysis, blocked file types (.exe attachments), and outbound sensitive data (DLP-style credit-card/SSN patterns). Because modern web traffic is HTTPS, deep content filtering typically requires **TLS/SSL inspection** (decrypt-inspect-re-encrypt).

| | URL filtering | Content filtering |
|---|---|---|
| Decision based on | The **address/category** requested (domain/URL) | The **actual payload/data** in the traffic |
| Layer of insight | Destination-based | Deep packet/content inspection |
| Example | Block `*.gambling-site.com` | Strip executable email attachments; block a page containing malware regardless of its URL |
| Blind spot | New/unknown URLs not yet categorized | Encrypted traffic without TLS inspection |

> ⚠️ **Common Pitfall:** "Block a *known bad site* / a *category* of sites" = URL filtering. "Scan/block based on *what's inside* the traffic (keywords, file types, malware)" = content filtering. Real products bundle both, but the exam tests the distinction.

## Zones

A security **zone** is a logical grouping of networks/interfaces sharing one trust level, with firewalls enforcing policy **between** zones. Zone-based design replaces "hard shell, soft center" flat networks: instead of one perimeter, every zone boundary is a checkpoint. Typical zones: **inside/trusted** (corporate LAN), **outside/untrusted** (Internet), **screened subnet/DMZ** (public-facing services), plus guest, management, and OT/IoT zones (tying back to the segmentation drivers in 4.1).

### Trusted vs. untrusted

- **Trusted zone:** the internal network under your administrative control — authenticated users, managed and patched devices, monitored traffic. Traffic *within* the zone is relatively unrestricted (though zero-trust thinking increasingly challenges that).
- **Untrusted zone:** networks you do not control — above all the **Internet**, but also partner links and, in most designs, guest/BYOD segments. Assume hostile.
- **Default policy between zones:** traffic from **trusted → untrusted** is generally allowed (users browsing out) and stateful firewalls permit the **return traffic** of those sessions; traffic **initiated from untrusted → trusted is denied** unless a rule explicitly permits it. Trust levels are relative — a firewall can rank zones (inside 100, DMZ 50, outside 0) and, by default, allow traffic only from higher trust toward lower.

### Screened subnet

The **screened subnet** — the term N10-009 uses for what older material calls a **DMZ (demilitarized zone)** or perimeter network — is a **buffer zone between the untrusted Internet and the trusted LAN** that hosts services which *must* be reachable from outside: public web servers, mail gateways, external DNS, VPN concentrators, reverse proxies.

Two classic builds:

- **Dual-firewall (screened) design:** Internet → **external firewall** → screened subnet → **internal firewall** → LAN. The external firewall admits only the published service ports (e.g., TCP 443 to the web server); the internal firewall permits only the minimal, specific flows the DMZ hosts need inward (e.g., web server → database on one port) — and ideally nothing else.
- **Three-legged (triple-homed) firewall:** one firewall with three interfaces — outside, inside, and DMZ — enforcing the same policy matrix on a single device (cheaper, but a single point of compromise/failure).

The payoff: when an Internet-facing server in the screened subnet is inevitably attacked and possibly compromised, the attacker is **contained in the buffer zone** — the internal firewall still stands between them and the trusted LAN. Internal clients are never directly exposed, and the Internet never initiates connections into the trusted zone.

> 💡 **Exam Tip:** "Where do you place a **public-facing web server**?" → **screened subnet (DMZ)** — never on the internal LAN, and not naked on the Internet. Know both terms: CompTIA's blueprint says *screened subnet*, but *DMZ* still appears in questions and the field.

## Attack → Defense quick map (4.2 ↔ 4.3)

| Attack (4.2) | Primary defense (4.3 and related) |
|---|---|
| MAC flooding | Port security (max MACs, violation action) |
| VLAN hopping | Disable DTP, unused native VLAN, shut unused ports |
| ARP poisoning/spoofing | Dynamic ARP Inspection (built on DHCP snooping) |
| Rogue DHCP | DHCP snooping (trusted ports) |
| Rogue AP / unauthorized device | 802.1X / NAC, disable unused ports, WIPS |
| Evil twin | WPA-Enterprise with server certificate validation, WIPS |
| DNS poisoning/spoofing | DNSSEC |
| Default-credential compromise | Change default passwords, firmware updates |
| Unwanted/unauthorized traffic | ACLs (implicit deny), zones/screened subnet |
| Malicious/inappropriate web use | URL filtering + content filtering |

## Key Takeaways

- [ ] Hardening = shrink the attack surface: **shut down unused switch ports** (black-hole VLAN), **disable unused services** (Telnet→SSH, HTTP→HTTPS, SNMPv3), **change default passwords/credentials/community strings**, keep **firmware patched**.
- [ ] NAC admits devices based on identity and **posture assessment** (patches, AV, encryption) via **agent or agentless** checks; non-compliant devices go to a **quarantine/remediation** network.
- [ ] Port security: limit MACs per port; **sticky MAC** saves learned addresses; violations → **shutdown** (err-disabled, default), **restrict** (drop + log), **protect** (drop silently).
- [ ] 802.1X roles: **supplicant** (client) ↔ **authenticator** (switch/AP) ↔ **authentication server** (RADIUS), using **EAPoL** on the wire; no traffic passes until authentication succeeds.
- [ ] MAC filtering is weak — MACs are cleartext and **easily spoofed**; use as defense-in-depth only.
- [ ] Key management lifecycle: generate → distribute → **store (HSM)** → **rotate** → **escrow** (recoverability) → revoke/destroy.
- [ ] ACLs: **top-down, first match wins, implicit deny at the end**, applied per interface per direction; rule order bugs and implicit-deny surprises are classic exam scenarios.
- [ ] **URL filtering** = block by destination/category; **content filtering** = inspect the payload itself (needs TLS inspection for HTTPS).
- [ ] Zones: trusted (LAN) vs. untrusted (Internet); untrusted may not initiate into trusted; **screened subnet (DMZ)** hosts public-facing servers between two firewalls or on a third firewall interface.

## Self-Check Questions

1. A switch port is configured with port security: maximum 1 MAC, violation mode restrict. An attacker unplugs the authorized PC and connects a rogue laptop. What happens to the laptop's traffic and to the port, and how would the outcome differ in shutdown mode?
2. Name the three 802.1X roles, identify which physical device typically plays each in a wired deployment, and state which protocol runs (a) between supplicant and authenticator and (b) between authenticator and authentication server.
3. An ACL contains: 10) permit tcp any host 10.0.0.5 eq 443; 20) permit ip any any; 30) deny tcp any host 10.0.0.5 eq 22. Users can still SSH to 10.0.0.5. Why, and how do you fix it?
4. Your company is launching a public web server that must also query an internal database. Describe the zone placement and the firewall rules involved.
5. The security team wants to (a) block all access to known gambling websites and (b) prevent users from downloading .exe files from *any* website. Which filtering technology addresses each requirement?

In **restrict** mode the rogue laptop's frames are **dropped**, the port **remains up** (the authorized MAC could still pass), and the switch **logs the violation, increments the counter, and sends an SNMP trap/syslog alert**. 2. **Supplicant** = the client device/software (the user's laptop). **Authenticator** = the access-layer **switch** (in wireless, the AP/WLC) that blocks the port and relays authentication. **Authentication server** = the **RADIUS** server that validates credentials. (a) Supplicant ↔ authenticator: **EAPoL** (EAP over LAN). (b) Authenticator ↔ authentication server: **RADIUS** carrying the EAP messages.

4. Place the web server in the **screened subnet (DMZ)** — between the external and internal firewalls (or on a third firewall interface). External firewall: permit inbound **TCP 443 (HTTPS)** from the Internet **only** to the web server; deny everything else. The Internet never initiates into the trusted LAN, and a compromised web server is contained in the buffer zone.
5. (a) **URL filtering** — block the gambling **category/domains** at the proxy/firewall based on the destination address, before content loads. (b) **Content filtering** — the requirement is about **what is being downloaded** (executable file type) regardless of source URL, so the payload itself must be inspected (with TLS inspection for HTTPS sites).
