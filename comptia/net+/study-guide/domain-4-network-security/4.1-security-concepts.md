# Objective 4.1 — Explain the importance of basic network security concepts

Domain 4 is worth **14% of the N10-009 exam**, and objective 4.1 is its conceptual foundation. This objective covers the vocabulary and building blocks that every other security question assumes you know: how encryption protects data in different states, how certificates and PKI establish trust, how identity and access management (IAM) controls who can do what, and how organizations measure and manage risk. The exam tests this material two ways: **definition matching** ("Which term describes a weakness that could be exploited?") and **scenario selection** ("A company needs centralized authentication for network device administration with full-packet encryption — which protocol?"). The highest-yield items here are the **RADIUS vs. TACACS+ comparison**, the **risk/vulnerability/exploit/threat** terminology set, the **CIA triad**, and **MFA factor categories** — expect direct questions on all four.

## Logical Security

Logical (technical) security controls protect data and systems through software, protocols, and configuration — as opposed to physical controls (locks, cameras) that protect the tangible environment.

### Encryption

Encryption transforms readable **plaintext** into unreadable **ciphertext** using an algorithm and a key, so that only parties holding the correct key can recover the original data. The exam divides encryption by the *state* of the data being protected.

#### Data in transit

Data in transit (data in motion) is data actively moving across a network — web requests, file transfers, VPN tunnels, remote logins. Protecting it prevents eavesdropping and on-path (man-in-the-middle) attacks.

| Protocol | What it protects | Notes |
|---|---|---|
| **TLS** (Transport Layer Security) | Application traffic — HTTPS (TCP 443), secure email (SMTPS/IMAPS/POP3S), LDAPS | Successor to SSL; uses certificates for server authentication and negotiates symmetric session keys |
| **IPSec** | IP packets — site-to-site and client-to-site VPN tunnels | Operates at Layer 3; AH provides integrity/authentication, ESP adds encryption; tunnel vs. transport mode |
| **SSH** (Secure Shell) | Remote CLI administration, SFTP/SCP file transfer (TCP 22) | Replaces unencrypted Telnet (TCP 23) |

> 💡 **Exam Tip:** If a scenario mentions administrators using **Telnet** or plain **HTTP/FTP**, the "apply security" answer is to replace them with **SSH** and **HTTPS/SFTP** — cleartext management protocols are a classic hardening gap.

#### Data at rest

Data at rest is data stored on media — disks, databases, backups, USB drives, SAN volumes. Encryption at rest protects data if the hardware is lost, stolen, or improperly decommissioned.

- **Full-disk encryption (FDE):** encrypts the entire drive (e.g., BitLocker, FileVault, self-encrypting drives). A stolen laptop's disk is unreadable without the key.
- **File/folder-level encryption:** encrypts selected files (e.g., EFS).
- **Database/column encryption:** encrypts sensitive fields (card numbers, SSNs) inside a database.
- **AES** (Advanced Encryption Standard) is the modern symmetric algorithm used for data at rest (AES-128/AES-256).

> ⚠️ **Common Pitfall:** Encryption in transit does **not** protect stored data, and encryption at rest does **not** protect data crossing the network. A file on an encrypted disk that is emailed over plain SMTP travels in cleartext. Comprehensive protection requires **both**, and some frameworks add a third state: **data in use** (in memory).

### Certificates

Digital certificates bind a **public key** to an identity (a server name, person, or device), signed by an authority so others can verify the binding. Certificates are what let your browser trust that `https://bank.com` is really the bank.

#### Public key infrastructure (PKI)

PKI is the complete system of hardware, software, policies, and roles that creates, distributes, validates, and revokes certificates. Key components and workflow:

1. **Certificate Authority (CA):** the trusted entity that issues and digitally signs certificates. A **root CA** sits at the top; **intermediate/subordinate CAs** issue day-to-day certificates so the root key can stay offline and protected.
2. **Certificate Signing Request (CSR):** the requester generates a public/private key pair, then submits the public key plus identity information to the CA as a CSR. The **private key never leaves the requester**.
3. **Issuance:** the CA validates the identity and signs the certificate.
4. **Chain of trust:** a client validates a server certificate by following signatures upward — server cert → intermediate CA → root CA. The root CA's certificate is pre-installed in the operating system/browser trust store.
5. **Expiration and revocation:** certificates have validity periods and must be renewed. Compromised certificates are revoked and published via a **CRL** (Certificate Revocation List) or checked in real time with **OCSP** (Online Certificate Status Protocol).

> 💡 **Exam Tip:** An **expired certificate** is one of the most common causes of sudden browser trust warnings on a previously working site — check the certificate's validity dates first in troubleshooting scenarios.

#### Self-signed certificates

A self-signed certificate is signed by its own creator rather than a trusted CA — the issuer and subject are the same entity.

| | CA-signed | Self-signed |
|---|---|---|
| Signed by | Trusted third-party (or internal enterprise) CA | The certificate's own key |
| Browser/client behavior | Trusted automatically via chain of trust | **Trust warning/error** unless manually installed in the trust store |
| Cost | May cost money (public CA) | Free |
| Appropriate use | Public-facing services | Internal labs, testing, closed systems where the cert can be manually distributed |

> ⚠️ **Common Pitfall:** Self-signed does not mean "weaker encryption" — the cryptography can be identical. The weakness is **trust**: there is no third party vouching for the identity, so clients cannot distinguish your self-signed cert from an attacker's. Training users to click through certificate warnings makes on-path attacks easier.

### Identity and access management (IAM)

IAM is the framework of policies and technologies that ensures the right identities get the right access to the right resources at the right time. The identity lifecycle:

- **Provisioning:** creating accounts and granting access when a user joins or changes roles.
- **Management:** authentication, authorization, and auditing during employment.
- **Deprovisioning:** promptly disabling/removing accounts and access when a user leaves — orphaned accounts of former employees are a major attack vector and a frequent audit finding.

IAM splits into two questions: **Authentication** ("Who are you? Prove it.") and **Authorization** ("Now that I know who you are, what are you allowed to do?"). A third A — **Accounting/Auditing** (logging what you did) — completes the **AAA** model.

#### Authentication

##### Multifactor authentication (MFA)

MFA requires proof from **two or more different factor categories**:

| Factor | Meaning | Examples |
|---|---|---|
| **Something you know** | Knowledge | Password, PIN, security questions |
| **Something you have** | Possession | Smart card, hardware token, authenticator app / phone, key fob |
| **Something you are** | Inherence (biometrics) | Fingerprint, facial recognition, iris scan |
| **Somewhere you are** | Location | GPS/geofence, source IP/network |
| **Something you do** | Behavior (less commonly listed) | Typing pattern, gesture |

> ⚠️ **Common Pitfall:** Two proofs from the **same** category are not MFA. A password **plus** a PIN is still single-factor (both "something you know"). A password plus a fingerprint, or a PIN plus a smart card, is true two-factor.

##### Single sign-on (SSO)

SSO lets a user authenticate **once** and then access multiple applications without re-entering credentials. Benefits: fewer passwords to remember (so fewer weak/reused passwords), centralized control and fast deprovisioning. Risk: the SSO credential becomes a single point of compromise — which is why SSO should be paired with MFA. SSO is commonly implemented with **SAML**, Kerberos (in Windows domains), or OAuth/OIDC.

##### RADIUS (Remote Authentication Dial-In User Service)

RADIUS is an open-standard AAA protocol used to centralize authentication for **network access** — VPN logins, wireless (WPA2/WPA3-Enterprise), dial-in, and 802.1X port authentication.

- Transport: **UDP** — port **1812 for authentication/authorization**, **1813 for accounting** (legacy implementations used 1645/1646).
- Encrypts **only the password field** of the access-request packet; the rest (username, attributes) travels in cleartext.
- **Combines authentication and authorization** in a single exchange; accounting is separate.

##### TACACS+ (Terminal Access Controller Access Control System Plus)

TACACS+ is a Cisco-developed (now open) AAA protocol favored for **network device administration** — controlling and logging what administrators do on routers, switches, and firewalls.

- Transport: **TCP port 49** (reliable delivery).
- Encrypts the **entire packet payload/body**, not just the password.
- **Separates all three AAA functions** (authentication, authorization, accounting), enabling per-command authorization — e.g., allow `show` commands but deny `configure`.

##### RADIUS vs. TACACS+ (memorize this table)

| Feature | RADIUS | TACACS+ |
|---|---|---|
| Transport / port | **UDP 1812** (auth) / **1813** (accounting) | **TCP 49** |
| Encryption | **Only the password** field | **Entire payload/body** |
| AAA functions | Authentication + authorization **combined** | All three **separated** (per-command authorization possible) |
| Typical use | **Network access**: wireless, VPN, 802.1X | **Device administration**: router/switch admin control |
| Origin | Open standard (IETF) | Cisco-developed |

> 💡 **Exam Tip:** Scenario keywords decide the answer. "Users authenticating to **Wi-Fi/VPN**" → RADIUS. "Controlling **which commands network admins can run** on switches" or "encrypt the **entire** authentication session" → TACACS+.

##### LDAP (Lightweight Directory Access Protocol)

LDAP is the protocol for querying and modifying **directory services** — hierarchical databases of users, groups, computers, and resources (Microsoft **Active Directory** is the classic example). Ports: **TCP 389** (plain/StartTLS) and **TCP 636** (**LDAPS**, LDAP over SSL/TLS). LDAP itself is a directory lookup protocol, but it underpins authentication in most enterprises because that's where the accounts live. On the exam: always prefer LDAPS or signed LDAP because plain LDAP can expose credentials.

##### SAML (Security Assertion Markup Language)

SAML is an **XML-based open standard for federated identity and web SSO** — exchanging authentication and authorization data between:

- the **Identity Provider (IdP):** the system that authenticates the user (e.g., corporate login portal, Okta, Entra ID), and
- the **Service Provider (SP):** the application the user wants to use (e.g., a SaaS app).

The user authenticates once to the IdP; the IdP issues a signed **assertion** the SP trusts. The SP never sees the user's password. Keywords: **XML, federation, IdP/SP, web-based SSO between organizations**.

##### Time-based authentication

Time-based one-time passwords (**TOTP**) generate short-lived numeric codes from a shared secret plus the current time — typically a new 6-digit code every **30 seconds** (authenticator apps like Google Authenticator; RFC 6238). Because codes expire almost immediately, a stolen code is nearly useless. Contrast with **HOTP**, which is counter-based (codes don't expire on a timer). TOTP devices/apps count as **something you have**. Time synchronization between client and server matters — clock drift breaks TOTP validation.

#### Authorization

Authorization happens **after** authentication and defines what an identity may access or do.

##### Least privilege

The principle of least privilege: give every user, service, and process the **minimum access required to do its job — and no more**. Admins should use standard accounts for daily work and elevate only when needed; service accounts should not run as domain admin. Least privilege limits the blast radius of compromised accounts and insider mistakes.

##### Role-based access control (RBAC)

RBAC assigns permissions to **roles** (job functions), then assigns users to roles — instead of granting permissions user-by-user. A new accountant simply gets the "Accounting" role. Benefits: consistency, scalability, easy auditing, and clean deprovisioning (remove the user from the role). RBAC is the standard way organizations *implement* least privilege at scale.

> 💡 **Exam Tip:** Authentication vs. authorization is heavily tested. **Authentication = proving identity** (password, MFA). **Authorization = what you can access** (least privilege, RBAC). A user who can log in but can't open a folder has an *authorization* issue.

### Geofencing

Geofencing creates a **virtual geographic boundary** using GPS, Wi-Fi, cell, or IP geolocation, and applies policy based on whether a device/user is inside or outside it. Examples: block logins originating outside the country, allow a mobile app to access corporate data only on campus, wipe alerts when a managed device leaves a boundary. Geofencing supplies the **"somewhere you are"** factor and is common in MDM (mobile device management) and conditional-access policies.

## Physical Security

Logical controls are useless if an attacker can walk up to the equipment. Physical security controls protect facilities, rooms, and hardware.

### Camera

Surveillance cameras (CCTV/IP cameras) serve two functions: **deterrence** (visible cameras discourage attempts) and **detection/evidence** (recording what happened and who did it — a *detective* control). Modern IP cameras support motion detection, night vision (IR), and pan-tilt-zoom (PTZ). Place cameras at entrances, server-room doors, and loading docks. Note: cameras **record** incidents; they do not physically prevent them.

### Locks

Locks are **preventive** physical controls restricting entry to buildings, rooms, racks, and devices:

- **Traditional key locks** — simple, but keys are copyable and hard to audit.
- **Electronic/badge locks** (smart card, proximity/RFID) — access can be logged, granted, and revoked per person.
- **Biometric locks** — fingerprint/iris entry to high-security areas.
- **Cipher/keypad locks** — PIN codes; rotate codes and shield from shoulder surfing.
- **Cabinet/rack locks and cable locks** — protect individual equipment.

Related physical measures worth recognizing: **access control vestibules (mantraps)** to stop tailgating, badge readers, security guards, and locked server rooms.

## Deception Technologies

Deception technologies are intentionally attractive decoys deployed to detect, misdirect, and study attackers — any interaction with them is by definition suspicious, producing high-signal alerts with almost no false positives.

### Honeypot

A **honeypot** is a **decoy system** made to look like a legitimate, vulnerable target (a fake database server, an "unpatched" web server). It has no production purpose, so *any* traffic to it indicates scanning or attack. Defenders use honeypots to detect intrusions early, gather intelligence on attacker tools and techniques, and waste attacker time — all while keeping them away from real assets. Honeypots are isolated from production systems.

### Honeynet

A **honeynet** is an **entire network of honeypots** — decoy servers, workstations, and services simulating a realistic environment. It captures richer intelligence: how attackers move laterally, escalate privileges, and what they target once "inside."

> 💡 **Exam Tip:** Honeypot = one decoy **system**; honeynet = a decoy **network** of honeypots. If the question says "observe attacker techniques without risking production," think deception technology.

## Common Security Terminology

These four terms are tested nearly verbatim — keep them straight:

| Term | Definition | Example |
|---|---|---|
| **Vulnerability** | A **weakness** in a system, configuration, or process | Unpatched server, default password, open port, untrained user |
| **Exploit** | The **method, technique, or code** that takes advantage of a vulnerability | Malware or a script attacking an unpatched flaw; EternalBlue exploiting SMBv1 |
| **Threat** | A potential **actor or event** that could cause harm | Hacker, disgruntled insider, malware campaign, hurricane |
| **Risk** | The **potential for loss** — commonly expressed as **likelihood × impact** of a threat exploiting a vulnerability | High-severity flaw on an internet-facing server holding customer data = high risk |

Memory chain: a **threat** uses an **exploit** against a **vulnerability**; the resulting potential for loss is the **risk**. Remove the vulnerability (patch) or reduce exposure, and risk drops even though threats still exist.

### Confidentiality, Integrity, and Availability (CIA) triad

The CIA triad is the classic model of what security protects:

| Principle | Goal | Supporting controls | Example violation |
|---|---|---|---|
| **Confidentiality** | Only authorized parties can **read** data | Encryption, access controls, MFA | Attacker sniffs cleartext passwords; stolen unencrypted laptop |
| **Integrity** | Data is not **altered** improperly; changes are detectable | Hashing, digital signatures, version control | Attacker modifies a DNS record or tampers with an invoice in transit |
| **Availability** | Systems and data are **accessible when needed** | Redundancy, backups, UPS, DDoS protection | DDoS takes a web server offline; ransomware encrypts files |

> ⚠️ **Common Pitfall:** Ransomware is primarily an **availability** violation (you can't access your own data), though data-theft "double extortion" also breaches confidentiality. DoS/DDoS = availability. Sniffing/eavesdropping = confidentiality. Unauthorized modification = integrity.

## Audits and Regulatory Compliance

Security audits systematically verify that controls exist, work, and satisfy internal policy and external regulation. Networks must often be designed *around* compliance requirements (segmentation, logging, encryption), so Network+ expects you to recognize the major regimes.

### Data locality

Data locality (data residency/sovereignty) means data is subject to the **laws of the country/region where it is collected or stored**, and some laws require certain data to *remain* within specific borders. Consequences for network design: choosing cloud regions, replicating data only to compliant locations, and restricting cross-border transfers. Example: EU personal data may only be transferred outside the EU under approved safeguards.

### Payment Card Industry Data Security Standards (PCI DSS)

PCI DSS is a **contractual industry standard** (not a government law) that applies to any organization that **stores, processes, or transmits payment card data**. Network-relevant requirements include: **segmenting the cardholder data environment (CDE)** from the rest of the network, firewalls, encrypting card data in transit and at rest, not storing sensitive authentication data (e.g., CVV), unique IDs and access control, logging/monitoring, and regular testing (vulnerability scans, penetration tests).

### General Data Protection Regulation (GDPR)

GDPR is the **European Union's data-privacy law** protecting the **personal data of people in the EU** — and it applies to *any* organization worldwide that handles such data. Key concepts: lawful basis and consent for processing, data-subject rights (access, correction, erasure — the "right to be forgotten"), **breach notification within 72 hours** to authorities, and severe fines (up to 4% of global annual revenue). GDPR drives requirements for encryption, minimization, and data-residency decisions.

> 💡 **Exam Tip:** Match the keyword: **card/payment data → PCI DSS**; **EU personal data/privacy → GDPR**; **"data must stay in-country" → data locality/sovereignty**.

## Network Segmentation Enforcement

Segmentation splits a network into isolated zones (VLANs, subnets, firewalled segments) so that devices with different trust levels, risk profiles, or compliance needs cannot freely reach each other. It limits lateral movement after a compromise and contains high-risk device classes. 4.1 highlights four segments you should be able to justify:

### Internet of Things (IoT) and Industrial IoT (IIoT)

IoT devices (cameras, smart TVs, sensors, badge readers, thermostats) and their industrial cousins (IIoT: connected sensors/actuators in manufacturing) are notorious for **weak/default credentials, infrequent or nonexistent patches, and long service lives**. They cannot run endpoint security agents. Placing them on a **dedicated, firewalled VLAN** ensures a hacked camera can't pivot to file servers — compromised IoT devices are also prime botnet recruits (see 4.2 DDoS).

### SCADA / ICS / OT

- **OT (Operational Technology):** the umbrella term for hardware/software controlling physical processes.
- **ICS (Industrial Control Systems):** the control systems category within OT.
- **SCADA (Supervisory Control and Data Acquisition):** ICS architecture for monitoring/controlling large-scale, often geographically dispersed processes (power grids, pipelines, water treatment).

Why strict segmentation (often near-total isolation or an "air gap" with tightly controlled gateways) is mandatory: these systems run **legacy, unpatchable software**, were designed for reliability rather than security, cannot tolerate downtime for patching, and a compromise can cause **physical damage or safety incidents** — not just data loss. OT networks prioritize **availability and safety** above all.

### Guest

Guest networks give visitors (and often personal devices) Internet access while **blocking all access to internal resources**. Typically an isolated VLAN/SSID with client isolation, captive portal, and bandwidth limits. Never bridge guest and corporate segments.

### Bring your own device (BYOD)

BYOD lets employees use personal phones/laptops for work. Because the organization doesn't fully control patching or installed apps, BYOD devices are placed on their **own segment** with policy-controlled access to corporate resources — commonly enforced with **NAC posture checks** (see 4.3) and **MDM** enrollment. Segmentation ensures a malware-infected personal laptop can't roam the internal network.

> 💡 **Exam Tip:** The common thread for all four: **untrusted or unpatchable devices get their own isolated segment**. If a scenario says "the company added smart sensors / a visitor Wi-Fi / employee personal devices — how do you protect the internal network?", the answer is segmentation (separate VLAN + firewall rules).

## Key Takeaways

- [ ] Encryption in **transit** (TLS, IPSec, SSH) and at **rest** (AES full-disk, database) protect different data states — you need both.
- [ ] PKI: CA signs certificates from a **CSR**; clients validate via the **chain of trust**; certs **expire** and can be revoked (CRL/OCSP).
- [ ] **Self-signed** certificates trigger trust warnings; acceptable only for internal/test use.
- [ ] IAM lifecycle: provision → manage → **deprovision promptly** (orphaned accounts are a top audit finding).
- [ ] MFA = factors from **different categories**: know / have / are / somewhere you are.
- [ ] **RADIUS**: UDP 1812/1813, encrypts only the password, combines auth+authz, used for network access.
- [ ] **TACACS+**: TCP 49, encrypts entire payload, separates AAA, used for device administration.
- [ ] **LDAP** TCP 389 / **LDAPS** TCP 636 — directory services; **SAML** = XML federation with IdP and SP; **TOTP** = time-based one-time codes.
- [ ] Authorization: **least privilege** (minimum necessary) implemented at scale via **RBAC** (permissions → roles → users).
- [ ] **Honeypot** = decoy system; **honeynet** = decoy network; any interaction = high-fidelity alert.
- [ ] Vulnerability = weakness; exploit = method; threat = actor/event; **risk = likelihood × impact**.
- [ ] CIA: sniffing hits Confidentiality, tampering hits Integrity, DoS/ransomware hit Availability.
- [ ] PCI DSS = card data (industry standard); GDPR = EU personal data (law, 72-hour breach notice); data locality = laws of where data resides.
- [ ] Segment IoT/IIoT, SCADA/ICS/OT, guest, and BYOD onto isolated networks — unpatchable or untrusted devices must not touch production.
