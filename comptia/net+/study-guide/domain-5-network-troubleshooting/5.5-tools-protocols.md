# Objective 5.5 — Given a scenario, use the appropriate tool or protocol to solve networking issues

This objective is the toolbox for everything else in Domain 5. The exam presents a symptom and asks **"which tool/command should the technician use?"** — or shows you command output and asks what it means. You need three things for each tool: *what it does*, *when it's the right choice*, and *what its output looks like*. The software tools (ping, traceroute, nslookup/dig, tcpdump, netstat, ip/ipconfig, arp, Nmap, protocol analyzers, LLDP/CDP, speed testers) diagnose logical problems; the hardware tools (toner, cable tester, taps, Wi-Fi analyzer, visual fault locator) diagnose physical ones; and the `show` commands interrogate switches and routers directly. Expect matching-style and scenario questions: "trace a cable in the wall" → toner; "find which port a device is on" → show mac-address-table; "see every DNS record detail" → dig.

## Software Tools

### Protocol analyzer

A **protocol analyzer** (packet sniffer) — **Wireshark** is the canonical GUI example — captures traffic and decodes every layer of every frame for **deep packet inspection**: headers, flags, payloads, timing, retransmissions, malformed packets. Use it when you need to see *exactly* what's on the wire: DHCP conversations that never complete, TLS handshake failures, retransmission storms, chatty applications, suspicious traffic. To capture traffic that isn't addressed to your machine, you need a **SPAN/mirror port** on the switch or a **tap** (see hardware tools), and the NIC in promiscuous mode.

> 💡 **Exam Tip:** Keyword mapping: "examine the contents/headers of packets," "deep packet inspection," "analyze the DHCP exchange" → **protocol analyzer (Wireshark)**. For the CLI equivalent, see **tcpdump** below.

### Command line

#### ping
Sends **ICMP echo requests**; reports reachability, **RTT latency**, and **packet loss**. First-line connectivity test and the heart of "divide and conquer" (ping loopback → gateway → remote IP → remote name).

```
C:\> ping 8.8.8.8
Reply from 8.8.8.8: bytes=32 time=14ms TTL=117
Reply from 8.8.8.8: bytes=32 time=15ms TTL=117
Request timed out.
Reply from 8.8.8.8: bytes=32 time=13ms TTL=117
    Packets: Sent = 4, Received = 3, Lost = 1 (25% loss),
    Approximate round trip times: Minimum = 13ms, Maximum = 15ms, Average = 14ms
```

- Windows: `ping -t` = continuous (Ctrl+C to stop); default is 4 echoes.
- Linux/macOS: continuous by default; `ping -c 4` = count of 4.
- Reading it: loss % (congestion/faulty path), latency and its *consistency* (widely varying times = jitter/congestion). "Ping by IP works, ping by name fails" → DNS problem.

#### traceroute/tracert
Maps the **hop-by-hop path** to a destination by sending probes with incrementing TTL (1, 2, 3…); each router that decrements TTL to zero returns "time exceeded," revealing itself. Windows: `tracert` (ICMP). Linux/macOS: `traceroute` (UDP by default). Use it to find **where along the path** traffic stops or latency jumps.

```
C:\> tracert example.com
  1     1 ms     1 ms     1 ms  192.168.1.1
  2    12 ms    11 ms    14 ms  10.20.0.1
  3     *        *        *     Request timed out.
  4    28 ms    27 ms    29 ms  203.0.113.9
  5    30 ms    31 ms    30 ms  93.184.216.34
```

Reading it: latency jumping at hop 4 and staying high afterward = delay introduced there. `* * *` at hop 3 while later hops answer = that router just doesn't reply to probes (normal); `* * *` from some hop **to the end** = traffic actually dies there (routing/ACL/outage).

#### nslookup
DNS query tool (Windows-native; also on Linux/macOS). Verifies **name resolution**: does the name resolve, to what, and by which server? Supports one-shot (`nslookup www.example.com`) and **interactive mode**, where you can change record type (`set type=MX`) and query a *specific* server (`server 8.8.8.8`) — perfect for "internal DNS says X, public DNS says Y" comparisons.

```
C:\> nslookup www.example.com
Server:  dns.corp.local
Address:  10.1.1.53

Non-authoritative answer:
Name:    www.example.com
Address:  93.184.216.34
```

"Non-authoritative" simply means the answer came from a resolver's cache, not the domain's own authoritative server.

#### dig
The DNS power tool on Linux/macOS (BIND's Domain Information Groper) — more **detailed and script-friendly** than nslookup. Shows the full response: **ANSWER SECTION** with records and TTLs, query time, which server answered. `dig +short example.com` prints just the answer; `dig MX example.com`, `dig @8.8.8.8 example.com` (query a specific server), `dig -x 93.184.216.34` (reverse lookup).

```
$ dig example.com

;; ANSWER SECTION:
example.com.        3600    IN      A       93.184.216.34

;; Query time: 18 msec
;; SERVER: 8.8.8.8#53(8.8.8.8)
```

> 💡 **Exam Tip:** nslookup vs. dig: both query DNS; **dig gives richer, more detailed output** (full sections, TTLs, timing) and is the Linux-native choice. A question emphasizing "detailed DNS record information" or showing an `;; ANSWER SECTION:` wants **dig**.

#### tcpdump
**Command-line packet capture** for Linux/Unix (and macOS). The CLI counterpart of Wireshark — ideal on servers with no GUI or for quick filtered captures; capture files (`-w file.pcap`) can be opened later in Wireshark.

```
$ sudo tcpdump -i eth0 port 53 -n
14:02:11.532 IP 10.1.1.50.44123 > 8.8.8.8.53: A? example.com.
14:02:11.551 IP 8.8.8.8.53 > 10.1.1.50.44123: A 93.184.216.34
```

Key flags: `-i <interface>` capture interface, `-n` don't resolve names, `-w`/`-r` write/read capture files, and BPF filters like `host 10.1.1.5`, `port 443`, `icmp`.

#### netstat
Displays **active connections and listening ports** on the local host, plus (with flags) statistics and routing. Use to answer: What is this machine talking to? Which service is listening on which port? Is that port actually open locally?

```
C:\> netstat -an
Proto  Local Address        Foreign Address      State
TCP    0.0.0.0:135          0.0.0.0:0            LISTENING
TCP    10.1.1.50:49722      140.82.113.26:443    ESTABLISHED
```

Common flags: `-a` all connections + listening ports, `-n` numeric (no name resolution), `-b` (Windows, admin) show owning executable, `-r` routing table, `-s` per-protocol stats. (Modern Linux prefers `ss`, but netstat is what the exam names.)

#### ip/ifconfig/ipconfig
The local interface configuration viewers — **first stop for any client-side issue** (What's my IP? Mask? Gateway? DNS? DHCP or APIPA?).

| Command | OS | Key uses |
|---|---|---|
| `ipconfig` | Windows | `/all` (full detail: MAC, DHCP server, lease, DNS), `/release` + `/renew` (new DHCP lease), `/flushdns` (clear DNS resolver cache) |
| `ifconfig` | Linux/macOS (legacy) | View/set interface addresses; deprecated on modern Linux |
| `ip` | Linux (current) | `ip addr` (addresses), `ip link` (interface state), `ip route` (routing table), `ip neigh` (ARP/neighbor table) |

Fingerprints you spot here: **169.254.x.x** = APIPA/DHCP failure; wrong mask/gateway; missing DNS servers.

#### arp
Views/manages the local **ARP cache** — the IP-to-MAC mappings for the local subnet. `arp -a` displays the table; `arp -d` deletes entries (flush a stale one).

```
C:\> arp -a
Interface: 10.1.1.50 --- 0x8
  Internet Address      Physical Address      Type
  10.1.1.1              00-1a-2b-3c-4d-5e     dynamic
  10.1.1.37             a4-83-e7-11-22-33     dynamic
```

Uses: confirm the gateway resolves to the **correct** MAC (a changed/duplicated MAC here reveals **duplicate IPs** or **ARP spoofing/poisoning**); stale entries after a NIC swap cause "can't reach one host until we cleared ARP."

| Command | Primary question it answers |
|---|---|
| ping | Can I reach it? How fast? Any loss? |
| traceroute/tracert | *Where* along the path does it break/slow? |
| nslookup / dig | Does the name resolve, to what, per which server? (dig = detail) |
| tcpdump | What packets are actually on the wire? (CLI) |
| netstat | What connections/listening ports does *this host* have? |
| ipconfig/ip/ifconfig | What is this host's IP config? (release/renew/flushdns) |
| arp | Which MAC does this host think owns that IP? |

### Nmap
**Network Mapper** — network/port scanner. Uses: **host discovery** (which IPs are alive on a subnet: `nmap -sn 10.1.1.0/24` ping sweep), **port scanning** (which TCP/UDP ports are open), **service/version detection** (`-sV` — what software/version answers on each port), and OS fingerprinting (`-O`). Troubleshooting uses: verify a service is actually reachable/open from the network side, find rogue devices or unauthorized services, inventory a subnet. Also a security-audit staple — and the exam expects the caveat: **only scan networks you are authorized to scan**.

> ⚠️ **Common Pitfall:** netstat vs. Nmap: **netstat runs on the host** and shows *its own* connections/listening ports; **Nmap probes across the network** to discover *other* hosts' open ports. "Check which ports are open on a remote server" → Nmap. "Check what this server is listening on locally" → netstat.

### Link Layer Discovery Protocol (LLDP)/Cisco Discovery Protocol (CDP)
Layer 2 **neighbor discovery** protocols: directly connected devices advertise identity, port, capabilities, and (for phones) voice VLAN/PoE info.

| | LLDP (802.1AB) | CDP |
|---|---|---|
| Standard | **Open IEEE standard** — multivendor | **Cisco proprietary** |
| Typical use | Mixed-vendor environments; LLDP-MED for VoIP | Cisco environments |

`show cdp neighbors` / `show lldp neighbors` answers "**what is actually plugged into this port?**" — invaluable for mapping undocumented networks and confirming an uplink goes where the diagram claims:

```
Switch# show cdp neighbors
Device ID     Local Intrfce   Holdtme   Capability   Platform    Port ID
CORE-SW1      Gig 0/48        155       R S I        C9300       Gig 1/0/12
AP-Floor2     Gig 0/14        142       T            AIR-AP3802  Gig 0
```

Reading: our port Gi0/48 connects to CORE-SW1's port Gi1/0/12. Security note: these advertisements leak topology info, so they're often disabled on untrusted/user-facing ports.

### Speed tester
Measures actual **throughput** (and usually latency/jitter) against a test server — web-based (speedtest sites) or dedicated (iperf between two hosts you control, hardware line testers). Use to validate ISP bandwidth ("are we getting the 500 Mbps we pay for?") and to isolate where throughput drops by testing from different points in the network (at the edge router vs. the user's desk vs. Wi-Fi). Results vary with server location, time of day, and everything in between — test multiple times/points before blaming the ISP.

## Hardware Tools

### Toner (tone generator and probe)
The **"fox and hound"**: clip the **tone generator** onto a cable/pair at one end; wave the **inductive probe** along cable bundles/patch panels/wall jacks — it sings when near the cable carrying the tone. Purpose: **identify/trace one specific cable** among many — unlabeled runs in walls, ceilings, or dense patch panels. It does *not* test cable quality — it only finds the cable.

### Cable tester
Verifies copper cabling correctness — **wiremap** testing pin-by-pin to detect **opens** (broken conductor), **shorts** (conductors touching), **miswires/reversed pairs** (wrong pins), and **split pairs** (right pins, wrong twisted partners — needs a decent tester). Advanced **certifiers** also measure length (TDR), attenuation, and crosstalk (NEXT/FEXT) against Cat 6/6a specs. Use after terminating new runs and whenever a physical fault is suspected.

> 💡 **Exam Tip:** Tool selection by verb: **find/trace** an unlabeled cable → toner/probe. **Verify/test** a termination or suspected bad cable → cable tester. **Certify** to category spec → certifier. Fiber break location → OTDR (or VFL for short range, below).

### Taps
A **network tap** is a hardware device inserted **inline** on a link that copies traffic to a monitoring port — feeding a protocol analyzer or IDS with a complete, unaltered stream. **Passive taps** (including optical splitters on fiber) need no power and cannot drop or modify monitored traffic — more faithful than a switch **SPAN/mirror port**, which can silently drop copies under load and adds switch CPU cost. Use for reliable, continuous capture and security monitoring. (Installing one interrupts the link briefly — plan a window.)

### Wi-Fi analyzer
Software or handheld hardware that surveys the RF environment: **SSIDs and BSSIDs heard, per-AP channel and signal strength (RSSI in dBm), channel utilization/overlap, and rogue AP detection**; spectrum-analyzer variants also see **non-Wi-Fi interference** (microwaves, Bluetooth). Use for: site surveys and heatmaps, choosing clean channels (1/6/11 planning), diagnosing "slow Wi-Fi in the west wing," and hunting **rogue/unauthorized APs**.

### Visual fault locator
A **VFL** injects **visible (typically red, ~650 nm) laser light** into a fiber strand. Where the fiber is **broken, sharply bent, or badly spliced**, red light visibly leaks/glows through the jacket — instantly localizing near-distance faults. Also the quick way to **verify continuity and polarity** ("which strand is which?" — light one strand, see which connector glows at the far end). Complements the **OTDR** (which measures loss events and distance-to-fault on long runs) and the **light meter/OPM** (which measures received power in dBm against the loss budget). Never look into fiber ends — even "visible" test lasers deserve respect.

| Fiber tool | What it tells you |
|---|---|
| Visual fault locator | *Where* a nearby break/bend is (visible glow); continuity/polarity |
| Light meter (OPM) | *How much* power arrives (dBm) vs. loss budget |
| OTDR | Loss events and their *distance* along a long run |

## Basic Networking Device Commands

The `show` family (Cisco-style syntax; other vendors are similar) — for each, know **what it displays** and **when you'd use it**:

### show mac-address-table
The switch's CAM table: **MAC address ↔ port ↔ VLAN** learnings. Use to **physically locate a device** ("which port is MAC aa:bb:cc… on?" → follow the cable), to hunt duplicate-IP/rogue devices (pair with `show arp` to go IP→MAC→port), and to spot loops (same MAC flapping between ports).

```
Switch# show mac address-table
Vlan    Mac Address       Type        Ports
  10    a483.e711.2233    DYNAMIC     Gi0/14
  20    001a.2b3c.4d5e    DYNAMIC     Gi0/48
```

### show route
(`show ip route` on Cisco IOS) The device's **routing table**: connected/static/dynamic routes, next hops, administrative distances/metrics, and the **gateway of last resort** (default route). Use for route-selection problems: Is there a route to the destination? The right next hop? A default route at all? Codes flag the source: `C` connected, `S` static, `O` OSPF, `B` BGP.

```
Router# show ip route
S*   0.0.0.0/0 [1/0] via 203.0.113.1
C    10.1.1.0/24 is directly connected, GigabitEthernet0/0
O    10.2.0.0/16 [110/20] via 10.1.1.254
```

### show interface
Per-interface **status and statistics**: up/down state (line + protocol), **speed/duplex**, input/output rates, and the error counters from objective 5.2 — **CRC errors, runts, giants, drops/discards**, collisions, resets. The go-to command for "is this port healthy?": err-disabled shows here; duplex mismatch shows as half-duplex + late collisions; congestion as output drops.

```
Switch# show interface gi0/14
GigabitEthernet0/14 is up, line protocol is up
  Full-duplex, 1000Mb/s
  5 minute input rate 2,304,000 bits/sec
  1043 input errors, 998 CRC, 12 runts, 3 giants, 0 output drops
```

### show config
Displays the device **configuration** (`show running-config` = active in RAM; `show startup-config` = saved for boot). Use to audit settings against the documented baseline, spot recent unauthorized/incorrect changes ("what changed?" — Step 1!), and verify VLANs, ACLs, addresses, and port settings are what you think they are. A running/startup mismatch means unsaved changes.

### show arp
The router/switch's **ARP table: IP ↔ MAC** bindings it has resolved. Use for duplicate-IP investigations (wrong/changing MAC on an IP), confirming a host is actually present, and as the IP→MAC step before `show mac-address-table`'s MAC→port step when physically locating a device.

### show vlan
**VLAN database and port assignments**: which VLANs exist and which access ports belong to each. First command for "user in the wrong VLAN" symptoms (link up, wrong subnet's DHCP, can't reach resources). Verify the port is in the intended VLAN and the VLAN actually exists on this switch.

```
Switch# show vlan brief
VLAN Name       Status    Ports
10   USERS      active    Gi0/1-0/24
20   VOICE      active    Gi0/25-0/40
99   MGMT       active    Gi0/48
```

### show power
(`show power inline` for PoE on Cisco) The switch's **PoE status: total power budget, power used/remaining, and per-port draw/class**. The command for objective 5.2's PoE scenarios: devices not powering or randomly rebooting → check whether the **budget is exhausted** and what each port is drawing/allocated.

```
Switch# show power inline
Available:370.0(w)  Used:359.8(w)  Remaining:10.2(w)
Interface Admin  Oper       Power   Device              Class
Gi0/1     auto   on         15.4    IP Phone            2
Gi0/2     auto   on         30.0    AP AIR-AP3802       4
Gi0/24    auto   faulty     0.0     n/a                 n/a
```

| Command | Question it answers |
|---|---|
| show mac-address-table | Which **port** is this MAC/device on? |
| show route | How will the device **forward** to destination X? Default route present? |
| show interface | Is the port up? Errors (CRC/runts/giants/drops)? Speed/duplex? |
| show config | What is the device actually **configured** to do? What changed? |
| show arp | Which **MAC** does the device have for IP X? |
| show vlan | Which **VLAN** is each port in? |
| show power | How much **PoE** is budgeted/used/left, per port? |

> 💡 **Exam Tip:** The classic two-step device hunt: `show arp` (IP → MAC) then `show mac-address-table` (MAC → switchport) → walk to the port and follow the cable. Expect a question built exactly on this sequence.

## Key Takeaways

- [ ] ping = reachability/RTT/loss; traceroute = per-hop path (`* * *` mid-path can be cosmetic); pattern: ping IP ok + name fails = DNS.
- [ ] nslookup (interactive, set server/type) vs. dig (detailed ANSWER SECTION, +short, @server) — both DNS; dig for detail.
- [ ] Wireshark = GUI deep packet inspection; tcpdump = CLI capture (-i, -n, -w, BPF filters); tap or SPAN gets you the traffic.
- [ ] netstat = local connections/listening ports; Nmap = remote discovery/port/service scans — authorized use only.
- [ ] ipconfig /all, /release, /renew, /flushdns; Linux `ip addr`/`ip route`; arp -a for IP↔MAC (duplicate IP/poisoning clues).
- [ ] LLDP = open standard (802.1AB), CDP = Cisco-proprietary; show *-neighbors reveals what's on each port.
- [ ] Toner **finds** cables; cable tester **verifies** them (opens/shorts/miswires/split pairs); tap **copies** traffic passively; Wi-Fi analyzer maps RF; VFL's visible laser exposes fiber breaks/polarity.
- [ ] show commands: mac-address-table (MAC→port), route (forwarding), interface (status/errors), config (settings), arp (IP→MAC), vlan (port VLANs), power (PoE budget).
- [ ] Device-hunt combo: show arp → show mac-address-table → physical port.

## Self-Check Questions

1. A technician must determine which switchport an unauthorized device (known IP address) is connected to. Which two show commands, in what order?
2. Users can reach servers by IP but not by hostname. Which two command-line tools directly test the failing function, and which gives more detailed output?
3. A server on a remote subnet seems down. Ping fails from your desk but works from the server's local subnet. Which tool tells you where along the path traffic is being dropped?
4. You need to identify one unlabeled cable among 200 in a patch panel, then confirm that same run has no opens or split pairs. Which hardware tool for each task?
5. VoIP phones on one switch keep rebooting randomly after ten new phones were installed. Which device command confirms the suspected cause, and what would you look for?

<details>
<summary>Answers</summary>

1. **`show arp`** first (resolve the IP to its MAC), then **`show mac-address-table`** (find which port learned that MAC). Then trace the cable from that port.
2. **nslookup** and **dig** — both query DNS directly. **dig** provides the more detailed output (full ANSWER SECTION, TTLs, query time, responding server).
3. **traceroute/tracert** — it shows each hop toward the destination; the point where responses stop for good (all subsequent hops silent) marks where traffic is lost or blocked.
4. **Toner (tone generator + probe)** to trace/identify the cable; **cable tester** (wiremap/certifier) to verify no opens, shorts, miswires, or split pairs.
5. **`show power` / `show power inline`** — compare the switch's total PoE budget against power used/remaining and per-port draw. Random reboots after adding devices indicate the **power budget is exceeded**.

</details>
