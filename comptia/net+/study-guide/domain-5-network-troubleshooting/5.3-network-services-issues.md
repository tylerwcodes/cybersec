# Objective 5.3 — Given a scenario, troubleshoot common issues with network services

If Layer 1 problems are about *wires*, objective 5.3 is about *logic*: switching loops, wrong VLANs, ACLs eating legitimate traffic, broken routing decisions, exhausted DHCP scopes, and the classic client misconfigurations — wrong gateway, wrong IP, duplicate IP, wrong subnet mask. These are the highest-frequency "given a scenario" questions in Domain 5 because each misconfiguration produces a *distinctive symptom fingerprint*: APIPA addresses point at DHCP, "local works but remote doesn't" points at the gateway, "some hosts reachable and others not" points at the subnet mask. Learn the fingerprints and these questions become pattern matching.

## Switching Issues

### STP (Spanning Tree Protocol)

STP (802.1D and successors like RSTP 802.1w) exists to prevent **Layer 2 loops** by electing a root bridge and blocking redundant paths. When STP is disabled, misconfigured, or slow to converge, loops form — and because **Ethernet frames have no TTL**, a looped broadcast circulates forever and multiplies.

#### Network loops (broadcast storms)
**Cause:** redundant links with STP disabled/failed, or someone plugs both ends of a cable into the same switch/two access ports (common with unmanaged mini-switches under desks).
**Symptoms — memorize this cluster:**
- Network-wide, severe slowness or total outage; even switch management becomes unreachable.
- **Broadcast storm:** broadcast/multicast traffic saturates every link.
- **Switch CPU spikes**; port LEDs blinking rapidly in unison.
- **MAC address flapping:** the same MAC is learned on different ports repeatedly (log messages like "MAC address flapping between port Gi0/1 and Gi0/2") — a signature symptom, because looped copies of the same frame arrive on multiple ports.

**Fixes:** re-enable/verify STP everywhere, physically remove the looped connection, enable **BPDU guard** on access ports (err-disables a port that hears BPDUs), loop guard, and storm control as containment.

> 💡 **Exam Tip:** "Users across the entire building suddenly lose connectivity, switch CPUs are at 100%, and logs show the same MAC learned on multiple ports" = **Layer 2 loop / broadcast storm**. The preventive-measure answer is BPDU guard on access ports.

#### Root bridge selection
The switch with the **lowest bridge ID (priority + MAC)** becomes root. All switches default to the same priority (32768), so the **oldest switch (lowest MAC) often wins by accident** — and if that's a slow access switch in a closet, traffic takes absurd paths through it, causing congestion and suboptimal performance after every topology change.
**Fix:** deliberately set the root: lower the priority on the core switch (e.g., 4096 or 0, or `spanning-tree vlan X root primary`), and enable **root guard** on ports where a new root should never appear.

#### Port roles
| Role | Meaning |
|---|---|
| **Root port** | The one port on a *non-root* switch with the best path **toward the root bridge** |
| **Designated port** | The forwarding port on each segment (all ports on the root bridge are designated) |
| **Blocked/alternate (non-designated)** | Redundant path placed in blocking to prevent the loop (RSTP: alternate/backup) |

Misunderstanding symptom: a link you expected to carry traffic is "down" for data — check whether STP has (correctly) blocked it. That's the protocol working, not a fault.

#### Port states
Classic 802.1D states, in order: **Blocking → Listening → Learning → Forwarding** (+ **Disabled**). Convergence through listening+learning takes ~30 seconds (15 s + 15 s, after up to 20 s max-age if a failure must be detected first).
**Symptom:** "When a PC boots, it fails to get a DHCP address, but works if we release/renew ~30 seconds later" → the port is sitting in listening/learning while the client's DHCP requests time out.
**Fix:** enable **PortFast** (edge port) on access ports so they jump straight to forwarding — combined with BPDU guard for safety. RSTP reduces states to discarding/learning/forwarding and converges in seconds.

> ⚠️ **Common Pitfall:** Don't fix the "slow port at boot" problem by disabling STP — that invites loops. The correct answer is **PortFast on access ports** (never on trunks/uplinks), typically with BPDU guard.

### Incorrect VLAN Assignment

A switchport assigned to the wrong VLAN drops the device into the wrong broadcast domain. Symptom fingerprint:
- Link light is on, interface up — **Layer 1 looks perfect**.
- Device gets **no DHCP lease** (or a lease from an *unexpected* scope — an address in the wrong subnet is the giveaway).
- Cannot reach its normal resources (file servers, printers on the correct VLAN), may reach the "wrong" ones.
- Two devices on the same physical switch can't communicate → check whether they're in different VLANs.

**Diagnosis:** `show vlan` (port-to-VLAN assignments) and `show interface` / `show interfaces switchport`. Also verify trunk links carry (don't prune) the needed VLANs and native VLAN settings match — a missing VLAN on a trunk isolates that VLAN across switches.
**Fix:** `switchport access vlan <correct>` on the port (or fix the trunk allowed-VLAN list).

> 💡 **Exam Tip:** "User moved desks; link is up but they receive an IP address from a different subnet than before and can't reach their department server" → the new wall jack's switchport is in the **wrong VLAN**.

### ACLs (Access Control Lists)

ACLs filter traffic on routers/L3 switches/firewalls. Misconfigurations block legitimate traffic:
- **Rules process top-down, first match wins**, and there is an **implicit deny (any) at the end**. A new permit added *below* a broader deny never matches; forgetting any permit rule means the implicit deny eats everything.
- Symptom fingerprint: **some traffic works, specific traffic doesn't** — e.g., ping works but HTTPS to the same server fails (ACL permits ICMP, blocks TCP/443), or one subnet can reach a service while another can't. Often appears **immediately after a change** ("after last night's firewall update…").
- Also check: ACL applied to the wrong interface or wrong direction (in vs. out), wildcard-mask errors, wrong port numbers.

**Diagnosis:** review the ACL (`show access-lists` — match counters reveal which rule is firing), check recent changes, use logging on deny rules.
**Fix:** reorder/insert the correct permit above the deny, or correct the interface/direction.

> ⚠️ **Common Pitfall:** "Traceroute dies at hop 3 for one application's port, but ping to the destination works" — that's not a routing failure; routing wouldn't discriminate by port. **Port-specific failure = ACL/firewall filtering.**

## Route Selection

### Routing table
A router chooses a route per destination using, in order:
1. **Longest prefix match** wins first: a /28 route beats a /24 beats a /16 beats a /0 for a matching destination.
2. Among equal prefixes from different sources, lowest **administrative distance** (connected 0, static 1, eBGP 20, OSPF 110, RIP 120…).
3. Among equal-AD routes of the same protocol, best **metric**.

Troubleshooting reads: `show route` / `show ip route` (Windows `route print`, Linux `ip route`). Look for the destination network: Is a route present? Does it point at the correct next hop/exit interface? Is a *more specific but wrong* route hijacking traffic (a stale static /32, an overlapping subnet)? Asymmetric or looping paths show up in `traceroute` (repeating hops = routing loop).
**Symptoms of route selection problems:** one remote network unreachable while others work; traffic taking a slow backup path; traceroute looping between two routers.
**Fixes:** add/correct the static route, fix the overlapping/mistyped prefix, restore the routing protocol adjacency, remove stale routes.

### Default routes
The **default route — 0.0.0.0/0 (IPv6 ::/0)** — is the "route of last resort" used when no more specific route matches, typically pointing at the internet edge/ISP.
- **Missing default route:** internal networks all reachable, but **no internet/external connectivity** from that router's perspective.
- **Incorrect default route:** traffic to unknown destinations goes to the wrong next hop and dies — or loops.
- Because 0.0.0.0/0 is the *shortest possible prefix*, **any** more specific route overrides it — useful to remember when a bogus specific route blackholes one destination while "the internet works."

> 💡 **Exam Tip:** Given a routing-table snippet and asked "which route will the router use for 10.1.5.77?" — apply **longest prefix match** first, before comparing AD or metric. This exact exercise appears on the exam.

## Address Pool Exhaustion (DHCP)

A DHCP scope has a finite pool. When every address is leased, new clients get nothing — and a Windows/macOS client that receives no DHCPOFFER self-assigns an **APIPA address: 169.254.x.x/16** (link-local; it can talk only to other link-local hosts on the same segment — **no gateway, no internet**).

**Symptom fingerprint:** new/returning devices can't get online and show 169.254 addresses, while already-leased devices keep working (until their leases expire). Often triggered by: long lease times in high-turnover environments (guest Wi-Fi, conference), scope sized too small for growth, a flood of new devices (BYOD, IoT), or a malfunctioning/malicious client grabbing many leases (DHCP starvation attack).

**Diagnosis:** check the DHCP server's scope utilization; `ipconfig /all` on a client (APIPA, no DHCP server listed).
**Fixes:**
- **Shorten the lease duration** (e.g., 8 days → 8 hours for guest networks) so abandoned leases return quickly.
- **Expand the scope/subnet** (larger range, or resubnet e.g. /24 → /23).
- Remove unnecessary exclusions/reservations; add another scope/VLAN.
- **Find rogue or misbehaving devices** hogging leases; enable DHCP snooping to stop starvation attacks.

> ⚠️ **Common Pitfall:** A **169.254.x.x** address means "DHCP failed" — pool exhaustion, DHCP server down, or no relay (`ip helper-address`) on the client's VLAN. It does **not** mean a bad NIC or bad cable: the link had to be *up* for the client to try DHCP at all.

## Incorrect Default Gateway

The default gateway is where a host sends traffic destined **outside its own subnet**. Misconfigure it and you get the cleanest fingerprint in networking:

- **CAN** reach everything on the local subnet (ping neighbors, local printers, local server).
- **CANNOT** reach anything on remote subnets or the internet.
- Ping tests: ping own IP ✔, ping local hosts ✔, ping gateway ✖ (or gateway pings but nothing beyond), ping 8.8.8.8 ✖.

Causes: typo in a static config, wrong gateway handed out by DHCP (scope option misconfigured), gateway on a *different subnet* than the host (invalid — must be within the host's subnet), or the gateway router itself down (then *everyone* on the subnet has the symptom).
**Fix:** correct the gateway on the host or in the DHCP scope options (option 3).

> 💡 **Exam Tip:** "Local yes, remote no" = **default gateway** issue. If only one user has it → their config/DHCP lease. If the whole subnet has it → the gateway router or its interface is down.

## Incorrect IP Address

A host with an address in the **wrong subnet** for its segment (fat-fingered static config, moved device keeping an old static address, wrong VLAN giving the "wrong" scope) can't communicate properly: ARP for its "local" peers fails because they're not actually on its wire, and the gateway ignores or can't reach it.

### Duplicate IP address
Two hosts claiming the same IP is a special, nastier case:
- **Symptoms:** **intermittent connectivity for both hosts** — traffic goes to whichever machine most recently answered ARP; connections drop and revive unpredictably. OS error messages: "Windows has detected an IP address conflict." Switch/router logs may show the IP flip-flopping between two MACs; **gratuitous ARP** announcements collide.
- **Common causes:** a static address assigned inside a DHCP scope (server later leases it to someone else — prevent with **exclusions/reservations**), two admins assigning the same static, a device brought from another site, or a rogue device.
- **Diagnosis:** `arp -a` (watch the MAC associated with the IP change), ping the address then check ARP, use the switch MAC table (`show mac-address-table`) to physically locate both offenders.
- **Fix:** change/DHCP-enable one host; add an exclusion or reservation so it can't recur.

## Incorrect Subnet Mask

The subtlest misconfiguration: the mask defines where a host believes its local network ends, so a wrong mask causes **partial, boundary-dependent reachability** — the host can reach *some* addresses but not others, in a pattern set by the math.

How it breaks, in both directions:
- **Mask too small (e.g., /25 configured where /24 is correct):** addresses in the other half of the real subnet look "remote," so the host sends them to the gateway — which may or may not hairpin them back. Host reaches 10.1.1.1–126 fine, struggles with 10.1.1.129+.
- **Mask too large (e.g., /16 where /24 is correct):** genuinely remote addresses (10.1.2.x) look "local," so the host ARPs for them directly instead of using the gateway — ARP gets no answer (unless proxy ARP saves it), and those destinations are unreachable while true local hosts and distant internet destinations (still clearly remote) may work.

**Fingerprint:** "Host can communicate with some devices on its subnet/neighboring subnets but not others; everyone else is fine" → check the mask. Diagnosis: `ipconfig`/`ip addr` and compare mask with the network design; do the binary math on the failing destinations — they'll cluster on one side of the wrong boundary.
**Fix:** correct the mask (host or DHCP scope).

> ⚠️ **Common Pitfall:** Wrong **gateway** = "local works, ALL remote fails." Wrong **mask** = "SOME destinations fail, based on address ranges." Duplicate **IP** = "intermittent for two specific hosts." The exam expects you to tell these three apart from symptoms alone.

## Symptom → Likely Cause → Fix

| Symptom | Likely cause | Fix |
|---|---|---|
| Whole network slow/down, switch CPU 100%, MAC flapping in logs | Layer 2 loop / broadcast storm (STP failed or bypassed) | Remove loop, verify STP, BPDU guard + storm control |
| Traffic flows through a slow closet switch; poor performance after topology change | Wrong root bridge (default priorities, oldest MAC won) | Set core switch priority low (root primary), root guard |
| PC gets no DHCP at boot; works ~30 s later | STP listening/learning delay on the access port | Enable PortFast (+ BPDU guard) on access ports |
| Link up, but IP from unexpected subnet; can't reach department resources | Incorrect VLAN assignment on the switchport | `show vlan`; set correct access VLAN / fix trunk allowed list |
| After a firewall/router change, one app/port fails while ping works | ACL misconfiguration (order/implicit deny/direction) | Review ACL top-down, fix rule order/placement |
| One remote network unreachable; traceroute loops or dies | Missing/incorrect route; routing loop | Fix routing table entry / protocol adjacency |
| Internal networks fine; nothing external reachable | Missing/incorrect default route (0.0.0.0/0) | Add/correct route of last resort |
| New clients get 169.254.x.x; existing users fine | DHCP address pool exhaustion (or DHCP/relay down) | Shorten leases, expand scope, find rogue devices; check relay |
| Can reach local subnet only; nothing remote | Incorrect default gateway | Correct host/DHCP gateway (option 3) |
| Two hosts drop connections intermittently; ARP shows changing MAC for one IP | Duplicate IP address | Reassign one host; add DHCP exclusion/reservation |
| Host reaches some address ranges but not others; neighbors fine | Incorrect subnet mask | Correct the mask to match the network design |
| Statically configured server suddenly conflicts after DHCP enabled | Static IP inside DHCP pool | Exclude/reserve the address in the scope |

## Key Takeaways

- [ ] Loop/broadcast storm signature: total slowness, CPU spike, **MAC flapping** — Ethernet has no TTL; STP is the cure, BPDU guard the prevention.
- [ ] Root bridge = lowest bridge ID (priority, then MAC); set your core's priority deliberately or the oldest switch wins.
- [ ] STP port roles: root/designated/blocked; states Blocking→Listening→Learning→Forwarding; PortFast for access ports (with BPDU guard).
- [ ] Wrong VLAN: link up but wrong-subnet DHCP and unreachable resources — check `show vlan`.
- [ ] ACLs: top-down, first match, **implicit deny**; port-specific failures after a change scream ACL.
- [ ] Route selection: **longest prefix match** first, then AD, then metric; default route = 0.0.0.0/0 = last resort.
- [ ] DHCP exhaustion → clients on **APIPA 169.254.x.x**; fix with shorter leases, bigger scope, rogue-device hunt.
- [ ] Wrong gateway = local-only connectivity; wrong mask = boundary-pattern partial connectivity; duplicate IP = intermittent conflicts for two hosts.

## Self-Check Questions

1. Switch logs show the same MAC address being learned alternately on ports Gi0/5 and Gi0/7, and the whole floor is crawling. What is happening?
2. A router has routes 10.0.0.0/8 via A, 10.2.0.0/16 via B, and 0.0.0.0/0 via C. Which next hop is used for a packet to 10.2.3.4?
3. A user's laptop shows IP 169.254.100.7. The user could connect yesterday. List two likely causes and the first thing to check.
4. A workstation can print to the local-subnet printer and reach a local file server, but cannot browse any websites or reach any other office. Everyone else is fine. What single setting is most likely wrong?
5. After an administrator adds a new "permit tcp any host 10.9.9.10 eq 443" rule to the *bottom* of an ACL that contains "deny ip any any" logging near the top, users still cannot reach the server on HTTPS. Why?

<details>
<summary>Answers</summary>

1. A **Layer 2 loop causing a broadcast storm** — looped frames make the switch see the same source MAC on multiple ports (MAC flapping). Find and remove the loop; verify STP; deploy BPDU guard.
2. **B (10.2.0.0/16)** — longest prefix match wins: /16 is more specific than /8, and the default /0 is only used when nothing else matches.
3. APIPA means DHCP failed: likely **address pool exhaustion** or the **DHCP server/relay being down**. First check the DHCP server's scope utilization (and that the VLAN's relay/ip helper is working); `ipconfig /release` + `/renew` to retest.
4. The workstation's **default gateway** — local subnet reachable, all remote destinations unreachable, and the scope of "just this one host" points to its own configuration or lease.
5. ACLs process **top-down with first match**: the earlier `deny` matches the traffic before the new permit is ever evaluated. The permit must be inserted **above** the deny.

</details>
