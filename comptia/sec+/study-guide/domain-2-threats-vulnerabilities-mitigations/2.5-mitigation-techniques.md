# Objective 2.5 — Explain the purpose of mitigation techniques used to secure the enterprise

Domain 2 is worth **22% of the SY0-701 exam**, and objective 2.5 is where the domain pays off: after four objectives on threat actors, vectors, attacks, and vulnerabilities, 2.5 asks what you actually *do* about them. The exam tests this material two ways: **definition matching** ("Which technique restricts software execution to a pre-approved list?") and — far more often — **scenario selection** ("A workstation is infected with a worm; what should the analyst do FIRST?" or "Which mitigation would have prevented this attack?"). Most 2.5 questions describe an attack or vulnerability from 2.3/2.4 and ask you to pick the *best* mitigation, so the skill is mapping scenario keywords to the one technique that directly addresses the stated problem. The highest-yield items are **segmentation vs. isolation** (contain lateral movement vs. cut off a compromised host), the **application allow list vs. deny list** distinction, **least privilege** as the default answer to over-permissioned accounts, **patching** as the default answer to known vulnerabilities, and the seven **hardening techniques** — expect at least one question that lists a system's weaknesses and asks which hardening step fixes them.

## Segmentation

**Segmentation** divides a network into smaller zones (VLANs, subnets, firewalled segments, or software-defined microsegments) so that systems with different trust levels, sensitivity, or compliance requirements cannot freely communicate. Traffic between segments must cross an enforcement point — a firewall, router ACL, or policy engine — where it can be inspected and restricted.

Purpose on the exam:

- **Limit lateral movement.** If an attacker compromises one workstation, segmentation stops them from freely reaching servers, databases, or other departments. It reduces the **blast radius** of a breach.
- **Contain high-risk device classes.** IoT devices, guest Wi-Fi, BYOD, and legacy/SCADA systems that can't run modern controls get their own segments.
- **Meet compliance requirements.** PCI DSS doesn't strictly mandate segmentation, but segmenting the cardholder data environment from the rest of the network is the standard way to shrink PCI audit scope.
- **Support Zero Trust.** Microsegmentation (per-workload segments, often in virtualized/cloud environments) enforces least privilege at the network level: each system can talk only to the systems it needs.

> 💡 **Exam Tip:** Scenario keywords **"limit lateral movement," "contain a breach to one part of the network," "separate IoT/guest/legacy devices from production," "reduce PCI scope"** → **segmentation**. It is a *preventive architectural* control applied **before** an incident; don't confuse it with isolation, which is applied *to a specific compromised or high-risk system*.

## Access Control

Access control determines **who or what can interact with a resource and what actions they may perform**. Authentication proves identity; access control (authorization) then enforces the rules. SY0-701 calls out two mechanisms.

### Access control list (ACL)

An **ACL** is an ordered list of rules that permits or denies access. The term appears in two contexts — recognize both:

| Context | What the ACL controls | Rule criteria | Example |
|---|---|---|---|
| **Network ACL** (routers, firewalls, cloud security groups) | Which **traffic** may pass through a network device or into a subnet | Source/destination IP, port, protocol, direction | "Deny all inbound TCP 3389 from the internet" |
| **Filesystem/resource ACL** (NTFS, cloud storage, directories) | Which **identities** may access an object | User/group + allowed operations | "Finance group: Read/Write on \\\\fs01\\budgets" |

Network ACLs are processed **top-down, first match wins**, and end in an **implicit deny** — any traffic not explicitly permitted is dropped. Misordered rules (a broad permit above a specific deny) are a classic troubleshooting scenario.

### Permissions

**Permissions** are the specific rights granted to a user, group, or service on a resource — read, write, modify, execute, delete, full control (or in Linux terms, `rwx` for owner/group/other). Permissions are the *entries* that make up a resource ACL. Exam-relevant practices:

- Assign permissions to **groups/roles**, not individual users — scalable, auditable, and clean to deprovision.
- **Review permissions regularly** (recertification/audits) to catch **privilege creep** — users accumulating access as they change roles without old access being removed.
- Permission problems are *authorization* problems: a user who can log in but cannot open a folder has a permissions issue, not an authentication issue.

> ⚠️ **Common Pitfall:** ACL vs. permissions on the exam: if the scenario is about **blocking traffic** (IPs, ports, protocols) on a router, firewall, or subnet, the answer is a **network ACL**. If it's about **which users can read or modify a file/share**, the answer is **permissions**. Both implement access control, but at different layers.

## Application Allow List

An **application allow list** (formerly "whitelist") permits **only explicitly approved applications to execute** — everything else is blocked by default, including malware that has never been seen before. Its inverse, a **deny list (block list)**, blocks known-bad applications and permits everything else.

| | Allow list | Deny list (block list) |
|---|---|---|
| Default stance | **Deny by default** — run only what's approved | **Allow by default** — block only what's listed |
| Stops unknown/zero-day malware? | **Yes** — unapproved code simply won't run | **No** — new malware isn't on the list yet |
| Security level | Higher | Lower |
| Administrative overhead | **High** — every legitimate app, update, and script must be approved | Low |
| Typical use | Fixed-function/high-security systems: kiosks, POS terminals, servers, OT | General-purpose environments where flexibility matters |

Applications are identified by file path, filename, hash, or (best) **publisher digital signature/certificate**, since hashes change with every update. Windows implementations include AppLocker and Windows Defender Application Control.

> 💡 **Exam Tip:** **"Prevent unauthorized/unknown software from running"** or **"stop malware that signature-based antivirus misses"** → **application allow list**. It's the strongest anti-malware execution control precisely because it doesn't need to recognize the malware — the malware just isn't on the approved list. The trade-off the exam loves: allow lists carry the highest management burden.

## Isolation

**Isolation** separates a system or process from other systems so it cannot interact with them — either **proactively** (running risky code where it can do no harm) or **reactively** (cutting off a compromised host during incident response).

- **Reactive isolation (containment):** when a host is infected or compromised, disconnect it from the network — unplug the cable, disable the switch port, move it to a quarantine VLAN, or use EDR's network-isolation feature. This stops malware from spreading and severs attacker command-and-control **while preserving the machine and its evidence for forensics**.
- **Proactive isolation:** **sandboxes** detonate suspicious files and run untrusted code in a contained environment; **air-gapped** systems have no network connection at all (classified networks, some OT/ICS); virtual machines and containers isolate workloads from the host and each other.
- **Quarantine:** NAC solutions place non-compliant or suspicious endpoints into an isolated remediation network until they pass health checks.

> ⚠️ **Common Pitfall:** **Segmentation ≠ isolation.** Segmentation is a *planned architecture* that divides the network into zones that still communicate through controlled points. Isolation *removes connectivity entirely* for a specific system — most often as the **containment step of incident response**. If the question says "a server is actively compromised — what should you do FIRST?", the answer is isolate/disconnect it, not re-architect the network (and usually not power it off, which destroys volatile evidence).

## Patching

**Patching** applies vendor-released software updates that fix security vulnerabilities (and bugs) in operating systems, applications, firmware, and drivers. It is the **single most effective mitigation for known vulnerabilities** — an unexploitable flaw is one that no longer exists.

Enterprise patch management lifecycle:

1. **Identify/monitor** — track vendor advisories, CVEs, and vulnerability scan results.
2. **Prioritize** — triage by severity (CVSS), exploitability (is it in CISA's KEV list? actively exploited?), and asset exposure/criticality.
3. **Test** — deploy to a test group or staging environment first; patches can break applications.
4. **Deploy** — roll out through a central tool (WSUS, Intune, SCCM, RMM) during maintenance windows, often in rings (pilot → broad).
5. **Verify** — rescan to confirm the vulnerability is remediated.

Where patching isn't possible (legacy/EOL systems, vendor-locked OT), apply **compensating controls**: segmentation, isolation, virtual patching via an IPS, and stricter monitoring.

> 💡 **Exam Tip:** If the scenario says a vulnerability scan found systems **missing updates**, or an attack **exploited a known CVE with a fix available**, the answer is **patching** (or "implement a patch management program"). If the scenario says the system **cannot be patched** (legacy, EOL, OT), the answer shifts to **segmentation/isolation + compensating controls**.

## Encryption

**Encryption** converts plaintext into ciphertext so that only holders of the correct key can read it — protecting **confidentiality** even when other controls fail: a stolen laptop, an intercepted packet, an exfiltrated database. Match the encryption type to the **state of the data**:

| Data state | Meaning | Encryption controls |
|---|---|---|
| **At rest** | Stored on media | Full-disk encryption (BitLocker, FileVault, self-encrypting drives), file/volume encryption, database/column-level encryption — AES is the standard symmetric algorithm |
| **In transit** | Moving across a network | TLS/HTTPS, VPN (IPSec), SSH; replace cleartext protocols (HTTP, FTP, Telnet) with encrypted equivalents |
| **In use** | Being processed in memory | Secure enclaves/trusted execution environments; hardest state to protect |

Encryption as a *mitigation* means: even if attackers steal the data or the device, they get unreadable ciphertext. It mitigates eavesdropping/on-path attacks (in transit), physical theft and improper disposal (at rest), and reduces breach impact and disclosure obligations. Keys must be protected and managed (TPM, HSM, key escrow) — encryption is only as strong as its key management. Note that encryption **does not stop ransomware or deletion** — it protects confidentiality, not availability; backups do that.

## Monitoring

**Monitoring** is the continuous collection, correlation, and review of logs, events, and metrics to **detect** malicious activity, policy violations, and anomalies — and to provide the evidence trail for investigation and compliance. Monitoring is a **detective** control: it doesn't stop the initial attack, but it determines whether you find out in minutes or in months.

- **Sources:** OS and application logs, authentication logs, firewall/IDS/IPS alerts, NetFlow, DNS queries, endpoint telemetry (EDR), cloud audit logs, vulnerability scans.
- **SIEM** (Security Information and Event Management) centralizes and correlates logs from across the enterprise, applies detection rules, and alerts analysts — the core monitoring platform in a SOC.
- **Behavioral/anomaly detection** and **UBA/UEBA** baseline normal activity and flag deviations: impossible-travel logins, a user suddenly copying gigabytes at 3 a.m., a server beaconing to an unknown host.
- Monitoring also **verifies other mitigations are working** (are patches deployed? did the ACL block the traffic?) and supports incident response with forensically useful, time-synchronized (NTP) logs.

Scenario keywords **"detect," "identify unusual activity," "correlate logs from multiple systems,"** and **"how long did the attacker go unnoticed"** all point to monitoring/SIEM. When a question asks how to *detect* insider threats or credential misuse — activity by *authorized* accounts that preventive controls can't block — monitoring is the answer.

## Least Privilege

**Least privilege** grants every user, service account, and process the **minimum access required to perform its function — and nothing more**. It is the guiding principle behind permissions, RBAC, and privileged access management.

- Users get standard accounts for daily work; administrators use separate admin accounts (or just-in-time elevation) only when performing admin tasks.
- Service accounts get only the rights the service needs — never domain admin.
- Access is reviewed periodically and removed when roles change, preventing **privilege creep**.
- **Why it mitigates:** a phished user or hijacked service account can only do what its privileges allow. Least privilege shrinks the blast radius of *any* account compromise, limits what malware inherits when it runs as the user, and blunts insider threats.

Note that least privilege is a **principle**, implemented *through* mechanisms like permissions, ACLs, and RBAC. If a scenario says "users have more access than their jobs require," "everyone was made a local administrator," or "malware encrypted every share the user could reach," the tested concept is a **least privilege violation** — the fix is to reduce access to the minimum needed, not to add authentication.

## Configuration Enforcement

**Configuration enforcement** ensures systems are deployed with — and **continuously kept in** — a secure, approved configuration (a **secure baseline**). Hardening a system once isn't enough; settings drift as users and admins make changes, so enforcement makes the baseline stick.

- **Secure baselines** define the approved configuration (derived from CIS Benchmarks, DISA STIGs, vendor guides): services disabled, password policy, logging enabled, firewall on, and so on. Baselines are **established, deployed, and maintained** (the Domain 4 verb set).
- **Enforcement tools:** Group Policy (GPO), Intune/MDM configuration profiles, SCCM, and configuration-management/IaC tools (Ansible, Puppet) automatically apply settings and **revert unauthorized changes**.
- **Compliance/posture checking:** scans compare systems against the baseline and flag **configuration drift**; **NAC** can quarantine endpoints that fail posture checks (missing patches, disabled antivirus) until remediated.
- Related discipline: **change management** — approved changes update the baseline; everything else is drift to be corrected.

Keywords **"systems drift from the secure baseline," "users disable security settings,"** and **"ensure all machines have identical approved configurations"** map to configuration enforcement. Keep the boundary with patching straight: patching fixes *software flaws* (missing updates); configuration enforcement fixes *setting flaws* (misconfigurations). A vulnerability scan finding of "SMBv1 enabled" or "default community strings" is a configuration problem, not a patch problem.

## Decommissioning

**Decommissioning** is the formal process of retiring a system, device, or application at end of life — removing it from service **without leaving data or access behind**. Skipping proper decommissioning creates two classic vulnerabilities: sensitive **data remnants** on disposed hardware, and forgotten "zombie" systems that stay on the network unpatched.

Proper decommissioning includes:

1. **Inventory update** — remove the asset from tracking, monitoring, and licensing; document the disposition.
2. **Data sanitization** — securely remove data per policy: **overwriting/wiping**, **cryptographic erasure** (destroy the encryption key), **degaussing** (magnetic media), or **physical destruction** (shredding/pulverizing) for the highest sensitivity. Simple deletion or formatting is **not** sanitization — data is recoverable.
3. **Certificate/credential cleanup** — revoke certificates, disable service accounts, remove the host from directories, DNS, ACLs, and firewall rules.
4. **Certificate of destruction/sanitization** — retain proof for audits when using third-party disposal.

Decommissioning also applies to **applications and cloud resources**: unused VMs, storage buckets, and SaaS tenants must be deprovisioned, or they linger as unmonitored attack surface.

## Hardening Techniques

**Hardening** reduces a system's **attack surface** by removing or locking down everything an attacker could use — unnecessary software, open ports, default credentials, weak settings — and adding protective agents. Every host starts in a vendor-default (convenient, insecure) state; hardening moves it to the secure baseline. SY0-701 names seven techniques — know each one and what specific weakness it addresses:

| Hardening technique | Weakness it mitigates |
|---|---|
| Encryption | Data readable if device is lost/stolen or media improperly disposed |
| Installation of endpoint protection | Malware executing undetected on the host |
| Host-based firewall | Unauthorized network connections to/from the individual host |
| Host-based intrusion prevention system (HIPS) | Attacks/exploits inside traffic the firewall allows |
| Disabling ports/protocols | Attack surface from unneeded services and cleartext protocols |
| Default password changes | Publicly known factory credentials |
| Removal of unnecessary software | Vulnerabilities in software nobody uses or patches |

### Encryption (as hardening)

Applied per host: enable **full-disk encryption** (BitLocker/FileVault, keys sealed by the **TPM**) on laptops and desktops so lost or stolen devices yield no data, encrypt sensitive volumes/databases on servers, and require encrypted protocols for any service the host offers. This is the same control covered above, applied as a baseline requirement on every endpoint.

### Installation of endpoint protection

Deploy protective software on each host: **antivirus/anti-malware** (signature and heuristic detection), or the modern superset **EDR** (Endpoint Detection and Response), which continuously records endpoint telemetry, detects behavioral indicators of attack, and enables response actions such as remote isolation. **XDR** extends the same detection/correlation across endpoints, network, cloud, and email. Endpoint protection must be centrally managed and kept updated — and configuration enforcement should prevent users from disabling it.

### Host-based firewall

A **host-based firewall** is software on the individual endpoint (Windows Defender Firewall, iptables/nftables) that filters that host's inbound and outbound traffic by port, protocol, and application. Purpose: protection **travels with the device** off-network (the laptop in a coffee shop has no corporate perimeter), blocks host-to-host worm propagation *inside* a subnet where the network firewall never sees the traffic, and can stop malware from making outbound C2 connections. Defense in depth: the network firewall protects the perimeter/segments; the host-based firewall protects each machine.

### Host-based intrusion prevention system (HIPS)

A **HIPS** runs on the endpoint, inspects activity and traffic reaching that host, and **actively blocks** detected attacks — dropping malicious packets, blocking exploit behavior, stopping unauthorized system changes. Contrast the family:

| | HIDS | HIPS | NIDS/NIPS |
|---|---|---|---|
| Location | On the host | On the host | On the network |
| Action | **Detects and alerts only** | **Detects and prevents/blocks** | Network-wide detect (NIDS) or block (NIPS) |
| Visibility | That host's traffic, logs, files, processes — including **encrypted traffic after decryption** | Same as HIDS | All traffic crossing its sensor, but not host internals or (usually) inside encrypted sessions |

> ⚠️ **Common Pitfall:** Detection vs. prevention is the tested distinction: **HIDS/NIDS alert but do not stop** the attack; **HIPS/NIPS block it in-line**. If the scenario requires the endpoint to *stop* an attack automatically, the answer is **HIPS**, not HIDS. And a host-based system is the right answer when the attack arrives inside **encrypted** traffic that a network sensor can't read.

### Disabling ports/protocols

Every listening service/open port is attack surface; every enabled protocol is a potential vector. Hardening closes what isn't needed:

- **Disable unnecessary services** so their ports stop listening (print spooler on servers, IIS on a database box).
- **Replace insecure protocols with secure equivalents:** Telnet (23) → SSH (22); FTP (21) → SFTP/FTPS; HTTP (80) → HTTPS (443); SNMPv1/v2c → SNMPv3; disable SMBv1 entirely.
- **Verify with a port/vulnerability scan** — the scanner shows what's actually listening; anything unexpected gets investigated and disabled.
- Also applies to **physical ports**: disable unused switch ports and restrict USB via policy.

### Default password changes

Devices and applications ship with factory credentials (admin/admin, admin/password) that are **published in manuals and freely searchable online** — attackers and botnets (e.g., Mirai, which conscripted IoT devices using default credentials) try them first. Hardening requires changing every default password **before deployment** on every device — routers, switches, printers, IP cameras, IoT sensors, BMC/iLO interfaces, database and application admin accounts. Also rename or disable default accounts where possible. A device with a default password is effectively unauthenticated.

### Removal of unnecessary software

Uninstall everything the system doesn't need: preinstalled vendor **bloatware**, trial software, games, unused browsers and runtimes, sample applications, and old tools nobody maintains. Every installed package is code that can harbor vulnerabilities and **must be patched forever** — software that serves no business purpose delivers zero benefit at nonzero risk, and unused software is exactly what nobody remembers to update. Fewer packages = smaller attack surface, smaller patch workload, and less for an attacker to live off. Server best practice: minimal/core installs that include only required components.

Hardening questions often present a finding list — "open Telnet port, default admin credential, preinstalled trial software" — and ask for the mitigations. Map each finding to its technique: open/insecure port → **disable ports/protocols**; factory credential → **default password change**; bloatware → **remove unnecessary software**; no malware defense → **install endpoint protection**; stolen-laptop data risk → **(full-disk) encryption**. ## Key Takeaways

- [ ] **Segmentation** divides the network into zones to limit lateral movement and contain breaches; it isolates IoT/guest/BYOD/legacy and shrinks compliance scope.
- [ ] **Isolation** removes a system's connectivity entirely — the FIRST containment action for a compromised host (disconnect/quarantine, don't power off).
- [ ] **Network ACLs** filter traffic by IP/port/protocol, processed top-down with an **implicit deny**; **permissions** define what identities can do to files/resources.
- [ ] **Application allow list** = deny-by-default execution; blocks unknown/zero-day malware but has high admin overhead. Deny list = allow-by-default, weaker.
- [ ] **Patching** is the primary fix for known vulnerabilities: identify → prioritize → **test** → deploy → verify; unpatchable systems get segmentation + compensating controls.
- [ ] **Encryption** protects confidentiality by data state — at rest (FDE/AES), in transit (TLS/VPN/SSH), in use — and is only as strong as its key management.
- [ ] **Monitoring** (SIEM, EDR telemetry, UEBA) is the detective control: it finds anomalies, insider misuse, and verifies other mitigations are working.
- [ ] **Least privilege** = minimum access needed; it caps the blast radius of any compromised account and is enforced via permissions/RBAC with periodic reviews to stop privilege creep.
- [ ] **Configuration enforcement** deploys secure baselines (CIS/STIG) via GPO/MDM and corrects **configuration drift**; NAC quarantines non-compliant hosts.
- [ ] **Decommissioning** = inventory removal + **data sanitization** (wipe, crypto-erase, degauss, destroy — deletion/formatting is not sanitization) + credential/certificate cleanup.
- [ ] **Hardening** reduces the attack surface; the seven SY0-701 techniques are encryption, endpoint protection, host-based firewall, HIPS, disabling ports/protocols, default password changes, and removing unnecessary software.
- [ ] **Host-based firewall** filters one host's traffic and travels with the device; **HIPS blocks** attacks on the host, while HIDS only **alerts**.
- [ ] Replace insecure protocols during hardening: Telnet→SSH, FTP→SFTP, HTTP→HTTPS, SNMPv1/v2c→SNMPv3; disable SMBv1 and unused switch ports.
- [ ] **Default passwords** are public knowledge — change them before deployment on every device, including printers, cameras, and IoT.

## Self-Check Questions

1. An analyst discovers a workstation actively spreading a worm to other machines on its subnet. What should the analyst do FIRST, and why is that action preferred over powering the machine off?
2. A hospital runs an MRI controller on an end-of-life operating system that the vendor will never patch. Which two mitigation techniques best reduce the risk, and why is "apply patches" wrong here?
3. A security team wants to guarantee that only IT-approved applications can execute on point-of-sale terminals, including blocking brand-new malware no antivirus signature exists for. Which technique fits, and what is its main operational drawback?
4. After a phishing incident, investigators find the compromised user's account could read every department's file shares, and the ransomware encrypted all of them. Which principle was violated, and what mechanisms implement the fix?
5. A vulnerability scan of a new branch-office router reports: Telnet enabled, the admin account uses the factory credential, and an unused media-server package is installed. Name the hardening technique that addresses each finding.

1. **Isolate the workstation from the network** — disable its switch port, unplug the cable, or use EDR network isolation. Powering it off also stops the spread but destroys volatile evidence (RAM contents, running processes, network connections) that investigators need — so isolation, not shutdown, is the FIRST containment action.
2. **Segmentation** (place the MRI controller on its own tightly firewalled segment so only required systems can reach it) and **isolation/compensating controls** (near-air-gap it, add IPS virtual patching and extra monitoring). 4. The **principle of least privilege** was violated — the account had far more access than the user's job required, so the compromise inherited that entire reach and the ransomware encrypted every share the account could touch. All three are hardening techniques that shrink the router's attack surface.
