# Objective 2.4 — Given a scenario, analyze indicators of malicious activity

Domain 2 is worth **22% of the SY0-701 exam**, and objective 2.4 is its analytical core — the largest single objective in the domain. Where 2.1–2.3 asked *who* attacks and *through what*, 2.4 asks you to look at symptoms — log entries, alerts, user complaints, packet captures — and name the attack in progress. The exam tests this material two ways: **definition matching** ("Which malware type activates only when a specific condition is met?") and, far more often, **scenario selection** ("Users report files renamed with a strange extension and a payment demand on screen — what happened?"). Nearly every question is a symptom-to-attack mapping exercise, so learn the *keyword fingerprint* of each attack. The highest-yield items are the **malware type distinctions** (worm vs. virus vs. Trojan, logic bomb, rootkit), **amplified vs. reflected DDoS**, **password spraying vs. brute force**, the **application attack lineup** (injection, buffer overflow, directory traversal, forgery), and the **account/log indicators** (impossible travel, concurrent sessions, out-of-cycle logging, missing logs).

## Malware Attacks

Malware ("malicious software") is any code designed to harm, exploit, or secretly control a system. The exam distinguishes malware types by **how they spread**, **what they do**, and **how they hide** — read the scenario for those three clues.

| Type | Spreads by | Signature behavior / indicator |
|---|---|---|
| **Virus** | Attaching to files/programs; **requires user action** to execute | Infected files, spreading after a file is opened/run |
| **Worm** | **Self-replicating over the network — no user action** | Rapid spread host-to-host, network congestion, bandwidth spikes |
| **Trojan** | Disguised as **legitimate, desirable software** the user installs | "Free" utility/game that opens backdoors or drops payloads |
| **Ransomware** | Any vector (phishing, RDP, worm behavior) | **Encrypted files, changed extensions, ransom note demanding payment** |
| **Spyware** | Bundled installs, Trojans, drive-by downloads | Covert monitoring: browsing habits, data harvesting, changed homepage |
| **Keylogger** | Software (malware) or hardware (inline USB device) | **Every keystroke captured** — credentials stolen despite no phishing |
| **Logic bomb** | Planted code (often by an **insider**) | Dormant until a **trigger**: date/time or event (e.g., account deleted) |
| **Rootkit** | Post-compromise installation | **Hides at OS/kernel level**; evades AV; system lies about its own state |
| **Bloatware** | **Pre-installed by the manufacturer** | Not malicious per se — wastes resources, enlarges attack surface |

### Ransomware

Ransomware encrypts a victim's files (or locks the entire system), then demands payment — usually cryptocurrency — for the decryption key. Modern campaigns add **double extortion**: exfiltrate data first, then threaten publication if the ransom isn't paid. Indicators: files with unfamiliar extensions, ransom notes (`README.txt` in every folder), mass file modifications in a short window, deleted volume shadow copies, and spiking disk I/O. Primary mitigation is **offline/tested backups** — which is why exfiltration was added, since backups defeat encryption-only extortion.

### Trojan

A Trojan (Trojan horse) is malware **disguised as legitimate software** — the user is tricked into installing it themselves. It does not self-replicate. A **Remote Access Trojan (RAT)** adds a backdoor giving the attacker ongoing remote control. Scenario keyword: "user downloaded a free tool/screensaver/crack, and afterward…"

### Worm

A worm **self-replicates across the network without any user interaction**, exploiting vulnerabilities in services to hop from host to host. Indicators: extremely rapid spread, sudden network bandwidth saturation, many hosts infected in minutes.

> 💡 **Exam Tip:** The virus/worm/Trojan triple is decided by one clue each. **Requires the user to open/run something → virus.** **Spreads by itself over the network → worm.** **User willingly installed what looked like legitimate software → Trojan.**

### Spyware and Keylogger

**Spyware** covertly gathers information about the user — browsing history, personal data, credentials — and reports it to a third party. A **keylogger** is a specialized form that records **every keystroke**; it can be software or a small **hardware device inserted between keyboard and computer** (a physical-access indicator: credentials keep leaking from one workstation despite a clean AV scan).

### Bloatware

Bloatware is **unwanted software pre-installed by manufacturers or bundled with installs**. It is not inherently malicious, but it consumes resources, may collect data, and — because it is often unpatched and forgotten — **expands the attack surface**. Mitigation: remove it during hardening / use clean OS images.

### Logic Bomb

A logic bomb is malicious code **planted inside a system that stays dormant until a trigger condition** — a specific date/time (time bomb) or an event, such as an employee's account being removed from payroll. Classic scenario: a **disgruntled admin plants a script that deletes data 30 days after their account is disabled**. Logic bombs pair with the **insider threat** actor from 2.1.

### Rootkit

A rootkit embeds itself at the **operating system kernel or firmware level** to hide its own presence and that of other malware — intercepting the very system calls that AV tools use to look for it. Indicators: security tools report clean while symptoms persist; discrepancies between what the OS reports and what an **offline/external scan** shows. Detection often requires booting from trusted media; remediation frequently means **reimaging the system**.

> ⚠️ **Common Pitfall:** Rootkit vs. Trojan vs. logic bomb confusion. **Rootkit = hides (kernel-level concealment).** **Trojan = disguises (pretends to be legitimate software at install time).** **Logic bomb = waits (dormant until a trigger).** The verb in the scenario tells you which one.

## Physical Attacks

Physical attacks require the attacker (or their tool) to be physically present — no network needed.

### Brute Force (Physical)

In this context, brute force means literal **physical force**: breaking doors or windows, cutting locks and cables, crowbarring server-room doors, smashing enclosures to steal equipment. Indicators: damaged locks/doors, forced entry marks, missing hardware. Mitigations are physical controls: reinforced doors, bollards, guards, cameras, access control vestibules.

### Radio Frequency Identification (RFID) Cloning

RFID cloning copies the data from a proximity badge or key fob onto a duplicate card. An attacker with a concealed reader can **skim a badge from inches away** — in an elevator or hallway — then replay it at the door. Indicators: badge access logs showing **entries when the legitimate holder was elsewhere**, or the **same badge used at two distant readers in an impossibly short time**. Mitigations: shielded badge holders, challenge-response smart cards instead of simple RFID, plus a second factor (PIN, guard, camera) at sensitive doors.

### Environmental

Environmental attacks target the **facility's supporting infrastructure** rather than IT directly: cutting power or backup generators, disabling HVAC so equipment overheats, triggering fire suppression, cutting network/fiber lines, water/flooding. The goal is usually **availability** disruption. Indicators: temperature alarms, power anomalies, simultaneous "unrelated" facility failures during an intrusion.

## Network Attacks

### Distributed Denial-of-Service (DDoS)

A DoS attack overwhelms a target's resources so legitimate users can't reach it; a **DDoS** does it from **many distributed sources simultaneously** — typically a **botnet** of compromised machines and IoT devices. Indicators: massive traffic spikes from many source IPs, service unresponsiveness, upstream bandwidth saturation. SY0-701 names two technique sub-types:

| Technique | How it works | Key clue |
|---|---|---|
| **Reflected** | Attacker sends requests to legitimate third-party servers with a **spoofed source IP = the victim**; the servers' replies flood the victim | Victim receives **responses to requests it never sent**; attacker's identity hidden |
| **Amplified** | A reflected attack using protocols where a **tiny request yields a huge response** (DNS, NTP, memcached) | **Small query → large reply**; response traffic many times the attacker's bandwidth |

> 💡 **Exam Tip:** Amplified attacks are (almost always) also reflected — the distinguishing feature of **amplification** is the **size multiplier** ("a 60-byte query produced a 4,000-byte response"). If the scenario emphasizes spoofed source addresses and third-party servers answering the victim, "reflected" is the answer; if it emphasizes response size vs. request size, "amplified."

### Domain Name System (DNS) Attacks

DNS attacks corrupt or abuse name resolution so victims are silently sent to attacker-controlled destinations:

- **DNS poisoning (cache poisoning/spoofing):** inserting forged records into a resolver's cache so an entire user population resolves a legitimate name to a malicious IP. Indicator: correct URL typed, wrong site reached; certificate warnings on a well-known site.
- **DNS hijacking:** altering DNS settings themselves — compromising the registrar account, changing a domain's authoritative records, or modifying a host's configured DNS server.
- **Domain hijacking:** stealing control of the domain registration itself.
- **DNS tunneling / exfiltration:** encoding stolen data or C2 traffic inside DNS queries. Indicator: **abnormally high volume of DNS queries with long, random-looking subdomains** leaving the network.

Mitigations: **DNSSEC** (signed DNS responses proving integrity/origin), registrar MFA and locks, monitoring DNS query volume and entropy.

### Wireless Attacks

| Attack | Description | Indicator / keyword |
|---|---|---|
| **Rogue access point** | Unauthorized AP attached to the network (often by a well-meaning employee) | Unknown SSID/BSSID on the corporate LAN; found via wireless surveys |
| **Evil twin** | Attacker's AP **impersonating a legitimate SSID** to lure clients and harvest traffic/credentials | Duplicate SSID with stronger signal; users prompted to "re-enter" credentials |
| **Deauthentication** | Spoofed 802.11 management frames force clients off the AP | Repeated sudden disconnects; often forces reconnects toward an evil twin or captures WPA handshakes |
| **Jamming** | RF interference floods the frequency, denying wireless service | Total Wi-Fi outage in an area; a wireless-layer DoS |

### On-Path Attack

An on-path attack (formerly man-in-the-middle) places the attacker **between two communicating parties**, secretly relaying — and possibly altering — traffic while both sides believe they're talking directly. Common techniques: **ARP poisoning** (attacker answers ARP with their own MAC for the gateway's IP, becoming the LAN's invisible relay), DNS spoofing, evil twin APs. A **browser-based variant (on-path browser attack / man-in-the-browser)** uses malware inside the browser to alter transactions after TLS decryption. Indicators: unexpected certificate warnings, duplicate IP-to-MAC mappings in ARP tables, TLS downgrade attempts. Mitigations: end-to-end encryption (TLS/HSTS), dynamic ARP inspection, certificate pinning.

### Credential Replay

In credential replay, the attacker **captures valid authentication material** — a password hash, session token, or cookie — **and re-submits it** to authenticate as the victim, without ever cracking the password. **Pass-the-hash** (replaying a captured NTLM hash) is the classic example. Indicators: logons from unusual hosts using valid credentials, authentication events with no preceding interactive logon. Mitigations: session tokens with expiration/nonces, mutual authentication, MFA, Kerberos over NTLM.

### Malicious Code (Network Context)

Malicious code delivered or observed **over the network**: exploit payloads in traffic, drive-by download scripts, worms propagating, C2 (command-and-control) beaconing. Indicators an analyst should recognize: IDS/IPS signature alerts, **outbound connections to known-bad IPs at regular intervals (beaconing)**, scripts or executables in unexpected protocol streams, traffic on nonstandard ports.

## Application Attacks

Application attacks target flaws in software — especially web applications — rather than the network path.

| Attack | Mechanism | Scenario keyword |
|---|---|---|
| **Injection** | Untrusted input executed as code/commands | `' OR 1=1--` in a login field; SQL/command/LDAP/XML in input |
| **Buffer overflow** | Input exceeds a memory buffer, overwriting adjacent memory | Crash + attacker code execution; "long string of characters" |
| **Replay** | Captured valid traffic/session data retransmitted | Reused session cookie/token; "captured and resent" |
| **Privilege escalation** | Gaining rights beyond those granted | Standard user obtains admin/SYSTEM; exploit after initial foothold |
| **Forgery** | Tricking a browser or server into making requests on the attacker's behalf | CSRF (user's browser abused) / SSRF (server abused) |
| **Directory traversal** | Escaping the web root with path sequences | `../../` or `..%2F` in URLs; reading `/etc/passwd` |

### Injection

Injection attacks feed **untrusted input that gets executed as code**. **SQL injection (SQLi)** manipulates database queries — the canonical `' OR 1=1--` payload turns a login check always-true, enabling authentication bypass or full data dumps. Other variants: command injection (OS commands via input fields), LDAP and XML injection. Indicators: quotes/SQL keywords in web logs, database errors returned to users. Mitigation: **input validation and parameterized queries (prepared statements)**.

### Buffer Overflow

A buffer overflow sends **more data than an allocated memory buffer can hold**, overwriting adjacent memory — potentially redirecting execution to attacker-supplied code. Indicators: application crashes on oversized input, logs showing abnormally long request strings. Mitigations: input validation/bounds checking in code, plus OS defenses **ASLR** (address space layout randomization) and **DEP** (data execution prevention).

### Replay

An application-layer replay attack **captures legitimate authentication traffic or a session token and retransmits it** later to impersonate the user — no decryption required. This is the application-level twin of network credential replay. Mitigations: **timestamps, nonces/one-time session tokens, short session expirations**, and TLS to prevent the capture in the first place.

### Privilege Escalation

Privilege escalation is gaining **higher access rights than granted** — the near-universal *second step* after initial compromise. **Vertical** escalation moves up (user → administrator/root, e.g., via an unpatched kernel flaw); **horizontal** escalation moves sideways to another user's access at the same level. Indicators: standard accounts performing admin actions, unexpected group-membership changes, processes running as SYSTEM spawned by user applications.

### Forgery

Forgery attacks make a trusted party issue requests the attacker chose:

- **Cross-site request forgery (CSRF/XSRF):** the victim's **browser**, already authenticated to a site, is tricked (via a malicious link/page) into sending a state-changing request — transfer funds, change email — that the site accepts because the session cookie rides along automatically. Mitigations: anti-CSRF tokens, SameSite cookies, re-authentication for sensitive actions.
- **Server-side request forgery (SSRF):** the attacker abuses a **server** feature that fetches URLs, making the server issue requests to internal systems (cloud metadata endpoints, internal APIs) the attacker couldn't reach directly.

> ⚠️ **Common Pitfall:** CSRF exploits the **user's browser** and its existing authenticated session; SSRF exploits the **server** and its internal network position. Also keep CSRF distinct from **XSS**: XSS injects and runs *script in the victim's browser*; CSRF sends a *forged request* using the victim's existing trust — no script execution on the target site required.

### Directory Traversal

Directory traversal (path traversal) uses **`../` sequences (or encodings like `..%2F`)** in a URL or parameter to escape the web root and read arbitrary server files — `https://site.com/view?file=../../../etc/passwd`. Indicators: dot-dot-slash patterns in web server logs. Mitigations: input validation/canonicalization, least-privilege file permissions for the web service account.

## Cryptographic Attacks

Cryptographic attacks target the algorithms and protocols themselves rather than stolen passwords or software bugs.

- **Downgrade:** the attacker (typically on-path) **forces a negotiation down to a weaker protocol or cipher** — e.g., from TLS 1.3 to SSL 3.0 or export-grade ciphers (POODLE is the classic) — then breaks the weak crypto. Indicator: connections completing at obsolete protocol versions the server "shouldn't" use. Mitigation: **disable legacy protocols/ciphers entirely** and use HSTS so HTTPS can't be stripped to HTTP.
- **Collision:** finding **two different inputs that produce the same hash value**. Since hashes verify integrity and sign certificates, a collision lets an attacker substitute a malicious file or forge a certificate that validates against a legitimate hash. Weak algorithms **MD5 and SHA-1 have demonstrated collisions** — use SHA-2/SHA-3.
- **Birthday:** the statistical attack that makes collisions practical. Per the **birthday paradox** (23 people give a >50% chance of a shared birthday), finding *any* two matching hashes among many candidates takes far fewer attempts (~2^(n/2)) than finding a match to one specific hash. The birthday attack is the **method**; a collision is the **result**.

> 💡 **Exam Tip:** Keyword map — "forced the connection to use SSL 3.0/older cipher" → **downgrade**; "two different files, same hash" → **collision**; "probability shortcut for finding matching hashes" → **birthday**. And MD5/SHA-1 in any answer choice about integrity = wrong/weak.

## Password Attacks

| Attack | Method | Fingerprint in logs |
|---|---|---|
| **Brute force** | Try **every possible combination** against one account (or a hash, offline) | **Many rapid failed logins on a single account** → account lockout |
| **Spraying** | Try **one or two common passwords** (e.g., `Winter2026!`) across **many accounts** | **A few failed attempts per account, across hundreds of accounts** — no lockouts |

**Brute force** attacks can be *online* (against the live login — slow, noisy, defeated by lockout policies) or *offline* (against stolen hashes — fast, silent, defeated by strong hashing/salting and long passwords). A *dictionary attack* is a smarter brute force using likely-password wordlists.

**Password spraying** deliberately inverts the pattern to **evade account-lockout policies**: because each account sees only one or two attempts, no lockout threshold trips. Detection requires correlating failures *across* accounts, not per account. Mitigations for both: MFA, lockout policies (brute force), banning common passwords, and monitoring aggregate failed-authentication patterns (spraying).

Keep the axis straight: "many failures, **one account**" = brute force; "one password, **many accounts**" = spraying. If the scenario says *accounts are locking out*, that's brute force in progress (or its side effect); if it says *failed logins spread thinly across the whole user base with no lockouts*, that's spraying. Don't let the phrase "common password" alone trick you — check the one-vs-many-accounts axis.

## Indicators

The last bullet group is a vocabulary of **observable symptoms** — SIEM alerts and log patterns you must map to what they imply. These appear constantly as answer-choice distractors, so know each one precisely.

| Indicator | What you observe | What it suggests |
|---|---|---|
| **Account lockout** | Account(s) repeatedly locked by failed attempts | Online brute-force attack (or an attacker who already changed the password, locking out the real user) |
| **Concurrent session usage** | Same account logged in from **two places at once** | Stolen/shared credentials; session hijacking |
| **Blocked content** | Security tools logging denied downloads/URLs/executables | Attack **attempts** underway — someone or something is trying to pull in malicious content |
| **Impossible travel** | Logins from **geographically distant locations in a timeframe no human could travel** (New York 09:00, Moscow 09:30) | Compromised credentials in use from a second location |
| **Resource consumption** | Unexplained CPU/memory/disk/bandwidth spikes | Cryptomining malware, exfiltration in progress, DDoS participation, ransomware encrypting |
| **Resource inaccessibility** | Files/services suddenly unavailable | Ransomware (files encrypted), DoS/DDoS, sabotage |
| **Out-of-cycle logging** | Log events at **abnormal times** — 3 a.m. logins, unscheduled patch/backup events, activity outside change windows | Attacker operating off-hours to avoid notice |
| **Published/documented** | Organization's **data appears publicly** — credentials on paste sites, data on leak sites, dark-web listings | A breach has already occurred and exfiltrated data is being released/sold |
| **Missing logs** | Gaps in logs, cleared event logs, disabled audit services | Attacker **covering their tracks** — deletion of evidence post-compromise |

A few of these deserve extra nuance:

- **Account lockout** cuts two ways. Lockouts *caused by failed attempts* point to an active online brute force; a user reporting "my password suddenly doesn't work" may mean the attacker already got in and **changed the password**, locking out the legitimate owner.
- **Concurrent session usage** is only an indicator when the account *shouldn't* have parallel sessions — a service account on two app servers is normal; a human user logged in interactively from two cities is not. Response: terminate all sessions and revoke tokens, not just reset the password — a live stolen session survives a password change.
- **Resource consumption vs. resource inaccessibility:** consumption is the machine working hard for someone else (cryptominer pinning the CPU, exfiltration saturating upstream bandwidth); inaccessibility is legitimate users being denied (encrypted files, downed service). Ransomware can present as both in sequence — heavy disk I/O during encryption, then inaccessible files.
- **Out-of-cycle logging** requires knowing the normal cycle: backups at 02:00 are fine *if that's the schedule*. The indicator is activity **outside established baselines and change windows** — which is why baselining normal behavior is a prerequisite for detection.

> 💡 **Exam Tip:** Two of these are heavily favored in questions: **impossible travel** (the answer whenever a scenario gives two login locations with timestamps that defy geography) and **missing logs / gaps in logs** (the answer for "how do we know the attacker tried to hide their activity?"). Also note the tense each indicator implies: *blocked content* = attack being **attempted**, *published data* = breach **already happened**, *missing logs* = compromise happened **and was concealed**. Centralizing logs to a SIEM defeats local log wiping — the attacker can clear the host's logs, but the copies already shipped.

## Key Takeaways

- [ ] Virus needs **user action** to spread; worm **self-replicates over the network**; Trojan is malware **disguised as legitimate software**.
- [ ] Ransomware = encrypted files + ransom note = **availability** attack; offline backups are the primary defense; double extortion adds data theft.
- [ ] **Logic bomb** lies dormant until a **trigger** (date or event) — classic disgruntled-insider move; **rootkit** hides at kernel level and usually requires offline detection and reimaging.
- [ ] **Bloatware** = pre-installed unwanted software: not malware, but resource waste and added attack surface.
- [ ] Physical attacks: **brute force** = literal forced entry; **RFID cloning** = duplicated badge (watch for impossible badge-log entries); **environmental** = attacking power/HVAC/facilities.
- [ ] **Reflected DDoS** = spoofed victim address bounces third-party replies onto the target; **amplified** = small request generates a massively larger response (DNS/NTP).
- [ ] DNS attacks: **poisoning** corrupts resolver caches; DNSSEC validates responses; long random subdomains in high query volume = DNS tunneling/exfiltration.
- [ ] Wireless: **evil twin** impersonates a legitimate SSID; **rogue AP** is any unauthorized AP; **deauth** frames force disconnects; **jamming** is RF denial of service.
- [ ] **On-path** = attacker secretly relays between two parties (ARP poisoning, evil twin); **credential replay** = reusing captured hashes/tokens (pass-the-hash) without cracking anything.
- [ ] Application attacks: `' OR 1=1--` = **SQL injection**; oversized input crash = **buffer overflow**; `../../` = **directory traversal**; user→admin = **privilege escalation**; CSRF abuses the **browser**, SSRF abuses the **server**.
- [ ] Cryptographic: **downgrade** forces weak protocols (disable SSL/old TLS); **collision** = two inputs, one hash (MD5/SHA-1 broken); **birthday** = the probability math that finds collisions fast.
- [ ] **Brute force** = many attempts, one account (causes lockouts); **spraying** = one common password, many accounts (evades lockouts — detect by correlating across accounts).
- [ ] **Impossible travel** and **concurrent sessions** = stolen credentials in use; **out-of-cycle logging** = off-hours attacker activity.
- [ ] **Blocked content** = attempted attack; **published/documented data** = breach already occurred; **missing logs** = attacker covering tracks — ship logs to a SIEM so they can't be silently erased.

## Self-Check Questions

1. A security analyst notices thousands of failed login events overnight: each of 800 user accounts shows exactly two failed attempts with the passwords `Spring2026!` and `Company123`, and no accounts are locked out. What attack is this, and why did the lockout policy not trigger?
2. Users across the company report that typing the correct URL for their bank takes them to a site that looks right but throws a certificate warning. The local hosts files are clean. What attack is most likely, and what control validates DNS responses to prevent it?
3. A web server's access logs show repeated requests containing `..%2F..%2F..%2Fetc%2Fpasswd`. Separately, the login page logs show inputs containing `' OR 1=1--`. Name both attacks and one mitigation for each.
4. The SOC sees a user authenticate from Chicago at 08:45 and from Singapore at 09:10 the same morning, with both sessions still active. Which two named indicators apply, and what do they suggest?
5. A victim's web server is knocked offline by a flood of large DNS responses arriving from hundreds of legitimate public DNS resolvers — servers the victim never queried. Classify this attack as precisely as possible and explain the roles of spoofing and the protocol choice.

<summary>Answers</summary>

1. **Password spraying.** The attacker tried one or two common passwords against many accounts instead of many passwords against one account. Lockout policies count failures **per account**, and two failures per account stays under any reasonable threshold — which is exactly the point of spraying. Detection requires correlating failed logins **across** accounts (a SIEM rule on aggregate failures); mitigations include MFA and banning common passwords.
2. **DNS poisoning (cache poisoning/spoofing).** Forged records in the resolver's cache send everyone who resolves the name to an attacker-controlled IP — the certificate warning appears because the fake site can't present a valid certificate for the real domain. **DNSSEC** prevents it by digitally signing DNS responses so resolvers can verify their origin and integrity and reject forged records.
3. The first is **directory traversal** — URL-encoded `../` sequences escaping the web root to read `/etc/passwd`; mitigate with input validation/canonicalization and least-privilege permissions for the web service account. The second is **SQL injection** — input breaking out of the query to force a true condition; mitigate with parameterized queries (prepared statements) and input validation.
4. **Impossible travel** (no one can get from Chicago to Singapore in 25 minutes) and **concurrent session usage** (both sessions active simultaneously). Together they indicate the account's **credentials are compromised** and being used by an attacker from a second location. Response: disable/lock the account, revoke all active sessions and tokens, reset credentials, require MFA, and investigate scope.
5. This is a **DDoS — specifically an amplified, reflected DNS attack**. **Reflection:** the attacker sent queries to legitimate open DNS resolvers with the **source IP spoofed to the victim's address**, so all responses "bounce" onto the victim, which receives answers to questions it never asked (and the attacker stays hidden). **Amplification:** DNS was chosen because a small query elicits a much larger response, multiplying the attacker's bandwidth many times over. Mitigations include upstream filtering/scrubbing, rate limiting, and providers blocking spoofed-source traffic.
