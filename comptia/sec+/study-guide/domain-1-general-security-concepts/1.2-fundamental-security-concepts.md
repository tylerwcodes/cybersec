# Objective 1.2 — Summarize fundamental security concepts

Domain 1 ("General Security Concepts") is worth **12% of the SY0-701 exam**, and objective 1.2 is its conceptual core — the vocabulary that every scenario question in Domains 2 through 5 silently assumes. The exam tests this objective two ways: **definition matching** ("Which principle ensures a sender cannot deny sending a message?") and **scenario selection** ("A company wants to detect an insider copying files without exposing real data — which technology?"). The highest-yield items are the **CIA triad mapped to attack scenarios**, **non-repudiation via digital signatures**, the **Zero Trust control plane vs. data plane components** (new and heavily emphasized in SY0-701), the **physical sensor types**, and the **honeypot/honeynet/honeyfile/honeytoken distinctions**. Expect direct questions on all five.

## Confidentiality, Integrity, and Availability (CIA)

The CIA triad defines the three goals every security control ultimately serves. Almost any exam question that asks "what is this control protecting?" or "what did this attack violate?" resolves to one of these three.

| Principle | Goal | Supporting controls | Example violation |
|---|---|---|---|
| **Confidentiality** | Only authorized parties can **read** data | Encryption, access controls, MFA, data masking | Packet sniffing, stolen unencrypted laptop, shoulder surfing |
| **Integrity** | Data is not **altered** improperly; changes are detectable | Hashing, digital signatures, version control, file integrity monitoring | Attacker modifies a bank transfer amount or defaces a website |
| **Availability** | Systems and data are **accessible when needed** | Redundancy, backups, UPS/generators, DDoS mitigation, patching | DDoS takes a site offline; ransomware encrypts production files |

The exam pairs each principle with characteristic attacks and controls:

- **Confidentiality** keywords: *eavesdropping, interception, disclosure, breach, exfiltration* → answer with **encryption** (in transit and at rest) and **access control**.
- **Integrity** keywords: *tampering, modification, "verify the file wasn't changed"* → answer with **hashing** (SHA-256 checksums) and **digital signatures**.
- **Availability** keywords: *downtime, outage, "must remain accessible"* → answer with **redundancy, failover, backups**.

The three goals also **tension against each other**: heavier encryption and stricter access checks (confidentiality) can slow systems and lock out legitimate users (availability). Real designs balance the triad against business needs — a point scenario questions raise when they ask which control "best balances security and usability."

> ⚠️ **Common Pitfall:** Ransomware is primarily an **availability** violation — you are locked out of your own data. If the scenario adds "attackers threatened to leak the stolen data" (double extortion), confidentiality is *also* violated, but the encryption of your files is an availability problem. DoS = availability; sniffing = confidentiality; unauthorized modification = integrity. Keep these mappings automatic.

## Non-repudiation

Non-repudiation guarantees that a party **cannot later deny** having performed an action — sent a message, signed a contract, approved a transaction. It is proof of *origin* and *action* that holds up to a third party.

The primary mechanism is the **digital signature**: the sender hashes the message and encrypts that hash with their **private key**. Anyone can verify with the sender's **public key** that (a) the message came from the holder of the private key — origin — and (b) the message was not altered — integrity. Because only the sender possesses the private key, they cannot plausibly deny creating the signature.

- Digital signatures provide **integrity + authentication + non-repudiation** in one mechanism.
- Supporting evidence sources: audit logs, video surveillance, and unique user credentials (shared accounts destroy non-repudiation because no one can prove *which* person acted).
- Non-repudiation is a distinct concept from the CIA triad — some models append it (and authentication) as extensions, but on the exam treat it as its own answer choice.

> 💡 **Exam Tip:** Keywords "**cannot deny sending**," "**proof of origin**," or "**legally prove who approved it**" → **non-repudiation**, implemented with **digital signatures** (asymmetric cryptography, signed with the sender's *private* key, verified with the *public* key). A plain hash alone gives integrity but **not** non-repudiation — anyone could have computed it.

## Authentication, Authorization, and Accounting (AAA)

The AAA framework answers three sequential questions about every access request:

| A | Question | Function | Example |
|---|---|---|---|
| **Authentication** | "Who are you? Prove it." | Verify a claimed identity | Password + TOTP code; certificate |
| **Authorization** | "What are you allowed to do?" | Grant or deny specific rights *after* authentication | User can read the share but not delete files |
| **Accounting** | "What did you do?" | Log and track actions and resource use | Audit logs of logins, commands, data access |

AAA is centralized with protocols such as **RADIUS** and **TACACS+** and directory services like Active Directory — the identity infrastructure that later objectives build on.

### Authenticating people

People prove identity with factors from distinct categories:

| Factor | Meaning | Examples |
|---|---|---|
| **Something you know** | Knowledge | Password, PIN |
| **Something you have** | Possession | Smart card, authenticator app/TOTP, hardware security key |
| **Something you are** | Inherence (biometrics) | Fingerprint, face, iris |
| **Somewhere you are** | Location attribute | GPS/geolocation, source network |

Combining two or more *different* categories is multifactor authentication (MFA, detailed in objective 4.6) — two proofs from the same category (password + PIN) is still single-factor. For 1.2, know that authenticating *people* means interactive credentials plus MFA, ideally through single sign-on with strong identity proofing at enrollment.

### Authenticating systems

Machines need to authenticate too — servers, workstations, services, IoT devices, and scripts all assert identity without a human typing a password:

- **Digital certificates (PKI):** a device presents a certificate signed by a trusted CA — the standard for servers (TLS), VPN endpoints, and 802.1X network access (a device must authenticate before its switch port or Wi-Fi association goes live).
- **Pre-shared keys and API keys/tokens:** service-to-service and application authentication.
- **Hardware roots of trust (e.g., TPM):** bind the identity to the physical device so credentials can't simply be copied off.

Scenario cue: if the question says "ensure only **corporate-owned devices** can join the network" or "the **service** must authenticate to the API," the answer is *system* authentication — usually **certificates/802.1X** for devices — not user MFA. Watch whether the subject of the sentence is a person or a machine.

### Authorization models

Once identity is proven, an authorization model decides what the identity may do. SY0-701 expects you to distinguish the major models by their decision criteria and keywords:

| Model | Access decided by | Who controls it | Keywords / typical use |
|---|---|---|---|
| **Role-based access control (RBAC)** | The user's **role/job function** | Administrators define roles | "Assigned to the Accounting role"; enterprise standard for least privilege at scale |
| **Rule-based access control** | System-wide **rules/conditions** applied to everyone | Administrators define rules | Firewall ACLs, "no logins after 6 p.m.", condition-triggered access |
| **Attribute-based access control (ABAC)** | **Attributes** of subject, object, action, and environment evaluated together | Policy engine | "Manager + on-site + business hours + confidential file" — fine-grained, contextual; underpins Zero Trust policy decisions |
| **Discretionary access control (DAC)** | The **owner** of each resource grants access at their discretion | Data owner | NTFS permissions a file owner sets; flexible but inconsistent |
| **Mandatory access control (MAC)** | **Security labels/classifications** compared to user clearances | The operating system/policy — users cannot override | Military/government: Top Secret, Secret; SELinux |
| **Least privilege** | Guiding principle across all models | — | Grant the **minimum** access needed to do the job |

> ⚠️ **Common Pitfall:** **Role-based** vs. **rule-based** — both abbreviate to "RBAC," and the exam exploits it. *Role*-based keys off **who you are organizationally** (job function); *rule*-based keys off **conditions that apply to everyone regardless of identity** (time of day, ACL entries). Also don't confuse **DAC** (owner decides, flexible) with **MAC** (system-enforced labels, most rigid — users cannot share data the policy forbids).

## Gap Analysis

A gap analysis compares an organization's **current security state** against a **desired state** — a framework (NIST CSF, ISO 27001), a regulation, or an internal baseline — and identifies the *gaps* between them. The output is a prioritized remediation roadmap.

The process: (1) select the target standard/baseline, (2) assess current controls, people, and processes (interviews, document review, technical testing), (3) document each shortfall, and (4) produce a **remediation plan** ranking gaps by risk so resources go to the worst deficiencies first.

Exam keywords: "**compare current state to a framework/desired state**," "**identify deficiencies before an audit**," "**where are we falling short of ISO 27001?**" → gap analysis. It is typically performed before certification audits, after mergers, or when adopting a new framework — including planning a **Zero Trust migration**, where the gap analysis maps how far current architecture is from the target model.

Don't confuse it with related assessments: a **vulnerability scan** finds technical flaws in systems; a **risk assessment** quantifies likelihood × impact; a **gap analysis** measures distance from a *chosen standard or desired state* across people, processes, and technology. "Compared against NIST CSF" → gap analysis, even if the deliverable happens to list technical weaknesses.

## Zero Trust

Zero Trust replaces the legacy perimeter model ("hard outside, trusted inside") with a simple rule: **never trust, always verify**. No user, device, or network location is trusted by default — every access request is authenticated, authorized, and continuously evaluated, regardless of where it originates. SY0-701 tests the Zero Trust architecture using NIST SP 800-207 terminology, split into two planes:

| Plane | Job | Components |
|---|---|---|
| **Control plane** | **Decides** — defines policy and adjudicates every access request | Adaptive identity, threat scope reduction, policy-driven access control, Policy Engine, Policy Administrator |
| **Data plane** | **Enforces** — where subjects, systems, and traffic actually live; carries out the decision | Implicit trust zones, subject/system, Policy Enforcement Point |

### Control Plane

The control plane is the "brain" — it never touches user traffic directly; it makes and communicates decisions.

#### Adaptive identity

Identity validation that **adjusts to context in real time**: the system considers where the user is logging in from, what device they're on, the resource's sensitivity, and behavioral history. A login from the corporate LAN on a managed laptop may need only a password; the same account from a new country at 3 a.m. triggers step-up MFA or a block. Keywords: *risk-based, context-aware, dynamic authentication requirements*.

#### Threat scope reduction

Deliberately **limiting the blast radius** of any compromise by minimizing what each identity can reach — least privilege, microsegmentation, and just-in-time access. If an account is compromised, the attacker gets access to almost nothing. Keywords: *limit lateral movement, reduce attack surface, minimize blast radius*.

#### Policy-driven access control

Access decisions come from **centrally defined, attribute-rich policies** evaluated per request — not from static network position ("it's on the internal VLAN, let it through"). Policies combine identity, device posture, location, time, and data sensitivity (ABAC in practice), and are re-evaluated continuously, not just at login.

#### Policy Engine

The **decision-maker**. The Policy Engine evaluates each access request against policy plus threat intelligence, device health, and identity signals, and renders the verdict: **grant, deny, or revoke**.

#### Policy Administrator

The **communicator/executor of the decision**. The Policy Administrator takes the Policy Engine's verdict and instructs the enforcement point — establishing or tearing down the session path and issuing the credentials/tokens that let the PEP open the connection. Together, the Policy Engine + Policy Administrator form the **Policy Decision Point (PDP)**.

### Data Plane

The data plane is where actual subjects, systems, and network traffic operate — and where decisions get enforced.

#### Implicit trust zones

An implicit trust zone is an area where, once inside, traffic flows **without further verification**. In NIST SP 800-207 terms, it is the portion of the data plane **past the Policy Enforcement Point** where an approved session's traffic is allowed to flow without being re-challenged (like the boarding area past an airport security checkpoint). The legacy model made the entire "internal network" one giant implicit trust zone; Zero Trust's goal is to **shrink implicit trust zones to the smallest possible size** (ideally a single resource) so that being "inside" grants nothing by itself.

#### Subject/System

The **subject** is the entity requesting access — a user, application, or process. The **system** is the device the subject uses to make the request. Zero Trust evaluates *both* on every request: the user's identity **and** the device's health/compliance (patched? managed? jailbroken?). A valid user on a non-compliant device is denied.

#### Policy Enforcement Point (PEP)

The **gatekeeper in the traffic path**. The PEP sits between the subject/system and the resource, forwards the access request to the control plane, and then **enforces** the PDP's decision — establishing, monitoring, and terminating the connection. It makes no decisions itself.

Request flow to memorize: **subject/system → PEP → Policy Engine (decides) → Policy Administrator (signals) → PEP opens or blocks the session** — and evaluation continues for the life of the connection, so access can be revoked mid-session if device posture or risk changes.

> 💡 **Exam Tip:** Memorize the division of labor: **Policy Engine = decides** (grant/deny), **Policy Administrator = signals the decision** and manages the session path (together the PDP, control plane), **Policy Enforcement Point = executes** in the traffic path (data plane). A question asking "which component actually *allows or blocks* the traffic between user and application?" wants the **PEP**; "which component *makes* the access decision?" wants the **Policy Engine**.

## Physical Security

Logical controls are useless if an attacker can walk up to the hardware. SY0-701 names specific physical controls — know what each one *prevents*, *deters*, or *detects*. Layered together they form defense in depth for a facility: the perimeter (fencing, bollards, lighting) delays and deters, entry points (vestibules, badges, guards) prevent and verify, and interior monitoring (cameras, sensors) detects whatever gets through.

### Bollards

Short, sturdy vertical posts (concrete or steel) that **stop vehicles** while letting pedestrians pass. Placed at building entrances, data-center perimeters, and storefronts to prevent ram-raids and vehicle-borne attacks. Keyword: *"prevent a vehicle from driving into/through the entrance"* → bollards.

### Access control vestibule

A small space with **two interlocking doors — the second cannot open until the first closes**, typically holding one person at a time between authentications (formerly called a *mantrap*). Its purpose is to defeat **tailgating/piggybacking** — an unauthorized person slipping in behind an authorized one. Often combined with a badge reader, guard, or scale/camera verifying single occupancy.

### Fencing

The perimeter's first physical barrier — it **deters and delays** intruders and clearly defines the property boundary. Height and construction set the security level (taller fencing with anti-climb features for high-security sites). Fencing channels all entry through controlled gates where other controls (guards, badges, cameras) apply.

### Video surveillance

CCTV/IP cameras serve as both a **deterrent** (visible cameras discourage attempts) and a **detective** control (recording who did what for investigation and evidence). Modern systems add motion detection, night vision (IR), pan-tilt-zoom, and object/facial recognition. Cameras **record** incidents; they do not physically stop them — pair them with preventive controls.

### Security guard

The flexible, human control: guards **deter, detect, and respond** — verifying identities, inspecting bags, challenging unfamiliar people, and exercising judgment no sensor can (spotting suspicious behavior, reacting to novel situations). Guards also defeat social-engineering entry attempts that fool automated systems. Trade-offs: cost, fatigue, and susceptibility to social engineering themselves.

### Access badge

Credential cards (proximity/RFID/smart card) presented to readers to unlock doors. Advantages over metal keys: per-person **grant and revocation**, and every use is **logged** — creating an audit trail of who entered where and when (supporting accounting and non-repudiation). Badges are also ID displays for guards to check. Risks: cloning of legacy RFID cards and lost/stolen badges — pair with PIN or biometric for sensitive areas.

### Lighting

Proper exterior and interior lighting is a simple, effective **deterrent**: intruders prefer dark approaches, and lighting removes concealment. It also makes video surveillance and guard observation effective at night. Cover entrances, perimeters, parking areas, and blind spots; motion-activated lighting both saves energy and startles intruders.

### Sensors

Sensors **detect** intrusion or movement and trigger alerts (detective controls). The exam names four types — differentiate them by what they measure:

| Sensor | How it works | Best at detecting | Typical placement |
|---|---|---|---|
| **Infrared** | Detects **body heat** (changes in infrared radiation, e.g., PIR) | People/animals entering a space | Rooms, hallways, motion-activated lights/cameras |
| **Pressure** | Detects **weight/force** on a surface | Someone stepping or driving on a specific spot | Floor mats, under carpet at entries, driveways |
| **Microwave** | Emits microwave pulses and measures **reflection changes** (movement) | Motion over large areas; penetrates thin walls/nonmetallic barriers | Large open areas, warehouses; can cover whole rooms |
| **Ultrasonic** | Emits high-frequency **sound waves** and measures reflections | Motion/presence in a contained area | Rooms, vehicle interiors, occupancy detection |

Dual-technology sensors (e.g., infrared + microwave) require both to trigger, cutting false alarms.

> ⚠️ **Common Pitfall:** Don't confuse the emission types: **infrared is passive** (it *senses* emitted heat), while **microwave and ultrasonic are active** (they *emit* energy — radio waves vs. sound waves — and read the reflections). "Detects heat signatures" → infrared. "Detects weight" → pressure. "Uses high-frequency sound" → ultrasonic. "Uses radio/microwave energy, covers a large area" → microwave.

## Deception and Disruption Technology

Deception technologies are intentionally attractive decoys with **no legitimate production purpose** — so *any* interaction with them is inherently suspicious, generating high-fidelity alerts with near-zero false positives. They detect intruders early, misdirect them away from real assets, waste their time, and gather intelligence on their tools and techniques.

| Technology | What it is | What interaction reveals |
|---|---|---|
| **Honeypot** | A decoy **system** posing as a legitimate, vulnerable target (fake database or web server) | Someone is scanning/attacking; captures attacker tools and methods |
| **Honeynet** | An entire decoy **network** of honeypots (servers, workstations, services) | Lateral-movement techniques, privilege escalation, attacker objectives |
| **Honeyfile** | A decoy **file** with an enticing name ("passwords.xlsx", "payroll-2026.docx") that alerts when accessed | Someone — often an **insider** — is snooping or exfiltrating data |
| **Honeytoken** | Decoy **data/credentials** (fake API key, bogus database record, dummy account) that should never be used | Wherever the token *surfaces* proves data was stolen and traces the leak path |

- **Honeypots/honeynets** are isolated from production so a compromised decoy can't become a pivot point.
- **Honeyfiles** sit on real file shares as tripwires; monitoring alerts the SOC the moment one is opened or copied.
- **Honeytokens** are planted in databases, code repos, or password vaults; if that fake credential is ever used or that fake record appears in a breach dump, you have proof of compromise and a pointer to the source. (Disruption aspect: decoys also slow and frustrate attackers, burning their time on worthless targets.)

> 💡 **Exam Tip:** Scale and object type decide the answer: one decoy **system** = honeypot; a decoy **network** = honeynet; a decoy **file** on a share = honeyfile; decoy **data/credentials** (fake API key, bogus record, dummy account) = honeytoken. "Detect an insider browsing files they shouldn't" → honeyfile. "Detect that a stolen credential/database record is being used" → honeytoken.

## Key Takeaways

- [ ] **CIA mappings:** sniffing/disclosure = Confidentiality; tampering = Integrity; DoS/ransomware = Availability.
- [ ] **Non-repudiation** = cannot deny an action; achieved with **digital signatures** (signed with the sender's private key); hashing alone is only integrity.
- [ ] **AAA:** Authentication proves identity, Authorization grants rights, Accounting logs actions — in that order.
- [ ] People authenticate with MFA factors; **systems** authenticate with **certificates, 802.1X, keys, and TPM-backed identities**.
- [ ] **Role-based** = job function; **rule-based** = conditions for everyone; **ABAC** = attributes/context; **DAC** = owner decides; **MAC** = system-enforced labels/clearances (most rigid).
- [ ] **Gap analysis** = compare current security state vs. desired state/framework, output a prioritized remediation plan.
- [ ] Zero Trust rule: **never trust, always verify** — every request is authenticated and authorized regardless of location.
- [ ] Zero Trust **control plane** = adaptive identity, threat scope reduction, policy-driven access control, **Policy Engine (decides)** + **Policy Administrator (communicates)** = PDP.
- [ ] Zero Trust **data plane** = implicit trust zones (to be minimized), subject/system, and the **Policy Enforcement Point (enforces in the traffic path)**.
- [ ] **Bollards** stop vehicles; an **access control vestibule** (two interlocking doors) stops tailgating.
- [ ] **Fencing and lighting deter**; **video surveillance and sensors detect**; **guards** deter, detect, *and* respond; **badges** control doors and create an entry audit log.
- [ ] Sensors: **infrared = heat (passive)**, **pressure = weight**, **microwave = radio reflections (large areas)**, **ultrasonic = sound reflections**.
- [ ] Deception: honey**pot** = system, honey**net** = network, honey**file** = file, honey**token** = data/credentials — any interaction is a high-fidelity alert.
- [ ] Shared accounts destroy non-repudiation and accounting — unique IDs are required to prove who acted.

## Self-Check Questions

1. An attacker launches a ransomware attack that encrypts a hospital's patient records, then threatens to publish stolen copies online. Which CIA principles are violated, and which is the *primary* impact of the encryption itself?
2. A finance director claims she never approved a wire transfer, but the approval was signed with her private key and logged. Which security concept proves she approved it, and what mechanism provides that proof?
3. In a Zero Trust architecture, a user's access request is evaluated and approved, and then a component in the traffic path opens the session to the application. Name the component that made the decision, the component that communicated it, and the component that opened the session — and state which plane each belongs to.
4. A data center wants to (a) stop a truck from being driven through the front entrance and (b) prevent an unauthorized person from slipping in behind a badged employee. Which two physical controls address these, respectively?
5. A security team plants a fake AWS API key in a private code repository and a decoy file named "salaries.xlsx" on a file share. What are these two deception technologies called, and what does an alert on each one tell the team?
