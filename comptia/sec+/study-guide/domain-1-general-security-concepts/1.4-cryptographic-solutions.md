# Objective 1.4 — Explain the importance of using appropriate cryptographic solutions

Domain 1 is worth **12% of the SY0-701 exam**, and objective 1.4 is its largest and most heavily tested objective — cryptography vocabulary from here reappears in every other domain (secure protocols, data protection, identity, incident response). The exam tests this material two ways: **definition matching** ("Which term describes replacing sensitive data with a non-sensitive placeholder?") and **scenario selection** ("A company must encrypt laptops so a stolen device is unreadable, with keys stored in hardware — which combination?"). The highest-yield items are the **symmetric vs. asymmetric comparison**, the **hashing / salting / digital signature** integrity chain, the **certificate lifecycle (CSR → CA → CRL/OCSP)**, the **TPM vs. HSM vs. secure enclave** distinction, and the **obfuscation trio (steganography, tokenization, data masking)** — expect direct questions on all five.

## Public Key Infrastructure (PKI)

PKI is the complete system of hardware, software, policies, and procedures that creates, distributes, manages, and revokes digital certificates — the machinery that makes asymmetric cryptography trustworthy at scale. PKI answers the question "how do I know this public key really belongs to that entity?"

### Public key

The public key is the half of an asymmetric key pair that is **shared openly** — published in a certificate, attached to emails, embedded in a TLS handshake. Anyone may hold it. It is used to **encrypt data destined for the key owner** and to **verify signatures the owner created**. Disclosure of a public key is not a security event; that is its whole design.

### Private key

The private key is the half that is **kept secret by the owner alone**. It **decrypts data encrypted with the matching public key** and **creates digital signatures**. If a private key is exposed, everything protected by the pair is compromised: attackers can decrypt captured traffic, impersonate the owner, and forge signatures — the corresponding certificate must be **revoked** immediately.

> 💡 **Exam Tip:** Direction is everything. **Encrypt for confidentiality:** sender uses the *recipient's public* key; only the recipient's *private* key decrypts. **Sign for integrity/authenticity:** sender uses their *own private* key; anyone verifies with the sender's *public* key. If a question flips these, it's wrong.

### Key escrow

Key escrow places a **copy of private/decryption keys with a trusted third party** (or an internal escrow authority) so the organization can recover encrypted data when the key holder is unavailable — an employee leaves, forgets a passphrase, or a court order demands access. Escrow trades some confidentiality risk (the escrow agent becomes a high-value target) for guaranteed recoverability. A related internal role is the **recovery agent**, an account authorized to decrypt on behalf of users. Scenario keyword: "the company must be able to decrypt employee data if the employee is terminated" → key escrow.

## Encryption

Encryption transforms readable **plaintext** into unreadable **ciphertext** using an algorithm and a key, protecting **confidentiality**. SY0-701 slices encryption three ways: by the *level/granularity* applied to stored data, by *transport* for data in motion, and by *cipher type* (symmetric vs. asymmetric).

### Level

Encryption at rest can be applied at several granularities — the exam expects you to match the level to the scenario:

| Level | What is encrypted | Typical use / example |
|---|---|---|
| **Full-disk** | The entire drive, including OS and free space | Laptops/desktops — BitLocker, FileVault; stolen device is unreadable |
| **Partition** | One partition of a drive, not the whole disk | Encrypting a data partition while the OS partition stays plain |
| **File** | Individual files/folders | EFS, GPG-encrypted documents; protection follows the file |
| **Volume** | A logical volume/container (may span disks or be a file-based container) | VeraCrypt containers, encrypted cloud volumes, removable-media volumes |
| **Database** | An entire database (e.g., Transparent Data Encryption) | Protects all tables at rest without app changes |
| **Record** | Individual rows/fields within a database | Encrypt only the SSN/card-number columns; granular, per-record keys possible |

> ⚠️ **Common Pitfall:** Full-disk encryption protects data **only while the machine is powered off or the volume is locked**. Once the OS boots and the volume is unlocked, files are transparently decrypted for any process — FDE does nothing against malware or a logged-in attacker. Likewise, database-level encryption doesn't stop an attacker with valid database credentials; **record-level** encryption plus access control limits that exposure.

### Transport/communication

Transport (communication) encryption protects **data in transit** across networks — the third data state alongside data at rest (the levels above) and data in use (protected by secure enclaves, below).

| Protocol | What it protects | Notes |
|---|---|---|
| **TLS** | Application traffic — HTTPS, secure email, LDAPS | Certificates authenticate the server; negotiates symmetric session keys |
| **IPSec** | IP packets — site-to-site and client VPN tunnels | Layer 3; ESP provides encryption |
| **SSH** | Remote administration, SFTP | Replaces cleartext Telnet/FTP |
| **WPA3** | Wireless traffic | Modern Wi-Fi encryption |

Real-world transport encryption is **hybrid**: asymmetric cryptography authenticates the server (certificate) and performs **key exchange**, then the session switches to fast **symmetric** encryption (e.g., AES) for the bulk data.

### Symmetric

Symmetric encryption uses **one shared secret key** for both encryption and decryption.

- **Fast and efficient** — used for bulk data: disk encryption, database encryption, VPN payloads, TLS session data.
- **Key distribution is the weakness:** both parties must obtain the same key over some secure channel, and *n* communicating parties need on the order of n(n−1)/2 unique keys.
- Algorithms to recognize: **AES** (the modern standard, 128/192/256-bit), **3DES** (legacy, deprecated), **DES** and **RC4** (broken — recognize as insecure), **Blowfish/Twofish**.

### Asymmetric

Asymmetric (public key) encryption uses a **mathematically related key pair** — public and private.

- **Solves key distribution:** publish the public key freely; no shared secret needed in advance.
- **Slow** relative to symmetric — used for small payloads: key exchange, digital signatures, certificates, not bulk data.
- Algorithms to recognize: **RSA** (encryption + signatures, 2048/4096-bit), **ECC/ECDSA** (elliptic curve — equivalent strength at much shorter key lengths, ideal for mobile/IoT), **Diffie-Hellman/ECDHE** (key agreement only), **DSA** (signatures).

| Feature | Symmetric | Asymmetric |
|---|---|---|
| Keys | **One shared secret** key | **Key pair** (public + private) |
| Speed | **Fast** — bulk data | **Slow** — small data only |
| Key distribution | Hard (secret must be shared securely) | Easy (public key is public) |
| Typical uses | Disk/database encryption, VPN payloads, TLS session data | Key exchange, digital signatures, certificates |
| Algorithms | **AES**, 3DES (legacy), Blowfish/Twofish, DES/RC4 (broken) | **RSA**, **ECC/ECDSA**, Diffie-Hellman, DSA |

Scenario keywords: "which algorithm encrypts the *bulk* of the session data?" → a **symmetric** cipher (AES); "how did the parties agree on that session key over an untrusted network?" → **asymmetric key exchange**.

### Key exchange

Key exchange is the process of establishing a shared symmetric key between parties who have never met, over an untrusted channel. Two models:

- **In-band via asymmetric cryptography:** **Diffie-Hellman (DH)** and **Elliptic-curve Diffie-Hellman (ECDH)** let both sides *derive* the same secret without ever transmitting it — an eavesdropper who records the exchange cannot compute the key. Ephemeral variants (DHE/ECDHE) provide **perfect forward secrecy**: compromising the server's long-term private key later does not decrypt past sessions.
- **Out-of-band:** delivering the key through a separate channel (in person, phone, courier) — impractical at scale.

### Algorithms

An algorithm (cipher) is the published mathematical procedure; the **key** is the secret input. **Kerckhoffs's principle:** security must rest entirely in the key — assume the attacker knows the algorithm. Use vetted, standardized algorithms (AES, RSA, ECC, SHA-256); "proprietary/secret algorithm" in a scenario is a red flag for weak security, not strong.

### Key length

Key length (key size) is the number of bits in the key — the primary lever for resistance to **brute-force** attacks; each extra bit doubles the search space. Longer keys cost more compute, so it's a security/performance trade-off. Benchmarks: **AES-128/256** (symmetric, strong), **RSA-2048+** (asymmetric minimum today), **ECC-256 ≈ RSA-3072** in strength — the reason ECC dominates on constrained devices. Comparing key lengths *across different algorithm families* is meaningless (a 256-bit ECC key is vastly stronger than a 256-bit RSA key would be).

## Tools

Cryptography is only as strong as its key storage. These four tools protect keys in hardware or isolated environments:

| Tool | What it is | Scope / keywords |
|---|---|---|
| **Trusted Platform Module (TPM)** | Dedicated cryptographic chip on a **single device's** motherboard | Stores full-disk-encryption keys (BitLocker), supports secure/measured boot, hardware root of trust for **one endpoint** |
| **Hardware security module (HSM)** | Dedicated **network appliance or PCIe/USB device** for enterprise key generation, storage, and crypto offload | Protects **CA private keys**, payment/database keys; tamper-resistant, high-performance, serves **many systems** |
| **Key management system (KMS)** | Centralized **software/service** managing the full key lifecycle | Generation, distribution, rotation, expiration, revocation, destruction, auditing — often cloud (e.g., cloud KMS backed by HSMs) |
| **Secure enclave** | Isolated **coprocessor/secure region inside a main processor** | Handles biometrics and keys in memory isolated from the OS — even a compromised OS can't read enclave contents (e.g., Apple Secure Enclave) |

> 💡 **Exam Tip:** Scale decides TPM vs. HSM. **One laptop** needing hardware-backed disk-encryption keys → **TPM**. An **organization/CA** needing tamper-resistant storage for many keys or crypto acceleration → **HSM**. A **mobile device** isolating fingerprint data from the OS → **secure enclave**. Lifecycle policy (rotation, expiration, auditing) across all of them → **key management system**.

## Obfuscation

Obfuscation makes data harder to find or understand **without necessarily encrypting it**. Three named techniques:

### Steganography

Steganography **hides the existence of data inside other data** — a message embedded in an image's least-significant bits, audio, video, or even network-packet timing. Encryption makes content unreadable but obvious; steganography makes it **invisible**. Attackers use it to exfiltrate data past DLP; investigators look for it in forensics. Keyword: "data hidden **inside an image/file**."

### Tokenization

Tokenization replaces sensitive data with a **non-sensitive placeholder (token) that has no mathematical relationship to the original**. The real value lives in a secure token vault; the token is useless if stolen. Classic use: payment systems — a stored card number becomes a token, shrinking PCI DSS scope; mobile wallets send one-time tokens instead of the card number. Unlike encryption, there is **no key that derives the original from the token**.

### Data masking

Data masking **replaces some or all characters** of sensitive data with substitute characters (e.g., `****-****-****-1234`) for display, or substitutes realistic fake values in test/development databases. The consumer of masked data **never needs the original back** — it protects data shown to call-center screens, receipts, and developers.

> ⚠️ **Common Pitfall:** Keep the trio straight by *reversibility and purpose*. **Encryption** = reversible with a key. **Tokenization** = reversible only via the secure vault lookup (no key/math relationship). **Masking** = generally *not* meant to be reversed (display/test data). **Steganography** = concealment of existence, not transformation of content. "Show only the last four digits" → masking, never encryption.

## Hashing

Hashing runs data through a **one-way function** producing a **fixed-length digest** (hash). Same input → same hash; any change → completely different hash; the original **cannot be derived** from the digest. Hashing provides **integrity**, not confidentiality — nothing is hidden, and there is no key or decryption.

- Uses: **password storage** (store the hash, never the password), **file integrity/download verification**, **forensic evidence integrity** (hash the disk image before and after analysis), and the foundation of digital signatures.
- Algorithms: **SHA-256/SHA-3** (current), **SHA-1** and **MD5** (broken — collisions found; recognize as insecure).
- A **collision** is two different inputs producing the same hash — the failure that killed MD5/SHA-1.

| | Hashing | Encryption |
|---|---|---|
| Direction | **One-way** — cannot recover input | Two-way — decrypt with the key |
| Output | **Fixed length** regardless of input size | Roughly proportional to input |
| Key | None | Required |
| CIA goal | **Integrity** | **Confidentiality** |

## Salting

A salt is a **unique random value added to each password before hashing**, with the salt stored alongside the hash. Salting defeats **rainbow-table attacks** (precomputed hash lookups become useless because every hash is unique) and ensures two users with the same password have **different stored hashes**. Salting does not stop a brute-force attempt against a *single* hash — that's what key stretching addresses.

## Digital Signatures

A digital signature proves **integrity** (message unchanged), **authenticity** (it came from the claimed sender), and **non-repudiation** (the sender cannot deny signing — only their private key could have produced it). Mechanics, in exam-testable order:

1. Sender **hashes** the message.
2. Sender **encrypts the hash with their private key** — that encrypted hash *is* the signature.
3. Recipient decrypts the signature with the **sender's public key**, hashes the received message themselves, and **compares the two hashes**. Match = intact and authentic.

Digital signatures sign email (S/MIME), code (drivers, apps, scripts), documents, and **every certificate a CA issues**. Note the signature does **not** encrypt the message itself — sign + encrypt are separate operations that are often combined.

> ⚠️ **Common Pitfall:** Signing uses the keys in the *opposite direction* from encryption. Encrypting a message for someone: **their public key**. Signing a message yourself: **your private key**. And remember what each service maps to — **hashing alone = integrity; signatures = integrity + authenticity + non-repudiation; encryption = confidentiality.** Only signatures give non-repudiation.

## Key Stretching

Key stretching feeds a password (plus salt) through a hash function **thousands of times** — deliberately slow, tunable algorithms like **PBKDF2**, **bcrypt**, and **scrypt** — turning a weak, low-entropy password into a stronger key and making each brute-force guess computationally expensive. A user notices a 200 ms login delay; an attacker trying billions of guesses is slowed by the same factor per guess. Scenario keywords: "slow down offline password cracking," "strengthen weak passwords," "PBKDF2/bcrypt."

## Blockchain

A blockchain is a **distributed, append-only ledger** in which transactions are grouped into blocks and **each block contains the hash of the previous block**, chaining them together. Altering any historical record changes its block's hash, which breaks every subsequent block — tampering is immediately evident. Copies are held by many independent nodes that reach **consensus** on new blocks, so there is no single authority or single point of failure. Uses beyond cryptocurrency: supply-chain provenance, records/title management, smart contracts.

## Open Public Ledger

An open public ledger is the blockchain model in which the ledger is **publicly readable and verifiable by anyone** — anyone can join, hold a copy, and audit every transaction (Bitcoin's ledger is the canonical example). Contrast with **permissioned/private** ledgers restricted to vetted participants (consortium supply-chain chains). Exam framing: **integrity through transparency and decentralization** — trust comes from hash-chaining plus thousands of public copies, not from a central trusted party.

## Certificates

A digital certificate binds a **public key to an identity** (server name, person, device, or code publisher), signed by an authority so third parties can verify the binding. Certificates follow the **X.509** standard and are the trust backbone of TLS/HTTPS.

### Certificate authorities

A **certificate authority (CA)** is the trusted entity that verifies identities and **digitally signs certificates**. The **root CA** sits at the top and is kept offline for protection; **intermediate/subordinate CAs** perform day-to-day issuance. A client validates a certificate by walking the **chain of trust**: server certificate → intermediate CA → root CA in the local trust store. A **registration authority (RA)** may handle identity verification on the CA's behalf.

### Certificate revocation lists (CRLs)

A CRL is a **CA-published, signed list of certificates revoked before their expiration date** (private key compromised, employee left, CA mis-issued). Clients download the CRL and check serial numbers against it. Drawbacks: CRLs grow large and are updated **periodically**, so a freshly revoked certificate may still pass checks until the next publication.

### Online Certificate Status Protocol (OCSP)

OCSP replaces bulk CRL downloads with a **real-time query**: the client asks the CA's OCSP responder about **one specific certificate** and receives a signed good/revoked/unknown answer. **OCSP stapling** improves privacy and speed: the *web server* fetches a time-stamped OCSP response and delivers ("staples") it during the TLS handshake, so the client never contacts the CA directly.

> 💡 **Exam Tip:** Revocation-checking keywords: "**downloaded list**, periodically updated" → **CRL**. "**Real-time** status check of a single certificate" → **OCSP**. "Server includes the proof itself, reducing client lookups / protecting user privacy" → **OCSP stapling**.

### Self-signed

A self-signed certificate is signed by **its own creator** — issuer and subject are the same entity, and no CA vouches for it. Free and instant, but clients throw **trust warnings** unless the certificate is manually installed in their trust store. Appropriate for internal labs, testing, and closed systems; inappropriate for anything public-facing. The cryptography can be identical to a CA-signed certificate — the missing ingredient is **third-party trust**, and training users to click through warnings invites on-path attacks.

### Third-party

A third-party certificate is issued by an **external public CA** (e.g., DigiCert, Let's Encrypt) whose root is pre-installed in operating system and browser trust stores — so any client on the Internet trusts it automatically. Public websites, e-commerce, and customer-facing services require third-party certificates. (Enterprises also run **internal/private CAs** for internal-only systems — trusted only by machines that have the internal root deployed.)

| | Self-signed | Third-party (public CA) |
|---|---|---|
| Signed by | Its own key | External trusted CA |
| Client behavior | **Trust warning** unless manually trusted | Trusted automatically via chain of trust |
| Cost / effort | Free, instant | Validation process; may cost money |
| Appropriate use | Labs, testing, internal closed systems | Public-facing services |

### Root of trust

The root of trust is the **anchor every chain of trust ultimately relies on** — a component trusted implicitly because nothing above it vouches for it. In PKI, it is the **root CA certificate** in the trust store; in hardware, the **TPM/secure enclave** anchoring secure boot (each boot stage verifies the signature of the next, starting from immutable hardware). Because everything below inherits its trust, the root must be maximally protected — root CA keys live in **HSMs**, and root CAs are kept **offline**.

### Certificate signing request (CSR) generation

The CSR is how a certificate is properly requested:

1. The requester **generates the public/private key pair locally**.
2. The requester builds a **CSR** containing the **public key** plus identity details (Common Name/FQDN, organization, Subject Alternative Names) and signs it with the private key.
3. The CSR goes to the CA, which **validates the identity** and returns a signed certificate.

The **private key never leaves the requesting system** — the CA never sees it. If a question shows a private key being emailed or uploaded to the CA, that is the error to flag.

### Wildcard

A wildcard certificate secures a domain and **all first-level subdomains** using `*` in the Common Name: `*.company.com` covers `www.company.com`, `mail.company.com`, and `vpn.company.com` — but **not** the deeper `portal.dev.company.com` (second level) and, strictly, not the bare apex `company.com` unless listed as a SAN. Benefit: one certificate to buy and renew across many hosts. Risk: the same private key is deployed on every covered server — one server compromise endangers **all** subdomains. Contrast with a **Subject Alternative Name (SAN)** certificate, which lists multiple *specific* names (even across different domains).

## Key Takeaways

- [ ] Asymmetric key pair: **public key** encrypts/verifies and is shared freely; **private key** decrypts/signs and must stay secret; **key escrow** stores key copies with a third party for recovery.
- [ ] Encryption levels at rest: **full-disk → partition → volume → file** and **database → record**, from broadest to most granular — match granularity to the scenario.
- [ ] **Symmetric** (AES) = one shared key, fast, bulk data; **asymmetric** (RSA/ECC) = key pair, slow, key exchange and signatures; real systems are **hybrid**.
- [ ] **Diffie-Hellman/ECDHE** derives a shared secret over an untrusted channel; ephemeral variants give **perfect forward secrecy**.
- [ ] Longer **key length** = more brute-force resistance; ECC matches RSA strength at far shorter keys; trust vetted algorithms, never secret ones (Kerckhoffs's principle).
- [ ] **TPM** = per-device crypto chip (BitLocker); **HSM** = enterprise tamper-resistant key appliance; **KMS** = key lifecycle management; **secure enclave** = isolated coprocessor shielded from the OS.
- [ ] Obfuscation: **steganography** hides data's existence; **tokenization** substitutes a vault-backed placeholder with no mathematical link; **masking** blots out characters for display/test use.
- [ ] **Hashing** = one-way, fixed-length digest, integrity only; use SHA-256/SHA-3; MD5 and SHA-1 are broken (collisions).
- [ ] **Salting** defeats rainbow tables and duplicate-hash detection; **key stretching** (PBKDF2/bcrypt/scrypt) makes each password guess computationally expensive.
- [ ] **Digital signature** = hash the message, encrypt the hash with the sender's **private** key; verifies integrity + authenticity + **non-repudiation**.
- [ ] **Blockchain** chains blocks by hash across distributed nodes; an **open public ledger** is readable/verifiable by anyone — integrity via transparency, no central authority.
- [ ] Certificate lifecycle: generate key pair locally → submit **CSR** (public key only) → **CA** validates and signs → revoke via **CRL** (periodic list) or **OCSP** (real-time; stapling = server-provided proof).
- [ ] **Self-signed** = free but untrusted (internal/test only); **third-party** CA = automatically trusted publicly; the **root of trust** (root CA / TPM) anchors every chain and must be maximally protected.
- [ ] **Wildcard** (`*.company.com`) covers all first-level subdomains with one certificate — convenient, but one compromised private key exposes every covered host.

## Self-Check Questions

1. A company must ensure that files encrypted by employees can still be recovered after an employee is terminated or loses their credentials. Which cryptographic solution satisfies this requirement?
2. A security engineer must protect a new e-commerce site. Bulk session traffic must be encrypted efficiently, but the client and server have never shared a secret. Which cipher types are used, in what order, and why?
3. An auditor finds that two users with identical passwords have identical hashes in the credential database, and cracking tools with precomputed tables recovered them in seconds. Which two controls fix this, and what does each specifically defend against?
4. A payment application stores `tok_9f3a71` in place of customers' card numbers, shows support staff only `****-****-****-4821`, and an attacker was caught smuggling stolen records out inside a JPEG. Name the technique in each of the three cases.
5. A web administrator generates a key pair, sends a CSR to a public CA, installs the issued certificate for `*.store.com`, and later suspects private-key theft. Explain what the CSR contained, which hosts the certificate covers, and how clients learn of the revocation in real time.
