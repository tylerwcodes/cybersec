# Objective 3.2 — Given a scenario, apply security principles to secure enterprise infrastructure

Domain 3 is worth **18% of the SY0-701 exam**, and objective 3.2 is its most hands-on, scenario-heavy objective. Where 3.1 asks you to *compare* architecture models, 3.2 hands you a network diagram or business requirement and asks **which device, placement, or configuration secures it**. The exam tests this material two ways: **definition matching** ("Which device forwards requests on behalf of clients?") and — far more often — **scenario selection** ("An administrator must ensure security controls continue blocking traffic even if the appliance loses power — which failure mode?"). The highest-yield items are **fail-open vs. fail-closed**, **IDS vs. IPS (and the inline/active vs. tap/passive attributes that separate them)**, the **firewall type lineup (WAF vs. UTM vs. NGFW vs. Layer 4/Layer 7)**, **802.1X/EAP port security**, and **jump servers**. Expect several questions that hinge entirely on matching a scenario keyword to one of these.

## Infrastructure Considerations

Before picking a product, an architect answers placement and behavior questions: *Where* does the device sit? *What zone* does it protect? *What happens when it fails?* *Does it sit in the traffic path or watch a copy?* The exam treats these considerations as their own testable vocabulary.

### Device placement

Device placement is deciding **where in the network topology** a security device belongs, because placement determines what traffic it can see and control:

- **Perimeter/edge:** firewalls and VPN concentrators sit at the boundary between the internal network and the Internet — the first and last inspection point.
- **Screened subnet (DMZ):** public-facing servers (web, mail, DNS) go in a buffer zone between two firewall interfaces so a compromised web server cannot directly reach internal systems.
- **Internal segmentation points:** firewalls/ACLs between internal zones (user VLANs vs. data center, IT vs. OT) limit lateral movement.
- **Sensor/monitor placement:** an IDS sensor **outside** the firewall sees every attack attempt (noisy, good for threat intel); a sensor **inside** the firewall sees only what got through (actionable alerts). Many designs use both.

> 💡 **Exam Tip:** Placement questions are really visibility questions. "The IDS generates thousands of alerts for attacks the firewall already blocks" → the sensor is **outside** the firewall; move it (or add one) **inside** to see only traffic that matters.

### Security zones

A security zone is a logical grouping of systems that share a **trust level and security requirements**, separated from other zones by enforcement points (firewalls, ACLs). Classic zones: **untrusted** (Internet), **screened subnet/DMZ** (public-facing services), **trusted/internal** (users and servers), plus purpose-built zones for **guests, management traffic, and OT/SCADA**. Traffic crossing a zone boundary must pass through inspection, and the default posture between zones should be **deny unless explicitly allowed**. Zero Trust architectures shrink zones down further — ultimately treating every request as crossing a boundary that must be authenticated and authorized.

### Attack surface

The attack surface is **the sum of all points where an attacker could try to enter or extract data**: open ports and listening services, exposed applications and APIs, user accounts, wireless access points, VPN endpoints, even personnel (phishing). Securing infrastructure means **minimizing** it:

- Close unused ports and disable unnecessary services (hardening).
- Remove unneeded software, accounts, and protocols.
- Limit Internet-facing systems to only what the business requires.
- Segment so that a breach of one component exposes as little as possible.

Every device you add (including security devices) also *adds* attack surface — a management interface on a firewall is itself a target, which is why management access belongs in a dedicated zone reached via a jump server.

### Connectivity

Connectivity considerations cover **how devices and sites link together and how those links are secured**: physical cabling vs. wireless, Internet circuits vs. private WAN links (MPLS), and site-to-site or remote-user connections. Security principles applied to connectivity: encrypt anything crossing untrusted transport (TLS, IPSec — covered below), authenticate devices before granting a connection (802.1X), and provide **redundant paths** so a single link failure doesn't take down security enforcement or availability.

### Failure modes

When a security device fails (power loss, software crash, overload), it does one of two things — and the choice is a business decision made **before** deployment:

| Failure mode | Behavior on failure | Prioritizes | Typical use |
|---|---|---|---|
| **Fail-open** | Traffic **continues to flow** uninspected | **Availability** | Networks where uptime outweighs inspection — e.g., an IPS on a revenue-critical e-commerce path |
| **Fail-closed** | Traffic is **blocked** entirely | **Security/confidentiality** | High-security environments where uninspected traffic is unacceptable — e.g., a firewall protecting classified or regulated data |

> ⚠️ **Common Pitfall:** Neither mode is universally "correct" — the exam asks which mode fits the **stated priority**. Keywords: "must remain available / cannot tolerate downtime" → **fail-open**; "no traffic may pass uninspected / security over availability" → **fail-closed**. Note the analogy to physical door locks: fail-safe (unlocks for human safety) vs. fail-secure (stays locked).

### Device attribute

Two attribute pairs describe *how* a security device interacts with traffic — and together they explain the IPS/IDS split:

| Attribute pair | Meaning |
|---|---|
| **Active vs. passive** | An **active** device takes action on traffic (blocks, resets, modifies). A **passive** device only observes and alerts — it never touches the traffic. |
| **Inline vs. tap/monitor** | An **inline** device sits directly in the traffic path — all packets physically flow *through* it. A **tap/monitor** device receives a **copy** of traffic from a network tap or a switch SPAN/mirror port and sees traffic *beside* the path. |

The pairs correlate: to block traffic in real time a device must be **inline and active** (IPS, firewall). A device fed from a **tap/monitor** port can only be **passive** — it can detect and alert but cannot stop the original packets (IDS, sensors, packet capture). Inline devices add latency and become a potential point of failure (hence the fail-open/fail-closed decision above); tap-based devices add zero latency and zero outage risk but zero prevention.

### Network appliances

#### Jump server

A **jump server** (jump box/jump host) is a **hardened intermediary** administrators must connect through to reach devices in a protected zone — the screened subnet, the data center, or the OT network. Instead of allowing management protocols (SSH/RDP) from anywhere, the firewall permits them **only from the jump server**, which itself requires strong authentication (MFA) and logs every session. Benefits: one tightly controlled, heavily monitored entry path; a drastically reduced management attack surface. Scenario keywords: "administer devices in the secure segment," "single hardened point for remote administration."

> 💡 **Exam Tip:** "Admins need to manage servers in the screened subnet without exposing them to direct internal/external access" → **jump server**. Don't confuse it with a proxy (which forwards *application* traffic for users, not administrative sessions).

#### Proxy server

A **proxy server** sits between clients and the services they request and makes requests **on their behalf**:

- **Forward proxy:** sits in front of internal **clients** going out to the Internet. Enables URL/content filtering, malware scanning, caching, and logging of user web activity — and hides internal client IPs. "Control which websites employees can reach" → forward proxy.
- **Reverse proxy:** sits in front of internal **servers**, receiving inbound requests from the Internet. Hides server details, terminates TLS, load balances, and can host a WAF. "Protect the web server by not exposing it directly" → reverse proxy.
- **Transparent proxy:** intercepts traffic without client configuration — users don't know it's there.

#### Intrusion prevention system (IPS) / intrusion detection system (IDS)

Both inspect traffic for malicious activity using **signature-based** detection (matching known attack patterns — accurate but blind to novel attacks) and **anomaly/behavior-based** detection (flagging deviations from a learned baseline — catches new attacks, more false positives). The difference is what they *do* about it:

| | IDS | IPS |
|---|---|---|
| Attribute | **Passive**, fed by **tap/monitor** (SPAN) | **Active**, deployed **inline** |
| On detection | **Alerts** only | **Blocks/drops** the traffic in real time |
| Latency / outage risk | None (out of band) | Adds latency; must choose fail-open or fail-closed |
| Risk profile | Attack may succeed before humans react | False positives **block legitimate traffic** |

Network-based (NIDS/NIPS) versions watch segments; host-based (HIDS/HIPS) run on individual endpoints.

> ⚠️ **Common Pitfall:** "The security team must **detect** threats without any chance of disrupting production traffic" → **IDS** (passive/tap). "Must **stop** the attack before it reaches the server" → **IPS** (active/inline). If a legitimate application suddenly breaks after a new signature deployment, suspect an **IPS false positive**.

#### Load balancer

A **load balancer** distributes incoming traffic across multiple servers, using algorithms such as round-robin or least-connections, with **health checks** that pull failed servers out of rotation and **persistence** (sticky sessions) where needed. Security relevance: it removes single points of failure (**availability** — the A in CIA), absorbs and spreads volumetric load (helps mitigate DoS/DDoS), and can centralize **TLS termination/offloading** so certificates are managed in one place. Active/active configurations share load across all nodes; active/passive keeps a standby ready.

#### Sensors

**Sensors** are collection points that feed monitoring systems — IDS/IPS engines, SIEM, and network performance tools — with raw packets (from taps/SPAN ports), flow records (NetFlow/sFlow), or logs. Sensors are **passive** by nature: they gather and forward telemetry for analysis and alerting. Placement determines coverage (per zone/segment), and sensor data is the raw material for the detection and monitoring work in Domain 4.

### Port security

Port security in 3.2 means **controlling which devices may use a switch port or wireless association** — stopping an attacker from plugging into a conference-room jack and landing on the internal network. (Legacy switch features like MAC filtering/limiting exist, but the objective highlights the standards-based approach.)

#### 802.1X

**IEEE 802.1X** is **port-based network access control (PNAC)**: a switch port or Wi-Fi association stays **blocked** until the connecting user/device authenticates against a central server. Three roles:

1. **Supplicant** — the client device requesting access.
2. **Authenticator** — the switch or wireless access point that guards the port and relays credentials.
3. **Authentication server** — a **RADIUS** server that validates credentials (typically against a directory) and tells the authenticator to open or refuse the port.

Until authentication succeeds, the port passes only authentication traffic. 802.1X is the backbone of wired NAC and of **WPA2/WPA3-Enterprise** wireless.

#### Extensible Authentication Protocol (EAP)

**EAP** is the **authentication framework** carried inside 802.1X — a container that supports many credential methods rather than a single protocol. Recognize the common variants:

| EAP method | Credential mechanism | Notes |
|---|---|---|
| **EAP-TLS** | **Digital certificates on both server and client** | Strongest; requires PKI to issue client certs |
| **PEAP** (Protected EAP) | Server-side certificate creates a TLS tunnel; user password (e.g., MSCHAPv2) inside | Only the server needs a certificate |
| **EAP-TTLS** | Server certificate + tunneled inner authentication | Similar to PEAP; flexible inner methods |
| **EAP-FAST** | Cisco alternative using a Protected Access Credential (PAC) | No certificate requirement |

> 💡 **Exam Tip:** Scenario: "prevent unauthorized devices from connecting to network jacks in the lobby" or "authenticate every device before granting LAN access" → **802.1X with a RADIUS server**. "Mutual certificate-based authentication for wireless" → **EAP-TLS**. Remember the chain: supplicant → authenticator (switch/AP) → RADIUS authentication server.

### Firewall types

Firewalls filter traffic based on rules — but SY0-701 expects you to distinguish four types by **what layer they inspect and what problems they solve**:

#### Layer 4 firewall

A **Layer 4 firewall** filters on **IP addresses, protocols, and TCP/UDP port numbers** — the transport layer and below. Stateful Layer 4 firewalls also track connection state (allowing return traffic for established sessions). Fast and simple, but blind to *content*: it can allow TCP 443 or block it, but cannot tell benign HTTPS from an application attack riding inside it.

#### Layer 7 firewall

A **Layer 7 (application layer) firewall** inspects the **actual application content** — URLs, HTTP methods, DNS queries, application identity — and can make decisions like "allow web browsing but block file uploads to personal cloud storage." Deeper inspection costs more processing. NGFWs and WAFs are both Layer 7-capable devices.

#### Web application firewall (WAF)

A **WAF** protects **web applications/servers specifically**, inspecting HTTP/HTTPS requests for application-layer attacks: **SQL injection (SQLi), cross-site scripting (XSS)**, directory traversal, and other OWASP-style exploits. Deployed in front of web servers (often as/behind a reverse proxy or as a cloud service). A WAF protects the **server from malicious clients** — it is not a general-purpose network firewall.

#### Unified threat management (UTM)

A **UTM** appliance consolidates **many security functions in one box**: firewall, IDS/IPS, gateway antivirus/anti-malware, URL/content filtering, spam filtering, VPN, and DLP. Aimed at **small/medium organizations** that want simplified, all-in-one management at lower cost. Trade-offs: a potential **single point of failure**, and performance that can degrade when every feature is enabled.

#### Next-generation firewall (NGFW)

An **NGFW** is an advanced firewall built around **deep packet inspection at Layer 7**: **application awareness** (identifying and controlling applications regardless of port), integrated **IPS**, TLS/SSL inspection, user/identity-based rules, and **cloud-delivered threat intelligence** feeds. NGFWs are the enterprise-grade choice where UTM is the SMB all-in-one — the features overlap, but NGFW implies higher performance and application-centric policy.

| Firewall type | Layer | Distinguishing capability | Scenario keywords |
|---|---|---|---|
| **Layer 4** | Transport | Port/protocol/IP filtering, stateful sessions | "block a port," "filter by IP and port" |
| **Layer 7** | Application | Content/application inspection | "inspect application data," "control by URL" |
| **WAF** | 7 (HTTP-specific) | Blocks **SQLi/XSS** against web apps | "protect the web application," "injection attacks" |
| **UTM** | Multiple | **All-in-one**: FW + IPS + AV + content filter | "single appliance," "small office," "consolidate" |
| **NGFW** | Up to 7 | **Application awareness** + IPS + threat intel | "identify applications regardless of port," "deep packet inspection," "enterprise" |

> 💡 **Exam Tip:** "SQL injection / XSS against our web server" → **WAF**, every time — not NGFW, not IPS. "One appliance combining firewall, antivirus, and content filtering for a branch office" → **UTM**. "Block a specific application even when it uses port 443" → **NGFW** (application awareness).

## Secure Communication/Access

Enterprises must extend the network securely to remote workers, branch offices, and cloud services. This section is the "traffic crossing untrusted networks" half of 3.2.

### Virtual private network (VPN)

A **VPN** creates an **encrypted tunnel over an untrusted network** (usually the Internet) so that traffic between endpoints is confidential and integrity-protected. Two deployment models:

| Model | Connects | Characteristics |
|---|---|---|
| **Site-to-site** | Two networks (HQ ↔ branch) via VPN gateways/firewalls | **Always-on**; transparent to users; classically **IPSec** |
| **Client-to-site (remote access)** | Individual user's device ↔ corporate network | On-demand; VPN client software or clientless browser portal; IPSec or TLS-based |

A related configuration choice for remote-access VPNs: **full tunnel** sends *all* client traffic through the corporate tunnel (full inspection, more bandwidth), while **split tunnel** sends only corporate-bound traffic through the tunnel and lets Internet traffic go direct (efficient, but that direct traffic bypasses corporate security controls).

### Remote access

Remote access covers all the ways users and administrators reach systems from outside: VPN clients, **SSH** (TCP 22) for CLI administration, **RDP** (TCP 3389) for Windows desktops, and modern **HTML5/browser-based gateways** that proxy sessions without client software. Securing remote access in scenarios: require **MFA**, never expose RDP/SSH directly to the Internet (put them behind a VPN or **jump server**), restrict source addresses, log sessions, and disable cleartext protocols (Telnet) entirely.

### Tunneling

Tunneling encapsulates one protocol inside another so traffic can cross a network it couldn't (or shouldn't) traverse natively — with encryption added for security. SY0-701 names two tunnel technologies:

#### Transport Layer Security (TLS)

**TLS-based VPNs** tunnel traffic inside a TLS session — the same protocol securing HTTPS. Because TLS rides **TCP 443**, it passes through firewalls, hotel networks, and NAT with almost no trouble, and clientless portal access works from a bare browser. Best fit: **remote-access/user VPNs** where compatibility and ease of deployment matter. (You may also see DTLS, the UDP variant, used to avoid TCP-over-TCP slowdowns.)

#### Internet protocol security (IPSec)

**IPSec** secures traffic at **Layer 3**, protecting IP packets themselves. Components to recognize:

- **AH (Authentication Header):** integrity and authentication, **no encryption**.
- **ESP (Encapsulating Security Payload):** encryption **plus** integrity/authentication — the one actually used for confidentiality.
- **IKE (Internet Key Exchange):** negotiates security associations and keys (UDP 500).
- **Transport mode:** encrypts only the **payload**; original IP header stays visible — host-to-host use.
- **Tunnel mode:** encrypts the **entire original packet** and wraps it in a new IP header — the standard for **site-to-site VPNs** between gateways.

| | TLS VPN | IPSec VPN |
|---|---|---|
| Layer | Application/session (over TCP 443) | Network (Layer 3) |
| Firewall/NAT friendliness | **Excellent** — looks like HTTPS | Can require NAT traversal (NAT-T) and open UDP ports |
| Client | Lightweight or **clientless (browser)** | Usually dedicated client / gateway config |
| Classic fit | **Remote-access** VPN | **Site-to-site** VPN |

> ⚠️ **Common Pitfall:** AH vs. ESP is a favorite trick: **AH never encrypts** — it only authenticates. If the scenario requires *confidentiality*, the answer must involve **ESP**. Likewise transport vs. tunnel mode: "encrypt the entire packet including the original header between two offices" → **tunnel mode**.

### Software-defined wide area network (SD-WAN)

**SD-WAN** applies software-defined networking to the WAN: branch offices use **multiple inexpensive transports** (broadband Internet, LTE/5G, MPLS) and a central controller **steers traffic dynamically** per application policy — voice over the low-latency path, bulk backup over cheap broadband, automatic failover when a link degrades. Security relevance: SD-WAN builds **encrypted tunnels between sites automatically**, replaces expensive backhaul of all branch traffic through headquarters, and enables **direct-to-cloud** breakout for SaaS. Keywords: "multiple branch offices," "replace MPLS," "application-aware routing over commodity Internet links."

### Secure access service edge (SASE)

**SASE** (pronounced "sassy") converges **SD-WAN networking with a cloud-delivered security stack** into a single service: secure web gateway (SWG), cloud access security broker (CASB), firewall-as-a-service (FWaaS), and **Zero Trust Network Access (ZTNA)**. Instead of hauling remote-user and branch traffic back to a headquarters firewall, users connect to the **nearest SASE cloud point of presence**, where identity-based policy is enforced on the way to any destination — cloud or data center. SASE fits the modern reality: users everywhere, apps in the cloud, perimeter nowhere. Keywords: "cloud-delivered security for a remote workforce," "combine SD-WAN with security functions," "eliminate backhauling traffic to HQ."

> 💡 **Exam Tip:** **SD-WAN = intelligent connectivity** (routing/transport). **SASE = SD-WAN + security as a cloud service**. If the scenario is only about link performance and branch connectivity, choose SD-WAN; the moment it adds "security enforcement in the cloud for users anywhere," choose SASE.

## Selection of Effective Controls

The closing bullet of 3.2 is the skill the whole objective builds toward: given requirements, **pick the control that actually addresses the risk** — considering the control's category (technical, managerial, operational, physical) and type (preventive, deterrent, detective, corrective, compensating, directive) from objective 1.1, plus cost, performance impact, and failure behavior. A practical selection method for scenario questions:

1. **Identify the asset and threat** the scenario names (web app + injection attacks; open network jacks + rogue devices).
2. **Match the control to the layer/vector** — application attacks need application-layer controls; network access needs port-based controls; no single control covers everything (**defense in depth**: overlapping layers so one failure doesn't equal breach).
3. **Respect the stated priority** — availability-first points to fail-open, load balancing, and passive/tap monitoring; security-first points to fail-closed, inline prevention, and default-deny zones.
4. **Prefer the most specific effective control** — when both an NGFW and a WAF appear as options for SQL injection, the WAF is the purpose-built answer.

Quick keyword-to-control map for review:

| Scenario says… | Select… |
|---|---|
| SQL injection / XSS against a web app | **WAF** |
| Detect without risk of blocking production | **IDS** (passive, tap/monitor) |
| Block attacks in real time | **IPS** (active, inline) |
| Traffic must stop if the appliance dies | **Fail-closed** |
| Uptime matters more than inspection | **Fail-open** |
| Authenticate devices on switch ports/Wi-Fi | **802.1X + RADIUS** (EAP methods) |
| One hardened path to manage secure segments | **Jump server** |
| Filter/log employee web browsing | **Forward proxy** |
| Hide/protect servers from direct inbound access | **Reverse proxy** |
| Distribute traffic, remove single point of failure | **Load balancer** |
| All-in-one security appliance for a small office | **UTM** |
| Application-aware filtering, block apps on any port | **NGFW** |
| Always-on encrypted link between two offices | **Site-to-site IPSec VPN (tunnel mode)** |
| Browser-based remote access through firewalls | **TLS VPN** |
| Branch connectivity over multiple cheap links | **SD-WAN** |
| Cloud-delivered security for users everywhere | **SASE** |

## Key Takeaways

- [ ] **Fail-open** keeps traffic flowing on device failure (availability first); **fail-closed** blocks everything (security first) — the scenario's stated priority picks the answer.
- [ ] **Inline + active** devices (IPS, firewalls) can block but add latency and outage risk; **tap/monitor + passive** devices (IDS, sensors) only copy-and-watch — zero disruption, zero prevention.
- [ ] **IDS detects and alerts** (passive, SPAN/tap); **IPS detects and blocks** (active, inline) — an IPS false positive blocks legitimate traffic.
- [ ] A **jump server** is the single hardened, monitored host through which admins reach protected zones.
- [ ] **Forward proxy** = controls internal clients' outbound web traffic; **reverse proxy** = fronts and shields internal servers from inbound requests.
- [ ] A **load balancer** distributes load, health-checks servers, and supports availability and TLS offload.
- [ ] **802.1X** = port-based NAC with three roles: supplicant (client), authenticator (switch/AP), authentication server (**RADIUS**); **EAP** is the framework — **EAP-TLS** uses certificates on both sides (strongest).
- [ ] **Layer 4 firewall** filters ports/IPs; **Layer 7** inspects application content; **WAF** stops SQLi/XSS on web apps; **UTM** = SMB all-in-one; **NGFW** = application-aware + IPS + threat intel.
- [ ] Security zones group systems by trust level; traffic between zones is default-deny through enforcement points; every exposed service adds **attack surface**.
- [ ] VPN models: **site-to-site** (always-on, gateway-to-gateway) vs. **client-to-site** (remote users); **full tunnel** inspects everything, **split tunnel** sends only corporate traffic through the tunnel.
- [ ] IPSec: **AH** = integrity only (no encryption); **ESP** = encryption + integrity; **transport mode** protects payload only, **tunnel mode** wraps the whole packet (site-to-site standard).
- [ ] **TLS VPNs** run over TCP 443 — firewall/NAT friendly, ideal for remote access, clientless options.
- [ ] **SD-WAN** = policy-driven routing over multiple WAN transports; **SASE** = SD-WAN **plus** cloud-delivered security (SWG, CASB, FWaaS, ZTNA).
- [ ] Control selection: match the control to the attack vector, prefer the most specific effective control, and layer controls (**defense in depth**).

## Self-Check Questions

1. A hospital deploys an inline security appliance on the network path to its patient-records system. Policy states that no traffic may reach the records system without inspection, even during an appliance malfunction. Which failure mode must be configured, and what is the trade-off?
2. A security analyst must monitor a production VLAN for indicators of compromise, but change control forbids any device that could add latency or drop legitimate packets. Which detection technology and connection method fit, and which device attributes describe them?
3. A penetration test report shows the company's e-commerce site is vulnerable to SQL injection and cross-site scripting. The firewall team says ports 80/443 must obviously stay open. Which control most directly addresses the finding, and why not an NGFW or a Layer 4 firewall?
4. An organization wants to ensure that only corporate-issued laptops with valid certificates can connect through wired ports in shared conference rooms. Name the standard, the three components involved, and the EAP method that fits the certificate requirement.
5. A retailer with 200 stores backhauls all branch traffic over expensive MPLS circuits to a headquarters firewall stack, and its growing remote workforce VPNs into HQ before reaching cloud apps. Leadership wants cheaper links, direct-to-cloud access, and consistent security policy for every user and site. Which two technologies address this, and how do they divide the work?

<summary>Answers</summary>

1. **Fail-closed.** On failure the appliance blocks all traffic, guaranteeing nothing reaches the records system uninspected — satisfying the "security over availability" policy. The trade-off is an **availability outage**: while the device is down, legitimate clinicians also lose access, so the design should add redundancy (HA pair) to offset the risk. Fail-open would preserve access but let uninspected traffic through, violating the policy.
2. An **IDS** (intrusion detection system) connected **out of band** via a **network tap or switch SPAN/mirror port**. Its attributes are **passive** (alerts only, never modifies or drops traffic) and **tap/monitor** (receives a copy of traffic rather than sitting in the path) — so it can neither add latency nor block legitimate packets. The cost is that it cannot *prevent* an attack, only detect it for response.
3. A **web application firewall (WAF)**. SQLi and XSS are application-layer (Layer 7) attacks carried inside legitimate HTTP/HTTPS requests on ports that must remain open. A **Layer 4 firewall** sees only IPs/ports and would have to allow the malicious requests along with everything else on 80/443. An **NGFW** adds application awareness and IPS but is a general-purpose control; the WAF is the purpose-built, most specific control for web application attacks — the exam expects the most specific effective control.
4. **IEEE 802.1X port-based network access control.** Components: the **supplicant** (the corporate laptop), the **authenticator** (the conference-room switch that holds the port closed), and the **authentication server** (a **RADIUS** server validating credentials). Because the requirement is certificate-based device authentication, the fitting method is **EAP-TLS**, which performs mutual authentication using digital certificates on both the client and the server (and therefore requires a PKI to issue client certificates).
5. **SD-WAN and SASE.** **SD-WAN** handles the connectivity: stores use multiple inexpensive transports (broadband, LTE) with application-aware, policy-driven routing and automatic encrypted tunnels — replacing or reducing MPLS and enabling direct-to-cloud breakout. **SASE** layers cloud-delivered security on top: users and branches connect to the nearest cloud point of presence, where SWG, CASB, firewall-as-a-service, and ZTNA enforce identity-based policy consistently everywhere — eliminating the need to backhaul remote-worker traffic through the HQ firewall stack.
