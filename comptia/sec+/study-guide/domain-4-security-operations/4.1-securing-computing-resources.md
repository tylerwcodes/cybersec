# Objective 4.1 — Given a scenario, apply common security techniques to computing resources

Domain 4 (Security Operations) is the largest domain on SY0-701 at **28% of the exam**, and objective 4.1 opens it with the day-to-day work of actually *securing* systems: establishing and maintaining secure baselines, hardening every class of device from workstations to SCADA controllers, deploying wireless and mobile solutions safely, and building security into applications. This objective is heavily **scenario-driven**: instead of asking "what is hardening?", the exam describes a situation ("a company issues phones that employees may also use personally — which deployment model?") and expects you to select the matching technique or model. The highest-yield items are the **establish/deploy/maintain baseline lifecycle**, the **BYOD vs. COPE vs. CYOD comparison**, **WPA3 and its SAE handshake**, the **EAP authentication protocol family**, and the **application security four** (input validation, secure cookies, static analysis, code signing) — expect direct questions on all of them.

## Secure Baselines

A **secure baseline** is a documented, approved set of security configurations for a system type — the "known-good" state every instance of that system should match. Baselines come from industry benchmarks (CIS Benchmarks, DISA STIGs), vendor hardening guides, and internal policy. The exam breaks the baseline lifecycle into three phases; scenario wording tells you which phase is being tested.

### Establish

Establishing the baseline means **defining** the secure configuration before anything is built: which services are enabled or disabled, password and lockout policies, encryption requirements, approved software, logging settings, firewall rules. The baseline is documented, tested against business needs (an over-hardened baseline that breaks applications will be bypassed), and formally approved. Keywords: *define, create, document, benchmark, hardening guide*.

### Deploy

Deploying the baseline means **applying** that configuration to real systems at scale — manually configuring hundreds of machines invites drift and error, so deployment uses automation:

- **System images / golden images:** build one hardened master, clone it to every new machine.
- **Group Policy (GPO)** in Windows domains; configuration-management tools (Ansible, Puppet, Chef, SCCM/Intune) elsewhere.
- **MDM profiles** push baselines to mobile devices.
- Infrastructure-as-code templates apply baselines to cloud resources at provisioning time.

### Maintain

Maintaining the baseline is the ongoing phase: systems **drift** from the baseline as users install software, admins make one-off changes, and patches alter configurations. Maintenance means **auditing/monitoring systems against the baseline**, remediating deviations, and **updating the baseline itself** as new threats, patches, and business requirements emerge. A baseline that never changes becomes insecure — maintenance keeps it current, and changes to it go through change management.

> 💡 **Exam Tip:** Match the verb to the phase. "Define a standard configuration" → **establish**. "Push the configuration to all systems / use a golden image" → **deploy**. "Detect configuration drift / update the standard after a new patch" → **maintain**. A question about a system that "no longer matches the approved configuration" is a *maintain* problem — compare against the baseline and remediate.

## Hardening Targets

Hardening reduces a system's **attack surface**: remove or disable what isn't needed, change defaults, patch what remains, and restrict access to the rest. The core recipe is universal — change default credentials, apply updates, disable unnecessary services/ports/features, enforce least privilege, enable logging — but the exam expects you to know how it *specializes* for each target class.

### Mobile devices

Smartphones and tablets leave the building daily, so hardening emphasizes loss and theft: enroll in **MDM**, enforce **screen locks and full-device encryption**, keep OS/apps **patched**, enable **remote wipe**, and block **sideloading** (installing apps from outside official stores) and **jailbreaking/rooting**, which strip away the platform's built-in protections.

### Workstations

End-user desktops and laptops: automated **patch management** for OS and third-party apps, **endpoint protection** (antivirus/EDR), **host-based firewall**, **full-disk encryption**, removal of unnecessary software, **application allow lists** where feasible, standard-user (non-admin) accounts for daily work, and screen-lock policies.

### Switches

Network switch hardening protects Layer 2 and the management plane: **change default credentials**, use **SSH/HTTPS (never Telnet/HTTP)** for management, **disable unused physical ports**, enable **port security** (limit MAC addresses per port), assign unused ports to an unused VLAN, use a dedicated **management VLAN**, and keep firmware updated. 802.1X port-based authentication forces devices to authenticate before getting network access.

### Routers

Same management-plane rules as switches (default credentials, secure management protocols, firmware updates), plus: apply **ACLs** to filter traffic, disable unneeded services (e.g., legacy discovery protocols, HTTP admin interfaces), and restrict which addresses may reach the management interface at all.

### Cloud infrastructure

Cloud hardening is mostly **configuration and identity** work, because the provider secures the physical layer under the **shared responsibility model** — the customer is always responsible for its own data, identities, and configurations. Key techniques: **least-privilege IAM** roles/policies, MFA on cloud consoles, **no public storage buckets** unless explicitly intended, tight **security groups/network rules**, encrypting storage and snapshots, protecting **API keys and secrets** (never hard-coded), and enabling provider logging/audit trails. Misconfiguration — not provider compromise — is the dominant cloud breach cause.

### Servers

Servers run one job well: install only the roles/services the server needs (a web server doesn't need a GUI or file-sharing services), apply vendor/CIS hardening benchmarks, patch on a defined schedule, close unused ports, use host firewalls, separate administrative accounts from daily-use accounts, and forward logs to central monitoring. Test patches on non-production systems first.

### ICS/SCADA

Industrial control systems and SCADA (supervisory control and data acquisition) run physical processes — power, water, manufacturing. They often run **legacy, unpatchable software**, cannot tolerate downtime, and prioritize **availability and safety** over confidentiality. Hardening therefore relies on **network segmentation/isolation** (separate OT network, tightly controlled or air-gapped links to IT), strict access control on engineering workstations, and monitoring — because the vulnerability frequently *cannot* be removed, exposure must be.

### Embedded systems

Embedded systems are special-purpose computers inside other products (medical devices, vehicles, printers, controllers). Constraints: minimal hardware, vendor-controlled firmware, infrequent (or no) updates, long service lives, and no room for endpoint agents. Harden by **applying firmware updates when available**, disabling unused interfaces/services, changing default credentials, and **isolating them on segmented networks**.

### RTOS

A **real-time operating system** guarantees processing within strict, deterministic time constraints — used in vehicles, industrial controllers, medical equipment, avionics. Security software that adds unpredictable latency can't be installed, and the OS is typically minimal by design. Hardening mirrors embedded systems: minimize exposed services, secure and update firmware, restrict communication paths, and segment the network so an attacker can't reach the device to disrupt its timing-critical operation.

### IoT devices

Consumer/enterprise IoT (cameras, sensors, smart TVs, badge readers) is notorious for **weak or default credentials**, abandoned firmware, and cloud dependencies. Harden by changing default passwords, updating firmware, disabling unused features (UPnP, remote access), and — because full hardening is often impossible — placing IoT on a **dedicated, firewalled VLAN** so a compromised device can't pivot into production. Unhardened IoT devices are prime botnet recruits.

> ⚠️ **Common Pitfall:** For ICS/SCADA, embedded, RTOS, and IoT questions, "install antivirus / patch immediately" is usually a **wrong** answer — these platforms often can't run agents or accept patches without breaking. The exam's preferred compensating control for hard-to-patch targets is **network segmentation/isolation**.

## Wireless Devices

Securing wireless starts before any security setting is configured — with *where and how* access points are installed.

### Installation considerations

#### Site surveys

A **site survey** is a physical walkthrough and RF analysis of the facility performed before (and after) deploying wireless: measuring existing signal coverage, identifying **sources of interference** (microwaves, neighboring WLANs, machinery), finding dead zones, and determining optimal **AP placement, power levels, and channel assignments**. Surveys also reveal where signal *leaks* beyond the intended boundary (parking lot, adjacent suites) — coverage bleeding outside the building extends the attack surface to outsiders.

#### Heat maps

A **heat map** is the site survey's visual output: a floor-plan overlay color-coding wireless signal strength (typically hot colors = strong, cool colors = weak). Heat maps document coverage, expose gaps and overlaps, and justify AP placement decisions. They are re-generated after deployment to validate the design and during troubleshooting when users report dead spots.

> 💡 **Exam Tip:** "Determine the best location to install new access points" or "identify interference before deployment" → **site survey**. "Visual/graphical representation of signal coverage on a floor plan" → **heat map**. The survey is the *process*; the heat map is the *deliverable*.

## Mobile Solutions

### Mobile device management (MDM)

MDM is centralized software for enrolling, configuring, monitoring, and securing mobile devices at scale. Typical MDM capabilities the exam expects you to recognize:

- **Policy enforcement:** require screen locks, passcodes, and encryption; push secure baselines and Wi-Fi/VPN profiles.
- **Application management:** allow/block lists, corporate app catalogs, blocking sideloading.
- **Remote actions:** locate, lock, and **remote wipe** lost or stolen devices (or selectively wipe only corporate data).
- **Containerization:** separate corporate apps/data into an encrypted container isolated from personal apps — the key technology that makes BYOD workable and lets the company wipe its container without touching personal photos.
- **Compliance/posture checks:** detect jailbroken/rooted devices or missing patches and block their access.

### Deployment models

| Model | Who owns the device | Who chooses it | Personal use | Organizational control | Trade-off |
|---|---|---|---|---|---|
| **BYOD** (bring your own device) | **Employee** | Employee | Primary purpose | **Lowest** — org manages a slice (container) of a personal device | Low hardware cost, high user satisfaction; privacy conflicts, unmanaged/unpatched hardware, hardest to secure |
| **COPE** (corporate-owned, personally enabled) | **Organization** | Organization | **Permitted** on the corporate device | **Highest** — full control of a device it owns | Predictable, fully manageable fleet; higher cost; company can see/wipe a device employees also use personally |
| **CYOD** (choose your own device) | **Organization** (typically) | **Employee picks from an approved list** | Varies by policy | High — every model on the list is vetted and supportable | Balances user choice with a standardized, supportable set of devices |

> 💡 **Exam Tip:** Ownership + choice decide the model. "Employees use **personal** phones for work" → **BYOD**. "**Company-issued** phone that employees may also use for **personal** tasks" → **COPE**. "Employees **select from a company-approved list**" → **CYOD**. If the scenario's problem is "corporate data on a lost personal phone," the answer pairs the model with **MDM + containerization/remote wipe**.

### Connection methods

| Method | Range / use | Security concerns | Countermeasures |
|---|---|---|---|
| **Cellular** (4G/LTE, 5G) | Wide-area carrier networks | Rogue base stations/IMSI catchers can intercept; carrier network outside org control | Treat as untrusted: VPN for corporate traffic; keep baseband/OS updated |
| **Wi-Fi** | Local wireless LANs and hotspots | **Evil twin**/rogue APs, open public hotspots, eavesdropping on weak encryption | WPA3/WPA2-Enterprise on corporate WLANs; VPN on public hotspots; disable auto-join for open networks |
| **Bluetooth** | Short-range device pairing (headsets, peripherals) | **Bluejacking** (unsolicited messages), **bluesnarfing** (data theft over Bluetooth), pairing hijacks | Disable when unused, turn off discoverable mode, reject unknown pairing requests, patch firmware |

## Wireless Security Settings

### Wi-Fi Protected Access 3 (WPA3)

WPA3 is the current Wi-Fi security standard and the exam's default "best" answer for wireless encryption. What makes it better than WPA2:

- **SAE (Simultaneous Authentication of Equals)** replaces WPA2's pre-shared key 4-way handshake. SAE is a password-authenticated key exchange that is **resistant to offline dictionary attacks** — an attacker who captures the handshake cannot brute-force the passphrase offline, which was WPA2-PSK's classic weakness.
- **Forward secrecy:** each session gets unique keys, so a later-compromised passphrase can't decrypt previously captured traffic.
- **Stronger encryption:** AES-based, with **GCMP** and an optional 192-bit security suite in WPA3-Enterprise.
- **Protected management frames** are mandatory, blunting deauthentication attacks.

WPA3-Personal uses SAE with a passphrase; **WPA3-Enterprise** uses **802.1X with a RADIUS server** for per-user authentication.

### AAA / Remote Authentication Dial-In User Service (RADIUS)

Enterprise wireless replaces the shared passphrase with **AAA — authentication, authorization, and accounting** — via **802.1X**: the client (supplicant) authenticates through the AP (authenticator) to a central **RADIUS server** (UDP 1812 authentication/authorization, 1813 accounting), typically against a directory such as Active Directory. Benefits: **per-user credentials** (no shared secret to leak or rotate when someone leaves), centralized policy, and accounting logs of who connected when. Scenario keyword: "each employee logs in to Wi-Fi with **their own username/password or certificate**" → WPA2/WPA3-**Enterprise** with RADIUS.

### Cryptographic protocols

| Protocol | Encryption | Status |
|---|---|---|
| **WEP** | RC4, broken key scheme | **Deprecated — never use** (trivially cracked) |
| **WPA (TKIP)** | RC4 with per-packet keys | Deprecated — stopgap for old hardware, now insecure |
| **WPA2 (CCMP)** | **AES-CCMP** | Acceptable; PSK handshake vulnerable to offline dictionary attacks |
| **WPA3 (SAE/GCMP)** | **AES-GCMP**, SAE key exchange | **Current best practice** |

### Authentication protocols

Enterprise (802.1X) wireless uses the **EAP** (Extensible Authentication Protocol) framework; the exam contrasts the common variants:

| Protocol | How it authenticates | Certificates required | Notes |
|---|---|---|---|
| **EAP-TLS** | Mutual certificate-based TLS authentication | **Server and every client** | **Most secure**; no passwords to steal; requires PKI to issue client certs |
| **PEAP** (Protected EAP) | TLS tunnel to server, then inner user authentication (commonly MSCHAPv2) | **Server only** | Encrypts the credential exchange inside the tunnel; far easier to deploy than EAP-TLS |
| **EAP-TTLS** | TLS tunnel to server, flexible inner methods (including legacy) | **Server only** | Similar to PEAP; supports broader inner protocols |
| **EAP-FAST** | Tunnel built from a Protected Access Credential (PAC) | None (optional) | Cisco-developed successor to LEAP |

> ⚠️ **Common Pitfall:** Don't confuse the layers: **WPA3** is the *security standard*, **SAE** is its *key-exchange/handshake*, **AES-GCMP/CCMP** are the *encryption ciphers*, and **EAP variants over 802.1X/RADIUS** are the *authentication protocols* for Enterprise mode. A question asking for "certificate-based mutual authentication for wireless clients" wants **EAP-TLS**, not WPA3 — and one asking "resists offline dictionary attacks on the passphrase" wants **WPA3/SAE**.

## Application Security

Securing computing resources includes the software running on them. 4.1 names four techniques:

### Input validation

Input validation checks all user-supplied data against expected type, length, format, and range **before the application processes it** — the front-line defense against **SQL injection, cross-site scripting (XSS), command injection, and buffer overflow** attacks, which all work by feeding an application input it never expected. Best practice is **allow-list validation** (accept only known-good patterns) rather than block-listing known-bad strings, and validation must run **server-side** — client-side (browser) checks improve user experience but are trivially bypassed with an intercepting proxy.

### Secure cookies

Cookies hold session tokens; stolen cookies mean hijacked sessions. The **Secure attribute** on a cookie instructs the browser to send it **only over encrypted HTTPS connections**, never cleartext HTTP — preventing session tokens from being sniffed in transit. Related attributes worth recognizing: **HttpOnly** (JavaScript cannot read the cookie, blunting XSS-based session theft) and **SameSite** (limits cross-site sending, mitigating CSRF).

### Static code analysis

Static code analysis (SAST) examines **source code without executing it** — automated tools (plus manual code review) scan for insecure functions, injection flaws, hard-coded credentials, and buffer-overflow patterns during development, catching vulnerabilities **before the application ever runs**. Contrast with **dynamic analysis**, which tests the *running* application (including **fuzzing** — throwing malformed random input at it). Static = source code, not running; dynamic = running, no source needed.

### Code signing

Code signing applies a **digital signature** to software using the publisher's private key. Verifying the signature with the corresponding certificate proves two things: **authenticity** (the code really came from the claimed publisher) and **integrity** (it hasn't been modified since signing). Operating systems and browsers warn on — or block — unsigned code, and application allow-listing policies commonly trust by signature. Code signing does **not** prove the code is bug-free or safe — only who published it and that it's unaltered.

> 💡 **Exam Tip:** Map the symptom to the control: "SQL injection/XSS getting through" → **input validation**. "Session cookie captured over HTTP" → **secure cookies**. "Find flaws in source code before release" → **static code analysis**. "Verify software came from the vendor and wasn't tampered with" → **code signing**.

## Sandboxing

A **sandbox** is an isolated execution environment where code runs with no access to production systems, data, or the wider network — whatever happens inside stays inside. Scenario uses the exam draws on:

- **Malware analysis/detonation:** open a suspicious attachment or binary in a sandbox and observe its behavior safely (many email gateways and EDR platforms do this automatically).
- **Application testing/development:** test untrusted or unfinished code without risking production.
- **Built-in isolation:** browsers sandbox tabs and plugins; mobile OSes sandbox every app — containing exploitation of any one component.

Sandboxes are implemented with virtual machines, containers, or OS-level isolation. Keyword mapping: "safely examine/execute suspicious or untested code" → **sandboxing**. (Sophisticated malware may detect sandboxes and stall its behavior — a noted limitation.)

## Monitoring

Monitoring is the continuous collection and review of data about computing resources — the control that makes every other control in 4.1 *verifiable*. Applied to this objective, monitoring means:

- **Baseline compliance:** continuously comparing systems to the secure baseline and alerting on **configuration drift** (the "maintain" phase in practice).
- **Log collection and alerting:** OS, application, and device logs forwarded to a central **SIEM** for correlation and alerts on anomalies — failed logins, new services, unexpected outbound connections.
- **Performance and availability metrics:** deviations from normal behavior (CPU spikes, unusual traffic) often signal compromise, especially on servers, ICS, and IoT devices that can't run endpoint agents and can *only* be watched from the network.
- **Mobile/cloud posture:** MDM compliance dashboards and cloud provider audit logs extend monitoring to devices and infrastructure outside the traditional perimeter.

Hardening without monitoring is a snapshot; monitoring turns it into an enforced, ongoing state. (Deeper alerting/SIEM material lives in objective 4.4 — here, know that monitoring is what detects drift, compromise, and policy violations on hardened resources.)

## Key Takeaways

- [ ] Baseline lifecycle: **establish** (define/document the secure config) → **deploy** (apply at scale via images, GPO, MDM) → **maintain** (detect drift, update the baseline).
- [ ] Universal hardening recipe: change defaults, patch, disable unnecessary services/ports, least privilege, log — then specialize per target.
- [ ] Switch/router hardening: default credentials changed, SSH not Telnet, unused ports disabled, port security, ACLs, firmware updates.
- [ ] Cloud hardening = configuration + identity: least-privilege IAM, no public buckets, protected API keys — customer's job under **shared responsibility**.
- [ ] ICS/SCADA, embedded, RTOS, IoT often **can't be patched or run agents** — the compensating control is **segmentation/isolation** (plus firmware updates and changed default credentials where possible).
- [ ] **Site survey** = pre-deployment RF analysis for AP placement/interference; **heat map** = the color-coded floor-plan visualization of coverage.
- [ ] **MDM** centrally enforces policy, manages apps, and enables remote wipe; **containerization** separates corporate from personal data.
- [ ] Deployment models: **BYOD** = employee-owned (least control), **COPE** = corporate-owned with personal use allowed (most control), **CYOD** = employee picks from an approved list.
- [ ] Connection methods: cellular (rogue base stations — use VPN), Wi-Fi (evil twins — WPA3/VPN), Bluetooth (bluejacking/bluesnarfing — disable discoverable mode).
- [ ] **WPA3** uses **SAE** (resists offline dictionary attacks, forward secrecy) and AES-GCMP; WEP and WPA/TKIP are dead.
- [ ] Enterprise wireless = **802.1X + RADIUS** (UDP 1812/1813): per-user credentials instead of a shared passphrase.
- [ ] EAP family: **EAP-TLS** = mutual certificates (most secure); **PEAP/EAP-TTLS** = server-cert TLS tunnel protecting inner credentials.
- [ ] Application security four: **input validation** (server-side, allow-list — stops injection/XSS), **secure cookies** (HTTPS-only session tokens), **static code analysis** (source code, not running), **code signing** (authenticity + integrity).
- [ ] **Sandboxing** = isolated environment to safely run/analyze untrusted code or malware.
- [ ] **Monitoring** closes the loop: detects baseline drift, collects logs to a SIEM, and watches devices that can't defend themselves.

## Self-Check Questions

1. An administrator built a hardened golden image last year and deployed it to all workstations. An audit now finds many workstations running unauthorized services and altered firewall rules. Which phase of the secure baseline lifecycle failed, and what should be implemented?
2. A manufacturer's programmable logic controllers run a vendor OS that reached end-of-support five years ago and cannot be patched or fitted with endpoint software. What is the most appropriate security technique for these devices?
3. A company wants to stop attackers who capture the Wi-Fi handshake from brute-forcing the passphrase offline, and separately wants each employee to authenticate to the WLAN with an individual certificate. Which wireless standard/feature addresses the first requirement, and which authentication protocol addresses the second?
4. An organization will purchase smartphones, issue them to staff, and allow reasonable personal use; IT must retain full management control and remote wipe capability. Which mobile deployment model is this, and which technology enforces the policies?
5. A web application's users are having sessions hijacked: attackers are sniffing session cookies sent over unencrypted connections, and separately the login form is vulnerable to SQL injection. Which two application security techniques from objective 4.1 directly address these issues?

<summary>Answers</summary>

1. The **maintain** phase failed. The baseline was established and deployed, but nothing detected **configuration drift** afterward. Implement continuous **monitoring/auditing against the baseline** (compliance scanning that compares each system to the approved configuration and alerts on deviations), remediate drifted systems, and route baseline updates through change management.
2. **Network segmentation/isolation.** These are ICS/embedded devices whose vulnerabilities cannot be removed (no patches, no agents, downtime unacceptable), so exposure must be removed instead: place them on a segmented OT network with tightly controlled gateways to IT, restrict which hosts can reach them, and monitor the traffic. "Patch them" or "install antivirus" are trap answers for this device class.
3. First requirement: **WPA3**, whose **SAE** handshake is a password-authenticated key exchange resistant to offline dictionary attacks (unlike WPA2-PSK's capturable 4-way handshake) and provides forward secrecy. Second requirement: **EAP-TLS** over 802.1X/RADIUS — mutual certificate-based authentication in which every client presents its own certificate; it is the most secure EAP variant but requires a PKI to issue client certificates.
4. **COPE (corporate-owned, personally enabled)** — the organization owns and fully controls the device but permits personal use. Enforcement comes from **MDM**: pushing configuration baselines, requiring encryption and screen locks, managing apps, and enabling remote wipe (with containerization to separate corporate data from the employee's personal use).

SQL injection → **input validation**: server-side, allow-list validation of all user input so crafted SQL never reaches the database (static code analysis would also help *find* the flaw pre-release, but input validation is the control that *prevents* the attack).
