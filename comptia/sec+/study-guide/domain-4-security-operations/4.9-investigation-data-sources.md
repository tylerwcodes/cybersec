# Objective 4.9 — Given a scenario, use data sources to support an investigation

Domain 4 (Security Operations) is the largest domain on SY0-701 at **28% of the exam**, and objective 4.9 is a scenario-driven objective: given an investigation question ("Who logged in? Was the attack blocked? What data left the network?"), you must pick the **data source that answers it**. The objective names two groups: **log data** (firewall logs, application logs, endpoint logs, OS-specific security logs, IPS/IDS logs, network logs, and metadata) and broader **data sources** (vulnerability scans, automated reports, dashboards, and packet captures). The highest-yield skill is **matching the investigative question to the source**: blocked/allowed traffic → firewall logs; signature-matched attacks → IPS/IDS logs; logons and account activity → OS security logs; who-talked-to-whom without content → network logs/flow data; full packet contents → packet capture; "data about data" (headers, timestamps, GPS) → metadata.

## The Investigator's Mindset

During an incident investigation, no single source tells the whole story. Each source sees the event from a different vantage point, and analysts **correlate** them to build a timeline:

| Investigative question | Best-fit data source |
|---|---|
| Was the connection allowed or denied at the boundary? | **Firewall logs** |
| Did a known attack signature fire, and was it blocked? | **IPS/IDS logs** |
| Who logged on (or failed to), and what accounts changed? | **OS-specific security logs** |
| What did the software itself record (errors, transactions, requests)? | **Application logs** |
| What happened on the host (processes, USB, AV/EDR detections)? | **Endpoint logs** |
| Which hosts talked, when, and how much data moved? | **Network logs / flow data** |
| Where did this email/file/photo really come from? | **Metadata** |
| Was the exploited weakness already known to us? | **Vulnerability scans** |
| What is the current at-a-glance security status? | **Dashboards** |
| What were the exact bytes on the wire? | **Packet captures** |

In practice these sources are centralized in a **SIEM (Security Information and Event Management)** platform, which aggregates logs from across the enterprise, normalizes them, correlates events from different sources, and raises alerts. The SIEM is where an investigation usually *starts*; the individual sources below are where it drills *down*.

## Log Data

### Firewall logs

**Firewall logs** record traffic decisions at a network boundary. A traditional entry captures the "5-tuple" — **source IP, destination IP, source port, destination port, protocol** — plus the **action taken (allow/deny)** and a timestamp. **Next-generation firewalls (NGFWs)** add application-aware detail: the identified application, URL/category, user identity, and any threat detections.

Investigation value:

- Confirm whether a suspicious connection was **blocked or allowed** through the perimeter.
- Spot **command-and-control (C2) beaconing** — regular, repeated outbound connections to the same external address.
- Detect **scanning** (one source probing many ports/hosts, generating many denies) and **data exfiltration** (unusually large outbound transfers).
- Establish exactly **when** a host first communicated with attacker infrastructure.

> 💡 **Exam Tip:** "Did the malware on the workstation successfully connect to the attacker's server?" → check the **firewall logs** for an *allow* entry from that host to the external IP. Allowed-vs-denied questions are firewall-log questions.

### Application logs

**Application logs** are generated by the software itself — web servers (Apache/NGINX access and error logs, IIS logs), databases, mail servers, and custom business applications. They record requests, transactions, errors, and application-level authentication events. On Windows, general application events also land in the **Application** event log.

Investigation value:

- Web server access logs show every request: source IP, timestamp, URL requested, status code, and user agent — **SQL injection** (`' OR 1=1`) and **directory traversal** (`../../`) attempts are visible right in the logged URL strings.
- Database logs reveal unusual queries or bulk data reads.
- Application errors can indicate exploitation attempts (crashes, malformed input).

> ⚠️ **Common Pitfall:** An attack *on a web application* (SQLi in a URL, brute force against the app's login form) shows up in the **application logs**, not primarily the OS security log. The OS security log tracks *operating system* logons and account events, not the app's own users.

### Endpoint logs

**Endpoint logs** come from the individual devices — workstations, laptops, servers — and include host-based sources: **EDR (endpoint detection and response)** telemetry, antivirus/anti-malware detections, host-based firewall logs, process execution records, software installs, and removable-media (USB) activity.

Investigation value:

- Trace exactly **what executed** on a compromised host and what it did next (child processes, files written, persistence created).
- AV/EDR logs show what was **detected, blocked, or quarantined** on the device.
- USB activity records support **data-theft** and policy-violation investigations.
- Endpoint logs are often the only view into activity that never crosses the network.

### OS-specific security logs

**OS-specific security logs** are the operating system's own record of security-relevant events — above all **authentication and account activity**.

| OS | Where | What it records |
|---|---|---|
| **Windows** | **Security** event log (Event Viewer) | Logon/logoff, failed logons, account creation/changes, privilege use, object access, policy changes |
| **Linux** | **/var/log/auth.log** (Debian/Ubuntu) or **/var/log/secure** (RHEL/CentOS) | Authentication attempts, sudo use, SSH logins |

Useful Windows Security log event IDs to recognize: **4624** (successful logon), **4625** (failed logon), **4740** (account lockout).

Investigation value:

- **Brute-force detection:** long runs of failed logons (4625) followed by a success (4624) on the same account.
- **Lateral movement:** logons to systems a user never normally touches, or logons at abnormal hours.
- **Privilege abuse:** account creation, group membership changes, privilege escalation events.

> 💡 **Exam Tip:** "Which log shows who logged on to the server and when accounts were modified?" → the **OS-specific security log** (Windows **Security** log; Linux **auth.log/secure**). Logon questions are OS-security-log questions.

### IPS/IDS logs

**IPS/IDS logs** record detections by intrusion detection/prevention systems: which **rule/signature** (or anomaly) matched, the source and destination, the time, and the **action taken**. The deployment mode determines the action:

- An **IDS** is passive (typically monitoring via a SPAN port or network TAP) — it can only **alert**; the traffic still gets through.
- An **IPS** sits **inline** in the traffic path — it can **block/drop** the malicious traffic and logs that it did so.

Investigation value:

- Identify the **specific attack** attempted (the matched signature names it, often with a CVE reference).
- Determine whether the attempt was **blocked (IPS)** or merely **detected (IDS)** — which decides whether the target host must now be investigated for compromise.
- Alert timestamps anchor the attack timeline.

> ⚠️ **Common Pitfall:** An IDS log entry showing a matched exploit signature does **not** mean the attack was stopped — a passive IDS only alerts. If the sensor was an IDS (or the IPS action reads "alert" rather than "block/drop"), the traffic reached the target and the endpoint must be checked.

### Network logs

**Network logs** come from the network infrastructure itself — routers, switches, wireless controllers, VPN concentrators, DNS and DHCP servers — and from **flow data**:

- **NetFlow** (Cisco-developed), the standards-based **IPFIX**, and the sampling-based **sFlow** record *conversation metadata*: which hosts talked, over which ports/protocols, when, and **how many bytes/packets** — but **not the packet contents**.
- **DNS logs** show every name a host tried to resolve (malicious domains, DGA lookups, possible DNS tunneling).
- **DHCP logs** map an **IP address to a MAC address/hostname at a specific time** — essential for turning "attacker IP 10.1.5.23" into an actual device.
- **VPN logs** show who connected remotely, from where, and for how long.

Investigation value: flow data is compact enough to retain for long periods, making it ideal for answering "which internal host moved 10 GB to that external address last month?" — even when no packet capture exists.

> 💡 **Exam Tip:** Need **who-talked-to-whom and how much**, without content → **flow data/network logs**. Need the **actual content** of the traffic → **packet capture**. This contrast is a classic exam discriminator.

### Metadata

**Metadata** is **data about data** — it describes a file, message, or session without being its content. Sources the exam highlights:

| Type | Examples of embedded metadata |
|---|---|
| **Email** | Header fields: originating IP, each relay (Received: lines, read bottom-up), timestamps, message ID |
| **File** | Author/creator, creation and modification timestamps, edit history, application used |
| **Image/photo** | **EXIF** data: camera model, timestamp, **GPS coordinates** where taken |
| **Web** | Browser/user-agent strings, cookies, referrer |
| **Mobile** | Call/SMS records (who, when, duration — not content), device identifiers |

Investigation value:

- **Email headers** expose the true originating server of a phishing message regardless of the spoofed "From" display.
- **File timestamps** build event timelines; authorship metadata ties documents to users.
- **EXIF GPS** can place a photo (and its taker) at a location and time.

> ⚠️ **Common Pitfall:** Metadata is evidence *about* the object, not the object's content. Phone-record metadata reveals **who called whom and when — not what was said**. Similarly, flow data is effectively metadata about network conversations.

## Data Sources

### Vulnerability scans

**Vulnerability scan** results support investigations by showing **what weaknesses existed and where**. After a compromise, the scan history answers: Was the exploited flaw already known? How long had it been unpatched? Which *other* systems share the same vulnerability (and may also be compromised)? Scan data also validates whether the hole is closed after remediation. During an investigation, a fresh scan of a suspect system can reveal the unpatched service or misconfiguration that served as the entry point.

### Automated reports

**Automated reports** are scheduled, tool-generated summaries — a SIEM's weekly authentication-failure report, a vulnerability scanner's monthly trend report, an EDR's daily detection digest. They consolidate and summarize raw data on a schedule without manual effort. For investigations they provide **historical baselines and trends**: an anomaly is only recognizable against the normal pattern the reports establish, and a past report may show exactly when a metric first deviated.

### Dashboards

**Dashboards** are **real-time, at-a-glance graphical views** of security data — typically the front end of a SIEM or monitoring platform, built from charts, counters, and status indicators, often on a SOC wall display. They surface *current* status and spikes (alert volume, failed logons, traffic anomalies) and let analysts **drill down** into the underlying events. Dashboards are where an investigation is often *triggered*; the detailed work then happens in the logs beneath.

> 💡 **Exam Tip:** **Dashboard** = live visual summary for quick situational awareness; **automated report** = scheduled, generated document summarizing a period. "SOC needs continuous at-a-glance visibility" → dashboard. "Management wants a weekly summary delivered automatically" → automated report.

### Packet captures

**Packet captures** record the **complete contents of network traffic** — every header *and payload* — using tools such as **Wireshark** (graphical analyzer) and **tcpdump** (command line), typically saved as **.pcap** files. This is the most detailed network evidence available: analysts can reconstruct entire sessions, extract transferred files, and read unencrypted credentials or commands exactly as they crossed the wire.

Limitations to weigh in scenarios:

- **Storage:** full captures are enormous; organizations can rarely capture everything all the time (flow data fills the long-term gap).
- **Encryption:** for TLS/encrypted traffic, the **payload is unreadable** — the capture still shows endpoints, timing, and volume (effectively metadata), but not content.
- Captures must be running (or triggered) when the traffic occurs — you cannot capture the past.

> 💡 **Exam Tip:** "Determine exactly **what data** was exfiltrated" or "reconstruct the attacker's session byte-for-byte" → **packet capture**. If the scenario notes the traffic was **encrypted**, the capture's payload value drops — expect an answer acknowledging that only metadata (endpoints, volume, timing) remains visible.

## Correlating Sources: A Worked Example

A phishing investigation shows how the sources chain together:

1. A user reports a suspicious email → **email header metadata** identifies the true originating IP and relay path.
2. Did the user open the attachment? → **endpoint logs** (EDR/process execution) on the workstation.
3. Did the host call out to the attacker? → **firewall logs** (allowed/denied) and **DNS/network logs** (lookups of the malicious domain).
4. Did a signature fire? → **IPS/IDS logs**, and whether the action was block or alert.
5. What actually left the network? → **packet captures** of the suspect flows.
6. How did the malware get a foothold? → **vulnerability scan** history for the unpatched client software.
7. Throughout, the **SIEM dashboard** shows scope in real time, and **automated reports** establish what "normal" looked like before the incident.

## Key Takeaways

- [ ] Match the question to the source: **allowed/denied → firewall**, **signature alerts → IPS/IDS**, **logons/accounts → OS security logs**, **app requests/errors → application logs**, **host activity → endpoint logs**, **who-talked-to-whom → network logs/flow**, **content on the wire → packet capture**.
- [ ] Firewall log entries record the 5-tuple (source/destination IP and port, protocol) plus the **action (allow/deny)**; NGFWs add application and user context.
- [ ] Web attacks like **SQL injection appear in application (web server) logs** — the malicious input is visible in the logged URL.
- [ ] **Endpoint logs** (EDR, antivirus, process execution, USB activity) show what happened *on the host*.
- [ ] Windows security events live in the **Security** event log (4624 success / 4625 failed logon); Linux authentication lives in **/var/log/auth.log** or **/var/log/secure**.
- [ ] An **IDS** (passive) can only **alert**; an **IPS** (inline) can **block** — the log's action field tells you whether the attack actually reached the target.
- [ ] **NetFlow/IPFIX/sFlow** record conversation **metadata** (endpoints, ports, bytes, times) — no payloads; compact enough for long retention.
- [ ] **DHCP logs** tie an IP to a device (MAC/hostname) at a point in time; **DNS logs** show every domain a host resolved.
- [ ] **Metadata is data about data**: email headers, file timestamps/authors, image **EXIF/GPS**, web user agents, mobile call records.
- [ ] **Vulnerability scans** tell investigators what weaknesses existed, when, and which other systems share them.
- [ ] **Automated reports** = scheduled tool-generated summaries (baselines/trends); **dashboards** = real-time at-a-glance visual status with drill-down.
- [ ] **Packet captures** (Wireshark/tcpdump, .pcap) hold full headers and payloads — the deepest detail, limited by storage and by **encryption**.
- [ ] A **SIEM** aggregates and correlates all of these sources; investigations pivot from its alerts into the underlying logs.

## Self-Check Questions

1. An analyst suspects a workstation is beaconing to a command-and-control server. Name two log sources that could confirm the outbound connections and state what each contributes.
2. A web server was defaced. Where would you look for evidence of the SQL injection attack that preceded it, and why wouldn't the Windows Security log show the attack itself?
3. An IDS log shows a signature match for a known exploit against a database server, action "alert." A colleague says the attack was therefore stopped. Correct the colleague and state the required next step.
4. Investigators must determine which internal device held IP 10.4.2.77 last Tuesday at 14:00 and how much data it sent to an external host — but no packet capture exists for that period. Which two network log sources answer these questions?
5. A phishing email claims to come from the CEO. Which data source reveals its true origin, and what specific artifacts within it would you examine?

1. **Firewall logs** show the repeated outbound connections from the workstation to the external IP and whether each was **allowed or denied** — regular, periodic allowed connections to the same destination are the classic beaconing pattern. **Network logs/flow data (NetFlow)** show the conversation pattern over time (frequency, timing, byte counts) even without content, and **DNS logs** would additionally show repeated resolution of the C2 domain. (IPS/IDS logs count too if a C2 signature fired.) Any two with correct contributions is a full answer.
2. The **application logs** — specifically the **web server access logs** — record every HTTP request including the URL and query string, so the injected SQL (`' OR 1=1`-style input) is visible in the logged requests, along with source IP and timestamps. The Windows **Security** log records *operating system* events (OS logons, account changes, privilege use); the attack occurred inside the web application's own request handling, which the OS security log does not capture.
3. An **IDS is passive** — it monitors a copy of traffic (SPAN/TAP) and can only **alert**, so the exploit traffic **was delivered** to the database server. Only an inline **IPS** could have blocked it (and its log would show a block/drop action). The required next step is to **investigate the database server itself for compromise** — check its endpoint logs, OS security logs, and application logs to determine whether the exploit succeeded.
4. **DHCP logs** map the IP address 10.4.2.77 to a specific **MAC address/hostname** during that lease period, identifying the physical device. **Flow data/network logs (NetFlow/IPFIX/sFlow)** record the conversation metadata — destination, ports, timestamps, and **byte counts** — quantifying how much data went to the external host, no packet contents required.
5. **Metadata** — specifically the **email headers**. Examine the **Received:** lines (read from bottom to top) to trace each mail server the message actually passed through and identify the **true originating IP/server**, compare the envelope/return-path with the displayed "From," and check the timestamps and message ID. The headers expose that the message did not originate from the CEO's legitimate mail system.
